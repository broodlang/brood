# Known issues

The record of every bug this runtime has had: what it was, how it was found, how it was
fixed, and **which test now guards it** — so a recurrence is recognizable rather than
rediscovered. This file holds the filing rules, any **open** entry, and the index. The full
section of every **closed** entry lives in
[archive/known-issues-closed.md](archive/known-issues-closed.md) — search it for `## KI-N`.
Deeper rationale lives in the cited ADR ([decisions.md](decisions.md)); the day-by-day
narrative is in [devlog.md](devlog.md).

## Filing an entry

**1. Take the next free number — check first.** Grep the headings across both files, do not
eyeball the index:

```bash
grep -ohE '^## KI-[0-9]+' docs/known-issues.md docs/archive/known-issues-closed.md \
  | grep -oE '[0-9]+' | sort -n | tail -1
```

A duplicate number is ambiguous forever (commit messages and tags cannot be corrected);
`doc_refs::no_two_entries_claim_the_same_number` fails the build on one — renumber the
newer entry.

**2. Write both halves, and later UPDATE both halves.** An index row *and* a
`## KI-N — <one-line symptom> <status> <date>` section (in this file while open).
`doc_refs::every_ki_reference_resolves_to_a_known_issue` requires the section;
`doc_refs::ki_index_row_status_agrees_with_its_section` requires the row's leading status
glyph to agree with it. When you resolve one, change the row in the same commit (lead with
the new status, keep the old text after it) and move the section to the archive.

**3. The section answers five questions, in this order:**

| | | why it matters |
|---|---|---|
| **Symptom** | what was observed, verbatim — the error text, the failing test name, the wrong value | this is what a recurrence will look like; it is the only part greppable from a future failure |
| **Cause** | the actual mechanism, not the layer | "a rename wave" is not a cause; "`check_into_inner` returned for any form that was not a `Pair`" is |
| **Why it survived** | which gates were green while this was broken, and *why* each one could not see it | where the *next* bug is hiding |
| **Fix** | what changed, and any deliberate non-fix with its reason | a recorded non-fix stops the next person re-litigating it |
| **Guard** | the test that now fails if this returns, **sabotage-verified** | an unverified guard is a guess |

**4. Sabotage-verify the guard, and say so in the entry.** Re-introduce the bug, confirm the
new test goes red, restore, confirm green; write the observed red output into the entry.

**5. Statuses.** `✅ fixed <date>` · `☑️` for retracted / not-a-bug / no-longer-reproduces /
superseded (keep the entry — a wrong diagnosis is worth recording) · `📦` archived ·
`⚠️ watching` **only** when it genuinely cannot be reproduced on demand, with the diagnostic
armed and named. Anything else is open, and per `CLAUDE.md` an open bug is the work —
before any feature.

## Where a finding goes

- **A bug in the runtime, toolchain or stdlib** → here, plus a dated
  [devlog.md](devlog.md) entry for the narrative.
- **A design choice** → an ADR in [decisions.md](decisions.md); cite it from here.
- **A trap in how to measure or verify something** → [benchmarking.md](benchmarking.md) or
  [handoff.md](handoff.md).
- **A user-visible break** → [CHANGELOG.md](../CHANGELOG.md), under the release that ships it.

## Before you call the tree green

`make green` (completed CI runs + the local gates `make check` skips), `make green-all` for
the slow corpus gates too. A **cancelled** CI run is not evidence, and `make check` is not
what CI runs (KI-68/KI-69). "Passed once" is not green for anything touching concurrency,
the scheduler, dist, GC or the JIT — run it repeatedly.
