# Design decisions: ADR-400 onward

One of the six files the ADR log is split across by number; the index, and the notes that
apply to every entry, are in [../decisions.md](../decisions.md).

## ADR-400 — `try` bodies run in the bytecode driver, not a nested evaluation

**Status:** implemented (2026-10-12).

**Context.** The compiler inlined `(%try (fn () body) (fn (e) handler))` as one
`Inst::TryCatch` that ran the body and the handler through `exec_value` — a nested evaluation
the bytecode driver cannot capture. Nothing inside it could be preempted (a 50 ms loop in a
`try` ran as one quantum, at every tier), and a `receive` inside it blocked its worker thread
instead of parking. `http/serve` runs every request handler inside `try`
(`std/net/http.blsp`), as `agent` runs its function, so every HTTP handler was
non-preemptible.

**Decision.** `try` compiles to ordinary bytecode in the arm's own chunk:
`TryEnter{handler, bind_slot} · body · TryExit · Jump end · handler: … · end:`. `TryEnter`
pushes a record on the process's handler stack (`Heap::vm_handlers`: the frame's base, the
operand height, the env-root/live-arm lengths, the handler ip, the bind slot); `TryExit` pops
it. The driver (`vm_run_bc`) owns the catch: every error it would return goes through
`raise!`, which — for a non-control error with one of THIS driver's handlers open (above the
floor it recorded on entry, carried in `Suspended::handler_floor`) — pops the frames above
the handler's, binds the caught value, truncates to the recorded heights and resumes at the
handler ip. The trace names exactly the frames popped, which is what the nested evaluation
used to collect. Control signals (suspend, kill, preempt-unwind) are never caught.

The non-inlined `%try` builtin (a computed thunk, `%try-described`) is unchanged and still
nested; only the MCP tooling uses it directly.

**Consequences.** Code in a `try` body or handler is preempted and parks at `receive` like any
other. Arms containing `try` stay off the JIT, as before. Guards:
`crates/lisp/tests/preemption_shapes.rs` (`every_shape_of_running_code_is_preemptible`,
`a_receive_inside_try_parks_instead_of_blocking_the_worker`), both failing on the previous
runtime.

## ADR-401 — A native preempt unwinds native activations into interpreter frames

**Status:** implemented (2026-10-12; the entries unified 2026-10-13).

**Context.** The driver parks only an all-interpreter stack, so native code was preemptible
only where the driver itself had entered it, and only at a self-tail back edge. A native loop
called from another native arm took its preempt as a deopt: the caller re-ran it on a nested
interpreter that could not capture either, so the loop finished there — slower, and still in
one quantum. A native recursion (no back edge) never polled at all. A warm request handler
calling a warm loop was one quantum however long the loop ran: the latency row's fat
handlers read 1–2 ms each.

**Decision.** Each native activation carries `JitCallCtx::unwind`: 1 only when every
activation between it and a top-level driver can be rebuilt as an interpreter frame. The
driver passes it to its native entries (frame path, VM→native direct call); a native→native
call passes on the caller's bit, unless the caller cannot be rebuilt mid-call (the
self-inlined upgrade, whose ips match no chunk: its prologue sets `no_child_unwind`, and its
own call sites pass 0) — a runtime callback reads that pair off the calling context
(`JitCallCtx::children_may_unwind`) and hands it down as an argument; every other way in (a
builtin calling back, a nested evaluation, the tree-walker) builds the context with 0. So
the safe answer is the default.

- **One entry, one finish.** Every Rust caller that runs native code enters it through
  `jit_runtime/entry.rs`: `enter_native` is the ceremony (env, name, IC cursors, depth,
  gateway, context — installed and restored), `native_feedback` the suspend latch and deopt
  feedback, and `finish_nested` every outcome of a call whose caller wants a value (unwind
  record, error, tail chain, checkpoint resume, VM re-run — re-entries at a raised native
  depth, KI-11). The driver's tier-in, the slow call out of native code, the fast link and a
  builtin's callback each used to carry their own copy of all three; a rule added to one —
  this ADR's unwind — had to be repeated in four.

- A spent budget preempts only an activation with `unwind` set, and only when some process
  is waiting for a worker (`scheduler::work_waiting`, one relaxed load of the queued count):
  unwinding and rebuilding is the costly preemption, and with nothing queued anywhere it buys
  no latency — the process would be re-queued and picked straight back up. Otherwise the
  activation keeps running native on a fresh quantum (it used to deopt into an interpreter
  that could not preempt either), except that a pending hard kill still leaves for the
  interpreter. The `:long-schedule` timer restarts there (ADR-404), so a lone compute process
  is not reported as code that held a worker it could not give up.
- The preempted activation's caller handler records it and parks `Control::PreemptUnwind`;
  each caller up to the driver leaves through its error path, which first writes an
  **in-call journal** — the ip after the call in flight, and the operands beneath it, copied
  to room `brood_rt_in_call_journal` reserves at the top of `roots` (a side record: every
  handler on the way out leaves `roots` as it lies, so the copies stay rooted until the
  rebuild). Only on the error branch, so the success path pays nothing; for a real error the
  callback returns null and nothing is stored. Each handler records its callee with the
  journal it wrote (a per-thread list: an unwind never crosses a park). The driver rebuilds
  each as an interpreter frame — callers paused just after their `Call`, the preempted one
  settled as the frame path settles a preempt — and parks. On resume the innermost re-tiers
  into native code and the callers finish interpreted.
- **Entry reduction poll.** An unwindable arm — one with a non-tail call whose layout can be
  rebuilt — charges one reduction per activation from a countdown on the heap
  (`Heap::jit_call_budget`), settling a batch with `brood_rt_tick_n`, so a native recursion
  is preemptible too. No branch on `unwind` of its own: the settle callback checks it.
- **No journal area for the in-call journal.** A first version wrote it into the frame's
  checkpoint journal and gave pure self-recursive arms that area: its zeroing and reset on
  every activation cost `bintree` 10% of its instructions. The side record needs none, so
  pure self-recursive arms keep the exemption they had (no area, a deopt re-runs from ip 0).
  The self-inlined upgrade's frame is named (`FrameLayout::SelfSpliced`) so nothing reads the
  small layout's journal index out of it — that index is a live local there.

**Not covered.** The unboxed register worker (`fib`'s path) keeps its whole recursion in
registers and cannot be rebuilt; demoting it to boxed code costs ~45× on `fib`, so a long pure
numeric recursion there still runs as one quantum, as does a self-inlined activation. Both
are visible through the `:long-schedule` system-monitor event.

**Consequences.** Guards in `crates/lisp/tests/preemption_shapes.rs` — one native shape per
test process (a hot re-lowering in one shape could run the next shape's callers interpreted
and pass for the wrong reason); each sabotage-verified by disabling the unwind start or the
entry poll. The value tests (a native chain; a pure tree walk, whose only operand record is
the side journal) run beside a companion hog so a process is always waiting, and fail when
the rebuild drops the journalled operands; `jit_lowers_and_runs_a_self_recursive_int_loop`
pins both sides of `work_waiting` (each direction sabotage-verified). Cost on the A/B rows
against v0.37.0 (best-of-11, pinned): `bintree` +3.8%, `nqueens` +4.7%, `ring` +5.0% — in
instructions only +4.6%, +1.6% and +1% (single worker), the rest lower IPC not yet
attributed; `fib` and `supervisor` unchanged. Bought: the `latency` row −47%. A parked process's floor is 3 997 B of the 4 000 B budget
(`tests/process_floor.rs`): the unwind list lives on the thread, not the heap, for that
reason.

## ADR-402 — `binding` bodies run in the bytecode driver

**Status:** implemented (2026-10-12).

**Context.** `binding` expanded to `(%binding '(n…) [v…] (fn () body…))`, and the native ran
the thunk as a nested evaluation — the same hole ADR-400 closed for `try`: a body that could
not be preempted, and a `receive` in it that blocked its worker. `with-out-str`
(`std/io.blsp`), the test runner and editor code all wrap bodies in `binding`.

**Decision.** The VM compiler inlines the macro's canonical shape as `Node::Binding`, emitted
as `vals · BindEnter{names} · body · BindExit(n)`: `BindEnter` pops the value vector and pushes
the bindings (`builtins::push_bindings` — the one implementation the native, the instruction
and the evaluator twin share, so the not-dynamic and count checks read the same), `BindExit`
pops them. An error that skips `BindExit` is undone by **truncation**: an inline `try`
records the dynamic stack's length (`VmHandler::dyn_len`) and a catch truncates to it; a
driver records its entry length (`Suspended::dyn_floor`, a `u32` packed beside the handler
floor so the parked-process floor holds) and truncates to it when an error leaves the driver.
The tree-walker keeps the native (its Rust frame restores on the way out).

**Consequences.** A `binding` body is preempted, parks at `receive` and resumes with its
bindings in force. Guards: `preemption_shapes.rs` ("a loop inside binding",
`a_receive_inside_binding_parks_and_keeps_its_binding`), both red with the inlining disabled.

## ADR-403 — Owed preemption, and folds walked in spans

**Status:** implemented (2026-10-12; simplified 2026-10-13).

**Context.** Code that cannot yield — a nested evaluation behind a builtin, a native activation
that cannot unwind (ADR-401) — refilled the budget when its quantum ran out and forgot it, so
the process carried on for another full quantum after returning. And the vector and range
folds (behind `fold`/`reduce`/`map`/`reverse`) called the reducer from one native loop: a
40-element fold whose reducer ran 10 ms was one quantum.

**Decision.**
- **One home for the policy.** `process/scheduler/quantum.rs` holds the budget, the debt and
  every preemption decision; the places that run code only ask it — `driver_safepoint` (the
  driver's loop top and an inline loop's back edge), `native_poll` (a native activation's
  poll), `tick` (the eval loop), `stop_between_elements` (a fold's span), `charge` (work done
  without ticking).
- A quantum that runs out where nothing can yield records an **owed** preemption when some
  process is waiting for a worker; every point that can capture pays it as it would a spent
  budget. A spent budget is paid — by a yield or an unwind — only while a process is waiting:
  with none queued, the process runs on into a fresh quantum (the `:long-schedule` timer
  restarted), since a yield would re-queue it and pick it straight back up.
- **Folds walk in spans.** `fold` over a vector or a range is a Brood loop over
  `%vector-fold-span` / `%range-fold-span`, each of which folds up to `%fold-span` (4 096)
  elements natively and returns the accumulator itself when the collection is done, or
  `(:%fold-more acc . next)` when the span stopped short (2026-10-13 (later): the first cut
  returned `[acc next]`, a vector allocated per fold even though most folds are one span). A
  reducer that returns a list headed by that internal keyword on purpose could pass for a
  continuation; nothing does by accident, and no Brood value is unforgeable (a private prelude
  name is reachable too), so the tag is chosen for being cheap to test. The
  process yields at the loop's back edge like any loop's. A span ends early, between two
  elements, when a reducer's own run left a preemption owed (`stop_between_elements`, once per
  debt: where nothing can capture the debt stays owed for the next point that can, and only a
  fresh one stops a span again). A primitive reducer (`+`, `*`) runs the whole span inlined and
  charges the quantum one reduction per 8 elements.
- A first version made the native folds *resumable*: they stopped on their own and left where
  in a thread-local that the prelude read back at once through `%fold-resume-at`. Rust and
  Brood coupled through hidden state; the span result carries the same fact as a value.

**Consequences.** A fold yields within one reducer call (or one primitive span) of its quantum
ending. A single long reducer call still runs to its end, and its debt is paid at once. Cost
against the resumable version, instructions: `reduce` +4% and `nqueens` +5% (a span result
allocated per fold), `json` −4%; the allocation-free result won back ~1.3% of `nqueens`
(devlog 2026-10-13 (later)). Guards: four fold shapes in `preemption_shapes.rs`
(`stop_between_elements` and the span charge each sabotage-verified),
`preemption.rs` (a hog preempted while a responder waits, which must reply first), and two
multi-span folds in `tests/sequence_test.blsp` (one across concurrent workers, which catches a
mid-span stop that skips an element; both sabotage-verified).

## ADR-404 — `:long-schedule` in the system monitor

**Status:** implemented (2026-10-12).

**Decision.** `(proc/system-monitor pid {:long-schedule-us n})` reports each scheduling quantum
that held its worker at least `n` µs as `[:system :long-schedule pid {:us d}]` — BEAM's
`long_schedule`. A quantum is bounded by the reduction budget, so one this long is code that
could not be preempted (a long native builtin, the unboxed register worker's recursion, a
blocking call). A budget that runs out with no process waiting for a worker is not
preempted (ADR-401/403); the quantum so far is reported if it ran long and the timer
restarts, so a process that has the worker to itself is reported for code that could not be
preempted, never for keeping the worker. The worker times
a quantum only while a subscriber selects the kind (one relaxed load otherwise). Selected by its threshold; a subscription armed with no options map
("every event") gets 10 ms. `telemetry/watch-runtime` re-emits it as `[:runtime
:long-schedule]` with the `{:us}` measurement.

**Consequences.** Every preemption gap this work closed would have shown up here first.
Guard: `tests/sysmon_test.blsp` (a large `sort`, one native call, at every tier).

## ADR-405 — `spawn` copies a closure's captured values instead of promoting it

**Status:** implemented (2026-10-12).

**Context.** `spawn` promoted the body closure into the shared RUNTIME region so the child
could use it. For a closure that captures locals — every `(spawn (handle request))` — that
appended a closure and an env to the region all processes share, per spawn; the multi-process
collector then had to age and reclaim it, and a spawn landing in its window waited on the
`promote_lock` writer for 100–300 µs. Under a request stream that was the dispatcher's latency
spikes, and the reclamation ran at the dispatcher's own safepoints.

**Decision.** When the closure's code already lives in a shared region,
`message::copy_closure_into` builds the child's copy with the SAME arms — so the compiled and
JIT'd bodies, keyed by that AST (`cache_key`), are shared as before — and an env frame in the
child's heap holding copies of the captured values, made exactly as a message copies them.
A closure that captures nothing, code that is not shared, or a value the message copy refuses
(a self-referential local closure) falls back to `promote`. The process's first run takes its
body (`Process::drive`), because a handle into the child's own heap is not rooted once the
driver has it.

**Consequences.** Spawns no longer grow the shared region or contend on its collector. A
captured local closure arrives as a copy (as in a message): `=` on it against the parent's is
false, as for any function that crossed a process boundary.

## ADR-406 — Native code memoises a computed-head call per closure instance

**Status:** implemented (2026-10-14).

**Context.** A call whose head is a value rather than a global name — `(f acc x)` with `f` a
parameter, every callback a higher-order function calls — has no call-site inline cache
(ADR-096 caches only free-global heads). From native code it went `brood_rt_call_slow` →
`jit_dispatch_call`, whose computed branch ran `compiled_arm_for` (the closure read, the
body-cache key, `sync_free_epoch`, a `SmallMap` probe, the arity scan), `closure(id)` for the
env and `vm_arm_block` (a second map probe) on every call. Measured from a native loop: ~940
instructions a call to an anonymous closure, ~1 060 to a capturing one, against 415 for the
same body called by name.

**Decision.** `jit_dispatch_call` memoises that resolve — the arm, the instance's env and the
arm's IC block — in a small direct-mapped table (eight slots) keyed on the closure INSTANCE's
handle bits and `argc`. The instance, not the template: the instance fixes the env as well,
and a higher-order loop passes one instance on every iteration. A hit is valid while nothing
it was derived from can have changed:

- **The body cache.** The table lives inside the body cache's own cell (`VmCacheCell`), whose
  one mutable accessor (`write`) drops it, so no write to the cache — a free-epoch or
  stale-binding sync (ADR-366), a compaction, a hibernate shrink, a new body — can leave a
  memo behind. The one write that keeps it (`write_derived`) only memoises an arity's handle
  from the entry's own body. The probe syncs the free epoch first, so a peer's free reaches
  the table before it is read.
- **The code epoch**, as for the named-head IC: a `def`, a module load, a compaction, a freed
  RUNTIME generation (whose slots are reused with bit-identical handles).
- **The collection count**: a collection moves LOCAL closures and their envs; their handle
  bits change with them, but the generation stamp in the bits is 29 bits and wraps.

The table is allocated at its first entry and costs an empty process one pointer (8 B; the
`process_floor` ratchet moved 4 000 → 4 020 for it, with the measurement).

**Alternatives.** *A call site per computed call* (the handoff's starting design): the IR
would carry a site id for every computed head, which means plumbing through lowering,
emission, `staged` (KI-19) and `mono_devirtualize`, and gives a monomorphic cache per site.
The per-process table gets the same hit on the dominant shape (one callback per loop) without
touching the IR; a site is still the way to an in-IR fast link later. *Keying on the
template* would share entries across instances but needs the env read per call anyway.

**Consequences.** ~240 fewer instructions per computed call from native code: anonymous
closure 943 → 706, capturing 1 058 → 817, a global function passed as a value 1 057 → 706
(named heads unchanged at 415). What remains of the gap to a named call is the frame and exit
handling (`fill_captures`, `finish_nested`, `native_feedback`) and the unconditional stack
probe (KI-14), which an in-IR fast link for computed heads would remove. A thin-wrapper
callback — `(fn (a x) (+ a x))`, which the dispatcher redirected to `+` by name (ADR-069)
rather than running its body — did not reach this path at all; ADR-408 routes it here.

**Amended 2026-10-14 (night):** two of the named remainders are gone without the IR change. A
value is finished inline rather than through `finish_nested`, and the link branches take the
depth-gated stack probe rather than the raw one — they enter through `enter_native`, which
counts the level, so a recursion of links is bounded the way `jit_run_fast_link`'s is; the
slow path and a builtin called directly (which can re-enter evaluation uncounted) keep the raw
probe. A computed call 771 → 652 instructions, a capturing closure 881 → 762 (named 415 → 408).
What is left of the gap is the Rust entry itself — the memo probe, the argument shift,
`fill_captures`, `enter_native` — which only the in-IR link removes. Guard for the probe:
`tests/jit_deep_recursion_test.blsp` "deep recursion through a computed-head call" (200 000
levels complete, 2 000 000 raise `recursion too deep`, in a spawned process).

## ADR-407 — A container's memory cap sets the default limits; a large allocation ends the quantum

**Status:** implemented (2026-10-14). Amends ADR-043 and ADR-399. KI-242, KI-243.

**Context.** `brood` and `nest run` set no memory limit unless `BROOD_MEM_LIMIT` is given.
In a container with a memory cap, a runaway then ends in the kernel's out-of-memory kill:
exit 137, nothing printed, every process gone. ADR-399 made the soft limit safe to default
(it stops the holder, not a bystander), which left the question of the number. Separately,
two gaps let a runaway reach the hard limit anyway: a loop allocating a megabyte an
iteration covered the soft limit's headroom inside one quantum (KI-242), and a victim stuck
in a native call kept the selector from stopping anyone else (KI-243).

**Decision.**
- With neither `BROOD_MEM_LIMIT` nor `BROOD_MEM_SOFT_LIMIT` set, a process in a
  memory-capped cgroup takes a hard limit of three quarters of the tightest `memory.max` on
  its cgroup path (v1: `memory.limit_in_bytes`), and a soft limit of three quarters of that.
  The test runners take the lower of their 3 GiB default and this. Outside a capped
  container nothing changes. `BROOD_MEM_LIMIT=0` turns the limits off.
- Three quarters, not seven eighths: the container counts resident memory, the allocator
  counts live bytes, and the difference — pages the allocator keeps after a free, stacks,
  mapped code — measured about 1.45× live for a leak making garbage as it grew. Under a
  600 MB cap a hard limit an eighth below was killed before the soft limit tripped; at three
  quarters, caps of 600 MB, 1 GB and 2 GB each ended the same leak with `E0043`.
- An allocation of 64 KiB or more over the soft limit ends the allocating thread's quantum,
  so the once-per-quantum check runs at the next safepoint; within the last eighth, once per
  1/64 of the limit, so a fast allocator measures itself for the selector. A native arm
  learns of it through a thread-local flag read when a builtin call returns.
- A victim not gone 250 ms after it was stopped is skipped by the next selection.

**Consequences.**
- A runaway in a capped container stops with `E0043` naming the process, and the rest of the
  runtime survives; a supervisor can restart it.
- A program that legitimately needs more than three quarters of its container's cap must set
  `BROOD_MEM_LIMIT` (or `0`).
- Near the soft limit, a process making large allocations ends its quantum at most once per
  1/64 of the limit allocated (a yield only if a process is waiting, ADR-401); with no soft
  limit set the hook is one comparison of the allocation size.
- The cap is re-read while running, at most every 5 s — from the once-per-quantum checks, a
  native loop's fresh quantum, and a park — so a container resized in place (a pod's
  in-place resize) moves the limits with it; under a `systemd-run` scope cut from 2 GB to
  600 MB, the hard limit followed to 450 MiB within seconds. Only when no env var set them.
- When no process holds an attributable share, or the one that does is the current process,
  the `E0043` names the table holding the most (a hint: `table #N holds about M MiB`). A
  table belongs to no process (ADR-107), so stopping one frees nothing it stores.

## ADR-408 — Native code runs a thin wrapper's compiled body instead of redirecting

**Status:** implemented (2026-10-14). Narrows ADR-069's redirect to the interpreters.

**Context.** A thin wrapper — an arm whose body only forwards its parameters to another
head, `(fn (acc x) (+ acc x))` — is redirected by the dispatcher (ADR-069): the call goes to
the inner head, resolved by name, on the already-evaluated args. That spares the tree-walker
and the VM a frame. From native code it was the slow path: `jit_dispatch_call` found the
wrapper's arm not native, fell to `dispatch`, and the redirect then took two by-name hops
(`+`'s own two-argument arm is a wrapper of `%add`), each a `passthrough_arm` read, an
`env_get`, `boundary_redirect` and an argument remap — ~1 900 instructions a call. And because
the redirect never runs the wrapper's body, its arm never got hot, never tiered, and so never
reached the native link. The canonical reducer was the slowest callback there is.

**Decision.** When native code reaches the slow path with a closure whose selected arm is a
thin wrapper, it runs the wrapper's compiled arm (`vm_apply`) like any closure's. The arm
tiers up on those runs, and later calls take the native path — with ADR-406's memo for a
computed head. The interpreters keep the redirect. The answer is the same: the compiled body
resolves its inner head by the same late-bound name, and applies the contract boundary
(ADR-383) at compile time, which is what `boundary_redirect` re-creates by value for the
redirect.

**Consequences.** A thin-wrapper callback from native code costs what any closure value does:
~714 instructions a call, from 1 892 (anonymous) and 2 120 (a global wrapper passed as a
value). An error's trace through such a call reads the same as before. Guards: `jit_computed_call_test` (the wrapper reaches `:native`; a
redefinition of the inner function is still seen through it), `contract_test` (the boundary
holds through a wrapper a native loop calls — red under `BROOD_NO_CONTRACT_BOUNDARY=1`).

**Amended 2026-10-14 (same day): the by-name call did not link.** The figures above are for a
wrapper passed as a VALUE. Called by NAME from native code — `(defn add (a x) (+ a x))` from a
native loop, the commonest helper there is — it stayed on the slow path at ~2 100
instructions a call: the caller runs interpreted until it tiers, the interpreter caches the
wrapper on the call IC WITHOUT an arm (it redirects), and `jit_dispatch_call` read an arm-less
hit as a builtin and returned nothing for a closure, so the miss branch that attaches the arm —
and from which the fast link is published — never ran again. The arm-less hit now attaches the
arm: ~420 instructions a call, a non-wrapper helper's cost. Guard:
`jit_runtime::link::tests::a_thin_wrapper_called_by_name_publishes_its_fast_link` (sabotage:
never publishes); late binding through the link in `jit_computed_call_test` ("a thin wrapper
called by name from native code").

## ADR-409 — `receive` matches simple patterns natively

**Status:** implemented (2026-10-16).

**Context.** Every `receive` built a matcher closure, `(fn (msg) …)` answering `[idx var…]` for
the clause that matched, and the kernel's mailbox scan called it for each candidate message —
a native → Brood call per scanned message, plus the closure itself per `receive`. On `ring`
that was ~800–1 000 of a hop's ~9 500 instructions, for patterns as plain as a catch-all or
`[:ping from]`. BEAM matches receive patterns in the VM.

**Decision.** When every clause of a `receive` is a simple shape — a binder, `_`, a literal
(int, float, keyword, string, `nil`, a boolean, a quoted symbol), a pinned SYMBOL, or a
fixed-length vector of those, with no `:when` guard — the macro hands `%receive` a pattern
SPEC instead of the closure, and the kernel matches it itself (`process/receive_spec.rs`),
answering the same `[idx var…]` so the clause bodies the macro emits at the call site are
unchanged. Anything else keeps the closure, for the whole `receive`.

- **The pattern language stays in Brood.** The macro (`%receive-spec`) decides what qualifies
  and builds the spec; the kernel only interprets `[:any]`, `[:bind]`, `[:same k]`, `[:eq v]`,
  `[:pin i]` and `[:vec p…]`. The kernel is mechanism, the language decides.
- **A spec is a keyword**, `:%rspec <printed patterns>`, made at expansion time by
  `%receive-spec-key`. A keyword is an immediate, so a `receive`'s arm embeds no heap constant:
  the first cut passed the patterns as a quoted vector, and an arm holding one is not shared
  across a runtime's processes — `spawn` read +47% recompiling it. The kernel parses the name
  once per thread into a heap-free form, cached by symbol, and resolves it once per `receive`.
- **Pins** ride beside it: a `receive` that pins passes `[key pin0 …]`, the pinned symbols read
  at the call site — once per `receive`, where the closure read them per candidate. That is why
  only a pinned symbol qualifies, the rule `%receive-pin` already applies. A pinned lazy
  seq-view is realised once at entry, as `%eq` would realise it per comparison; a message never
  carries one.
- **Equality** is `Heap::equal`, `%eq`'s.

**Consequences.** No closure per `receive` and no Brood call per scanned message for the common
shapes. Instructions against `16abc996`, both arms' stdlib images live (median of 5):
`supervisor` −7.9%, `spawn-live` −7.8%, `pingpong` −3.7%, `spawn` −2.4%, `ring` −2% (10 a side,
and it no longer has a slow mode). `latency` is a wall-clock spin loop, not an instruction row;
its gate is `make latency-gate`. A guard keeps the closure, so a guarded `receive` costs what it
did. Guard: `tests/receive_spec_test.blsp` — which shapes become a spec, and every case run on
the spec and on the closure (a `:when true` forces it) against the same mailbox, on tiers 0–2
and across processes; sabotage of the length check and of the repeated-binder check each red
it.


## ADR-410 — A receive loop runs in native code

**Status:** implemented (2026-10-16).

**Context.** The `%receive` fence kept every arm that calls `%receive` out of the JIT: a native
activation cannot be state-captured, so a `receive` that found nothing in native code had no
way to park. Every server loop, `(defn loop (state) (receive …))`, ran on the bytecode VM, and
on `ring` the VM's dispatch (21 bytecode ops a hop) was ~2 500 of a hop's ~8 700 instructions.
A spike that let one such loop go native took a drained message from ~4 575 to ~3 220
instructions.

**Decision.** An arm that **receives at its head** may be compiled to native code. Its single
`%receive` must have nothing before it but loads and the vectors a `receive` builds for its
arguments (`jit_plan::receive_at_head`, recorded once as `CompiledArm::receive_at_head`). Then
re-running the arm from ip 0 is the same as re-running that `%receive`. A second `%receive`
would come after the first one's effect (the message it took), so an arm with two does not
qualify.

- **The park is a capture at ip 0.** The native `%receive` does the whole park (scan position,
  status, deadline timer) and surfaces the suspend on the error channel. The top-level driver
  (`vm_run_bc`) captures the activation's frame at **ip 0**, with no VM re-run and no second
  scan. The frame holds the current iteration's arguments because the native self-tail call
  stores them every iteration. A resume at ip 0 re-tiers, so the wake runs the native loop
  again.
- **Only an activation that can park may run it natively.** `jit_tier_in_frame` refuses such an
  arm unless the entry can unwind, which means one a top-level driver made. Under anything else
  (a builtin's callback, a primitive's fallback call, a nested driver) the `receive` would block
  the worker, and the suspend-host latch would take the shared arm off native code for every
  process. The bypass entries refuse it too: the interpreter's direct native call
  (`vm_direct_eligible`), the higher-order fast frame (`hof_apply_native`), and the native
  links (`jit_dispatch_call`, `fast_link_from_entry`). These run nested, where nothing can
  capture the frame.
- **A caller is still checked.** `arm_hosts_receive` skips the arm's own `%receive` but follows
  its non-tail callees as before. A native caller lowered before its callee was compiled (which
  that check cannot see) links to the loop through the slow path. There the loop runs on the VM
  and blocks, and the latch takes the *caller* off native code, as it always has.
- The suspend-host latch (`jit_suspend_feedback`) exempts these arms: their suspend on the error
  channel is the protocol, not a dirty park.

**Consequences.** Instructions against `55e6f3c4`, both stdlib images live (median of 5): `ring`
−19.4%, `pingpong` −7.3%. `supervisor`, `spawn`, `spawn-live`, `json`, `fib` and `nqueens` are
flat (within ±0.7%). A loop that does work before its `receive`, such as `(send …)` and then
`(receive …)`, stays on the VM. Guards: `tests/receive_loop_jit_test.blsp` runs on tiers 0–2.
It checks that a hot loop stays `:native` across parks and carries exact state, that `after`
timeouts and selective order still hold, and the other entries: a hot non-tail call site, a
native caller that linked before it saw the loop, `apply`, `map` and `fold` callbacks, and many
loops across processes. The unit test `receive_at_head_admits_only_a_leading_receive` pins the
shape. Sabotaging each guard turns it red: the latch exemption, the driver's capture, the
central refusal, the direct-call, callback and both link refusals, the `hosts-receive`
exemption, the fence, and the shape test's prefix and one-receive checks. Two guards I first
wrote could not be made to fail, so I removed them: a VM park rewinding to ip 0 and a refusal
in `dispatch`'s fast path (folded into the central one). *Corrected 2026-10-17:* the first was
load-bearing. Without it a loop that parks on every message never reaches the tier threshold.
It is restored, guarded by a test that sends one message at a time.

*Amended 2026-10-17:* widening the gate to every arm that journals checkpoints (a park resumes
at the last checkpoint instead of ip 0) was built and measured slower (`pingpong` +1.9%,
`supervisor` +4.8%), so the receive-at-head gate stands; see the devlog of that date.

## ADR-411 — `monitor` takes a remote registered name

**Status:** accepted, implemented 2026-10-17.

**Context.** `(monitor {:name n :node peer})` refused a remote address ("pass the pid"), so
`gen/call`, which monitors its server for the call's duration, failed at once on a server
registered by name on another node. Erlang's `gen_server:call({Name, Node}, …)` works, and
the address was already good for `send`. Found writing the cross-node `gen/call` test.

**Decision.** A `Frame::MonitorName { watcher_pid, name, mref }`. The receiver resolves `name`
on arrival and registers an ordinary remote watcher on that pid (`add_monitor` with
`Watcher::Remote`, the `Frame::Monitor` path), so DOWN, demonitor and net-split behave as for a
pid monitor. An unregistered name watches the placeholder pid `u64::MAX`, which fires `:noproc`
at once: the local `monitor`'s behaviour for an unregistered name, through the same function.
The sender records its pending entry under that placeholder too, so an unreachable node or a
net-split before the answer delivers `[:down mref <placeholder pid> :noconnection]`. The name
is resolved once; a later re-registration is a different process, as in Erlang.

**Alternatives rejected.** Delivering the `{:name :node}` address as the DOWN's object, as
Erlang does: the local name path already delivers a pid, and two shapes for one message would
split every pattern that reads it. A remote `whereis` round trip before monitoring: two frames
and a window in which the server can die unobserved.

**Guards.** `cli::distribution gen_call_round_trips_across_nodes_by_pid_and_by_name` (a call by
name, its crash, `:noproc` after, an unregistered name, a demonitor, an unconnected node) — red
with the receiver ignoring the name; `dist::wire::tests::monitor_name_roundtrips`.

## ADR-412 — `std/registry`: the kernel's atomic registry write, for registries a program defines

**Status:** implemented (2026-10-17).

**Context.** A plugin-shaped program keeps tables that LOADING fills: each module adds its rows
as it loads (a timer, an event handler, a status-bar chip), and the core reads the table
without naming any of them. bedit had seventeen, each a `defonce` global re-bound with `def`.
Every one carried the three bugs the kernel's own registries were fixed for. Two processes
registering at once each read the old table, so the later `def` drops the earlier row (KI-22,
KI-23). A registration inside an `%isolate` window is lost at the restore (KI-134, KI-141). And
a global that loading MUTATES is invisible to the startup image, which carries what loading
creates (ADR-218, KI-106). `%registry-update!` fixes all three, but it names a registry by its
fully qualified global. A project module cannot spell that: `model/*jobs*` in source is
`bedit/model/*jobs*` at runtime, and a bare name silently writes a root global of that name.

**Decision.** A std module, `registry`, owns ONE global, `registry/*registries*`, holding
`id → key → entry`, where `id` is a value the caller chooses (a namespaced keyword by
convention, `:model/idle-jobs`). `put!` / `remove!` are `%registry-update!`'s two-level `:assoc`
/ `:dissoc` on `[id key]`, so every registry gets the locked write, the isolate replay and the
image (attributed to the writing module, KI-136) without spelling a global. Reads are
`entries`, `lookup` and `ranked`. `ranked` orders by an entry's numeric `:rank`, then by the
printed key, so the order never depends on which module loaded first. Hooks in entries are
meant to be SYMBOLS, called with `reflect/call-if-bound`, which calls a bound name and answers
a fallback for one whose module has not loaded. A redefinition then takes effect on the next
call.

Rejected: a `defregistry` macro qualifying a per-registry global at expansion time. It only
works where the registry's own module expands it, and a feature registers from ITS module. A
kernel resolver from source spelling to runtime global would also do it, but it would be a new
primitive serving one caller, where a keyed table needs none.

**Consequences.** A registry is no longer a global, so it is not `M-.`-able as one, and two
programs choosing the same id share it; namespaced ids make that a choice. Removing a module's
rows when it is unloaded is still the caller's job. Guards: `tests/std_registry_test.blsp`.
Sixteen processes registering 25 rows each all land. Sabotaged to a plain read-then-`def`, that
test reds (rows are lost), as do the separation and tie-order tests. Rank order holds against
registration order. A hook kept as a symbol follows a redefinition.

## ADR-413 — State on the seam: music, lighting, post-processing and particles

**Status:** implemented (2026-10-18). Asked for by `b2d` ("use the graphics card fully", and a
looping music op), on ADR-374's display seam.

**Context.** The pixel-space vocabulary was two quads, text and a one-shot `[:sound …]`. A game
wanted three more things that no Brood policy can build out of those: music that loops, a lit
scene with a glow and a CRT look, and particles by the thousand. The cost rule is ADR-374's:
O(entities) on the Brood side, O(pixels) natively. A light map, a blur and ten thousand
particles stepped every frame are pixels and particles, not entities. Two constraints shaped
the design. The frame is the whole truth, re-sent every tick and replayed to a late joiner
(`serve-shared`), so anything that persists between frames must be readable from one frame.
And both painters draw every op (ADR-374 addendum 4).

**Decision.**

1. **State ops, beside event ops.** `[:sound …]` and the new `[:burst id n]` are EVENTS:
   they fire once when the frame carrying them arrives (`UserEvent::Draw`, after the
   identical-frame check), never on a repaint. `[:music snd vol]` and `[:emitter id x y opts]`
   are STATE: the frame says what should be going on, and the window reconciles. The same
   handle keeps the track or the particle system going (a new volume fades to it; a new
   position or spec takes effect), a different one replaces it, and a frame without it stops
   it. A late joiner or a thin client therefore hears and sees the right thing from the first
   frame it draws, with nothing replayed. An emitter that stops emitting keeps its particles
   until they die; a track fades out over 50 ms rather than clicking.
2. **Lighting is a multiply under an overlay.** `[:ambient color]` turns lighting on for the
   frame; each `[:light x y radius color intensity]` adds `(1 − d²/r²)²` of its colour into a
   light map that starts at the ambient. Everything before the top-level `[:overlay]` (all of
   the frame, without one) is multiplied by it; the ops after it are drawn unlit on top. That
   one marker covers both a HUD and something that glows, and keeps the op order the only
   layering concept.
3. **Post-processing over the finished frame.** `[:bloom threshold intensity radius]` (a
   soft-kneed bright pass at half size, a separable gaussian, added back) and
   `[:crt scanlines curvature vignette]`, in that order, after the overlay.
4. **Particles are simulated in the window.** Each emitter is a ring of `max` slots (default
   1024, at most 65 536). The bookkeeping (how many to spawn this paint from `rate × dt` plus
   bursts, which slots, which seed) is ONE `EmitterBook` both painters share
   (`host/gui/effects.rs`). The per-particle work is a compute shader on the GPU, which spawns
   and integrates (gravity, drag), then the same buffer is drawn as instanced quads (alpha or
   additive). The CPU painter runs the same arithmetic in Rust. The random numbers are one hash
   (lowbias32) written in both languages, so the two targets agree on which particles exist,
   where, and how old. While particles are alive the window repaints itself at ~60 Hz, since
   they move between frames even when the game's frame does not change.
5. **The CPU painter draws all of it, in software.** A frame with an effect or a live particle
   is rasterised whole (it has no damage to diff). About 40 ms for an 800×600 frame with
   lighting, bloom, CRT and a 2048-particle emitter, where the GPU takes 0.5 ms. Slow, correct,
   and the same picture: both dumps of the check scene match by eye.

Rejected: post-processing as a list of user shaders. WGSL from a frame would be a code-loading
path (the sandbox, the wasm build and signed packages all exclude one), and the CPU painter
could not run it. Rejected: lights that cast shadows. A shadow needs occluder geometry, which
the frame does not have, and the first game did not ask for it.

**Consequences.** Three shader modules (`LIGHT_SRC`, `POST_SRC`, `PARTICLES_SRC` /
`PARTICLE_DRAW_SRC`) and their pipelines are made lazily, the first time a frame asks, so a
window that draws text pays nothing. An effect frame renders through four extra textures
(scene, light map, two half-size bloom targets). A pass may not bind a texture it renders
into, so passes that read no glow bind a 1×1 placeholder (wgpu refused the first version with
a usage conflict). Guards: `effects.rs` unit tests (bursts fire once per arrived frame, the
ring wraps, a dropped emitter outlives its last particle, light and CRT arithmetic),
`gpu.rs`'s (no batch merges across the overlay, the uniform layout word for word),
`native.rs`'s music parse, and `tests/gui_robustness_test.blsp` (garbage effect ops are
skipped or clamped, never a panic).

Found on the way: every `nest run --for` on the GPU target segfaulted at exit on an NVIDIA
driver. `process::exit` ran the driver's exit handler while the GUI thread was still painting a
queued frame. The GUI thread now holds a gate around each event, and an `atexit` handler,
registered once the device exists (so it runs before the driver's), closes it.

## ADR-414 — A program kept running in a browser tab

**Status:** implemented (2026-10-18). For `b2d` ("the runtime in the browser tab").

**Context.** The wasm build ran snippets to completion: the playground hands a source text
to a fresh interpreter, `wait` pumps the cooperative scheduler until nothing can run, and a
receive timeout fires in LOGICAL time — the clock jumps to the deadline — so a snippet that
sleeps finishes at once. A game is the opposite shape: it never finishes, its frame
deadline must arrive in real time, and the page it runs in has one thread that must keep
painting and taking input. It also needs its own modules and assets, and a tab has no
filesystem to `require` them from.

**Decision.**

1. **The bundle is the program.** `nest release` already packs a project — manifest, every
   module, dependencies — and `require` already consults a mounted bundle before the load
   path. `bundle::mount_bytes` mounts one from bytes the page fetched, rather than from the
   executable's tail. A release over an empty runtime writes the archive and footer alone,
   so no new packing format exists. Assets ride as a module (`b2d-assets/embed!`), as they do
   in a release binary.
2. **A real-time pump with a budget.** `pump_due(budget)` (wasm) runs what is runnable, fires
   only the receive timeouts whose deadline has passed on the wall clock (`use_real_time`
   switches the scheduler's clock), and returns how long until the next one, or zero when the
   budget ran out with work left. The page pumps on that delay and after each input. The
   budget is enforced at quantum boundaries: on wasm a spent quantum yielded only to a
   waiting process, so a lone game behind its frame rate ran forever in one pump. Now
   `work_waiting` also answers true once the host's deadline (`set_host_deadline`) has
   passed. The first version ran a frame past the budget every time; this one keeps a 12 ms
   budget to within a millisecond.
3. **A display that is the page.** `%tab-post event json` queues a display event into an
   outbox the page drains (`take_events`); `%tab-subscribe` names the process the page's
   input goes to, as text to be read, never evaluated. The event names and JSON are exactly
   what b2d's SSE bridge streams, so one painter (`web/app.js`) draws a served game and a
   tab-hosted one, and only the transport differs.
4. **`crates/tab`** is the wasm-bindgen shim: `mount`, `start(args)` (the bundle's `:main`,
   booted by `project-release/run-bundle`, as a release binary boots), `pump(budget_ms)`,
   `events()` (name/JSON pairs NUL-separated, so a frame's JSON crosses once, unparsed),
   `input(text)`, `ended()`. It builds under `release-tab-wasm`: `opt-level = 3` where the
   playground's `release-wasm` takes `"s"`, because a game interprets every frame (wasm has
   no JIT). Measured on b2d's demo: 45 → 55 fps, and the wasm came out smaller (10.6 MB).

**Consequences.** A b2d game ships to the web as static files (`web/build-tab.sh`). Startup
loads every module from source (no startup image in wasm), which takes about half a second
of one unpreempted quantum: a nested load cannot yield. Measured in node on the same
artifact: the demo's first frame at ~0.9 s, then ~55 fps at 92% of the thread (it wants 60).
Not done: a JIT for wasm, a startup image for the tab, and audio decoding off the main
thread. Guards: `bundle.rs` (a bundle reads from bytes with or without a runtime before it;
anything else is refused and mounts nothing), `host/tab.rs` (events drain in order, the
oldest dropped past the limit, input needs a subscriber), and b2d's headless-Chrome check of
its demo.

## ADR-415 — Guest links: a node link that can reach what it was given and cannot ship code

**Status:** implemented (2026-10-18). For bedit's shared sessions (its issues.md S8).
A guest link's node name is the host's to mint, not the guest's claim: ADR-425.

**Context.** A node link is all or nothing. The handshake proves the peer holds the cookie
(ADR-034, ADR-068), and from then on the peer may send any message to any process: a
registered name, or a pid, which on this node is a small sequential integer anyone can
guess. A closure crosses the wire as data (ADR-033), and `:remote-spawn` runs one, so a
connected peer runs code. That is right between your own nodes. It is wrong for a
collaborator: bedit's shared session told you to hand over `~/.config/brood/cookie`, which
is every node on your machine, for the rest of time, with code execution. Three things were
missing: a credential that is not the machine's, a link that carries data and not code, and
a way for a server to know who it is talking to instead of trusting what the client says.

**Decision.**

1. **A guest grant is a second cookie with limits.** `(node/grant-guest cookie {:names [...]
   :as "alice"})` registers it; `(node/revoke-guest cookie)` forgets it. The handshake's
   responder checks the initiator's proof against the node's own cookie first, then against
   each grant, and answers under whichever matched, so the guest's side is an ordinary node
   started with that cookie (`node/start`'s override) and needs no new code. A link
   authenticated by a grant is a GUEST link and carries the grant.
2. **What a guest link can reach** is the grant's `:names`, and the local pids this node has
   sent to it — collected from every message routed out over that link. A capability by
   introduction: the server's reply to `[:attach …]` names the session pid, so the client
   can talk to its session; it cannot talk to a pid it guessed. A message to anything else
   is dropped and logged once.
3. **What a guest link can carry** is data. A message containing a closure, a native
   function or a shared function handle is dropped whole. A guest frame that couples
   processes — link, unlink, exit, a monitor of something it cannot reach — is dropped too:
   an exit signal is how a peer kills a process. A guest never takes part in the mesh: it is
   not gossiped to other peers and its gossip is ignored.
4. **Who the guest is** comes from the grant. `(node/peer-grant node)` answers the grant a
   connected peer authenticated with (nil for a full peer), and `editor/serve` uses its `:as`
   as the client's identity, overriding the name the client claims.

**Consequences.** bedit's `--listen` hands out a fresh guest cookie per session, scoped to
the serve entry, and the attach hint carries it; the machine cookie never leaves the
machine. A full link is unchanged. What a guest grant does NOT make safe: anything a
reachable process does with the data it is sent — the serve session turns keys into
editing, and an editor can run a shell command. A guest is limited to what the session it
was given can do, which is the point of giving one, but a session that can run commands is
still a session that can run commands.

### ADR-414 addendum (2026-10-18, later) — what a tab spends its time on

Measured on the built artifact in node (`node --cpu-prof` names wasm functions) and natively

### ADR-414 addendum 2 (2026-10-18, later) — the std modules imaged, and a smaller tab

**The stdlib image in a tab.** The sectioned image (ADR-218) read from a file through a held
descriptor. A path under `mem:` now names bytes held in memory instead (`boot::image`'s
`ImageFile::Memory`): `%image-write` to such a path keeps the bytes for the host
(`boot::memory_image`), a host hands bytes in with `boot::provide_memory_image`, and
`%image-index` / `%image-load-section` read either kind alike; `%image-exists?` answers for
both. The prelude's `%std-image-path` prefers `mem:std-image` when one was provided, so the
install path is unchanged. `stdimage/build` split into `build` (the cache directory's policy:
mkdir, prune) and `build-at path modules`. `crates/tab` exports `std_image(modules)`,
`use_std_image(bytes)` and `loaded_modules()`.

Which modules: a boot from source loads every module a body NAMES, while an imaged boot
(the kind index, ADR-335) loads only those it calls — so the list is learned by running the
game on an image of every std module and asking `loaded_modules`, then the image is rebuilt
with only those. b2d's demo: 3.1 MB for all of std, 1.47 MB (347 KB gzipped) for the 17
modules it calls, built in ~9 s by `web/tab-images.mjs`. First frame in node: ~540 → ~250 ms.

**A smaller wasm.** Four default-on features the tab builds without: `brotli`, `checker` (the
advisory checker's entry points; what lazy loading's signature index reaches stays linked),
`image-formats` (JPEG, GIF, WebP, BMP; PNG is always in) and `toolchain` (the std modules a
program is built with — `nest`, `project-check`, `scaffold`, `codemod`, `coverage`,
`complete`, `explain`, `update-brood`, `workspace` — and the two reference documents).
`crates/cli` and the playground ask for all four, so every native binary and the playground
are unchanged; `dev-tools` implies `toolchain`; `(system/features)` lists them. With the name
section dropped at bindgen: 10.8 → 7.4 MB, 3.71 → 2.61 MB gzipped.

**Consequences.** A game's first frame no longer waits on evaluating std, only on its own
modules (still from source) and its assets. Not done: imaging the bundle's own modules (a
project image in memory is the same mechanism), and the checker's signature scanner, which
lazy loading still links (~420 KB).

## ADR-416 — A stepping tree-walker: `BROOD_TIER=0` reaches process bodies, and its `receive` parks

**Status:** implemented (2026-10-19), all five stages, each in the devlog of that date.
Stage 1 (the escape audit); stage 2 split, 2a (the frame stack, `eval/machine.rs`) and 2b
(closure entry, macro expansion and `&optional` defaults as frames); stage 3 (`try`/`binding`
frames); stages 4 and 5 together (capture, and the flip). One departure from point 5: the
audit stays a diagnostic rather than a runtime hard check — nothing on a program's path
reaches the VM at tier 0, the paths that still do are unit tests driving `vm_run_bc` on
purpose, and a CLI guard asserts the audit stays empty over a parking program. Builds on
ADR-100 (full migration is a stepping-engine change), ADR-135 (the top level is a process),
ADR-222 (`BROOD_TIER`), ADR-400/402 (the VM runs `try`/`binding` inline).

**Context.** `BROOD_TIER=0` is meant to run everything on the tree-walker, and the
tree-walker differential (`make test-both`'s second half, CI's `differential (tree-walker)`
job) is meant to compare the two engines. Neither is true of process bodies.
`run_process_body` runs any VM-eligible body on the VM whatever the ceiling says, and every
`--test` body is a spawned process, so the differential tree-walks each test file's
top-level forms and runs the test bodies on the VM. Found on 2026-10-18, when a tier-0 guard
written in `tests/contract_test.blsp` passed with its fix removed.

The carve-out exists for a reason. The tree-walker keeps its pending work on the Rust stack:
argument evaluation, an `if` test, a `let` binding, a non-last `do` form, a closure body are
each a native recursion. A `receive` under that stack cannot hand anything to the scheduler,
so it blocks the worker (the dirty carve-out, ADR-100 §7.4). Tree-walking every process body
would make every `receive` in a tier-0 run block an OS thread, and no tier-0 run could be
preempted or migrated. The top level already pays this: `vm_run_bc`'s tier-0 branch runs a
whole top-level form synchronously.

The alternatives were to document the gap (the differential stays half-blind), or to make
tier 0 a debug engine that blocks freely (the differential then compares two schedulers as
well as two evaluators). Both leave tier 0 as something other than the language's reference
semantics.

**Decision.** Give the tree-walker the VM's shape: its pending work becomes an explicit
stack of continuation frames in the process, not Rust recursion. ADR-100 did the same for
the VM's frames.

1. **Same engine, same eight special forms.** `eval`'s `'tail` loop stays; what changes is
   that a step which today recurses (`eval` of an argument, a test, a binding RHS, a
   non-last body form, a closure body entered non-tail) instead pushes a frame naming what
   to do with the value, and the loop continues with the sub-form. A value pops the top
   frame. A tail position pushes nothing, so proper tail calls hold by construction.
2. **Frames are traced roots.** The pending values (evaluated arguments, the environment,
   the remaining forms) live in the frame stack, which the GC traces and relocates. This
   replaces the tree-walker's scattered per-site rooting.
3. **`try` and `binding` are frames**, as they are in the VM (ADR-400/402): a handler frame
   and a dynamic-binding frame, unwound by an error or a value. `%try` stops calling its
   thunk through a native boundary, so a `receive` inside a `try` parks.
4. **Capture.** A `receive` that does not match, the reduction budget, and a kill return the
   frame stack to `run_one` as the tree-walker's `Suspended`; the scheduler parks it,
   re-enqueues it, or resumes it on any worker. A native-nested `receive` (under a HOF
   callback or a primitive that calls back into Brood) still blocks, as it does on the VM.
5. **The ceiling holds everywhere.** At tier 0, `run_process_body` and the top-level driver
   run the stepping tree-walker, and `vm_run_bc`'s tier-0 synchronous branch is deleted.
   Under tier 0 no bytecode runs, and the escape audit (stage 1) is promoted to a hard
   check to enforce it.
6. **Errors and traces are frame data.** `TwFrame`'s trace bookkeeping (names, contract-shim
   untagging, ADR-385) and the catchable "recursion too deep" move onto the frame stack,
   with the positions they produce today.

**Stages** (each leaves the tree green under `make test-both`, the differential, fuzz and
`make gcstress`):

1. **Escape audit.** `BROOD_TIER0_AUDIT=<file>` records every distinct path by which
   bytecode starts under a tier-0 ceiling (`vm_run_bc` is the one chokepoint). Run over the
   suite, it enumerates what tier 0 does not reach, so the later stages are sized by data.
2. **The frame stack, behaviour-identical.** `eval`'s recursion becomes frames inside one
   `eval` call. No parking yet; judged by the existing suite, `tail_calls_do_not_overflow`,
   the position tests and the differential corpus.
3. **`try`/`binding` frames.**
4. **Capture**: the tree-walker's `Suspended`, through `run_one`, resumed on any worker.
5. **Flip**: process bodies and the remaining escapes run on the stepping tree-walker at
   tier 0; the audit becomes a hard check; the tree-walker CI job's time budget is
   re-measured (the tree-walker is roughly 18× slower than bytecode).

**Consequences.** Tier 0 becomes the reference semantics for the whole program, scheduler
included, and the differential compares test bodies. Error positions after a tail call
already differ between the engines (the VM names the call that entered a reused frame);
that difference is documented, not removed. The cost is stage 2: a rewrite of the
evaluator's core loop on a moving collector. The existing guards are what keep it honest,
and nothing parks until stage 4.

## ADR-417 — What belongs in `std/editor`: mechanisms, not an editor's features

**Status:** implemented (2026-10-19). Ten modules moved from std to bedit.

**Context.** bedit's rule is to fix a gap in the language rather than work around it in the
editor. It worked for `*out*` / `with-out-str`, which the language really lacked. It was
also read as "anything bedit could reuse belongs in std", and `std/editor` grew features with
one consumer: Org-mode (`editor/org`), Magit's transient menus and section trees
(`editor/transient`, ADR-387; `editor/section`, ADR-388), form buffers (`editor/formbuf`,
ADR-199), a highlighter per file format (`editor/configs`, `shell`, `dotenv`, `dockerfile`,
`markdown`), and a mail parser (`mime`). Nothing in this repository used any of them except
its own test. Each one versioned with the kernel, added to the embedded module table, and
took a std name that a project module could never use (a release resolves a std name
first). One of them, `editor/section`, shared a type name with `vt` and caused KI-187.

**Decision.** A module belongs in std when all three hold:

1. **It is a mechanism, not a feature.** Examples are a rope, a keymap, a render-op protocol,
   a lexer engine and an eval session. Org-mode, Magit sections and a YAML colour table are
   features built on mechanisms.
2. **Something besides one application uses it.** That can be the REPL, the observer, `nest`,
   the eval server, the checker, or a plausible program that is not an editor.
3. **It has to version with the kernel.** Display ops, the buffer-process protocol and the
   eval-session wire are spoken by the runtime and its tools together. A file format's
   highlighter is not.

A module that fails 1 and 2 lives in its application. One that several programs want but
that fails 3 is a hive package. It moves there when a second program wants it, and until
then it lives in the application that uses it.

Applied to `std/editor` and its neighbours:

- **Stay:** `buffer`, `buffer-client`, `buffer-registry`, `display`, `ui`, `serve`, `web`,
  `keymap`, `layers`, `face`, `lineedit`, `highlight`, `pane`, `list-motion`, `evalsession`,
  `treesit`, `lexer`, `ansi`; and `vt`, `markdown` (the HTML renderer the docsite uses),
  `diff`, `fuzzy`.
- **Moved to bedit, with their tests:** `editor/org` → `org`, `editor/transient` →
  `transient-core`, `editor/section` → `section`, `editor/formbuf` → `formbuf`,
  `editor/configs` / `shell` / `dotenv` / `dockerfile` / `markdown` → `lex-configs` /
  `lex-shell` / `lex-dotenv` / `lex-dockerfile` / `lex-markdown`, and `mime` →
  `mail-message`. The new names avoid std's names (`markdown`, and `mime` on releases that
  still have it). If another program wants the format highlighters or the mail parser,
  they become hive packages then.
- **Stay in brood's tests:** the `editor/lexer` cases from `configs_test` (now
  `lexer_test.blsp`) and the `shebang-interpreter` cases from `shell_test` (now in
  `layers_test.blsp`), because the code they test stayed in std.

There are no deprecation aliases, because this is greenfield. bedit stopped using the std
modules in the same change that removed them.

**Consequences.** std loses ten modules and about 2,700 lines, and the embedded module table
loses ten entries. ADR-387 and ADR-388 remain the design records of those modules, which now
live in bedit. The KI-187 regression test (`deftype_through_imports.rs`) no longer depends on
`editor/section`; it declares its own second `row`. Any new `std/editor` module has to pass
the three questions, and a plan that proposes one must name the caller besides the
application that needs it.

## ADR-418 — A table dies with the process that created it, unless a global holds it

**Status:** implemented (2026-10-21).

**Context.** ADR-107 made a table live until `table-drop` or runtime exit, with owner/`heir`
semantics deferred: an app-lifetime store created at startup was the model. Real code makes
short-lived tables too — the linear-map rewrite builds one per call, `memoize` one per memoized
function, a worker one per job — and a table its creator forgot to drop, or could not drop because
it crashed, was kept for the life of the runtime. KI-283 is what that cost: a rewritten tally
exhausted a 16 GB address-space cap after ~25 000 calls.

**Decision.** A table is owned by the process that calls `table/new`, and that process's exit
drops it — Erlang's ETS rule. The exception is a table that becomes reachable from a global:
every write to the shared table of globals (`def`, a registry update, a staged module binding)
runs `promote_global`, which **pins** any table it meets, so it lives as long as the runtime.
That is what keeps a module's `(def- cache (table/new))` alive whichever process happened to
load the module, and what keeps `(def f (memoize g))` working. A table created outside any
process (an embedder's `Interp` before it spawns, the boot image restoring a module's table) has
no owner.

A dropped table's registry slot is **reused** when nothing else can hold the handle: the handle
never left its creator (`escaped` is latched by `to_message` and by every promotion), and no JIT'd
loop of the dropping process can hold its dense slot base (`jit_shared`), or the drop is the
owner's exit. The slot's generation is the handle's high half, so a stale handle errors rather
than reaching the next table. The linear-map rewrite frees its own table through `%table-free`,
which the compiler may use because the loop that hoisted the base has returned.

**Alternatives.** *Reachability GC* — collect a table when no process holds its handle — needs
every heap's handles traced into a global census, against a GC whose point is that processes
collect independently; ETS has never needed it. *Keep `table-drop` only and document the leak* —
the rewrite's tables are invisible to the user, so there is nothing for the user to drop.
`heir`/`give_away` stay deferred (ADR-011): a table that must outlive its creator is held by a
global or created by a process that outlives its users, as a supervisor-owned ETS table is.

**Consequences.** A worker that creates a table and sends it away no longer keeps it alive by
doing so: once the worker exits, the recipient's operations error with `no such table`, as they
would in Erlang. A table inside a container that a `spawn` promoted earlier is not pinned by a
later `def` of that same already-shared container — promotion does not re-walk shared values;
binding the table itself, or anything built since, pins it. An owner that dies on the scheduler's
panic-recovery path has no heap left to list its tables, which then live on, as before.

## ADR-419 — An edit reloads the edited modules and their dependents; the project image keeps the rest

**Status:** implemented (2026-10-22).

**Context.** The project startup image (ADR-218) is keyed as ONE snapshot: path + size + mtime
of every source file, the build, the contract mode, the dependency and included files. Any edit
invalidated all of it, and the next `nest run`/`test`/`check` loaded every module from source —
33 s of a 40 s edit loop at 1 000 × 3k lines, to re-derive one file (`large-project-scaling.md`,
Finding 3, queue item 5). A section is still right after an edit when nothing it was built from
moved; the question is knowing what each module was built from. The image recorded only header
edges, and since ADR-335 a qualified reference such as `(def x (b/f 1))` loads `b` without
recording one, and a read of an already-loaded module records nothing at all.

**Decision.** When the full fingerprint misses but the rest of the key (build, contract mode,
dependency and included files) still matches, and every changed file is an existing file that
declares a module, the loader rebuilds **partially**:

1. **Dependency evidence is read wide.** A module depends on what its file requires, on every
   module prefix that appears anywhere in its TEXT — code, quoted data, keywords, comments, the
   insides of strings (`%module-direct-requires`'s `:mentions`, kept in the module index, v4) —
   and on the requires its load actually performed (`*require-edges*`). A macro whose expansion
   names a third module is covered transitively: the macro's own file mentions it. An extra
   prefix costs a reload; a missing one would be a stale value nothing reports.
2. **A load that evaluates source text is pinned.** `reflect/eval-string`, `%load-string` and
   `%eval-in` with a module's namespace open record that module (`%dynamic-loaders`); its
   section is never reused across an edit. `reflect/eval` does not pin: the prelude calls it at
   load time to resolve contract shims, ability defaults and lazy calls, and what it evaluates
   there is the module's own forms.
3. **The invalid set** is the edited modules and the pinned ones, closed over dependents. The
   loader opens the old image by the fingerprint its record stored (`.brood/image.modules`),
   loads the root section, takes each invalid module's registrations out of the restored
   registries — the entries its previous load wrote (the KI-136 writer journal, recorded per
   module at write time), its ability impls (`*impl-from*`), its require edges — drops its
   section, materialises everything else, loads the invalid modules from source, and writes
   the image again. A module materialised in this process wrote nothing here, so its previous
   ownership record carries over.
4. **Anything else rebuilds whole**: a new binary, the contract mode, a dependency or included
   file, a deleted file, or a changed file with no `defmodule` (its globals ride the root
   section).

**Amended 2026-10-22 (later): the unchanged sections are COPIED.** A partial rebuild used to
materialise every unchanged module and re-encode it, only so the image could be written whole
again. `%image-write` now takes `[name [:copy offset length]]` in place of a section's names and
copies that section's bytes from the image on disk (a section is self-contained; its macro names
come from the old footer), so a lazy caller — `nest run`, through `load-sources-cached`'s
`:lazy` — materialises only what the reloaded modules require. One module edited on the 302 × 3k
rig: `nest run` 2.7 → **0.30 s** (265 MB); check and test, which need the whole project, still
materialise it (~2.2 s).

**Alternatives.** *Static references only* (the checker's `:refs`): misses a load that builds code
from a string — silently. *Track every cross-module global read during each load*: complete, but
it taxes every load to protect against a case the pin already catches. *Key sections per module
by content hash*: the same dependency question, answered no better.

**Consequences.** 302 × 3k rig, release: one module edited 13.2 s → **2.7 s** (the cold build
against the partial one), of which ~1 s materialises the 301 unchanged modules and 1.4 s
rewrites the image — both still O(project), the next lever. `nest` prints `Rebuilt NAME: N
modules from source …` for a partial rebuild and `Building …`/`Built …` for a whole one. Guard:
`crates/nest/tests/partial_image.rs` asserts after each edit WHICH modules loaded from source
(a top-level marker a materialised module cannot print) and that the answers equal a
from-scratch build — a load-time qualified reference, a macro expansion, a computed
`eval-string`, a removed impl and registry row across two partial rebuilds, and the
whole-rebuild fallbacks. Sabotage: dropping the mentions from the dependency graph reloads 3
modules instead of 6 and serves `area-k=100 m=30` after the edit to `k = 20`.

## ADR-420 — Typed parameters: `(defn area (w:number h:number -> number) …)`

**Status:** implemented (2026-10-22). Revises ADR-082's surface; `sig` stays.

**Context.** A signature lived in a separate `(sig name (T… -> R))` form beside the
definition — the Haskell/ML/Elixir (`@spec`) tradition — so a function's name, parameters and
types drifted apart, and the reader had to line positions up by hand. ADR-163 deferred the
inline form to its own ADR. The sketch it recorded, `(defn f ((x int) -> int) …)`, cannot work:
`((x int))` is already a list-pattern parameter, and `&optional (y string)` already names a
default — any type syntax INSIDE a sub-list changes the meaning of existing code.

**Decision.**

1. **`name:type` on the parameter, `-> TYPE` closing the list.** A colon inside a symbol was
   free (the reader keeps `w:number` one symbol; a leading colon is still a keyword), and
   `name: type` is how most typed languages annotate a parameter. `name:` takes the FORM that
   follows as its type (`xs: (list int)`), for a type a symbol cannot spell. `&optional`
   slots keep their defaults: `(greeting:string "hello")`.
2. **The compile pass strips them** (`eval/macros/typed.rs`), before lowering, hygiene, resolve
   and every engine, so nothing downstream can bind `x:int`. A named definition `(def NAME (fn
   …))` — what `defn`/`defn-` expand to — becomes `(do (def NAME (fn PLAIN…)) (%register-sig
   'NAME '(T… -> R)))`: the declaration `(sig …)` would make, through the primitive so the
   prelude can use it anywhere. `fn` and `defmacro` take them too (an anonymous `fn`'s types
   declare nothing yet; a macro's arguments are forms).
3. **`_` is the open position.** An untyped parameter is `_` (unconstrained); a missing
   `-> TYPE` is a `_` result, which the checker keeps INFERRING — a declared name with an open
   result stays an inference candidate, its inferred return is written into the declaration,
   and its body is not checked against a return nobody declared; across modules, `sig_of`
   merges the inferred return the same way. Typing one parameter therefore never costs the
   return the checker inferred before. `_` is also accepted in a written `sig`, and
   `type-matches?` never checks it.
4. **Refused with an error, never mis-bound:** a type inside a destructuring pattern, a typed
   `let`/`letrec` binder, types on a multi-clause `fn`, and a `->` that is not second-to-last.
5. **Readers of raw source split the same way** (`syntax/typed.rs`): the CST scope analysis
   binds the name (its span is the name alone, so a rename keeps the type), the std
   signature index counts the parameters and carries the spelled signature, and the
   checker's raw-form passes (`fn_params`, guard effects) bind the name.

**Alternatives.** *A `:sig` marker after the parameter list* (`(defn f (x) :sig (int -> int)
…)`): unambiguous but still a second spelling of the same positions. *A macro-only `defn`
rewrite*: left `fn`, `defmacro`, the CST tools and the checker's raw passes binding `x:int`, and
declared `any` for every untyped position, so annotating one parameter erased the inferred
return. *Types on `let` and pattern elements*: deferred (ADR-011) — refused loudly until
there is a design for what they mean at run time.

**Consequences.** `(sig …)` remains for multi-arity functions, values and overloads; nothing in
std was migrated. A parameter named with a colon, or literally `->`, is no longer an ordinary
binder. Guards: `types/check/tests/typed_params.rs` (call checks, the open result keeps the
inferred return, a stated result is checked), `tests/typed_params_test.blsp` (binding, the
registered signature, contracts, the refusals, workers calling a typed definition across
processes), the scope analysis' binder spans and the std index's arity.

## ADR-421 — A stateful transducer stage keeps its state in the run's own table

**Status:** implemented (2026-10-22). **Completes ADR-376's deferred half.**

**Context.** ADR-376 gave transducers an early exit (`reduced`) and left stateful stages out:
`xtake`'s counter needs somewhere to live across inputs, and Brood's only mutable structure
is a table (ADR-026), which something has to release. The design ADR-376 sketched was
Clojure's completing arity — `(rf acc)` once at the end, every stage forwarding it. That
arity would reach the CALLER'S reducing function too, and a caller's `-` negates its result
under `(- acc)`; Clojure answers with `completing`, a wrapper every caller must remember.
It would also have given every stateless stage — the ones the `l*` seq-views run per element
— a second arity to carry.

**Decision.** The RUN owns the state. `seq/transduce` creates one table, binds it as
`*transduce-run*` while it applies the transducer stack to the reducing function, and drops
it on every exit: the input ending, a `reduced`, a throw. A stateful stage calls
`(seq/stage-slot initial)` when it is applied — it returns `[table slot]` — and reads and
writes its slot with `table/get`/`table/put`. Nothing in a stage releases anything; a
stateful stage built outside a `transduce` raises. `seq/xtake` is the built-in one.

**Alternatives.** *Completing arity*: above. *A table per stage, dropped on its own
`reduced`*: leaks whenever the input ends first. *Lazily creating the run's table only when
a stage asks for one*: the stage would have to hand it back to the run, which takes a
mutable cell the language does not have.

**Consequences.** Every `transduce` call pays for the table and the binding: 2.0 → 2.45 µs
for a three-element run, nothing measurable on a real input. Stateless stages and the `l*`
seq-views are untouched. Since ADR-418 a table also dies with the process that created it,
so even a run killed mid-way leaks nothing past its process. Guard:
`tests/transduce_stateful_test.blsp` — `xtake`'s shapes, the caller's `-` never called with
one argument, the run's table dropped on all three exits (a stage records it, and the test
asks it after the run), a stateful stage refused outside a run, and concurrent runs owning
separate state.

## ADR-422 — A cursor steps by grapheme cluster, over the rope's own chunks

**Status:** implemented (2026-10-22). **Completes ADR-159's deferred rope cursor.**

**Context.** ADR-159 added cluster-indexed string accessors and deferred "a rope-level grapheme
cursor … sized against a real editor workload". Sizing it found something more basic: neither
the editor (`bedit`) nor `std/editor` used graphemes at all. `forward-char`/`backward-char`
moved point by one CODE POINT, `delete-char`/`delete-backward-char` removed one, and the line
editor did the same with `inc`/`dec` — so on `e` + U+0301 or an emoji ZWJ sequence the cursor
stopped inside a character and a backspace left an orphan accent, the corruption
`docs/language.md` warns about.

**Decision.** Two boundary primitives per text kind, taking and returning code-point indices
(the positions everything else uses) but always landing on a cluster boundary:
`%rope-next-grapheme`/`%rope-prev-grapheme` (published as `text/next-grapheme`/
`text/prev-grapheme`, with `text/forward-graphemes`/`backward-graphemes` for `n` steps) and
`string/next-grapheme`/`string/prev-grapheme`, which clamp at the ends like ADR-159's
accessors. The rope pair runs `unicode-segmentation`'s `GraphemeCursor` over the rope's own
chunks — ropey's documented recipe — so a step costs the cluster it crosses plus a chunk
lookup. The editor buffer's motions and deletions and the line editor's step by them.

**Alternatives.** *A cached segmentation per buffer* (what ADR-159 imagined): measured
unnecessary — a step in the middle of a 389 000-character rope costs ~0.3 µs uncached — and a
cache is state to invalidate on every edit. *Grapheme-indexed positions*: every position in
the editor, the rope and the protocol is a code-point index; changing the unit is a rewrite
for no gain once every step lands on a boundary.

**Consequences.** `forward-char` etc. now count user-perceived characters; for ASCII nothing
changes. Guards: a Rust test steps a ZWJ/decomposed text across several rope chunks against
`grapheme_indices`; `tests/grapheme_cursor_test.blsp` covers the primitives, buffer motion and
deletion, the line editor, and workers stepping their own ropes.

## ADR-423 — A module's own definition wins over a root macro; macro templates pin their heads to root

**Status:** implemented (2026-10-23).

**Context.** `(defmodule m) (defn- spy (x) …)` was accepted — the reserved-name hint even
says that inside a module a name "is yours" — yet every bare `(spy …)` in `m` still expanded
the prelude's `spy` macro. A function shadowed a root function, but a root macro shadowed
the module: the worst of the three rules on offer. Elixir rejects a local function that
conflicts with an auto-imported `Kernel` one; Clojure lets the namespace's own `def` replace
the referred var, with a warning.

Letting the module win was tried first and reverted: prelude templates emit bare names
(`when-let` → `(when v …)`), which resolve in the *caller's* namespace, so a module defining
its own `when` captured every `when-let` it used. ADR-236's `/name` escape existed for this,
written by hand for functions, and macro heads were safe only because a macro always won.

**Decision.**
1. **Module wins.** Inside a module, a bare head that names a root macro resolves like any
   other bare name — own namespace, then `(:use …)` imports, then root (`macro_head_id`). The
   module's own macro expands; its own function is called. `/name` reaches the root macro.
2. **Templates pin their call heads to root.** When a macro is defined — at `resolve`, on the
   `(%make-macro (fn …))` that `defmacro` expands to, at root and in modules — every literal
   call head of its quasiquote templates that names a root binding is rewritten `/name`
   (`template_escape.rs`), the way Clojure's syntax-quote qualifies template symbols. A
   module's own names were already qualified to `mod/name` by ADR-065 §7, so what is left
   bare and bound is root. The resolver now also keeps a hand-written `/name` inside a
   module's template rather than stripping it at definition.
3. **A warning, and a declaration that silences it.** Defining a root macro's name in a
   module prints `warning: \`m/spy\` shadows the prelude macro \`spy\` …` once per definition
   per process, unless the header declares it with `(:shadow spy)` (recorded in the per-file
   import table, which the load scope restores — and read by the checker's own header
   parse). `BROOD_NO_SHADOW_WARN` mutes it with the import-shadow warning. Shadowing a root
   *function* stays silent: 45 std definitions do it by design (ADR-236).

**Scope, sound rather than complete.** Only templates inside a macro's function (a quasiquote
elsewhere builds data, whose symbols travel by name, ADR-034); only call heads (the class the
capture gate checks); never a head spelled like any binder of the same template — binders of
`let`/`fn`/`doseq`/`for`/… lists, parameter lists, `match`/`receive` patterns — so a binder
the walk misreads can only leave a head unescaped, never rename a local. An argument naming a
root function (`(map ~xs first)`) still needs the hand-written `/first`, and
`tests/prelude_capture_test.blsp` keeps checking the `(list 'head …)` shape.

**Consequences.** `macroexpand` shows the escapes: `(when-let (x 5) x)` →
`(let (v 5) (/when v (let (x v) x)))`. std's three root-macro shadows (`fuzzy/match`,
`os/spawn`, `node/spawn`) declare `(:shadow …)`. Guards: `crates/cli/tests/macro_shadow_warning.rs`
(the warning, its silencing, the module's win, `/spy`), and in `prelude_capture_test.blsp` a
module's own `when`/`and` not capturing `when-let`/`if-let`/`cond`, a module macro not
captured by a consumer defining `first`, and parallel workers each compiling their own shadow.

## ADR-424 — A package ships its own `nest new` templates, as data

**Status:** implemented (2026-10-23).

**Context.** `nest new --template hatch` and `--template web-api` scaffolded Hatch apps from
~250 lines of string concatenation in `std/tool/scaffold.blsp`. std carried one framework's
module names (`web/endpoint`, `deflive`), its idea of a starter app, and a table of sibling
`:path` checkouts (`../hatch`, `../store-postgres`) the project needed beside it — so a fresh
machine got a project that failed every command until those were cloned, and a change to a
Hatch starter was a brood release, not a hatch one. The rule the audit applied: std may serve
external projects only through generic mechanism, never with their specifics.

**Decision.**
1. **A package declares its templates in its manifest:** `:templates {"app" {:dir
   "templates/app" :about "…" :next ["…"]}}`. A template is a directory of plain files.
2. **`nest new NAME --from SOURCE [--template T]`** fetches the package — a path, a git URL
   (`url#ref`, else HEAD pinned to the commit read) or a registry name (`registry-install` into
   a temporary directory) — reads its manifest as DATA (`reflect/read-first`, never loaded),
   and copies the chosen template's files. `--template` may be left out when the package has
   one template, or one called `default`. Everything is resolved before the first write, so a
   bad source or template leaves no half-made directory.
3. **Two placeholders, both plain text:** `{{name}}` (the project's name) and `{{package}}`
   (the dependency entry reaching the package the way `--from` named it: `[hatch :path …]`,
   `[hatch :git URL :ref …]`, `[hatch :version "^X.Y.Z"]`). The second is what removed the
   sibling-checkout problem: a template's manifest names its own framework without knowing
   where it lives.
4. **hatch's two starters moved to hatch** (`templates/app`, `templates/api`). std keeps only
   its own starters (`default`, `tui-loop`, `gen`, `editor`, `gui`).

**Why data, not a template module.** A module would let a template compute (ask questions,
branch on options), but scaffolding would then run code fetched from a URL before the user has
read any of it, and `nest new` would need the package's dependencies resolved to run it. Files
plus two substitutions cover every starter std carried, and `nest format` runs over the result
as it always did, so a template need not be canonical to produce canonical code. If a starter
ever genuinely needs logic, that is a new decision, not a hole in this one.

**Not done.** No listing of a package's templates beyond the error that names them, and no
placeholder for anything but the name and the package. Guards:
`crates/nest/tests/scaffold_quality.rs` — a fixture package's template scaffolds a project that
formats clean, tests green and runs against the package found by path; an undeclared template
is named with the ones that exist and writes nothing; `--template hatch` points at `--from`.

## ADR-425 — A guest link's node name is the host's to mint, never the guest's claim

**Status:** implemented (2026-10-23). Closes the case KI-287 left open; amends ADR-415.

**Context.** A node name is whatever the initiator writes in its `Hello`. The cookie proves
the initiator holds the node cookie or a grant (ADR-415); it says nothing about the name. For
a full peer that is fine — a cookie holder can run code here anyway. For a guest it is not:
`NODES` is keyed by name, `route` sends whatever is addressed to a name over the link
registered under it, and a pid carries its node's name. KI-287's first fix refused a guest a
name a full link holds or has ever held HERE (`guest_may_take`, `FULL_PEER_NAMES`). What no
check on this node can refuse is a name that is a full peer's ELSEWHERE in the cluster and
has never linked here: a guest claiming it is registered under it, and a pid of the real
peer that a third node forwards here (in a message to a local process, which then replies)
routes to the guest — with whatever this node's process said to it. Closing that needs node
names a guest cannot choose.

Three things a design has to live with. One session cookie (bedit's `--listen`) serves any
number of attach clients, each under its own generated name (`editor/serve`'s
`attach-<time>`). A grant's `:as` is who a PERSON is, not a node name. And old guest
clients (every bedit build out there) write their own name and expect to be called by it.

**Options.**

1. **A reserved namespace the guest must claim in.** The host refuses a guest whose `Hello`
   name is not `guest/…`, and refuses `guest/…` to full links. It needs a new client (an old
   one claims `attach-…` and is refused), the client must know the host's naming before it
   dials, and names are still chosen by the guest within the namespace — so two hosts' guests
   can collide at a third node unless the namespace also names the host, which the guest
   then has to spell exactly.
2. **The host assigns a name in its `Hello` reply.** The responder cannot: it learns the
   initiator is a guest only when the `Auth` verifies, after both `Hello`s. An extra frame
   after `Auth` is a protocol change every old client fails, and the guest would have to
   rename ITSELF after `node/start` — its pids already carry the old name.
3. **Bind node names into the grant.** The grant has no node name to bind (`:as` is an
   identity), and an exact bound name admits one client per session cookie.
4. **The host mints the name and translates at the link.** The claim is never a node name
   here: a guest link is registered under a name the host mints, and the link rewrites the
   pids of the guest's node between the two spellings, in both directions. Nothing changes on
   the wire or in the client.

**Decision: 4.**

1. **The name.** `establish` gives a guest link `guest~<serial>.<incarnation>~<claim>`
   (`guest::GuestLink::new`): the serial is unique to this life of the host, the host's
   incarnation (random per runtime, the one its `Hello` sends) makes it unique across hosts
   and lives, and the claim rides along only so `(node/list)` reads as who it is. It is the
   link's `NODES` key, the
   node its reader stamps on its frames, the node of its pids here, the name its
   `[:nodedown]` carries.
2. **The namespace is reserved.** `node/start` refuses a name starting `guest~`, and
   `register_link` refuses a full link claiming one. So every `guest~` name in `NODES` is a
   guest link this node minted, no full peer anywhere has one, and no two guests share one.
3. **Translation at the edge.** A frame read from the guest, once admitted, has its pids of
   the claimed node renamed to the minted one (`translate_inbound`: a `Send`'s payload, a
   `Down`'s reason); a frame going out to it has the minted name's pids renamed back
   (`translate_outbound`, in `route` and `send_frame`). A pid of any other node is not
   touched. The guest never learns its minted name and needs none.
4. **What it replaces.** `guest_may_take`, `FULL_PEER_NAMES` and the "a full link always
   displaces a guest" arm of `register_link` are gone: a guest key collides with nothing, so
   there is nothing left to arbitrate. A guest that claims a full peer's name now coexists
   with that peer's link, under its own name. `linked_peer_for` still never answers a dial
   with a guest link (its advertised ADDRESS is still a claim), and the mesh skips a gossiped
   `guest~` name.
5. **What a server sees.** `(node/peer-grant pid-or-node)` answers for the minted name, and
   adds `:claimed` — the name the guest gave itself — for showing a person. `editor/serve`
   keeps reading `:as` for identity; bedit's attach UI shows that, and needs no change.

**Consequences.** The never-linked-peer case is closed by construction: no guest is ever
registered under a name it chose, so nothing addressed to a full peer — linked, down, or
never seen here — routes to a guest, on this node or (since a minted name names no link
anywhere else) on a third node a guest's pid travels to. Interop: no wire change and no
protocol version bump. An old guest client against a new host works unchanged — it is
called by its claim on its own side and by the minted name on the host's, and never sees the
difference; a new client against an old host is the same client. Old full peers are
unaffected; an old third node holding a pid of a new host's guest has no link under its
`guest~` name and drops the send, as it should. What an old HOST still does is its own
KI-287 until it upgrades. The cost: every message to or from a guest is walked once more for
pids (beside the walk `note_outbound` and `carries_code` already make), and each guest link
interns one more symbol (as its claim already did). A guest that claims a full peer's name
still confuses only itself: that peer's pids, sent to the guest, look like its own.

**Not done.** A guest's pid that it spells with another node's name (`nonode`, the host's,
a third node's) is passed through as it is — what the host's processes do with a pid in a
guest's message is ADR-415's "what a reachable process does with the data", not a naming
question. Guards: `dist::tests::a_guest_is_never_registered_under_the_name_it_claims`,
`dist::tests::guests_and_a_full_link_claiming_one_name_are_separate_links`,
`dist::tests::no_full_peer_may_use_the_guest_namespace`,
`dist::tests::a_guest_receives_its_own_pids_in_its_own_spelling`,
`dist::guest::tests::a_guest_link_is_named_by_the_host_and_its_pids_are_translated_at_the_edge`,
and the distribution test `a_guest_link_reaches_what_it_was_given_and_ships_no_code` (the
host's `(node/list)` shows a `guest~` name, `:claimed` is the client's, and the client's own pid
comes back to it as its own) — written on a desktop that runs no tests, so not yet run.

**Amendment 2026-10-24: the "Not done" is done (KI-296).** Passing another node's spelling
through was not only a naming question. `note_outbound` turns every pid this node sends a guest
into reach, so a local pid the guest GUESSED and put in a message became reach the moment
anything here echoed that data back (a collaborative app broadcasting what participants wrote).
And `std/editor/serve` reads who a client is from the grant of the client pid's node, so a guest
attaching with a full peer's pid (or a local one) got no grant: no `:guest true`, and its own
`:name`. A guest's `Send` — and a `Down`'s reason — is now refused unless every pid in it is of
the guest's own node or one this node sent it (`GuestLink::reachable` keys `(node, id)`, this
node's pids under `nonode`). Guard: `a_guest_reaches_its_names_and_the_pids_it_was_sent_and_nothing_else`
(red with the check disabled). Still open, and small: each guest link interns its minted name for
the runtime's life, outside the wire-symbol budget, so a cookie holder reconnecting in a loop grows
the symbol table by one name per connection.

## ADR-426 — A cold project build loads its modules in a pool of processes

**Status:** implemented (2026-10-23).

**Context.** A cold build loaded every source file on one thread — 39 s for 3M lines
(docs/large-project-scaling.md, Finding 3), and since ADR-419 a cold build is what the first
run, a CI checkout and every `rm -rf .brood` pay. Modules in different parts of the require
graph are independent, and `require-one` is already safe under concurrency: a module is
claimed atomically, a racing requirer parks until the claimant provides, a failed load
releases its waiters, and `def` publishes to the runtime's shared code that every process —
and the image write after — reads.

**Decision.** `project/load-sources` hands a COLD walk of at least `*load-min-parallel*`
(16) module files to a pool of `%worker-threads` processes. Each asks the driver for the next
`[feature file]` and `require-one`s it, so a dependency another worker is mid-way through is
simply waited for. Kept sequential, deliberately:
- a WARM walk, which re-loads already-loaded modules (the hot-reload contract) — `require-one`
  never re-loads;
- files with no `defmodule`, which define root-level globals and have no key to claim — loaded
  first, in walk order;
- a module `require-one` cannot find by its key — loaded by `reflect/load` after the pool.

What the first cut got wrong, each now pinned by `crates/nest/tests/parallel_load.rs`, which
compares every case with `BROOD_LOAD_SEQUENTIAL=1`:
1. The worker bound `*require-parent*` to `""`, so every module became a require of the ROOT
   section, which a warm start replays — the whole project loaded on every warm run (0.2 s →
   1.3 s). The worker binds `nil`: its own require is the walk's, not an edge.
2. The pool size came from `dev/worker-threads`, which loaded `dev` into the build and its
   registries into the user's image. It reads `%worker-threads`.
3. `*features-waiting*` — processes parked on in-flight loads, pids and all — reached the
   image; only a racing requirer writes it, so a sequential build never had one. Excluded.
4. An error raised in a worker reached the driver as a message string, from whichever
   dependent reported first. The driver stops dispatching on the first failure and re-loads
   that file sequentially, which raises exactly what a sequential build does.
5. It exposed KI-289: positions were lost on code re-homed after an aging flip.

**Measured** (302 × 3 067-line rig, 12 cores): the load 8.5 s → **2.1 s**; a cold
`--check-boot` 12.9 s → 6.5 s, of which the image write (1.7 s) and the rest of the run are
now the larger part. Warm runs unchanged (0.2 s / 124 MB). Records beside the image identical
to a sequential build's.

**Amended 2026-10-24: OPT-IN (`BROOD_LOAD_PARALLEL=1`).** CI's downstream bedit job went red
the next run: bedit's image built in the pool differed from a sequential one in 89 of its 116
module sections, and on a warm run from it 14 of `mdpreview_test`'s 19 failed (C-c C-p opened no
pane). Every record and the 302-module rig agreed — the rig's modules read nothing at load.
The working hypothesis is load-ORDER dependence: a module computing load-time values from state
other modules write (a registry read at load time) sees whatever the walk had loaded before it,
and the walk's order is something existing code relies on, deliberately or not. Until that is
pinned down — find which bedit value differs and why — the pool is a choice, not the default.
The sequential walk is unchanged, so the default build is what it was before ADR-426.

**Worse, measured the same day: it can DEADLOCK.** A parallel build of bedit hung in 2 runs of 4
(`timeout 120`; the sequential build never does). bedit has require cycles. In ONE process a
module requiring itself back mid-load proceeds (the load-once cycle rule in `%require-one`);
across processes worker A holds X and waits for Y while worker B holds Y and waits for X.
KI-290 (in progress the same day, `f6e2ed49`) teaches `require-one` to break a cycle that spans
processes — one member backs out — and records the double load behind bedit's differing image.
**Until that lands green, the pool is not safe for arbitrary projects even opt-in.** The design that would make it the default: read the require graph from the
headers (`(:use …)`, `(:load …)`), load each strongly-connected component on ONE worker,
start a component only once its dependencies have loaded — which also restores the
dependency half of the load order — and decide what to do about requires a module makes that
its header does not declare (inferred qualified references).

**Left.** A failing load is slow on both paths — every rolled-back load clears the shared
compiled code, and the prelude's arms are recompiled at each level of the failing chain
(13 levels: 4 s sequential); the pool multiplies it because each dependent retries the load.

*Corrected 2026-10-24:* the recompiles were a symptom. The header-dependency pre-pass
(`%require-header-deps`) swallowed a dependency's failure for the header to raise again, and the
header raised it by LOADING the dependency again — at every level, so the bottom module loaded
2^(depth−1) times (13 deep: 4 096 loads, 3.4 s; 20 deep ran for minutes at 4.7 GB). The pass now
records each failure in `*require-failed*`, bound around the module's own load, and the header
raises the recorded error; the module loads once (13 deep: 0.05 s). Guard:
`tests/require_failure_test.blsp`.

**Amendment 2026-10-24 (later).** *The driver.* It counted workers by message order — `live`
dropped at `:stop` and again at a non-normal `[:down …]` — so a worker dying abnormally after its
`:stop` counted twice and the driver could block for good, and a dead worker was reported under
the "file" `"a load worker"` (KI-294). It now tracks pids, and the pool is a **prefetch**: after
it, every module still unloaded — not found by key, failed, met a cross-process cycle, never
handed out after fail-fast, or lost with its worker — is loaded sequentially in walk order. A
failure raises what a sequential build would, where it was raised; a load only the race broke
succeeds. *Bedit's differing image.* KI-290's entry names the likely cause: `mdpreview` uses
`aside`, which uses `panes`, the very cycle KI-290 caught across workers, whose 30 s backstop
loaded `panes` twice and left `aside` compiled against a half-published module ("C-c C-p opened
no pane"). Not proven — one throwaway CI run with the pool on by default passed bedit's smoke.
And "89 of 116 sections differ" proves little by itself: `GENSYM_COUNTER` is one process-wide
atomic, so workers' macro expansions interleave gensym numbers and an equivalent image differs
byte for byte in nearly every section with a macro. Compare images semantically before trusting
a diff. A header-clause cycle still doubled its waits per level (KI-293, fixed).

**Amendment 2026-10-24 (last): the default again; `BROOD_LOAD_SEQUENTIAL=1` opts out.** Both
things that made it opt-in are gone. The deadlock was KI-290, now closed: its guard is green
in CI, and red in every job with `%require-cycle?` disabled. The differing image was that
cycle's double load, as the amendment above argues. And whatever the race still breaks is
loaded again by the sequential pass, so it can no longer build something a sequential load
would not. With the pool on by default (throwaway ref, run 40072666463), bedit's downstream
smoke passed three attempts out of three. Before KI-290 it failed about one run in two or
three. The flag is now an opt-out, named like `BROOD_CHECK_SEQUENTIAL`, its sibling for
`nest check`.

**Amendment 2026-10-25: a load-order dependence, found — and now a lint.** bedit's
`defchrome` registered each face with `(def theme/*chrome-faces* (conj theme/*chrome-faces*
row))`, expanded in every feature module. Two modules doing that in the pool at once each read
the old vector, and the later `def` dropped the earlier module's rows. The sequential pass
cannot repair it, because both loads succeeded. One image built that way had no `vcsproc` or
`project-search` faces and another no `debugger` ones, so a theme switch left git's diff
colours on the old palette in some builds only (bedit `appearance_test`, red on one desktop,
green in CI). bedit moved the faces to `std/registry`, which has a locked write. `nest check`
now warns on the shape (`:cross-module-def`, `check/cross_module_def.rs`): a load-time `def`
re-binding a global another module already defined, read on the EXPANDED forms because the
write sits in the owner's macro template. std's one such writer, `describe`, is allowed: the
runner loads test files one at a time.

**Amendment 2026-10-30: pool workers give a cycle up, and a failure stops the pool** (KI-312).
A ring of many modules aliasing each other hung the pool: the one process that broke a cross-process cycle
shortened it by one member a round, and bedit's cold build never ended. Pool workers now bind
`*require-cycle-abandons*`, so every worker on a cycle raises and none retries; the driver already
leaves such a module to the sequential pass, and each cycle costs the pool only its jobs. Outside
the pool one member still breaks a cycle and retries. The driver also kills its workers at the
first real failure instead of waiting for the jobs in flight, which loaded the broken dependency
again and again, and a waiter on a failed load raises the loader's error instead of loading it
itself.

## ADR-427 — A rethrown user error keeps where it was raised

**Status:** accepted 2026-10-24 (KI-291).

**Context.** `catch` binds a user `throw`'s value verbatim — `(throw 42)` → `42` — and that
contract leaves the position and trace the error collected nowhere to live: `(throw e)` raised a
NEW error, located at the rethrow. Every cleanup-and-rethrow moved the error: `finally`, the
loader's journal and claim release, ~24 `(throw e)` sites in `std/`. A build error from an
`(error …)` in a required module was reported at the outermost requirer's header, in another file.

**Decision.** The runtime keeps, per process, the origin (position, file, trace) of the last four
caught user errors whose payload is a LOCAL heap value (one the process minted), keyed by the payload's handle; `throw` of that
handle takes the origin back. The record is a collector root, so while it is kept no other value
can come to have the handle: a match is the same object, never a lookalike. Immediates are not
recorded. The catch path pays a tag test; the recording and the lookup are cold functions.

**Alternatives.** Make `error` raise a map, so `catch` binds a positioned value (breaks every
caller comparing a caught string — a wave for a diagnostic). A `%rethrow payload description`
primitive with `%try-described` inlined by the VM (exact, but only where a site is converted, and
`finally` would need a described catch of its own).

**Consequences.** A heap payload caught, dropped, and later thrown again AS THE SAME OBJECT from
somewhere else reports its first raise — it is the same error value, and the trace says so. An
immediate rethrown is still located at the rethrow.

**Amendment 2026-10-24.** The first cut recorded any heap payload, shared regions included. A
string literal or a `def`'d sentinel is one object to every raise of it, so a raise caught and
dropped lent its line and trace to a later, independent raise of the same constant — two errors
reported as one. Only LOCAL payloads are recorded now: `error` builds its message with `str`,
always a fresh LOCAL string, so every case above keeps its origin, and a constant thrown and
rethrown is located at the rethrow, as before this ADR. It also stops a parked process's record
from pinning an old RUNTIME code generation. Guard: `tests/rethrow_position_test.blsp` "a shared
payload thrown by two raises is two errors, not one rethrown".

## ADR-428 — A setting is declared once: `std/settings`

**Status:** implemented (2026-10-23). For bedit's init file (its `docs/configurability.md`,
stage 1) and nest's user config.

**Context.** A program with a user config file that is data (ADR-065) kept every setting in
four hand-maintained places: the default file's text, the value check, the list of accepted
values and the code that applies it with its fallback. bedit's `init.blsp` had thirteen keys
spread that way; adding `:hl-line` alone touched four places. nest's own
`~/.config/brood/config.blsp` had three keys and no check, so `(config :git-int true)` was
silently ignored. The language already had what a declaration needs: `type-matches?` gives a
`sig` type-expression a runtime meaning, literal and interval types spell an accepted-value
list (`(or :block :bar)`, `(int 0 _)`), and `std/registry` holds rows that modules add as
they load.

**Decision.** `std/settings`, over `registry`:

1. `(settings/define id name spec)` declares a setting under a registry id: `:default`,
   `:type` (a type-expression), `:valid?` (a predicate SYMBOL called late, for a rule no type
   spells, such as a float range), `:want` (how a warning describes a good value), `:doc`,
   `:commented?` / `:example` (how the default file shows it) and `:rank`. A redefinition
   keeps its place, so reloading a module does not reorder the file.
2. `read-form` / `read-file` read the `(head :key value …)` form as data; a broken file is
   `{}` and nothing throws.
3. `warnings` reports each rejected value by name, with what was wanted, then each key no
   setting declares.
4. `value-of` / `values-of` give the file's value when it is valid, else the default.
   An invalid value is never applied, and a deleted key means the default on a reload.
5. `default-source` generates the documented default file from the declarations.

nest's user config is the first caller (its three keys, its default file and a warning on
stderr). bedit's `config.blsp` is the second.

**Consequences.** A new setting is one `define`. A plugin declares its own settings under the
program's id when it loads, and the program's config code names none of them. A key the
file sets before the plugin that declares it has loaded is reported as unknown. The warning
text says so. Not done here: a live `set-variable` and named hooks; those are bedit's
(configurability.md stages 2–4). `key-parse` / `key-describe` in `editor/keymap` are still
the language work stage 2 needs. Guards: `tests/std_settings_test.blsp` and each function's
executed examples.

## ADR-429 — A space in a fuzzy query separates terms that must each match, in any order

**Status:** implemented (2026-10-24). Amends ADR-357 and ADR-375: the rules both state now
include terms.

**Context.** `std/fuzzy` matched a query as one subsequence, so a space was a character to
find. Typing `lim ex` in bedit's find-file asked for a file with `lim`, then a space, then
`ex`, in that order, and found nothing in a project of paths without spaces. A person typing
a space is naming two things they remember about the candidate (part of its directory, part
of its name), and they rarely remember them in path order. Emacs completion settled on this
reading with orderless; fzf calls it an extended search.

**Decision.** A query is split on spaces into terms; empty pieces are dropped.

1. A candidate matches when every term matches it, each by the existing rules (greedy walk
   or contiguous run, whichever scores higher), independently and in any order.
2. Its score is the terms' scores added; `match`'s `:positions` are all of theirs, sorted,
   each index once, so a UI can highlight every term.
3. One term is exactly the old walk, so a query without a space ranks as before. A query of
   nothing but spaces asks for nothing, like `""`: the candidates come back in their order.
4. The native `%fuzzy-top` splits and adds the same way (`score_terms`), and
   `tests/fuzzy_native_test.blsp` holds the two equal on multi-term queries too.

**Consequences.** A literal space can no longer be searched for; a candidate with a space in
it is still found by its words. A custom `*fuzzy-scorer*` receives the whole query as before
and decides for itself (`fuzzy/scorer`, which it may wrap, splits).

## ADR-430 — Sorted map and set: a treap whose priorities are the keys' hashes

**Status:** implemented (2026-10-24). ROADMAP "What the other Lisps have", item 4.

**Context.** `compare` is a total order over every value (ADR-285), but nothing in the library
kept a collection in that order. `pq` is a sorted list (O(n) insert) and `multimap` a hash
map. A range query ("every entry between these two keys"), a nearest-key lookup and an
in-order walk all meant sorting a hash map's entries again on every call.

**Decision.** `std/sorted`: `sorted-map` and `sorted-set` records over one persistent
balanced tree, a **treap whose priorities are the keys' structural hashes**.

1. A treap's shape is fixed by its keys and their priorities. A random priority would make the
   shape random, and an AVL or red-black tree's shape records the order the keys arrived in.
   With priority = `(%hash key)`, ties broken by `compare`, there is exactly one tree for a
   given set of keys. A record is compared field by field, so **two sorted collections with
   the same contents are `=`** with no equality hook. Every other tree would have needed one,
   and Brood has no `Eq` ability.
2. `%hash` is a new kernel primitive: `Heap::hash_value`, the hash CHAMP maps already key by.
   It is deterministic because a symbol or keyword hashes by its spelling (KI-166). It is
   `%`-prefixed because `std/sorted` is its only caller. A public `hash` can follow when a
   second use asks for one.
3. Both collections join the protocol: `Seqable` (key order), `Counted`, `Conjable` (a map
   takes a `[k v]` pair or a map, a set an element), `Lookup` (bare `get`; `keys` in order),
   `Display` and `Inspect`. The module adds what a hash map cannot do: `min`/`max`,
   `floor`/`ceiling` and a half-open `range` that visits only the part of the tree in range.
4. The record fields are `%tree`/`%size`: a record answers `get` from its fields before
   `Lookup`, so a field name is a key the collection cannot hold. `sorted/get` takes a
   default and `sorted/contains?` tells a stored nil from absence.

**Consequences.** Insert, delete and lookup are O(log n) in expectation, for keys whose
hashes are well spread. The shape is canonical across processes and nodes, because the hash
is by spelling and not by interning. It is not canonical across builds that change the hash
function: a sorted collection persisted by one build and extended by another stays correct
but may not be `=` to one built from scratch. Bare `get` with a default asks `Lookup` for a
key that is not a field before answering the default (KI-298, fixed 2026-10-25); `sorted/get`
remains the direct read. The module reads its own fields with
`%map-get`: an empty tree is a nil field, which `get` would take for a miss and hand to
`Lookup`, whose impl reads the tree again. Guards: `tests/sorted_test.blsp`, including insertion-order independence
of `=` and a cross-process build-and-merge.

## ADR-431 — `seq/iterate` is a source only `transduce` consumes

**Status:** implemented (2026-10-24). ROADMAP "What the other Lisps have", item 3.

**Context.** `x, (f x), (f (f x)), …` is the natural input for "the first power of two over a
million" or "step a simulation until it settles". Brood had only `seq/iterate-times` (a fixed
count, built as a list). Unbounded laziness stays rejected (ADR-111, deferred.md #2), because a
lazy list brings a GC story, force semantics and head-holding. `transduce` already has the
stopping half: `xtake`, `xtake-while` and any stage's own `reduced` end a run (ADR-376/421).

**Decision.** `(seq/iterate x f)` returns a `%iterate` record that only `seq/transduce`
consumes. `transduce` runs it in a tail loop applying the stack's reducer until a stage ends
the run. It steps `f` only after the reducer has taken the element, so the element that ends
the run is never stepped past. A failure accumulator stops it, as it stops `fold` (ADR-315).
A `seq/l*` view whose source is an iterate hands its stages to the run, ahead of the
caller's. Everything that would realise it (`seq`, so `fold`, `into`, `count`, `map`) raises
an error naming the way to consume it, rather than looping forever.

**Consequences.** There is no lazy value to hold or force: an iterate is a seed and a function,
and sending one to another process sends those. A pipeline that forgets its stopping stage
runs until memory or the caller's patience runs out, as the same `fold` over a huge range
would. A process-backed generator for values that cross a `send` remains `std/stream`. Guard:
`tests/seq_iterate_test.blsp`.

## ADR-432 — `next-impl`: an impl calls the one it shadows

**Status:** implemented (2026-10-24). ROADMAP "What the other Lisps have", item 7.

**Context.** ADR-172's precedence ladder (app > type-owner > ability-owner > other, then
`:default`) decides which impl dispatch runs. But the losing registrations were dropped, so an
app overriding a library's impl to add one thing had to copy the library's body. The other Lisps
answer this with `call-next-method` or `super`.

**Decision.**

1. Registration keeps every tier: `*impl-tiers*` maps `[ability op id]` to `{tier [fn ns]}`.
   It is written beside `*impls*` on every registration (the winner and the shadowed alike),
   cleared by `%unregister-impl`, and never read on dispatch. Dispatch is unchanged.
2. `(next-impl)` inside an `impl` method body calls the highest tier below the method's own,
   with the same arguments. `(next-impl args…)` passes others. With nothing below for the id,
   the ability's `:default` answers; with no `:default` either, it raises. The method's own
   tier is computed from its namespace, so the chain is right for a method that was itself
   reached through `next-impl`.
3. `impl` binds `next-impl` only in a method body that mentions it: a local fn calling
   `%next-impl`, built with `list` so the binder is the literal name the body uses. Every
   other method is registered exactly as written, so the elision KI-182 protects is
   untouched. A method with pattern parameters has no argument list to rebuild, so its bare
   `(next-impl)` raises and asks for explicit arguments.
4. Both images (the stdlib's and a project's) carry every tier, not just the winner:
   `stdimage/%std-impls-by-module` reads `*impl-tiers*`, and a restored module replays its own
   tiers. Otherwise a warm start would lose the shadowed impls a cold start keeps. Replay order
   does not matter, because precedence picks the winner. The project image's forget paths drop
   a module's own tier entry.

No `:before`/`:after` method combination (ADR-011).

**Consequences.** An override is a few lines around `(next-impl)`. Two impls from different
modules at the same tier still replace each other (warned, last wins), and the loser is not
kept: `next-impl` walks tiers, not registrations. Guard: `tests/next_impl_test.blsp`.

## ADR-440 — The GPU target reuses what a frame repeats, presents mailbox, and opens on a real frame

**Status:** accepted 2026-10-24 (`gpu.rs` `RunCache` / `changed_span` / `segments`,
`pick_present_mode`; `backend.rs` `SHOW_TIMEOUT`, `record_latency`; `gui/latency`; the
`:hollow` cursor and its colour).

**Context.** The installed build paints on the GPU (`--with-gui-gpu`), and that path had none
of what makes the CPU painter feel quick. Every frame re-walked every text op's graphemes and
looked every cluster up in the atlas, and re-uploaded every instance; the CPU painter re-rasterises
only the rows a frame changed (ADR-332/343). Its present mode fell through IMMEDIATE first, so a
`gui/open` without `:vsync` could tear, with two frames in flight. The window was mapped before
its app drew, so opening flashed an empty background. Text skipped the ADR-337 contrast setting,
and all geometry blended in the encoded space, where the CPU's `blend` is linear. Nothing measured
input to screen.

**Decision.**

- *Reuse, not a row diff.* A swapchain image is not retained, so the GPU cannot repaint "only
  row 7"; but drawing is the cheap half there. What it retains is the expensive half: a text
  run's quads, relative to where the run starts, keyed by its text, face, column (a tab stop),
  cell metrics, resolved family and the window background (`RunCache`). Position is not in the
  key, so a scroll of whole lines or a sub-cell glide replays every run it keeps; a run unused
  for one frame is dropped. The instance buffers keep a shadow of what they hold and write only
  the span that differs (`changed_span`): a blink writes the cursor's quads, a typed character
  the tail after it. No scroll blit: reuse already makes a scroll cost one shaped line.
  `BROOD_GUI_DAMAGE=0` turns both off, as it does the CPU diff.
- *Blending as the CPU does it.* Text stays in the encoded space (ADR-358) and gets the contrast
  lift in the shader: `cov^(1/γ)` for a glyph lighter than its ground. The ground is the run's
  own `:bg`, or the window background for a transparent face. The CPU decides per pixel; the GPU
  decides per glyph, because the blend unit cannot read the destination. Translucent solids
  (the cursor wash, `:frect` opacity) are drawn through an sRGB view of the same swapchain image,
  so they blend in linear light like `blend`. A frame takes extra render passes only where such
  geometry and text interleave (`segments`). Opaque fills go in whichever pass is open, their
  anti-aliased rims included: those blended in linear light at first, which put every pane
  divider and mode-line chip between two runs of text in a pass of its own (10–20 full-target
  passes a bedit frame), for a one-pixel rim that reads the same either way (2026-10-25). The CPU painter still blends
  those rims in linear light, so a rounded corner can differ between the two painters by part of
  one pixel's shade: accepted, since only the corner pixel differs and holding the passes apart
  was what cost. A software adapter (llvmpipe, lavapipe: a machine without a GPU) counts as none
  and the window takes the CPU painter, unless `BROOD_GUI_GPU=1` asks for it. A surface without `SURFACE_VIEW_FORMATS` keeps the old
  single encoded pass, and so does an effects frame.
- *Grayscale AA stays on the GPU.* Subpixel text needs a per-channel blend, which means
  dual-source blending (a feature not every adapter has). It also needs the subpixel order,
  which the compositor may scale or rotate away from under the window. The CPU path keeps LCD
  text at 1x; the GPU's grey AA is what kitty and foot ship on Wayland.
- *Present.* With no `:vsync`, the window gets MAILBOX where offered, else FIFO: the newest frame
  at the next refresh, never torn. `{:vsync true}` is FIFO. `{:vsync false}` asks for IMMEDIATE
  (then MAILBOX, then FIFO). `desired_maximum_frame_latency` is 1, so a keystroke's frame is the
  next one shown.
- *No flash.* A window is built hidden and painted only once its app has drawn. It is shown
  after that first paint, or after 500 ms (`SHOW_TIMEOUT`) with whatever it has, so a window is
  never left invisible. Wayland ignores the hidden flag, but maps a surface only at its first
  commit, and the paint gating makes that commit the real frame.
- *Latency.* The GUI thread stamps each key press, mouse button and wheel step. The first
  `UserEvent::Draw` after it carries the stamp, and that frame's paint records input → present,
  split into to-paint and paint (and the GPU's encode / upload / acquire / submit / present).
  This is an approximation: which turn of the app's loop an input caused is hidden behind its
  mailbox, so "the next frame drawn" is taken as its answer. A present returning means the
  compositor has the frame, not that the panel shows it. `BROOD_GUI_TRACE=1` prints each
  sample; `(gui/latency id)` returns the last 64 as maps of milliseconds.
- *The cursor* (bedit's unfocused window): `[:cursor row col style colour]`. The new style
  `:hollow` is an outline box, its rim thinner than a block's (`cursor_rim`). `colour`, a face
  colour, sets the block's wash and every solid stroke. `style` may be nil, so a coloured block
  can be asked for. Both painters, same geometry; the terminal maps `:hollow` to a block and
  ignores the colour.

**Alternatives rejected.** *A retained offscreen target with a scroll blit* (the CPU design on
the GPU): one more full-frame copy each present, to save draws that are already cheap. *Keeping
IMMEDIATE as the default*: tearing is a visible defect in text, and a sim that wants the
work-bound rate can ask for it in one key. *Stamping inputs inside the Brood loop*: the
mailbox is the thing being measured.

**Consequences.** A cursor blink or one typed character no longer shapes the page: the trace's
`runs=hits/total` and `up=bytes` show it per frame. Not measured on this machine: no GUI was run
and no tests were run here (ADR-440's tests are in `gpu.rs` `reuse_tests`, the cursor and
present-mode tests beside them, for CI). Not done: the GPU target still re-encodes `[:cells]`,
`[:vspans]`, rects and sprites every frame. They are a few quads each, or a sim that changes
every frame anyway. On X11 a window shown after its first paint may take one Expose repaint,
which is harmless because the frame is retained.

**Amendment 2026-10-25: subpixel text on the GPU.** The grey-AA decision above is replaced on
every adapter. On one with `DUAL_SOURCE_BLENDING` the device asks for it, and a second
textured pipeline draws text
whose glyphs were baked per channel (`LCD_SRC`, `fs_tex_lcd`): the second fragment output
is each channel's coverage, blended `colour·cov + dst·(1 − cov)` per channel (`Src1`). That
is `blend_text_rgb`, the CPU's per-channel lerp in the encoded space, and the contrast lift
is taken per channel too. The subpixel ORDER objection is answered the CPU path's way:
`gui/text-aa` decides, `:auto` meaning subpixel at a 1× scale only, so a scaled surface
stays grey. Glyph modes 3 and 4 are the per-channel 1 and 2. `Batch::Tex` carries
`lcd`, so a run never mixes pipelines. The atlas key and the run cache carry the subpixel order.
The LCD pipeline is built inside a validation error scope, so a driver that offers the
feature and rejects the shader costs subpixel text, not the window. Measured on an RTX 5060
under Wayland with `BROOD_GUI_DUMP`: the GPU frame is byte-identical to the CPU painter's
for subpixel and for grey text, light-on-dark (lifted, mode 4) and dark-on-light (mode 3).
Guards: `gpu.rs` tests validate both shaders under naga (the LCD one only with the
capability), the mode mapping, and LCD glyphs batching apart from grey ones.

*Later the same day: and on an adapter without the feature.* The per-channel blend needs no
second output if it is done one channel at a time: the LCD glyphs are drawn three times, each
pass writing only red, green or blue (`ColorWrites`) with that channel's coverage as its
alpha (`fs_tex_lcd_red` / `_green` / `_blue`), so ordinary alpha blending gives the same
`colour·cov + dst·(1 − cov)` per channel, over any destination. It costs two more draws per
batch of LCD glyphs (`LcdText::PerChannel`); dual-source stays preferred where offered.
`BROOD_GUI_NO_DUAL_SOURCE=1` forces the three-pass path, and `BROOD_GUI_TRACE` prints
`lcd=dual-source|per-channel|none`. On the same RTX 5060 the three-pass frame is
byte-identical to the CPU painter's too. So grey AA on the GPU is now only what
`gui/text-aa` asks for, as on the CPU.

## ADR-441 — A GUI window's keyboard is the user's: OS repeat, Super, F-keys, layouts, IME, focus, the wheel

**Status:** accepted 2026-10-24.

**Context.** A Brood window typed like a game console, not like kitty, foot or GUI Emacs. Its key
path (`host/gui/backend/input.rs`) read Ctrl, Alt and Shift and never Super; dropped F1–F24,
Insert and every other named key beyond the arrows and editing keys; kept only the first
character a keystroke typed; re-applied Shift to a chord through a hard-coded US table, so on a
German layout Alt+Shift+`.` was `M->` where the keycap says `:`; had no input method at all, so
dead keys, compose and every CJK IME were dead; delivered focus loss (`:blur`) but never gain;
and dropped the OS auto-repeat (ADR-086), so an app had to re-implement repeat on a timer, at a
delay and rate that were not the user's. A wheel notch, meanwhile, glided for half a second
where a terminal and Emacs move three lines at once.

**Decision.**

- **OS repeat, opt-in: `{:key-repeat :os}`** (`:app`, the default, keeps ADR-086). Each OS
  auto-repeat is delivered as another PRESS of the held key — the bare key value, so dispatch
  is unchanged and an editor's repeat is Emacs's (a repeated `C-n` is `C-n`). ADR-086's worry was
  a producer-paced stream outrunning a slow frame and playing on after key-up. That is answered
  by a gate, not by dropping repeats: a repeat goes out with a mailbox delivery CREDIT
  (`process::deliver_credited`, the net reactor's backpressure mechanism) charged to the window's
  `RepeatGate`, which returns when the message leaves the mailbox; while one is outstanding,
  further repeats are dropped. At most one repeat is ever queued, so a slow frame repeats once
  per turn and nothing plays on after release (the one queued was a real repeat that happened
  before it). The repeat detection stays ADR-086's transition test (a press for the key already
  held), which Wayland's unreliable `ke.repeat` cannot fool. The default stays `:app`: the OS
  mode is the better feel, but bedit and other apps currently drive their own repeat from
  `gui-held-key`, and flipping the default under them would double every repeat. bedit should
  opt in and drop its timer.
- **Super and the rest of the keyboard.** Key names spell modifiers in Emacs order,
  `[ctrl-meta-|ctrl-|alt-][shift-][super-]<name>` (`host::gui::named_key`, now taking a
  `KeyModifiers`): `:super-s`, `:ctrl-super-x`, `:shift-super-left`. A character chord with Super
  folds Shift into the glyph, as Meta does (`:super-S`, `:alt-super->`); without Super the
  character chords are unchanged (`:ctrl-x`, `:alt-O`, `:ctrl-meta-f`). Named keys: F1–F24
  (`:f1`…`:f24`, `host::gui::function_key`), `:insert`, `:menu`, `:pause`, `:scroll-lock`,
  `:help` `:find` `:undo` `:redo` `:copy` `:cut` `:paste` `:select` `:execute` `:cancel`
  `:clear`, `:back` `:forward`, `:volume-up/-down/-mute`, `:media-play-pause` `:media-stop`
  `:media-next` `:media-previous`, each carrying modifiers (`:ctrl-f5`). PrintScreen, the lock
  keys and bare modifiers stay unreported. The terminal frontend names F-keys, `:insert`,
  `:menu`, `:pause`, `:scroll-lock` the same way and reads Super when the terminal reports it
  (the kitty protocol); `std/vt` already spelled `:insert` and `:f1`–`:f12` this way, and a
  Super chord has no terminal spelling there (nil), which is right.
- **The layout's glyph for a shifted chord.** winit's `logical_key` has Shift and the layout's
  levels applied but not Control, so it is the glyph the keycap shows. A chord with Shift takes
  it (`shifted_chord_char`) when it is printable ASCII; the US table (`shift_char`) stays only
  for the case `key_without_modifiers` was introduced for — macOS, where Option also changes the
  logical key (Option+Shift+`.` is `˘`) — and letters keep their base, the chord deciding case.
- **Typed text and the input method.** Plain typing reads `ke.text` (dead keys and compose
  applied), not the bare logical key. A keystroke that typed MORE than one character is
  `[:text "…"]`. The IME is allowed unless `{:ime false}`: its composition is
  `[:preedit "…" [from to]]` (`range` in characters, winit's bytes converted; nil when hidden;
  `""` clears), its commit `[:text "…"]`. A single-character commit with no composition shown
  is delivered as the plain 1-char key: some IMEs commit every key they pass through, and a
  keymap (vim's normal mode) must not be able to tell. Each frame's first `[:cursor …]`,
  resolved through scroll and cell regions like the hover zones, is handed to
  `set_ime_cursor_area` when it moves, so the candidate window opens at the caret.
- **Focus gain: `:focus-in`**, the pair of `:blur` (kept). Not `:focus`, which `ui-run` takes
  as another process's raise-this-window request.
- **The wheel: `{:wheel :lines}`, the default** — a notch scrolls three lines in ONE
  `[:mouse :scroll-up/down …]` message, now, with the same fractional slot it always carried.
  Notches arriving before the app has drawn the last one are summed into the next message
  (`flush_wheel`, the glide's `scroll_pending` handshake; a window that never draws is not held
  past 100 ms). `{:wheel :glide}` is the half-second kinetic glide this replaces as default;
  a trackpad's pixel deltas and momentum are the same under both. The default changed because
  an editor's wheel is for reading, where the line you were looking at should be where you put
  it, and every terminal and Emacs do this.

**Alternatives.** A marked `[:key-repeat k]` message (lets an app refuse to repeat a prefix key,
but every keymap would need to unwrap it — Emacs does not distinguish, so neither do we). A
"drop the repeat when the mailbox is non-empty" guard (starved by any background stream). An
ack through the next `gui-draw` (stalls repeat in an app that does not redraw on a no-op key).
Delivering every IME commit as `[:text]` (correct, but a pass-through IME would silently turn
vim's `j` into text).

**Consequences.** Apps keep their behaviour unless they ask, except the wheel, which now scrolls
at once. An app sees new messages: `:focus-in`, `[:text …]`, `[:preedit …]`, and new keywords;
`ui-run` passes them to `update` like any input. A held composed key repeats as its base
character under `:os`, as GTK does. Guards (Rust unit tests in `backend/input.rs` `adr_431_tests`,
`host/gui.rs` `named_key_tests`, the terminal's `key_to_value_tests`) were written but not run
on the development machine; the winit event paths (repeat, IME, focus, wheel) have no headless
test and were not exercised here.

Amended 2026-10-25, from review. A keystroke that types several characters finds its repeats
as a key does, by the held physical key with no release between (it trusted winit's `ke.repeat`,
which GNOME/Wayland sets unreliably), so one press path serves both, and its release sends no
key-up. The input method's state is one `Composition` (idle, showing, just ended) instead of two
flags. A chord is spelled by one `character_chord` for the window and the terminal, and `Key` is
`Char` or `Named`. IME commits are not gated: telling a repeat from fast typing of the same
character is impossible without a release, and dropping typing is worse than an unbounded flood
that no tested pairing produces.

Amended 2026-10-25, held keys as a native app has them. Two gaps were left between this and a
GTK or Cocoa window:

- **The repeat queued at the release played after it.** "The one queued was a real repeat"
  holds, but behind a slow frame it lands a turn after the key came up, so the screen moved
  once more after the hand stopped. A mailbox credit's source can now WITHDRAW its message
  (`CreditSource::withdrawn`): the receive that reaches a withdrawn message drops it unseen,
  which returns the credit. The scan checks it beside the tag filter, under the lock it already
  holds, and only a credited message pays more than a null test. `RepeatGate::withdraw` runs on
  the release of the held key and on focus loss (`let_go`, which both share), and charging the
  next repeat clears it, so it only ever names the repeat in flight.
- **Idle work ran in the delay before the first repeat.** Between a press and its first repeat
  (250 ms on GNOME, 660 ms under X's default, up to about two seconds on macOS) no input
  arrives, so `ui-run`'s `:idle?` timers fired as after any lone keystroke: bedit's idle beat
  (120 ms), its typing undo boundary (600 ms), and its caret blink (530 ms), which blinked the
  caret off before the repeat began. A display now answers `:key-held?` (a GUI window from
  `gui-held-key`; `display-broadcast` when any member does; the terminal cannot tell), the
  loop reads it before each park, and an idle timer waits while a key is down, no longer than
  `*ui-held-quiet-ms*` (2 s) past the last input: a hold that never repeats, or a release the
  window never saw, holds idle work back without losing it. Every change to the held state
  arrives as input (the press, its `[:key-up]`, `:blur`), so the park is never stale.
  A held compose sequence is held like a key (below).

Alternative: withdrawing by scanning the queue from the GUI thread at the release. It would
take the receiver's mailbox lock from the event loop and remove from under a scan's cursor;
the receive already walks the queue under that lock. Guards: `mailbox.rs`
`a_withdrawn_message_is_dropped_unseen_and_returns_its_credit`, `input.rs`
`repeat_gate_tests`, and `tests/ui_test.blsp` "idle timers while a key is held". None was run on
the development machine, and the winit paths still have no headless test.

Amended 2026-10-25, a keystroke that typed several characters is held as itself. What is held
is a `Keystroke`, a `Key` or the `Text` a compose sequence (or a layout key that types two)
typed, so `gui-held-key` reports `[:text "…"]` while one is down, which holds `ui-run`'s idle
timers as any key does, and its release is `[:key-up [:text "…"]]`: a release names what its
press delivered. That is now true of every key, not only the held one. The window keeps each
key that is down by physical key with its press (`down`, cleared on focus loss), so with `(`
(Shift+9) still down after another key was pressed, letting Shift go first and then 9 still
sends `[:key-up "("]`, where it sent `[:key-up "9"]`. A release with no press seen here relays
its own key, as before. The first amendment's "its release sends no key-up" no longer holds.
The OS repeat of a compose sequence's last key is still its base character, a fresh press (GTK
does the same). Guard: `input.rs` `keystroke_tests` (the message shapes); the event paths have
no headless test.

Amended 2026-10-25, the keyboard as a unit, measured, and over the wire:

- **One `Keyboard` per window** (`backend/keyboard.rs`) owns what the event loop kept in five
  fields of `Win`: the held keystroke, its physical key, every key down, the repeat mode and the
  `RepeatGate`. `press`, `release` and `blur` take an event and answer the message to send, so
  the rules (a repeat by transition, the gate, the withdraw, a release naming its press, Shift up
  first, overlapping keys, a compose sequence, focus loss) are tested without winit or a
  window, where before only a person holding keys could check them.
- **`gui-key-repeats`** reports how a window's repeats went: delivered, dropped because one was
  still waiting, and the desktop's delay and interval from the last key that repeated. A drop
  is the app falling behind the repeat rate (a held key moving slower than the desktop asked),
  which nothing showed before; beside `gui-latency` it says whether the app answers a repeat
  before the next one comes.
- **A thin client ships whether a key is down** with each input, `[:key input held?]`
  (`attach-display` from its window, `attach` from the terminal), read after the input arrived,
  so every change rides on the input that caused it. `remote-display` keeps it in a table the
  session process owns and answers `:key-held?` from it, so a served app's `ui-run` holds its
  idle timers through a held key as a local window's does: bedit `--attach`, and the host's own
  window under `--serve`, which attaches the same way. `display-key-held?` is public for it. A
  client that sends `[:key input]` holds nothing; a shared session (`serve-shared`) accepts both
  and keeps its idle timers, since one model has no client to ask.

Guards: `keyboard.rs` `tests` (seven sequences), `tests/serve_test.blsp` "a key down in the
client's window holds the session's idle timers". Not run on the development machine.

Amended 2026-10-25, the terminal holds keys as the window does. A legacy terminal sends a held
key as presses queued in the tty, so behind a slow frame they back up and play on after the key
came up, and it reports no release, so `:key-held?` could not be answered. A terminal that
speaks the kitty keyboard protocol (kitty, foot, WezTerm, Ghostty, Alacritty 0.13+) reports
both. `term-enter` asks it whether it does (crossterm's `supports_keyboard_enhancement`: the
flags query, answered or not before the device-attributes reply) and, when it does, pushes
disambiguated escape codes, event types and alternate keys onto the alternate screen's flag
stack; `term-leave` and `restore_terminal`, which every exit path reaches, pop them before
leaving that screen. The inline REPL seam (`term-raw-enter`) pushes nothing.

- **No backlog.** `term-poll` reads ahead everything the tty has buffered, and a repeat whose
  key's next event there is another repeat or its release is dropped
  (`terminal/native/keyboard.rs` `repeat_superseded`): the terminal's version of the gate and
  withdraw, decided from input already in hand. A press is never dropped, nor typed text.
- **A release is `[:key-up press]`**, the press found by the key, not its modifiers (a
  character in lower case, Shift+Tab as Tab), so Ctrl or Shift let go first still names the
  chord. A symbol released after its Shift arrives as its base key (`,` for `<`), which only
  the layout ties to the glyph; it names the latest symbol down, and a wrong guess only ends a
  hold early. A release with no press seen relays its own key, a bare modifier nothing.
- **The held key.** `term-held-key` answers as `gui-held-key` does, and `*term-display*` has
  `:key-held?` over it. A key is held from its press only once the terminal has reported a
  release or a repeat of that key. The protocol keeps a key that types text as text unless
  every key is sent as an escape code, which this does not ask for (it would replace text with
  key codes and lose what an input method or a compose sequence types), so a text key's repeat
  may arrive as a plain press, kept as it always was, and its release may never arrive; a key
  that is never seen to come up must not hold idle work back.

Alternate keys keep a shifted chord's glyph as a legacy terminal sends it (`:alt-<`, not
`:alt-,`), and a capital in a chord counts as shifted (`:alt-X`), since crossterm drops Shift
from an alternate key. Disambiguation moves a few chords to the window's spelling, which was
the point of one rule for both: `C-i` is `:ctrl-i` rather than `:tab`, `C-/` is `:ctrl-/`
rather than the legacy byte's `:ctrl-7`. A terminal without the protocol reads exactly as
before. Guards: `terminal/native/keyboard.rs` `tests` (the coalescing rule, the held key, a
release naming its press) and `native.rs` `key_to_value_tests`
(`an_alternate_key_chord_spells_as_the_legacy_one`, `a_key_up_is_its_press_spelled`). None was
run on the development machine, and no terminal drove the protocol under test.

Amended 2026-10-25, every terminal. The protocol left out most of where a terminal editor runs:
tmux and every legacy terminal report no repeat or release, and under the protocol text, Enter,
Tab and Backspace still arrive as legacy bytes (asking for every key as an escape code would
lose what an input method or a compose sequence types, since crossterm drops the associated
text). Held Backspace, the key most often held, played on after the release everywhere. Those
keys now have the hold inferred (`keyboard.rs` `Inbox`):

- **A held key is the same press arriving faster than a hand presses one key**: some stretch of
  a run's repeats averaging at most `REPEAT_GAP` (70 ms, about 14 a second; desktops repeat at
  25 to 33). The first gap, the desktop's delay, never counts. Each arrival is bounded by the
  tty reads around it, the read before (it came after) and the read that brought it, so a
  backlog read all at once behind a slow frame is judged by when it could have come, not when
  the app got to it, and three taps buffered behind a busy second stay three taps.
- **Only the latest repeat of a held run is live**, the gate's rule, and the run ends when its
  repeats stop for `RELEASE_AFTER` (140 ms, read from a drained tty: a read cut short proves
  nothing) or another key is pressed. Its end is `[:key-up press]` and drops the repeat still
  waiting, the withdraw. A stall in the link longer than that ends the hold early, and the next
  repeat starts another. The poll waits no longer than the release is due, so the key-up wakes
  the app on time.
- **Typed text is held and comes up but is never dropped.** A terminal sends a paste as keys (no
  bracketed paste is asked for), so a run of one character can be pasted `====` as easily as a
  held key.
- **A tapped key has no key-up**: nothing says when it came up. A key the terminal reports is
  the tracker's from its first reported event, and the run of its legacy press ends without a
  key-up. The inline REPL infers nothing.

Guards: `keyboard.rs` `tests` (`a_key_repeating_at_the_desktop_rate_is_held_and_comes_up_when_it_stops`,
`a_backlog_behind_a_slow_frame_collapses_and_its_last_repeat_goes_at_the_release`,
`taps_buffered_behind_a_slow_frame_are_all_delivered`, `typed_text_is_held_but_never_dropped`,
`another_key_ends_the_hold_before_its_press`, `a_read_that_left_input_behind_does_not_release`,
`a_reported_repeat_hands_the_key_to_the_tracker`), written over an inbox fed timed reads and not
run on the development machine.

From the same review, the window: a key still down that comes to type another keystroke (Shift
let go while `(` repeats, so it repeats as `9`) used to replace its press silently, and `(` never
came up. It is now `[:key-up "("]` then the press of `9` (`KeyMessage::Restroke`), so every
press has its key-up. And a new key's first repeat clears the interval `gui-key-repeats`
reported, which was the previous key's until the new one repeated twice. Guard:
`backend/keyboard.rs` `a_key_that_comes_to_type_another_keystroke_ends_the_first`, not run.

## ADR-442 — Installed fonts by name, fallback by coverage, ligatures as an opt-in unit

**Status:** accepted 2026-10-24.

**Context.** The GUI drew only what it bundled: DejaVu Sans Mono in four styles and Noto Color
Emoji (ADR-046's self-contained rendering). A font the user has installed could only be reached
by giving `gui-font-register` four file paths — bedit's themes hard-code
`/usr/share/fonts/truetype/hack/…` — and a glyph neither bundled font has (every CJK ideograph,
many symbols) drew as tofu, because cosmic-text's fallback only walks the faces in its database.
Text was shaped one grapheme cluster at a time, so a programming font's ligatures (`->`, `!=`,
`===`) never formed. The line height was already a primitive (`gui-line-height!`, ADR-332) and
bedit's `:line-height` already reaches it, so that needed nothing.

**Decision.**

1. **One shape for a family: a keyword bound by `gui-font-register`.** The styles map takes
   `{:family-name "JetBrains Mono"}` as well as paths. The name is looked up case-insensitively
   in a SYSTEM font database (fontdb's `load_system_fonts`, i.e. fontconfig's directories on
   Linux), each style picked by fontdb's CSS weight/slant matching, and those files loaded into
   the SHAPING database. Faces and `gui-font!` keep naming the keyword, so nothing downstream
   changes. A name nothing installed answers to binds the keyword to the bundled DejaVu.
2. **Two databases, and the system one only on demand.** The system database is scanned the
   first time a family is asked for by name, or a glyph needs a fallback that nothing loaded
   covers — never at startup. The shaping database holds only the faces in use, so
   cosmic-text's own fallback walk (which visits every face it has) stays short.
3. **Fallback by coverage, only where there was tofu.** Before a cluster is shaped, its chars
   (less ZWJ and variation selectors) are checked against the face's character map, then the
   bundled DejaVu's and the emoji font's. Any hit leaves the cluster to cosmic-text exactly as
   before, so emoji still come from the bundled Noto. Otherwise the cluster is shaped in an
   installed family that covers it. The candidates are the fallbacks already loaded, then a scan
   of the system's regular faces: monospaced first, then Noto Sans / DejaVu, then the rest. The
   found family is loaded (all its faces) and remembered per codepoint. A 128-codepoint block
   whose scan came up empty is not scanned again. The glyph lands on the grid baseline, in the
   cells `cluster_cells` gives it (two for a wide char), like any other.
4. **Ligatures are a unit, not a run.** `gui-ligatures!` (off by default) makes `text_units`
   cut a `:text` op into its grapheme clusters, except that a run of 2–8 ASCII punctuation chars
   (`ligature_byte`) is ONE unit. A unit is shaped together, baked into one canvas `unit_cells`
   wide (one cell per char), and cached like a cluster. Each glyph is moved onto the cell of the
   char it starts at (`grid_shift`), so fractional advances never drift off the grid. Both
   painters, CPU and GPU, walk `text_units` for `:text`.
5. **Inspectable.** `gui-font-info [family]` reports the family name, what was requested, the
   origin (`:bundled` / `:files` / `:system` / `:not-found`), the file each style resolved to,
   and the fallback fonts loaded so far.

**Alternatives.** A `:family-name` key on `gui-font!` and on faces: two ways to name a font, and
a face would carry a string the renderer resolves per op. Loading every system face into the
shaping database (cosmic-text's default `FontSystem::new`): about a second at startup, and a
fallback walk over thousands of faces for every missing glyph. Linking fontconfig for coverage
queries: a C dependency for what fontdb plus a cached scan already answers. Shaping a whole op
as one run: a ligature would form across words, but the glyph cache would key on whole lines and
the per-cell diff and atlas would lose their reuse.

**Consequences.** Rendering is no longer identical on every machine once a family is asked for
by name, or a glyph needs a system fallback. Only the bundled-ASCII path is untouched (it skips
the coverage check). The first name lookup or fallback scan blocks the GUI thread while fontdb
reads every installed font's header (a fraction of a second on a typical desktop; not measured
here). A fallback glyph wider than its cells (a proportional symbol) is clipped at the cell edge
rather than scaled. Ligatures do not form across a face change (two ops), across letters (`www`,
`0x`), or in `:text-px` (HUD text keeps per-cluster shaping). A run is shaped without its
neighbours, so a contextual alternate that looks past the run does not fire. Re-registering a
family now re-measures every window's cell (`fonts_changed`), and the GPU atlas key carries a
registration count, because a keyword can name new faces.

## ADR-443 — A parse tree is a handle the caller keeps, reparsed from its edits

**Status:** accepted 2026-10-24. Amended by ADR-495: a handle is owned by a process, not held in a 32-entry LRU.

**Context.** Tree-sitter highlighting was a pure `text -> spans` service. bedit sliced a window
(the viewport plus a lead-in) out of the buffer on every edit and handed it to
`%tree-sitter-spans`. The kernel copied the slice, found what changed by diffing it byte by byte
against its cached parses, and reparsed the WINDOW: text with no context above it, so a string
or heredoc opened off screen coloured as code. The incremental parser never saw the document,
and nobody could tell it what changed, though an editor knows.

**Decision.** A parse tree is a value the caller holds. `%tree-sitter-tree text lang` parses a
whole document, a rope read through `parse_with_options`'s chunk callback (no flat copy), into
a `Ref` handle naming the tree, a rope clone of its text (a refcount) and its language. Handles
are immutable. `%tree-sitter-tree-reparse tree text lang edits` edits a COPY of the tree and
returns a new handle; the old one answers as before. `edits` are char triples
`[start old-end new-end]`, one or a sequence in order. The kernel composes them into one
covering edit, converts it to bytes and points on the two ropes, and refuses one whose
unchanged tails differ in length rather than build a wrong tree. nil derives the edit by a
chunk-wise `memcmp` of the two ropes' common prefix and suffix, widened to whole chars.
`%tree-sitter-tree-spans tree kinds keywords? from to` walks only the nodes reaching chars
`[from, to)` and clips spans to the range. `%tree-sitter-tree-changes` reports the edited range
merged with tree-sitter's `changed_ranges`, so a cache can drop only the bands an edit
recoloured. Handles live in a runtime-wide registry, bounded at 32 and evicted least recently
used. A gone handle reads nil from every query, and reparsing from one is a full parse. A
grammar reload bumps an epoch, so no tree is ever reparsed by a different grammar.
`editor/treesit` wraps all of it (`open-tree`, `update-tree`, `fontify-tree`, `tree-changes`,
`free-tree`).

**Alternatives.** A new `Value` variant with GC-driven freeing. That is exact lifetime, but it
means a new heap kind across GC, promotion, printing, equality and the message path, for one
consumer. Extending the implicit cache to ropes: no lifetime question, but still a diff per
call, still a guess at which cached document an edit belongs to, and no way to report changed
ranges. A MUTABLE document handle like a table: one slot per buffer, but a model holding an
old rope beside it (undo, a second frame, a stale snapshot) would query a tree for different
text.

**Consequences.** A caller that forgets `free-tree` costs registry slots until eviction.
Consecutive versions share subtrees, so that is cheap, but more than 32 live documents evict
each other and turn into full parses. Points use ropey's line breaks (which include a lone
`\r` and U+2028); tree-sitter is byte-addressed, so only a point query could notice, and none
exists. The slice-based primitives and their cache are unchanged until bedit moves over. Rust
tests (edit composition, the rope diff, reparse-equals-fresh-parse, free) were written and not
run on the development machine.

## ADR-444 — `ui-run` skips the frame when the turn changed nothing

**Status:** accepted 2026-10-24.

**Context.** `ui-loop` called `view`, harvested the memo table and handed a full frame to
`:draw` at the top of every turn, including turns whose `update` returned the model it
was given: a timed-out poll whose timer had nothing to do, an idle timer that found no work,
a key release or a mailbox message the app ignored. The GUI thread already dropped a frame equal to the last one (`UserEvent::Draw`),
but only after `view`, the harvest and the op marshalling had run: a few milliseconds of
work that changed nothing.

**Decision.** The loop keeps `[model cols rows]` of the last frame it drew on its `clock`
(`:shown`). A turn whose model and grid are `=` to it skips `view` and `:draw` and goes
straight to the poll. `=` on maps tests the pointer first and compares CHAMP subtrees by
pointer, so an untouched model costs one comparison and a changed one stops at the first
difference. The memo table is kept as it was.

**Alternatives.** An app-side "dirty" flag (every app has to maintain it, and a forgotten
set paints a stale screen). Comparing frames instead of models (the frame has to be built
first, which is the cost being avoided).

**Consequences.** `view` must be a function of the model and the grid alone. That was always
the `ui-run` contract, and the observer and bedit keep live data in the model. A view that
reads the clock or another process now repaints only when the model changes. A frontend that
loses its picture and needs a repaint without a model change (a terminal cleared from outside)
has to deliver an input that changes the model.

A skipped turn is still a turn to a display that paces on its frames. The GUI thread cleared
its wheel-glide `scroll_pending` and answered the latency stamp on each Draw, so a glide whose
steps stopped changing the model (a buffer already at its end) re-armed a timer already in the
past and spun the GUI thread, and an input that changed nothing was timed to the next unrelated
frame. So a display may carry `:settle`, called on every skipped turn; `gui-display`'s sends
`%gui-settle`, which does what a Draw does for the pacing and drops the stamp (amended
2026-10-25, from review). The latency stamp also skips bare modifier presses and mouse releases,
and a frame the GPU target skipped records no sample.

## ADR-433 — `gen/start` takes options; `start-link` and `start-named` are gone

**Status:** implemented (2026-10-24). Closes the residue ROADMAP's 2026-08-29 naming audit left
open ("verbs vs options").

**Context.** `gen/start`, `gen/start-link` and `gen/start-named` were three one-line wrappers
that did not compose. There was no spelling for a server that is both linked and named, and
`start-named`'s own docstring told the caller to register `start-link`'s result by hand.
`supervisor/start` already takes an options map.

**Decision.** `(gen/start f state opts)`, where `opts` is an optional map with `:link` (spawn it
linked to the caller) and `:name` (register it). The two compose, and an unknown key is an
error rather than ignored, so `{:linked true}` fails loudly. `start-link` and `start-named` are
deleted, with no alias (greenfield). They go in the rename ledger with a CALL SHAPE as the
target (`gen/start f state {:link true}`), so the runtime's `unbound symbol` error says what
to write. `nest check --fix-renames` now leaves any ledger target that is not a bare name to a
human: rewriting `gen/start-link` to bare `gen/start` would have dropped the link silently.

**Consequences.** One entry to learn and document. A downstream caller of the old names gets
the pointer at its first run. Nothing in bedit used them. Guards: `tests/gen_test.blsp`
("`:link` and `:name` together", "an unknown option is an error") and `tests/renames_test.blsp`
(a call-shape target's head must be bound).

## ADR-434 — A pattern clause may take `& rest`, so a macro can take one clause per shape

**Status:** implemented (2026-10-24). ROADMAP "What the other Lisps have", item 6, taken a smaller
way than planned.

**Context.** The plan was multi-pattern clauses on `defmacro` heads plus a `:hint` per clause,
so a call matching no shape would raise the macro's own message. `defmacro` already forwards to
`fn`, and a pattern-dispatched `fn` already lowers to `(fn (& args) (match* :fn args clause…))`,
so each clause head is a LIST PATTERN over the argument list. The one thing missing was a rest:
`fn` rejected any `&`/`&optional` in a pattern clause. Nearly every macro takes `& body`, so in
practice no macro could use pattern clauses.

**Decision.** A pattern-dispatched clause may take `& rest`. In a list pattern `&` already means
the rest (`(x & more)`), which is exactly a variadic clause, so this lifts a rejection and adds
no new mechanism. `&optional` stays an error: a list pattern gives it no meaning. A macro then
writes one clause per accepted shape, and a final `((& args) (error "m: expected …"))` gives
its own message. That covers what `:hint` was for, so no `:hint` syntax was added (ADR-011). The
same applies to every `defn`: `((:all & more) …)`, `((x :else & fallback) …)`.

**Consequences.** The prelude's hand-rolled macro checks (`%for-check-binds` and others) can move
to clauses as they are touched. The error's position is the macro call, not the offending
sub-form: pointing at a sub-form is still open. Guard: `tests/pattern_clause_rest_test.blsp`.

## ADR-435 — A process can trap the runtime's SIGTERM, SIGINT and SIGHUP as a message

**Status:** implemented (2026-10-25). The prerequisite ROADMAP "Supervision B" (`defapp`)
named.

**Context.** A program a supervisor (systemd, a container runtime, `kill`) runs is asked to
stop with SIGTERM, and Brood could not hear it: `os/signal` signals a child, and the REPL's
`%install-interrupt-handler` turns SIGINT into a flag that only a poller reads. A shutdown
wants a message, so the process that owns it can wait in `receive` like any other.

**Decision.** `(%trap-signal sig pid)`, wrapped as `(os/trap sig [pid])`. Its handler writes
the signal number to a self-pipe (`write` is async-signal-safe); one non-worker thread reads
the pipe and delivers `[:signal sig]` to the subscriber (ADR-059's blocking-work rule). Only
`:term`, `:int` and `:hup`: the signals a program is asked to stop or reload by. There is one
subscriber per signal, not a list: whoever owns shutdown owns the signal, and a list would
need an order nobody could state. The first trap saves the disposition the signal had —
the default, the `SIG_IGN` a `nohup` leaves on SIGHUP, the REPL's Ctrl-C handler — and a nil
pid puts it back. When the subscriber has exited, the thread puts it back and re-raises the
signal, so a forgotten trap cannot make the runtime unkillable, nor a lifted one make a
`nohup`'d program die on a hangup.

**Consequences.** The kernel grows one primitive, its atomics and the saved dispositions;
what a signal does is Brood (ADR-436). Trapping `:int` replaces the REPL's handler for as long
as it holds. Windows has no Unix signals, and the primitive raises there. Guards:
`tests/application_test.blsp` (a SIGHUP the runtime sends itself arrives as a message) and
`crates/cli/tests/application_sigterm.rs` (a dead subscriber leaves SIGTERM fatal; lifting a
trap leaves an ignored SIGHUP ignored).

## ADR-436 — `defapp`: an application starts its requirements first and stops in reverse

**Status:** implemented (2026-10-25). ROADMAP "Supervision B".

**Context.** `nest run` calls a function. A long-running program is a supervision tree whose
dependencies must start before it and stop after it, on a signal, and nothing expressed that.

**Decision.** `std/proc/application.blsp` (module `application`, not `app`, which is a likely
name for a user's own module). `(defapp name {:start … :stop … :requires […]})` defines a
record. `:requires` holds application VALUES, not names: no registry, and because values are
immutable, no cycle is possible and none is checked. `start` orders the requirements
depth-first, each once, and stops what started if a later start raises. `stop` goes in reverse:
`:stop` gets the root, and a pid root with no `:stop` gets `gen/stop` and is killed after 5 s.
`run` starts, traps `:term` and `:int` (ADR-435), registers `:application` so `shutdown` can
reach it, and waits for a signal, a `shutdown`, or a root's exit. The resolution is one change
in `project-entry-fn`, the function `nest run`, `--check-boot` and a release bundle share: an
application at `:main` runs as one. `--check-boot` also starts and stops it, since `:start` is
where a missing dependency dies. A release's boot check (`--brood-boot-check`, which
`nest release` runs on the binary it wrote) resolves the application and does not start it:
it runs on the machine that built the release, where a start would bind the app's ports and
open its files, and what a bundle can get wrong that the dev tree did not — its snapshot of
the sources — is covered by loading every module and resolving `:main`. Both checks resolve
through one `project-entry` and print through one `boot-ok-message`, so they differ only in
that step. `:start` takes no arguments: the command line stays the program's to read.

**Consequences.** `system/halt` still exits at once, skipping the stops; graceful exit from
code is `application/shutdown`. Guards: `tests/application_test.blsp` (order, reverse stop,
failed start, supervisor root, run, crash), `crates/cli/tests/application_sigterm.rs` (a
real SIGTERM against `brood file`: the stops print in reverse and the exit is 0),
`crates/nest/tests/boot_check_and_renames.rs` (`--check-boot` starts and stops in order, and
fails on a start that raises) and `crates/cli/tests/release_bundle.rs` (a release's boot
check never starts the application that the same binary starts when run).

## ADR-437 — `defstatem`: a state machine is a dispatch the macro writes and a loop in Brood

**Status:** implemented (2026-10-25). ROADMAP "Supervision D", built ahead of a consumer at
the user's request (it had been gated on one under ADR-011).

**Context.** A protocol handler or an editor mode is a server whose answer to a message depends
on a named state, and wants two things `defserver` cannot say: an event that must wait until
the state changes, and a timeout that belongs to a state and dies with it.

**Decision.** `gen/defstatem`. Each `(:state clause…)` block holds `cast`, `call`, `info` and
`timeout` clauses (patterns may take `:when`), and an `(any clause…)` block applies in every
state. Every body returns an action as data: `[:next state data]` or `[:next state data
{:timeout ms}]`, `[:keep data]`, `[:postpone]`, `[:stop data]`. A `call` clause binds `reply`
and answers with `gen/reply`, as `defserver`'s `defer` does, so replying now, later and
postponing are one mechanism instead of a reply slot in the action. The macro generates only
a handler, one `match` over `[state event]`; the loop is an ordinary function
(`gen/run-statem`), so postponing and timeouts are readable Brood rather than macro output.
It speaks `defserver`'s envelopes, so `gen/start`, `cast`, `call` and `stop` drive a machine
unchanged. A state timeout is a `timer/send-after` carrying the transition count that armed
it: every `:next` cancels the pending timer, and one that fires anyway is recognised as
stale and dropped. Postponed events replay oldest first when the state changes.

**Consequences.** No kernel work. Not built: event timeouts, generic named timeouts,
`enter` clauses and inserting events. Each is additive when a machine needs it. Guard:
`tests/statem_test.blsp`.

## ADR-445 — A process registry is a server that owns a table; reads skip the server

**Status:** implemented (2026-10-25). ROADMAP runtime gap E, its local half.

**Context.** The kernel's `proc/register` binds a keyword to one pid and releases it when the
process dies. Real servers want more: a key that is a value (`[:session 42]`), several
processes under one key (a topic's subscribers, a pool), a value beside each holder, and a
way to address a server by such a key from `gen/call`. `std/registry` (ADR-412) is a
different thing: load-time tables of plugins, not processes.

**Decision.** `std/proc/names.blsp`, module `names`.

1. **A registry is a `defserver` that owns a table** (ADR-418). Writes — `register`,
   `unregister` — are calls, so the one process serialises them; a unique key is checked and
   taken in one step. Because the registry owns the table, every entry dies with the
   registry: a crashed registry takes its names with it, as a dead process takes its kernel
   name, and the restart a supervisor gives it starts empty.
2. **Reads do not go through the server.** A module-level table in `gen` (the via
   directory, `gen/%via-publish`) maps each registry's name to its pid and its table, and `lookup`/`whereis`/`count` read the
   registry's table in the caller. Pinning `directory` with a `def` does not pin the tables
   it points to; a dead registry's handle reads as dropped, which the read checks for.
3. **A holder is monitored once**, and its `[:down …]` drops every key it held. Until the
   registry has handled the down a read could see the dead pid, so reads keep live holders
   only.
4. **Two modes, chosen at `start`:** `:unique` (one holder per key; a key another live
   process holds answers a `failure`, ADR-310) and `:duplicate` (any number, each with its
   own value). `lookup` answers `[[pid value] …]` in both.
5. **`{:via registry :key key}` is a `gen` address**: `gen/call`, `cast`, `stop`,
   `code-change` resolve it to the live holder at each call, and `gen/start`'s `:name`
   registers through it (a taken key stops the new server and answers the failure). The
   directory lives in `gen`, and `gen/start` sends the registry's `[:register …]` call
   itself, because `names` is built on `gen`: a `names/…` reference in `gen` made loading
   either module load the other first, and `defserver` was unbound when `names` needed it.

**Rejected.** A Rust registry: everything here is policy over `table`, `monitor` and
`gen`. Reads through the server: a lookup per message would make the registry the
bottleneck of every via call. A pinned table owned by nobody: entries would outlive a dead
registry and need sweeping. Kernel `send` resolving `{:via …}`: `send` is a primitive and
cannot call into Brood; `gen` is where addressed calls already live.

**Consequences.** No kernel work. Cluster-wide process groups (the other half of gap E)
build on `node/monitor` and stay open. Not built: match specs over keys, a per-key
partition for write throughput, and `send` by via address outside `gen` (`names/whereis`
then `send`). Guard: `tests/names_test.blsp`, including eight processes racing for one
unique key and reads from a process other than the writer.

## ADR-446 — Process groups: each node owns its members and tells its peers

**Status:** implemented (2026-10-25). ROADMAP runtime gap E, its cluster half.

**Context.** A group — a name with member processes on any node — is how a cluster fans
work out and events in: every worker of a kind, every subscriber to a topic. `names`
(ADR-445) is local, and a cluster-wide unique name needs consensus, which Brood does not
want in the kernel or the library.

**Decision.** `std/proc/groups.blsp`, module `groups`.

1. **One group server per node**, registered as `:groups`, owning a members table
   (ADR-418): group → pid → the node the member came from (`:local` for its own).
2. **Each server is the authority for its own node's members.** It monitors them; a join,
   a leave or a member's death is cast to every peer's `:groups`. So no server needs to ask
   a pid which node it lives on: a member's origin is the node that told us about it.
3. **Peers are found by polling `(node/list)`** (`:interval`, default 1000 ms) — the kernel
   has no node-up event, and `telemetry/watch-nodes` polls for the same reason. A new peer
   is `node/monitor`ed and sent a full sync of this node's members, which replaces what the
   peer held from us; a server that first hears of a peer through its sync answers with its
   own, once, so the two converge whichever polls first. `[:nodedown n]`, or `n` gone from
   the poll, drops every member from `n`.
4. **Reads go straight to the table** — `members`, `local-members` — as in `names`.

**Consequences.** Eventually consistent, by design: a join is seen elsewhere once its cast
arrives, and a member on a node cut off from us stays listed until the link is seen to drop.
No locking and no unique names; a node without a group server neither tells nor hears.
Not built: a scope per application (one `:groups` per node), group-change subscriptions,
and member values. Guards: `tests/groups_test.blsp` (one node, eight concurrent joins read
from another process) and `crates/cli/tests/process_groups.rs` (two real nodes: a member is
seen across the link through the new-peer sync, and dropped when its node goes).

## ADR-447 — `caar` to `cdddr`: Lisp's compositions of `first` and `rest`, in the prelude

**Status:** implemented (2026-10-25).

**Context.** A nested list taken apart was written inside out wherever it was done:
`(first (first (first lines)))` for a row's kind three deep, `(first (rest (rest game)))`
for a record's third field. The user asked for "a construct for `(first (first (first …`
… in lisp you have the usual `cddr`". `second` and `third` cover the first two items of a
list, and nothing covered a list of lists.

**Decision.** The twelve compositions two and three deep — `caar` `cadr` `cdar` `cddr`
`caaar` `caadr` `cadar` `caddr` `cdaar` `cdadr` `cddar` `cdddr` — are prelude functions in
`std/prelude/predicates.blsp`, beside `second` and `third`. Each `a` is a `first` and each
`d` a `rest`, applied right to left as Lisp has always read them, so `cadr` is
`(first (rest x))`. They are written over `first` and `rest`, so they take whatever those
take: a list, a vector, nil. Four deep (Common Lisp's other sixteen) is left out: a fourth
level is a record that wants a name, not a longer word.

**Consequences.** The names are reserved as the language's (ADR-166), and nothing in `std/`
or the tests defined one. `second` and `third` stay the words for an item by position;
these are for structure. wos's compiler of Brood to its device's bytecode expands each into
the `car`s and `cdr`s it is, inline. Guard: `tests/list_compositions_test.blsp`.

## ADR-448 — Public-key primitives beyond ed25519: ECDSA, RSA, X25519, Argon2id

**Status:** implemented (2026-10-25).

**Context.** `std/crypto` signed with ed25519 only (ADR-212). What programs meet is wider: a
JWT is RS256, ES256 or PS256; an identity provider publishes RSA JWKs (`n`, `e`); WebAuthn
signs with P-256; a protocol agrees a key with X25519; a stored password wants a
memory-hard hash, which PBKDF2 is not. Each needs native code, so a Brood package could not
supply it (no FFI, docs/interop.md), and the gap analysis ranked it with time zones
(docs/general-purpose-gaps.md, gap 6).

**Decision.** Ten primitives in `builtins/pubkey.rs`, raw bytes in and out, with the key
maps, string messages and names in `std/crypto` (Brood policy, as for ed25519):
`%ecdsa-keygen/sign/verify` (P-256, P-384, the fixed r‖s form JOSE uses),
`%rsa-keygen/sign/verify` (PKCS#1 v1.5 and PSS over SHA-256/384/512, a public key as its
`n` and `e` so a JWK needs no DER), `%x25519-keygen/shared`, `%argon2id-hash/verify` (PHC
strings). Verification never raises: a malformed key or signature is false.

- *ECDSA and RSA are `aws-lc-rs`*, the provider rustls already links on every native
  target: no new crate, a FIPS-validated library, and constant-time signing (RustCrypto's
  `rsa` carries the Marvin advisory, RUSTSEC-2023-0071, which `cargo deny` would refuse).
  Default features off: its `ring-io` feature pulls a second `untrusted`, so a key's `n`
  and `e` are read from its PKCS#1 DER (`rsa_public_integers`). It has no wasm target, so
  on wasm32 these six raise, naming why.
- *X25519 is the `x25519-dalek`* the dist handshake uses (ADR-089). *Argon2id is the
  RustCrypto `argon2` 0.6*, the one new crate: pure Rust, the digest generation `sha2` and
  `hmac` are on, so it builds for wasm and adds no duplicate version.

**Alternatives.** RustCrypto `p256`/`p384`/`rsa` for every target: wasm too, but the RSA
crate's timing advisory, and four new crates where one suffices. `ring`: in the lock
already, but a second C crypto library beside aws-lc. A hive package: impossible without
native code (gap 3).

**Consequences.** Guards: `tests/crypto_test.blsp` checks round trips and refusals for each,
and signatures, keys and a shared secret made by OpenSSL 3.5 (fixed vectors), so an
encoding that agrees only with itself fails. Not done: PEM/DER key import (a JWK's `n`/`e`
and raw points cover the token cases), ECDSA's ASN.1 signature form, HKDF as a public name.

## ADR-449 — UDP sockets on the TCP reactor, datagrams to the owner's mailbox

**Status:** implemented (2026-10-25).

**Context.** The kernel had no UDP (`std/net/dns.blsp`: "the kernel has no UDP", so DNS ran
over TCP only). Every protocol built on datagrams was out of reach: DNS as resolvers speak
it, syslog, statsd and other metrics, mDNS/SSDP discovery, QUIC, game and audio traffic.
The general-purpose gap analysis named it with ALPN as the networking floor (gap 4).

**Decision.** A UDP socket is one more kind on the one reactor thread (ADR-143), with the
same ownership model as a stream (ADR-059): `%udp-open host port` binds it and the caller
owns it; each datagram arrives as `[:udp sock host port data]`; `%udp-send sock host port
data` sends one. Close, owner transfer and the local port reuse `tcp-close`,
`tcp-controlling-process` and `tcp-local-port`, so a socket handle stays one kind of value.
`std/net/udp` names them (`open`, `send`, `recv`, `close`, `local-port`).

- *Inbound* is flow-controlled like a stream's chunks ([`InboundFlow`]): past the high water
  the reactor stops reading and the kernel's buffer drops further datagrams — the only
  backpressure UDP has. A receive error (an earlier send's ICMP refusal) is skipped.
- *Outbound* goes at once; only while the kernel buffer is full is a datagram queued, under
  the stream's `OUT_CAP`, past which it is dropped — what UDP promises anyway.
- *Binary by default*: a datagram is a message, not text. `tcp-set-binary false` decodes
  each one as UTF-8.
- *Addresses are IP literals or `localhost`*. A datagram call has no dialler thread to hide
  a name lookup in (TCP's connect has one), and resolving on a worker would block it; a
  name is resolved first, with `net/dns`.

**Consequences.** Guards: `tests/udp_test.blsp` — a round trip with the sender's address,
all 256 byte values, text mode, a hundred datagrams in order on loopback, refusals (a name,
`tcp-send` on a UDP socket), owner transfer and silence after close. The TCP, TLS, HTTP and
SSE tests pass unchanged. Not done here: multicast and broadcast options, connected-UDP, and
`net/dns` switching to UDP with TCP for truncated answers.

## ADR-450 — A moved code epoch revalidates a native arm instead of resetting it

**Status:** accepted (2026-10-26). Implemented 2026-10-25, withdrawn the next day after CI run
40237227384 (the fast-link mirror's debug cross-check fired; `jit_self_rebind_test` answered 12
for 1001; `optional_defaults_test` answered 1 for 5000050000), and reinstated the same day with
what the first attempt missed, below. The third failure was not this decision's: it is KI-304, a
miscompile the resets had been hiding. KI-303 closed.

**Context.** ADR-217 split the code epoch from `version` so a first-time `def` no longer
invalidated compiled code. A rebind still does, and so does every module publish (it
rebinds `*features*`), every registry write and every isolate restore — and a native arm
entered after any of them reset to untried and recompiled, whatever had been rebound. A
runtime that keeps defining (a REPL, a hot reload, a test suite loading files) therefore
kept its hot arms off the native tier: with one process redefining an unrelated function in
a loop, an inner loop sat at `:queued` for every round of a diagnostic.

**Decision.** At native entry, a moved epoch asks `native_still_valid` instead of resetting.
It checks, against the runtime as it is now, what a lowering bakes in that a rebind can
change: no RUNTIME handle has moved (a `compile_relocations` stamp beside `compile_epoch`),
every inlined operator still resolves to the same native primitive, a leaf derivation is
still valid (its own check, ADR-unchanged), a named self-tail loop's name still names it, and
the arm is not marked stale by a module load (ADR-366). If all hold, the stamp moves to the
epoch read before the checks; a rebind racing them moves the epoch again and the next entry
checks again. Otherwise the arm resets as before.

What the reinstatement adds:

- **Every call by the arm's own name**, not only a `SelfCall` loop: the register worker's
  direct self-link is a non-tail `Call` on `dbg_name`, and an inlined upgrade recurses into its
  own body by `inline_name`. Either one means the name must still resolve to this arm.
- **The stamp only moves forward** (`fetch_max`), the leaf derivation's first: two processes
  moving it with plain stores could leave it behind a fast-link mirror published at a later
  epoch. The lowering reads the arm's stamp before the derivation's, and refuses a derivation
  only when it is BEHIND.
- **The background compiler's install check counts resets** (`native_resets`, bumped by
  `reset_native_state`) instead of comparing the stamp, which now also moves without one; a
  lowering in flight across a revalidation still installs.
- **The fast-link mirror's debug cross-check** accepts a callee stamped past the mirror's epoch:
  the epoch moved under the IR's raw load, the race the check already allows for an entry.
- **The tier-up election asks the pre-load** whether a name the arm reads went from unbound to
  bound (`preload_arm_globals` → `Option<bool>`), instead of reading a moved epoch as "the
  pre-load loaded a module". Read off the epoch, any concurrent rebind marked the arm stale
  (ADR-366) and rebuilt it untried — KI-303's second reset, which the entry-side change alone
  left in place.

Not in the list, by design: global reads and calls, which native code re-checks against the
live epoch itself (the global-read cache, the fast links, the dispatch fast path); and a
float context taken from a `def`'d global, a guess behind `as_f64`'s tag guard, so a changed
type is a deopt, never a miscompile. Checking current state rather than which event moved
the epoch is what makes registry writes and isolate restores safe to revalidate after: a
removed or rebound operator fails the check whatever removed it.

**Consequences.** A rebind costs only the arms that depend on what was rebound. Shared-cache
adoption still requires the cached code's epoch to be current, so a peer may recompile code
this process revalidated — slower, not wrong. Guard: `tests/jit_unrelated_rebind_test.blsp`
(a native arm stays native across an unrelated rebind; an arm settles native while a process
rebinds in a loop; a rebound callee is still reached).

## ADR-451 — A TLS stream that stays open, with ALPN, and HTTP/1.1 connections over it

**Status:** implemented (2026-10-25).

**Context.** TLS was one-shot on the client side: `%tls-request` sent one request and read
the response to close. So no HTTPS connection could carry a second request, no TLS protocol
could be spoken at all beyond request/response (WebSockets, a database's wire protocol), and
no protocol could be negotiated — without ALPN a client cannot even ask for HTTP/2. std's
HTTP client spoke 1.0 only, a socket per request, its body read to close. The general-purpose
gap analysis put this with UDP (ADR-449) as the networking floor (gap 4).

**Decision.**
- *`%tls-connect host port ca alpn binary`*: a persistent TLS client stream on the reactor's
  existing client machinery, without the one-shot request. The owner gets `[:tcp-connected
  sock]` when the handshake completes — emitted before any decrypted data, so it is always
  first — and from then on the socket is an ordinary stream (`tcp-send`, `[:tcp …]`,
  `tcp-close`). `alpn` is offered to the server; `%tls-protocol sock` reads its choice from a
  slot the reactor fills at that moment. `tls/connect` waits for the outcome and raises on
  failure, as `tcp/connect` does.
- *`%tls-listen`'s optional fifth argument*: the protocols a server speaks, so a Brood server
  can choose one (and the client side has something local to negotiate with).
- *HTTP/1.1 in std*: `http/read-response` frames a response the 1.1 way — `chunked` decoded,
  `Content-Length` read exactly, a body framed by nothing read to close, HEAD/204/304/1xx
  bodiless — and returns the bytes read past it. `http/connection` is a process holding one
  socket to one origin: `http/request-on` sends a request on it and waits, `Connection:
  close` or an unframed body retires the socket, a socket the server closed while idle is
  replaced, and a request that failed on a reused socket is tried once more on a fresh one.
  It ends with its creator (a monitor). `http/request` stays one-shot HTTP/1.0.

**Alternatives.** Keep-alive inside `http/request` with a global pool: implicit state shared
by every caller, and no answer to who owns the sockets. A connection as a plain map: the
socket's owner is the process that opened it, so the caller could never hand the map on.

**Consequences.** Guards: `tests/http_keepalive_test.blsp` — three requests on one accepted
connection, a chunked body and the request after it, a 204, `Connection: close` costing a
second connection, a refused connect as `:status 0`, and over TLS: ALPN choosing
`http/1.1` from `["h2" "http/1.1"]`, two requests on one stream, an https `connection` on
one socket, an untrusted certificate refused. The HTTP, TLS and SSE tests pass unchanged.
Not done: HTTP/2 (a hive package now that ALPN exists), pipelining, a pool of connections
per origin.

## ADR-452 — A Debug Adapter Protocol server over the process-native debugger

**Status:** implemented (2026-10-25).

**Context.** `debug` is a debugger as a process (ADR-174): `break-fn` parks a function's
callers in a queue, each paused process inspectable (`locals-of`), evaluable-in
(`eval-at`) and resumable. Only bedit could drive it (its own wire); VS Code, Emacs outside
bedit, Neovim and Zed speak the Debug Adapter Protocol, and so could not (general-purpose
gap analysis, gap 7).

**Decision.** `std/tool/dap` translates DAP onto `debug`, and `nest dap` serves it:
function breakpoints are `break-fn`; a line breakpoint is `break-fn` on the function defined
at or above that line (the granularity Brood breaks at, said in the breakpoint's message);
each paused process is a thread with one frame; its captured scope is the variables;
`evaluate` is `%eval-in` that scope; `continue` resumes the process. A launch names the
`program` and the `function` to call once it has loaded (default the file's `main`), and
the breakpoints are applied in between. `debug` gains `watch-breaks` — a watcher told of
each break as it happens — so the adapter sends `stopped` without polling.

- *TCP, not stdio.* The program runs in the adapter's runtime; whatever it, or a process
  it spawns (`*out*` does not follow a spawn), prints would land in a stdio protocol
  stream. On a socket the program keeps its terminal. Editors connect to a port (VS Code
  `debugServer`, dape `port`).
- *No stepping, no pause, no attach*: `debug` breaks at function boundaries and parks
  processes; it has no instruction stepping, and a running process is not interruptible
  from outside. The capabilities say so.

**Consequences.** Guard: `tests/dap_test.blsp` drives a real session over TCP — a function
breakpoint stopping the call, its stack frame, its `args` as a variable, evaluate in its
scope, continue to exit 0; a line breakpoint; a missing program refused at launch.

## ADR-453 — A WASM guest gets WASI only by grant, and holds resources as tokens

**Status:** implemented (2026-10-26).

**Context.** ADR-145 shipped the component host as pure compute: no WASI, and only
top-level function exports with plain-data parameters. That rules out the consumer the
interop design names as its test, SQLite: it opens files, reads the clock and returns a
connection the caller keeps using. A component built by any mainstream toolchain
(`wasm32-wasip2`, `wit-bindgen`) also imports WASI even when it does nothing with it,
puts its functions in an exported interface rather than at the top level, and models a
stateful object as a `resource`. None of the three loaded.

**Decision.**

1. **WASI preview 2 is linked only when the loader passes grants.** `(%wasm-load source
   grants)`: nil keeps ADR-145's deny-by-default (a WASI import fails instantiation); a
   map links `wasmtime-wasi`'s p2 host with exactly what it lists — `:dirs`, each
   `[host guest]` read-only or `[host guest :write]`; `:env`, the only variables the guest
   sees; `:args`; `:stdio` true to pass stdout and stderr through. Clocks and randomness
   come with any grants map, `{}` included: denying them breaks every libc start-up and
   protects nothing. **The network is never granted** — a guest that wants it is a
   program, not a library, and talks to a Brood process instead. A grant naming a
   directory that cannot be opened fails the load rather than starting a guest without it.
2. **Interface exports are callable.** One level into each exported instance; the
   canonical name is `interface#function` (`brood:sqlite/db#[method]connection.query`),
   and the bare function name is an alias when no other export shares it.
3. **A guest resource is a token**, the same unguessable 62-bit shape as an instance
   handle, valid only with its instance. An `own<T>` result is held by the host under a
   fresh token; a `borrow<T>` argument lends it; an `own<T>` argument moves it into the
   guest, after which the token names nothing. `%wasm-release` drops one, running the
   guest's destructor (fuel-metered, like a call). Closing the instance frees every
   resource it holds.
4. **Enums, variants and records lower as they lift** (amended the same day): a keyword for
   an enum, `[:case payload]` / `[:case]` / `:case` for a variant, a keyword-keyed map for a
   record, where a missing `option` field is none. A value a component returned can be
   passed straight back, which a SQL parameter (`null | integer | real | text | blob`) needs.
5. **`use-native` names resource functions as Brood would**: `[constructor]T` → `T-new`,
   `[method]T.f` and `[static]T.f` → `T-f`, interface dropped (`wasm/native-name`).

**Rejected.** *A resource as a GC-tracked opaque value* (interop.md's first sketch): the
store is per-instance mutable state already behind a handle, and a resource is
meaningless without it, so a second kind of handle with its own finaliser adds a lifetime
rule without adding safety. *Granting the clock separately*: no real guest runs without
it. *Network grants*: see 1.

**Consequences.** A guest's file I/O runs on whichever thread makes the call, so a call
that reaches the disk belongs on `wasm/call-blocking`. The test fixture is a real
`wit-bindgen` guest (`tests/support/wasm-guest/`), committed built, so the suite still
needs no wasm toolchain. Guard: `tests/wasm_wasi_test.blsp` — no grants refuses a WASI
import; `{}` gives a clock but no file or variable; a granted directory is readable and
nothing outside it is; read-only unless `:write`; env and argv are exactly as given;
malformed grants refuse to load; a constructor's token, methods on it, `release` running
the destructor once, an `own<T>` argument moving it, and a token refused by another
instance. Left: the package manager's `:native` clause (the delivery vehicle), and the
SQLite component itself.

## ADR-454 — A package ships its component with `include-bytes`; an include resolves against its own package

**Status:** implemented (2026-10-26).

**Context.** interop.md planned a `:native` manifest clause — `:wasm-build` (build on fetch)
or `:wasm-artifact` (a prebuilt `.wasm`, hash-pinned) — with lock fields, a cache under
`_deps/<name>/native/`, and a wrapper that finds the file at load. Most of that machinery
exists already for a different reason. The lock pins a dependency's content hash, which covers
a committed `.wasm` as it covers source. `include-str` carries a file into the program at
build time, and `nest release` archives it as a literal, so it travels in the image and in a
code-only bundle (ADR-038). What was missing was a binary form, and a correct root.

**The root was wrong in development.** `%include-str-path` resolved a relative path against
`*project-root*`, the consuming project, while the release collector resolves a dependency's
include against that dependency (`bundle-dep-root`). So a package's `(include-str
"priv/x.sql")` read the consumer's `priv/` under `nest run` and its own in a release.

**Decision.**

1. **`include-bytes`** is `include-str` for a binary file: spliced as a `bytes` literal at
   expansion, recorded for image staleness (KI-275), archived by `nest release` as a `#b"…"`
   literal. A package that ships a WASM component commits the `.wasm` and writes
   `(wasm/instantiate (include-bytes "native/x.wasm") grants)`.
2. **An include resolves against the package of the file that names it**: the nearest
   directory above `(%current-file)` holding a `project.blsp`, then `*project-root*`, then the
   working directory — the release collector's answer, now also the development answer.
3. **No `:native` clause for a prebuilt artifact.** The package's content hash is its pin.
   Build on fetch (`:wasm-build`) stays deferred: it needs a wasm toolchain on every
   consumer's machine, and a committed artifact needs none.

**Consequences.** Guard: `tests/project_test.blsp` — `include-bytes` splices a NUL, a non-UTF-8
byte, a quote and a backslash, and a release archives the same bytes as a literal; a relative
`include-str` in a module of another package reads that package's file while the suite's own
`*project-root*` is bound.

## ADR-465 — `reflect/eval` of a lone bound symbol is a table read

**Status:** implemented (2026-10-26).

**Context.** A late-bound name is how the editor stays redefinable: a keymap binds a command
SYMBOL, a layer list holds layer symbols, a hook registry holds function symbols, and each is
resolved when it runs (`editor/layers` `layers-resolve`, `editor/keymap` `keymap-run`,
`reflect/call-if-bound`, bedit's mode services, idle jobs, mode-line chips). Every one resolves
through `(reflect/eval sym)`, and `reflect/eval` ran the whole compile pass on it — macroexpand,
namespace resolution, privacy enforcement, a clone of the known-names set, then a VM run — for
what is one global read. An editor event resolves fifty to a hundred and fifty of them.

**Decision.** `reflect/eval` answers a lone symbol from the global table when the compile pass
provably would: the symbol is resolved by the same `resolve_sym` the pass uses (namespace,
`(:use …)` imports, `(:alias …)`, package rooting, the `/name` root escape), and the read is
taken only when the result is a bound global that is not a macro, the bare name is not an
ambiguous import, and — inside a module — the reference is not a foreign private one. Anything
else (unbound, a macro, a privacy or ambiguity error, a non-symbol) runs the full pass exactly as
before, so every error still comes from one place. A dynamic var answers its innermost
`binding`, since the table read goes through `env_get`, as the compiled read does.

No new primitive: the fast path is invisible, so every existing late-bound caller gets it and
there is no second spelling for "evaluate this name" to choose between.

**Consequences.** Guard: `tests/namespace_test.blsp` "namespaces: reflect/eval of a bare
symbol" — a module's own `count` over the root one, `/count` reaching the root, a qualified
name at root, a redefinition read next time, a `binding`, and a foreign private name still
refused from inside a module. Two sabotages went red: resolving the bare symbol without
`resolve_sym` (the module's `count` read the root's), and dropping the privacy check (the
private name was returned).

## ADR-466 — The buffer's splice log keeps a run as one entry, and an undo logs what it restored

**Status:** implemented (2026-10-26).

**Context.** `editor/buffer`'s splice log (`buffer-splices-since`) is what lets a holder of a
buffer — a language server, a buffer process, a collaborator — be told the exact positional
edits rather than diff two texts. It kept one entry per primitive edit, 32 of them, and an undo
or redo restored a snapshot without logging anything. A language server synced on the idle
beat therefore got the whole document after any burst of more than 32 keys, and after every
undo (341 ms to encode a 44k-line buffer, measured in bedit), and a hosted buffer diffed two
full texts on the loop.

**Decision.**

1. **A run is one entry.** An edit that continues the newest entry's run — typing at its end,
   deleting back into what it typed, extending a run of backward or forward deletions — merges
   into it. The merged splice only widens, and keeps `mids`: each text the run passed through
   as `[rope delta]`. A holder that synced mid-run asks from one of those texts; the rest of
   the run is one splice, found by trimming the run's small region against the run's
   replacement (`%str-splice-diff`). A run is capped at 256 edits, the log at 32 entries.
2. **An undo or redo logs a splice.** The log is walked from the restored text to the current
   one; the covering range of that path, re-read from the restored text and trimmed, is the
   single splice that reverses it. When the path is not in the log, nothing is logged and the
   caller diffs, as before. A region undo, which already holds both texts, logs their trim.

Entries are `[rope-before rope-after lo hi repl mids]`; nothing outside `editor/buffer` reads
them. The two consumers (`buffer-client/link-propagate-buffers`, bedit's
`lsp-content-changes`) apply the splices in order and need no change: fewer, larger splices
are the same edit.

**Consequences.** Guard: `tests/buffer_test.blsp` "buffer-splices-since" — a 40-key burst is
one splice, a holder that synced mid-run gets exactly the rest (`[3 3 "ab"]`, not the run),
deletion runs both ways, an undo is `[0 1 ""]` and its redo `[0 0 "X"]`, an amalgamated typing
run undoes as one splice, a region undo logs its splice, and replaying the splices of an
edit-undo-edit sequence rebuilds the text. Ropes compare by content, so a walk from a text
equal to the target answers `()` even across different handles.

## ADR-467 — Structural tree-sitter queries over a held tree

**Status:** implemented (2026-10-26).

**Context.** ADR-443 gave a document a tree handle, reparsed incrementally per edit, but only
the fontify query reads it. The structural queries — the enclosing chain (`indent-column`,
`point-up`, beginning-of-defun) and the sibling list (`point-forward` and the other motions) —
took TEXT, and the kernel parsed it (cached by text, so the first query after an edit paid a
whole parse: ~650 ms CPU on a 250 KB file). bedit warmed that parse off the loop after every
pause rather than ask the tree it already kept. It also called `tree-changes` on every event
just to learn whether its handle was still alive.

**Decision.** `%tree-sitter-tree-chain tree offset` and `%tree-sitter-tree-kids tree offset`
answer the text-keyed queries' questions from a held tree: the same walk, written once over
the `SpanText` trait (a flat string or the handle's rope), nil for a gone handle.
`%tree-sitter-tree-alive?` answers liveness without building anything (and marks the handle
used, as a query does). In `std/editor/treesit`, `indent-column` and every `point-*` motion
take an optional last `tree` — the held tree of exactly `text` — and read it instead of
parsing, falling back to the text when the handle is gone; `tree-alive?` wraps the predicate.

`update-tree` already takes explicit edits; its docstring now says how a caller with the
buffer's splices (`buffer-splices-since`, ADR-466) passes them as `[lo hi (+ lo (string/length
repl))]` to skip the prefix/suffix comparison of the two texts.

**Consequences.** Guard: `tests/treesit_module_test.blsp` "treesit queries over a held tree":
every motion and `indent-column` agree with the text query at every offset of a source with
multi-byte characters, an empty text with the tree still finds the enclosing node (the tree is
what is read), a freed tree falls back and `tree-alive?` says so, and a tree updated with the
buffer's own splices answers for the new text. The new primitives are registered last, as
registration order feeds the intern table.

## ADR-468 — A native line diff in `std/diff`

**Status:** implemented (2026-10-26).

**Context.** `diff/seq` is an O(m·n) LCS table in Brood, fit for a few hundred items. bedit's
change gutter (diff-hl) therefore shelled out per idle beat: `mktemp`, two temp files, `git diff
--no-index --unified=0`, `rm` — four subprocesses — to learn which lines of a buffer differ from
its base text, chosen over a Brood diff for speed and for git's placement of a change among
equal lines.

**Decision.** `%diff-line-hunks old new` (strings or ropes) is Myers' O((N+M)·D) diff over
interned lines in linear space, followed by git's compaction with its default indent heuristic
(`xdl_change_compact`, `measure_split`, `score_add_split` and their constants, ported), so a
change lands where `git diff` puts it. It answers git's zero-context hunks, 0-based. A region
whose search passes D·(N+M) > 5·10⁷ is reported as replaced whole, as git caps the same search.
`diff/line-hunks` exposes it; `diff/line-status` reads the hunks the way a change gutter does
(`{line -> :added | :modified | :deleted}`). A line diff is a mechanism every tool that
compares versions wants — undo-in-region, a REPL's reload report, `nest`'s formatter check —
and the speed needs Rust; the reading stays Brood.

**Consequences.** Guard: the unit tests in `builtins/line_diff.rs` and `tests/diff_test.blsp`
"line-hunks / line-status" — replacement, insertion and deletion positions, a trailing-newline
difference is none, an added blank-separated block lands as git lands it, a rope diffs as its
text, the hunks rebuild the new text over scattered edits, and the answer is the same in other
processes.
## ADR-469 — A caret that blinks in the window, not in the app's loop

**Status:** implemented (2026-10-26).

**Context.** An editor's caret blinks every ~530 ms for as long as it is open. Done by the
app, as bedit did, every toggle is a timer firing a whole turn of the loop: `update`, `view`,
`%ui-harvest`, the op parse in `%gui-draw`, the frame diff and a paint. Nothing on screen
changes but one cell. The window already owns everything a blink needs — a clock, the input
that should reset it, and a painter that can repaint one cell row — so the blink belongs
there, as a property of the caret the app draws once.

**Decision.**

1. **`[:cursor row col style colour blink]`.** The cursor op takes a sixth element, a map
   `{:interval ms :blinks n}` (`editor/display/cursor`'s third optional, built by
   `cursor-blink`). `:interval` is the half-period (default 530, floored at 50); `:blinks`
   whole cycles then steady, Emacs's `blink-cursor-blinks` (default 0, forever). Absent, the
   caret is steady: the op is the 5-element one, so every existing frame is unchanged. The
   terminal ignores it (its own cursor blinks or not, as the terminal is set).
2. **The window keeps the clock** (`CaretBlink` on the GUI thread). A frame whose blinking
   caret moved, changed or appeared restarts it, shown; the same caret in a new frame (a
   spinner turned, a line elsewhere changed) keeps its phase. Every key press, button press,
   wheel step and IME commit restarts it shown, as Emacs does on every command. A window
   that loses focus holds its caret shown; regaining focus restarts it. `about_to_wait`
   sleeps until the next toggle and stops waking once the blinks run out.
3. **A toggle repaints the caret's row.** Both painters skip a blinking caret in its hidden
   half (`Renderer::caret_hidden`). The CPU painter's strip diff treats a leaf that is, or (a
   cell region) holds, a blinking caret as changed when the phase flipped since the canvas
   was painted, and never blits such a strip: a toggle re-rasterises one cell row and
   presents that row's damage. The GPU target redraws its frame from its run cache, as it
   does for any frame.

**Rejected.** *A `:blink` render op the app toggles cheaply*: the cost is the loop turn, not
the op. *Blinking in Brood on a timer that skips `view`*: the loop has no way to say "this
frame but without the caret" short of re-rendering. *Repainting just the caret's cell
rectangle*: the strip (one cell row) is the CPU painter's unit of damage, and a row of glyphs
from the run cache is cheap; a column clip is a later refinement.

**Consequences.** bedit drops its `:cursor-blink` timer and draws its caret with
`(cursor row col style colour (cursor-blink 530 10))`. Guard: `paint::strip_diff_tests` —
a phase flip of an unchanged frame repaints exactly the caret's row, a hidden caret is
pixel-identical to the frame without it, and a blinking caret in a scrolling pane matches
a full raster in every phase through blits; `CursorBlink::hidden_after`/`next_toggle` by
the arithmetic. Not covered by an automated test: the GUI thread's clock (`about_to_wait`,
the input resets) — `BROOD_GUI_HEADLESS` makes a draw a no-op, so only a window shows it.

## ADR-470 — Memoised fragments reach the window: parsed once, shared, diffed by pointer

**Status:** implemented (2026-10-26).

**Context.** `ui-memo` (ADR-336) spares `view` recomputing a fragment whose deps are equal,
but everything after `view` still paid for the whole frame: `%ui-harvest` spliced every
fragment flat, `%gui-draw` parsed every op of every frame from the heap (each text op a
string copy and a face-map walk), the GUI thread compared the new frame with the one on
screen op by op and string by string, the CPU painter compared every strip's ops again and
then deep-cloned the whole frame as `prev_ops`. A keystroke paid that over every line on
screen to change one.

**Decision.**

1. **The marker says whether it was reused.** `ui-memo` emits `[:ui/memo key deps ops
   reused?]` — `true` exactly when `ops` is the previous turn's value for `key`.
2. **A display can take the markers.** `ui-harvest` takes `keep-markers?`; `ui-run` passes
   the display's `:fragments?`, and `gui-display` sets it. Such a display is drawn the frame
   with its markers in (the table for the next turn is collected without splicing); every
   other display — the terminal, `display-broadcast`, a served client — still gets them
   spliced.
3. **`%gui-draw` keeps a per-window parse cache** (`terminal/native/fragments.rs`): the
   last frame's fragments by key hash, each with the heap value it was parsed from and the
   keys nested in it. A marker is a HIT only when it says reused, its key's entry exists and
   its ops are that very heap value; then the parsed ops are shared, and the nested entries
   are carried forward so a later turn that recomputes the outer fragment still finds its
   rows. A key that occurs twice in a frame is never cached; a draw from another process
   starts the cache empty; `gui-close` drops it. Anything short of a hit parses, so a miss
   costs what every frame cost before.
4. **`Op::Fragment(FragmentOps)`** carries the shared `Arc<[Op]>` to the window. Every
   painter descends into it with the context it sits in (render, GPU expand, zones, IME
   area, the strip diff's leaves). Its equality tries the pointer first, so the frame diff,
   the strip diff and `prev_ops` cost a pointer per unchanged fragment rather than a walk.
   A fragment holding a frame-global op (sound, music, an effect, an emitter) is spliced
   instead, so the scanners that read those never look inside one.

**Rejected.** *Keying the cache on the heap value alone*: the collector moves objects, so an
id can be reused by another vector; the loop's reuse flag, the key and the value together
are what make a hit exact. *Diffing the fragment tables in Brood and sending only changes*:
the window needs the frame anyway, and an `Arc` makes "the same as last time" free on its
side.

**Next steps.** (a) Per-fragment geometry on the GPU target: an unchanged fragment at the
same grid could replay its quads as `RunCache` replays a shaped run, skipping `expand` over
it. (b) A damage rect narrower than a cell row (a column range) for the CPU present.
(c) `display-broadcast` could pass markers to the members that take them.

**Consequences.** Guard: `terminal::native::fragments::tests` (a reused marker is last
frame's allocation; not-reused, a different value with equal ops, and a duplicated key all
parse again; an outer hit carries its inner fragments; a fragment with a sound is spliced);
`paint::strip_diff_tests` (a fragment paints exactly as its ops spliced, in and out of a
scroll region, and a run of frames sharing one matches full rasters; an unchanged
fragment's leaves compare by pointer and dirty nothing); `tests/ui_test.blsp` (the reuse
flag per turn through `ui-run` with a `:fragments?` display; `keep-markers?` returns the
frame and tables it).

## ADR-471 — A line-state highlight cache, and what changed between two ropes

**Status:** implemented (2026-10-26).

**Context.** A lexical highlighter whose lines carry state (markdown's fences, org's
blocks, heredocs) can colour line N only from how line N-1 ended. bedit lexes a window with
a 200-line lead-in on every keystroke for that — a guess that still mis-colours a fence
opened further up, and the cost of ~250 lines per key to change one. A stateless table
lexer (every `editor/lexer` grammar) re-lexes its whole band per edit for no reason at all.

**Decision.**

1. **`text/changed-range old new`** (native `%rope-changed-range`): `nil`, or `[start
   old-end new-end]` in chars, from the two ropes' common prefix and suffix compared chunk by
   chunk (a memcmp per run, no string built). The edit shape `update-tree` takes.
2. **`editor/highlight`'s line cache.** A lexer is `(line-lexer (fn (line state) [spans
   state-out]) initial)` or `(stateless-lexer (fn (line) spans))`; the cache is a plain value
   (`line-cache`), and `(line-cache-update cache lexer rope lo hi)` returns `[cache' spans]`
   for lines `[lo, hi)`, absolute. Each line keeps `[text state-in spans state-out]`, spans
   line-relative. After an edit the lines before its first line are kept, lexing restarts
   there, and stops at the first line past the edit whose state-in matches its old entry's:
   the old entries from there on are reused, moved by the lines the edit added or removed.
   A stateless lexer keeps a memo of the window's lines by text instead, so it never lexes
   above the window and never lexes a line it has just seen.
3. **`editor/lexer/lexer-line-lexer grammar`** is every table grammar as a stateless lexer.

**Callers.** bedit's `:fontify` band for its lexer modes (markdown and org as `line-lexer`s,
the `lex-*` formats through `lexer-line-lexer`). In brood, `editor/lexer`'s grammars are
the second: any `std/editor` app colouring a JSON, YAML, TOML or INI buffer gets incremental
highlighting from the same table. The REPL's multi-line input (`lineedit`) re-lexes the
whole input with `highlight-spans` per key and would be a third once Brood's own lexer is
expressed per line (its state: the form stack and an open string) — not done here.

**Rejected.** *A splice log as the change source*: `buffer-splices-since` belongs to
`editor/buffer` and overflows (`*splice-log-max*`), while two ropes are all a cache keyed on
a rope ever has. *Keeping the cache inside a process*: it is per-buffer, per-mode data the
caller already threads.

**Next steps.** An edit that adds or removes lines copies the cached vector after it
(`subvec` + `into`, O(lines kept)); a persistent splice would make it O(log n). treesit's
`derive_edit` / `common_prefix` / `common_suffix` (`host/treesit.rs`) are the same comparison
as `changed_chars` and should share it.

**Consequences.** Guard: `editor_native::changed_range_tests` (equal texts; an insertion, a
deletion, a replacement; a repeated char never overlapping; a multi-byte char split by the
byte comparison counted whole; a change thousands of chunks in);
`tests/highlight_test.blsp` (a fence above the window colours as a lex from the top; an
in-line edit lexes one line; opening a fence re-lexes until agreement and matches a cold
cache; deleted lines shift without a re-lex; an equal text lexes nothing; a stateless lexer
lexes only its window and only new text); `tests/lexer_test.blsp` (a grammar through the
cache equals `lexer-spans`).

## ADR-480 — A contract check costs what changed: verdicts remembered by identity

**Status:** implemented (2026-10-27).

**Context.** Under `nest run` / `nest test` every `(sig …)` is a contract (ADR-381), and
`type-matches?` walked the whole value on every check. bedit's `model` is a record of every
buffer, every diagnostic, every pane; dozens of contracted functions take or return it per
event, so a typed character cost 7.7 ms armed against 1.3 ms unarmed, the profile ~45%
`type-matches?` and ~41% `reverse`. The `reverse` was the record branch: `partition` built
and reversed a two-element list per field, through `take`, on every check of every record.
Two further costs surfaced once the walk was gone: a type name that is neither base nor
alias (a record name, an open ability, a name nothing defines) scanned every `*record-ids*`
entry through contracted `->string` — ~240 µs a check with 67 records — and the shim's own
Brood plumbing (`%contract-args!` over `count` and `drop`, themselves contracted).

**Decision.** Values are immutable, so an unchanged sub-value is the very heap object it was
on the previous check, and its verdict cannot have changed. The kernel remembers verdicts
by identity and vouches for what it can decide; the Brood walk runs only over the rest.

1. **A per-heap verdict memo** (`core/heap/type_verdicts.rs`): `(type, value) → bool`,
   keyed by identity — a type's symbol id or a compound form's raw handle bits, a value's
   raw handle bits. Only compound values are kept (pair, vector, map, set). A type form in
   the nursery is not kept: a declared type lives in a shim's spec, the declared-sig store
   or compiled code, while a nursery form was built for one check (`rec` unrolled per level).
2. **What the kernel decides without the walk** (`%type-verdict`): a base name by the
   value's tag (the tag `type-of` reports, which every type predicate reads), a keyword or
   bool literal, a type variable `?A` no alias claims, an arrow type (`fn?`), an `or` of
   decided alternatives, an alias over any of those, a remembered verdict — and, on a miss,
   a record (open or closed, `(optional T)` fields) or a uniform vector or list ONE level
   deep when every part is decided. So a new model whose buffers are the same objects is
   decided in one call. A record INSTANCE's absent field is left to the walk, since `get`
   answers it through `Lookup`. Alias and `or` cycles are cut at a depth bound and left to
   the walk, which has `seen`.
3. **`type-matches?` is the memo over a walk, `%type-match`.** Every descent into an
   element, field or position re-enters `type-matches?`; a re-ask about the same value
   (`or`, `and`, `not`, `len`, `rec`, an alias) stays in the walk. `type-matches?` loses its
   internal `seen` parameter. The record branch walks its field list in place
   (`%record-fields-match?`, `%record-declares?`): no `partition`, no `reverse`.
4. **The shim asks the kernel first.** Each template calls `(%contract-args-known? spec a
   b …)` with its arguments directly (no list built) and `%type-verdict` on its result;
   only what the kernel cannot vouch for reaches `%contract-args!` / `%contract-check-ret`,
   which walk, remember and blame. An ability op's declared result does the same.
5. **`%type-names-record?`** answers "does any record carry this name" once per name under
   the memo's stamp, replacing the per-check scan in `%nominal-type-matches?`.

**Soundness.** A key is only as good as the guarantee that its bits name one object:
- a minor collection moves every nursery survivor, and `reset_local_to` truncates the
  nursery so its slots are minted again at the same epoch — both drop every entry naming a
  nursery object; a minor leaves old objects in place, so their entries stay, which is what
  lets a tenured model answer across collections;
- a major collection drops every LOCAL entry;
- a stamp compared on every lookup clears the table when anything moves that can change a
  verdict for the same pair or re-point a RUNTIME handle: the global table's `version` (a
  `defrecord` growing `*record-ids*`, a sealed ability gaining members, any rebinding),
  `declared_sigs_version` (a new or changed `deftype`), `relocations` and `free_epoch` (the
  shared region moving or freeing), and the namespace and package a bare name resolves in.
The table starts over past 65 536 entries. A cleared table costs one walk per value, never
a wrong answer. Per heap, so per process; no lock, no process-wide table.

**Why a Brood walk with native decisions, not a native `type-matches?`.** The walk is where
the contract and the checker are made to agree — the grammar of fifteen ADRs (intervals,
`len`, `rec`, closed records, sealed abilities, record naming, aliases with cycle guards)
that `annot.rs` mirrors and `type_grammar_agreement.rs` pins. The kernel takes the cases
that are cheap to state exactly and hot in practice — tags, a decidable form, one level of
record or vector over decided parts — and declines everything else (`len`, `rec`, `map`,
`set`, `seqable`, sealed abilities, record names), which the walk keeps. What Brood cannot
express is the memo itself: the identity of a heap object, and a table the collector prunes.

**Measured** (bedit at cc4cca20, `src/view.blsp` 160×50, release-fast, wall time without
the sampler, 40 reps; the machine was shared, so ±0.3 ms):

| | before, armed | after, armed | unarmed |
|---|---|---|---|
| update `"x"` | 7.67 ms | 1.78 ms | 1.24–1.31 ms |
| update `:ctrl-n` | 8.01 ms | 1.19–1.39 ms | 0.98–1.05 ms |
| view | 3.46 ms | 1.89–1.99 ms | 1.69–1.77 ms |

Per call: `string/char-at` armed 2.05 → 0.65 µs (0.24 unarmed); re-checking an unchanged
five-field record 40 → 0.4 µs; an unknown type name on a scalar 239 → 3.9 µs. An update
asks the kernel about ~230 contracted calls and it vouches for ~225.

**Rejected.** *Hashing the value structurally*: costs what the walk costs. *Clearing the
table at every collection*: bedit collects often enough that its model would rarely hit.
*Caching on the object*: a heap object has no header for a per-type verdict. *A native
shim* (the remaining ~0.5 µs a contracted call): a VM-level change to how a binding is
wrapped, for a cost now within reach of the target; left for when it is the bottleneck.

**Consequences.** Guard: `gc::tests::reset_local_to_forgets_verdicts_about_reclaimed_slots`,
`collections_forget_exactly_the_verdicts_whose_objects_move`,
`a_declaration_or_a_rebinding_starts_the_verdicts_over`; `tests/contract_memo_test.blsp`
(a hit on an unchanged value; a new model sharing its buffers; a violation deep inside a
new value caught; a closed record on a new value; a redefined `deftype` and a late
`defrecord` change the verdict for the same value; a collection between checks; the
kernel-decided forms agree with the walk, a record instance's absent field goes through
`Lookup`, and a contracted call over them still blames). `type_grammar_agreement.rs` runs
the grammar through the new path.
## ADR-481 — A grammar declared by path, loaded at its first use

**Status:** implemented (2026-10-27).

**Context.** `%tree-sitter-load-grammar path lang` dlopens a grammar when it is called. An
application with a directory of grammars had two choices: load them all before its first
frame (bedit did: eight libraries, ~7 MB, for a frame that shows one buffer), or load them
later and leave a file opened in between uncoloured (bedit's `load-user-grammars-later`, a
spawned process 200 ms after startup). Loading on the first parse that names the language is
what both wanted, and only the runtime can do it: the parse is resolved in the kernel's
`language_for`, which had no way to ask anybody for a grammar it lacked.

**Decision.** `%tree-sitter-declare-grammar path lang` records `lang -> path` in a
process-wide table (`DECLARED`, beside `DYNAMIC`) and opens nothing. `language_for` consults
it first: a pending declaration is loaded through the same code as the eager load (dlopen, the
ABI gate, the parser pool and tree cache cleared, the epoch moved) and leaves the table. The
table's lock is held across that load, so two processes parsing the language at once load it
once. The text-keyed parse resolves the grammar before it consults its tree cache, and
`%tree-sitter-tree-reparse` before it reads the epoch, so a declaration that is a RELOAD (see
below) never hands an old grammar's tree to the new grammar's parser.

- **A re-declaration is a reload at the next use** — of a pending, failed or loaded language
  alike. That is bedit's `M-x grammar-reload` (replace the library, declare it again), made
  lazy; the reload's semantics are the eager load's, unchanged.
- **A failed load is a failure, kept.** The declaration becomes `Failed { message }` and is
  not retried until the language is declared again — a parse per keystroke must not dlopen a
  broken library per keystroke. When the language still has a grammar (loaded earlier, or
  built in) parsing keeps it, as a failed `%tree-sitter-load-grammar` does; with none, every
  parse, query and tree open raises the load's message ("the :x grammar declared at P did
  not load: …").
- **`%tree-sitter-grammar-status lang`** asks without loading: `:declared`, `:loaded`,
  `:built-in`, a failure value carrying the load's message, or nil. `%tree-sitter-languages`
  counts a pending declaration (asking must not load) and not a failed one.
- **An eager load supersedes a declaration** of the same language, so a caller that wants a
  library NOW (bedit's ABI column in `M-x grammar-list`, `grammar-install`'s fresh build) keeps
  `%tree-sitter-load-grammar` and is never undone by an older declaration.
- `std/editor/treesit` wraps both: `declare-grammar`, `grammar-status`.

**Callers.** bedit declares every library in `~/.config/bedit/grammars` at startup in place of
its eager load of the opened file's grammar and its deferred loader. Besides bedit: any
program that colours or navigates foreign source through `std/editor/treesit` and keeps
grammars outside the binary — `grammar-install`'s output is a library such a program declares;
none exists in this repository today. It is a kernel change regardless: the resolution it
hooks is `language_for`, which no std module can reach.

**Rejected.** *A resolver callback* (the runtime asks a Brood function for a path): the parse
runs in whatever process asked, possibly mid-native-call, and calling back into Brood from
`language_for` would need a heap and an evaluator there; a path known up front is all a
grammar directory ever gives. *An explicit entry-point symbol* in the declaration: the
library's entry point is named for the grammar (`tree_sitter_<lang>`, hyphens as
underscores), and the eager load already decided there is no aliasing; a declaration follows
it. *Retrying a failed load on each use*: a missing library would cost a dlopen per keystroke.

**Consequences.** One more uncontended lock per grammar resolution (a parse, a reparse, a
text-keyed query). A lazy load blocks other grammar resolutions for the dlopen's duration —
once per language. Guard: `host::treesit::declared_grammar_tests` (declaring opens nothing and
lists the language; a missing library is a failure carried by the status, not retried, and a
re-declaration is a new attempt; a failed eager load leaves the declaration; a failed
re-declaration of a built-in language keeps parsing with the built-in);
`tests/tree_sitter_test.blsp` "declared grammars" (the same through the primitives, a tree
open and a structural query fail with the message, and — when the test's Elixir library is
built — the first parse loads a declared grammar and a re-declaration of the loaded one reloads
it through a held tree).
## ADR-483 — A lean line cache, and structural queries over a rope

**Status:** implemented (2026-10-27).

**Context.** Adopting ADR-471 in bedit showed two costs that grow with the document. The line
cache kept `[text state-in spans state-out]` for every line from 0 to the deepest line ever
shown, so a long markdown file viewed to its end held a copy of all of it. The text was read
only by the resume check, which is redundant: the lines after an edit are the old lines by
construction. And every edit copied the cached vector before and after it — O(lines cached)
per keystroke. Separately, `editor/treesit/indent-column` and the `point-*` motions took a
string, so bedit's RET built the whole buffer's string (~2 ms on 2.35 MB) to indent one line,
even with the held tree (ADR-467) in hand.

**Decision.**

1. **No line text.** An entry is `[state-in]` (a checkpoint) or `[state-in spans state-out]`
   (a shown line).
2. **A treap with relative keys.** Entries live in a treap keyed by line. Each node's key is
   relative to its parent's, so moving every line after an edit means re-basing one subtree.
   An edit costs a few O(log n) splits and joins, whatever it added or removed, plus the lines
   it re-lexes.
3. **One tentative chain.** After an edit the lines past it keep their entries, marked
   tentative behind a `:verified` seam. The next walk re-lexes from the seam and stops at the
   first old entry whose state agrees. From there the whole chain is true again, and a walk
   above the window jumps straight to the window's checkpoint. A second edit before that
   drops the entries between the two seams, so there is only ever one chain to confirm. A
   walk that ends past the seam without agreeing leaves a checkpoint there and moves the
   seam to it.
4. **Bounded memory.** Spans are kept only near the last `lc-retained-windows` (3) windows.
   A window near the latest grows it, clamped to a margin of its own height either side, so
   scrolling evicts one row per row scrolled. Elsewhere a line keeps its state-in every
   `lc-checkpoint-every` (32) lines, and a far region shown again is re-lexed from the
   checkpoint above it.
5. **Ropes in `editor/treesit`.** `indent-column`, every `point-*` motion and
   `point-defun-start`/`-end` take a string or a rope. Their text reads go through
   line-oriented helpers (`ts-line-start`, `ts-line-end`, `ts-slice`), which use the rope's
   line index. With a held tree, a rope query reads only the lines it inspects. Without one,
   the kernel's parse needs a string, so the rope is converted at that call only.

The public API of ADR-471 is unchanged (`line-lexer`, `stateless-lexer`, `line-cache`,
`line-cache-update`). The cache's internal shape changed (`:lines` is gone), which no caller
read. A caller of `indent-column` may now pass `(buffer-rope buf)` where it passed
`(buffer-text buf)`.

**Rejected.** *A vector of chunks*: a line-count change still renumbers every chunk after
it. *A gap-buffer split at the last edit*: cheap while typing in one place, but a jump moves
everything between. *Keeping several tentative chains*: a chain is consistent only over
lines that have not changed since it was lexed, and tracking that per chain costs more than
it saves. *Hashing line text for a sanity check*: nothing in the invariant needs it.

**Consequences.** Guard: `tests/highlight_test.blsp`, "a lean cache". An edit inside a fence
re-lexes one line however deep. Opening and then closing a fence stays exact, near and far.
Lines inserted and deleted above the window move the window's lines without re-lexing them.
The same edit lexes the same number of lines in a 300- and a 3000-line document, the
lexer-call count rather than a time. A far window shown again after its spans were evicted
re-lexes at most a window plus one checkpoint gap. Scrolling through 2000 lines leaves at
most 160 lines with spans. A run of mixed edits and windows matches a cold cache at every
step. `tests/treesit_module_test.blsp`: `indent-column` and the motions over a rope agree
with the string at every line and offset, with a held tree and without, on a multi-byte
line.

## ADR-484 — A release bundle starts from its own startup image

**Status:** implemented (2026-10-27).

**Context.** A `nest release` bundle booted by compiling every embedded module's source on
every launch (`run-bundle` → `require-one` per module). bedit's bundle reached its prelude and
stdlib images at ~30 ms and its first frame at ~750 ms: ~120 modules, nearly all of the start
spent evaluating their source. ADR-218 gave `nest run` a sectioned project image for exactly
this, but a bundle has no project directory to keep `.brood/image.bin` in, and an image only
works for the runtime that wrote it — `nest`'s runtime is a different build from the lean one
it ships.

**Decision.**

1. **The bundle writes its own image.** After writing a binary, `nest release` runs it with a
   third reserved argument, `--brood-build-image PATH` (`project-release/write-bundle-image`).
   The binary loads its embedded sources on its own runtime and stdlib, groups the globals
   into per-module sections and writes the image (the project image's writer, ADR-218, with
   ADR-317's registration pruning). `nest` then rewrites the binary with the image appended.
   The image is valid for the runtime that ships it by construction.
2. **An optional tail in the archive.** After the modules: `BRDIMG01`, a `u64` length, the
   image bytes. A runtime older than the tail stops reading after the modules, so the bundle
   format version is unchanged. Bytes after the modules that are not a whole tail make the
   archive corrupt. At mount the runtime hands the bytes to the image reader as
   `mem:bundle-image` (the `mem:` paths of ADR-414) and drops its own copy.
3. **The stamp is the release.** `system/build-id` holds the executable's mtime, which
   changes on every copy and on the rewrite itself, so it cannot be the key. The stamp is the
   stdlib id, the contract mode, and the bundle's manifest, which carries `:built-at`. An
   image can only be installed by the archive it was built for; any mismatch is a miss and
   every module loads from source.
4. **The same sections, keyed by what `require` asks for.** A module's section is its
   namespace. A uniquely named dependency module (`store/repo`) loads at root as `repo`, so
   the boot loop now requires each module by that name (`bundle-require-name`) and the
   prelude's image branch marks the rooted key loaded as well, as its source branch already
   did. A colliding dependency module stays rooted and is sectioned under its rooted name.
   A module whose file name and namespace differ has no section under the name it is
   required by and loads from source.
5. **The boot check uses the image path.** `--brood-boot-check` (and `nest release`'s smoke)
   boots as a launch does and says whether the modules came from the startup image.
   `BROOD_NO_BUNDLE_IMAGE=1` ignores the image, for comparison on one binary. A target this
   host cannot run, or a project that cannot be imaged (a `table` global), ships without an
   image; `nest release` says so on its `image:` line.

**Rejected.** *`nest` writing the image itself*: its runtime is not the shipped one, so the
image would never match. *Keying on `system/build-id`*: an installed copy has a new mtime and
would never hit. *Loading only what `main` reaches*: a bundle loads every embedded module
today, and a lazier boot is a separate change to what a release guarantees.

**Consequences.** bedit's bundle: first frame ~750 ms → ~185 ms; the binary grows by the
image (5.3 MB on 56.7 MB). `nest release` takes one more run of the binary (~5 s for bedit).
Guard: `crates/cli/tests/release_bundle.rs` — an imaged bundle evaluates no module source
(the project's own and a dependency's), its ability dispatch works, a module without a section
loads from source, the boot check reports the image, `BROOD_NO_BUNDLE_IMAGE` gives the source
boot, colliding dependency modules stay apart when materialised, and an image built for
another release is ignored. `bundle::tests` covers the archive tail.
## ADR-485 — `nest check` re-checks what an edit reached: a definition's fact is its content, and the pool takes real projects

**Status:** implemented (2026-10-27).

**Context.** bedit's `tests/strict_ratchet_test.blsp` shells out to `nest check --strict` and
took 55 s of the suite's 97 s. An unchanged tree replayed its verdict in 0.08 s (ADR-382), so
the cost was every run after an edit. Measured on bedit (204 files, 4.5 MB, release `nest`):
touching one module, `src/eldoc.blsp`, re-checked **158 files in 42 s**, one at a time. Three
causes, each enough to cost most of that:

1. **The fact of a user global was its defining FILE's mtime** (`deps::fact_of_sym`,
   `D<file>@<mtime>`). Inference walks callee bodies, so nearly every file observes something
   in nearly every module, and any edit, or a bare `touch`, invalidated every file that
   observed anything in the edited file.
2. **The reuse test read a different heap from the one the fingerprint was stamped in.** The
   fingerprint is stamped after the re-check, in a heap `project-preload!` has filled. The
   test ran before the preload. A global of a std module that only the preload brings in
   (`datetime/format`, reached through a project body) read `U` at test time where it had been
   stamped `F|S…`. Every file that observed one missed the cache on every run, whatever
   changed.
3. **The re-check ran on one core.** The pool engages at 2 000 files or 7 MB, a threshold
   set for many small, cheap files whose per-worker setup (the O(globals) caches each worker
   heap rebuilds) would outweigh the work. A bedit file costs 50 ms to 1.8 s to check, so
   4.5 MB of them never reached the pool. Chunks were also consecutive runs of the
   alphabetical file list, so the six 1.4–1.8 s test suites landed in neighbouring chunks of
   one wave.

**Decision.**

1. **A definition's fact is what the checker can see of it** (`deps::definition_digest`).
   For a closure or macro, the fact is a digest of its name and every arm's parameters,
   optionals and body forms, which are the values `infer_sig`, `infer_overload_of`,
   `arity_of` and `param_names_of` read. For a primitive bound under a user name, it is the
   primitive's name. Any other value contributes its KIND, which is all `global_value_ty`
   takes from it. A dynamic or earmuffed global, which is never typed, contributes only that
   it is bound; `*image-path*` is nil in a source-loaded process and a string in an imaged
   one. The digest is process-independent: symbols are hashed by name, a gensym by its first
   appearance in the definition, maps and sets order-independently. A closure's digest is
   memoised by its move-stable identity and its arms allocation. Anything the walk cannot
   render (a function value spliced into a body, a pid) falls back to the old mtime fact.
   The declared sig, registries, export sets and known namespaces stay separate facts, as
   before.
2. **The macroexpander records the macro it expands** (`macros::macroexpand_1`, through
   `rec_check_dep_sym`). A file's check analyses the expansion, and nothing in the expansion
   names the macro. Under the mtime fact this dependency was caught by accident, because the
   macro's file also defined something the file observed. Without the record, a macro edit
   would leave the verdicts of the files that expand it standing. `rec_check_dep_sym` now
   checks that a recording is active before the gensym test, since every expansion reaches
   it.
3. **`nest check` preloads before the reuse test**, every file's closure, so the test reads
   the heap the stamp was taken in. This costs what preloading the re-check set did, because
   the closures overlap almost entirely. The launch pre-flight (`checks-run`, mtime only) is
   unchanged.
4. **The pool engages at 1 MB, and chunks are dealt by size**: heaviest first, round-robin
   (`project-deal-chunks`), so every chunk carries about the same bytes.
5. **A replay prints what the run printed.** The recorded lines were the raw warnings, in
   reverse file order, so a replayed advisory note lost its `(advisory — not gating)` marker
   and the order flipped. They are now recorded as printed (`project-printed-warning`).

The check-cache version is v4. A v3 manifest is dropped once.

**Rejected.** *Hashing the source text of the def form.* The form does not carry what
the file around it decides: the `(:use …)` header that resolves its bare names, a macro it
calls. The stored body has both resolved, and it is what the checker reads. *Digesting
every value's content.* The checker ignores a non-function's literal, so a value computed at
load would only change the fact on every run and re-check its readers.
*Lowering the pool threshold further.* Each worker heap costs about 0.5 s of CPU to set up
(bedit: 75 s CPU in the pool against 47 s on one core), so a handful of cheap files is
faster on one core.

**Consequences.** bedit, release `nest`, `nest check --strict`:

| run | before | after |
|---|---|---|
| unchanged | 0.08 s (replay) | 0.07 s (replay) |
| `touch src/eldoc.blsp` | 53.5 s, 158 re-checked | 3.3 s, 1 re-checked |
| one-function body edit in `eldoc.blsp` | not timed (the same 158 by mtime) | 5.5 s, 3 re-checked |
| body edit in `ed-current-buf` (`model.blsp`, the hub) | not timed | 7.7 s, 123 re-checked |
| cold, cache wiped, image warm | 42 s of checking alone, sequential | 5.9 s |
| cold, new binary (stdlib image and project image built) | — | 16.8 s |

The ratchet test after a one-function edit takes 10.5 s, against ~55 s. Every verdict is
byte-identical, in order, to the old binary's `BROOD_NO_CHECK_CACHE=1` run: three advisory
notes, zero warnings, across cold, replay, touch, edit and revert. On a three-module project, a
body edit that changes a callee's return, a macro edit and an arity change each re-check
the edited file and its dependent and report the new warning. An edit to an unrelated
function in the same file re-checks that file alone. Before item 2 the macro edit went
unreported.
Guard: `types::check::tests::gradual_checks::a_definitions_fact_is_its_content_not_its_files_mtime`
(an unchanged reload, gensyms included, keeps a dependent's fingerprint; a macro edit and a
body edit each move it). `crates/nest/tests/check_incremental.rs` (leaf, arity and replay
cases) is unchanged and expected to hold; it was not run here.

The per-module check cost inside the editor (`reflect/check-string-here` on the idle beat)
does not use the fingerprint and is unchanged. The fixed cost of an edit is now
`ensure-loaded` (0.8 s) plus the preload (0.8–2 s).

## ADR-486 — A face table keys on a node's context; an indent spec names verbatim nodes

**Status:** implemented (2026-10-27).

**Context.** Adding Terraform/HCL to bedit found two gaps in `editor/treesit`.

1. **A face table could only name a node KIND.** In HCL every name is an `identifier`: a
   block's type (`resource`), an attribute's name (`ami =`) and a called function
   (`lookup(`) cannot be told apart, so bedit left all three uncoloured. Rust, Go and Python
   lose function-name colouring the same way: a call's function is an `identifier` under
   `call_expression`'s `function` field. The walk is native (`spans_into`, ADR-443), so a
   Brood callback per node to look at the parent was not an option.
2. **`indent-column` gave every line a level**, so TAB on a line inside an HCL heredoc, a
   Rust raw string or a Python triple-quoted string re-indented text that is content.

**Decision.**

1. **A face-table key is a SELECTOR**: a node kind keyword as before, or a map
   `{:kind :parent :field :nth}`. `:kind` is the node's kind, `:parent` its parent's kind,
   `:field` the tree-sitter field name the node fills in its parent, and `:nth` its index
   among the parent's NAMED children. Every constraint given must hold. At least one is
   required, and any other key is an error. When several entries match a node, the most
   specific wins. The weights are distinct powers of two (field 8, parent 4, nth 2, kind 1),
   so different constraint sets never tie and the map's hash order never decides. Any
   context entry therefore beats the plain kind. A coloured node is still coloured whole, so
   an entry reaches only nodes whose ancestors the table leaves uncoloured.

   ```
   {:string_lit :syntax/string
    {:parent :block :kind :identifier :nth 0} :syntax/keyword    ; resource, locals
    {:parent :attribute :kind :identifier} :syntax/special       ; ami =
    {:parent :function_call :kind :identifier} :syntax/function  ; lookup(
    {:field :function :kind :identifier} :syntax/function}       ; Rust / Go / Python calls
   ```

   The kernel takes the TABLE. `%tree-sitter-spans` and `%tree-sitter-tree-spans` accept a
   kind vector, as before, or the face table map. They answer `[start end reported]`, where
   `reported` is the table's value (the face name) copied through, and `:__keyword__` for the
   keyword rule. The selectors compile once per call into a `SpanTable`: rules indexed by
   kind, plus the few that name no kind. The walk carries a `NodeContext` read off the
   cursor it already uses for the parent's children: the parent's kind,
   `TreeCursor::field_name`, and a named-child counter. Per node that is one hash lookup
   and a scan of that kind's few rules, the same cost as the kind set. Brood resolves face
   names to faces once per name (`table-spans->faces`), no longer per kind. The text,
   held-tree and windowed paths share the walk. A window still walks from the root, so a
   node's context is the whole document's.

   `face-table-problems` checks a table's shape (a malformed selector, a non-keyword face)
   and returns one message per bad entry. A registration calls it beside `missing-services`,
   so a misspelt selector fails at load and not at the first frame.

2. **`:verbatim` in an indent spec** is a set of node kinds whose interior is content. When
   a `:verbatim` node that began on an EARLIER line encloses a line, `indent-column` answers
   the indentation the line already has. A caller that indents to the answer then changes
   nothing. The heredoc's opening line is code and is indented as code. A BLANK verbatim
   line answers the previous non-blank line's indentation, which covers RET inside a
   heredoc: the new line has no indentation yet, and the content's is the one to continue.
   The check comes before the broken-parse fallback, because a heredoc stays one while code
   above it is half-typed. Indentation is counted in characters, as everywhere in the
   indenter.

**Rejected.** *A vector selector `[:parent :kind]`.* It is shorter, but cannot say which
position is a field and which a parent kind without a sentinel, and it cannot omit the kind.
*Reporting the selector itself, for Brood to map to a face.* A map key hashes a map per span.
The table's value is what Brood wants, so the kernel copies it through. *Tree-sitter's query
language (`(call_expression function: (identifier) @function)`).* It is the general answer.
It needs a query compiled per grammar and a capture per match, and it changes what a face
table is from data to a source string. The selector covers the parent-and-field cases that
were missing at the cost of the existing walk. *A distinct "leave it" value (nil) from
`indent-column`.* Every caller would need a new branch. Callers that indent to a column (all
of bedit's) already get a no-op from the current indentation. The cost is a line indented
with tabs: a caller that rewrites indentation as spaces turns each tab into one space. That
cost is accepted: content indented with tabs is rare in the languages that have heredocs.

**Callers.** bedit, for Terraform/HCL and for function names in Rust, Go, Python, JavaScript
and TypeScript. Beside bedit: the mechanism lives in the kernel's span walk (question 3 of
bedit's CLAUDE.md, it versions with the kernel), and every consumer of
`%tree-sitter-spans` / `editor/treesit/fontify` gets it. Today that is bedit alone: no
other in-tree caller fontifies tree-sitter text (std/editor/web serves no spans of its
own). brood-lsp's semantic tokens run on Brood's own reader, not tree-sitter, and do not
use it. The kernel placement is what the selector needs: a std or bedit walk would mean a
Brood callback per node.

**Consequences.** Guards are in `tests/treesit_module_test.blsp`. With the built-in Ruby
grammar: field beats kind, the most specific entry wins, `:nth` counts named children, a
coloured ancestor hides a context entry, the held tree equals the text path, and a
malformed selector is refused by the kernel and named by `face-table-problems`. With an
installed HCL grammar: block type, label, attribute, function and variable are told apart;
held-tree spans equal text spans over the file and over a window; a heredoc keeps its
lines' indentation, through the text and through a held tree. With installed Rust and Go
grammars: a call's function name differs from its arguments. The installed-grammar suites
run only when `~/.config/bedit/grammars/libtree-sitter-<lang>.so` exists.

## ADR-487 — A face-table selector matches a node's text and nests its parent

**Status:** implemented (2026-10-27).

**Context.** ADR-486's selectors name a node's kind, its parent's KIND, its field and its
position. Two cases that bedit's languages need still fall outside that:

1. **Elixir's keywords are calls.** tree-sitter-elixir parses `def go(x) do … end`,
   `if x do … end` and `case`/`cond`/`with`/`use`/`import`/`alias` as a `call` whose
   `target` is an `identifier`, exactly like `foo(x)`. Only the text tells them apart.
2. **A method call's name sits one level further up.** Rust's `s.bar()` is
   `call_expression(function: field_expression(field: field_identifier))`; the read `p.x`
   is the same `field_expression` outside a call. What separates them is the field the
   PARENT fills in the grandparent. Go (`selector_expression`/`field_identifier`),
   JavaScript and TypeScript (`member_expression`/`property_identifier`), Python
   (`attribute`/`identifier`) and C (`field_expression`) have the same shape.

**Decision.**

1. **`:text`** is a string, or a non-empty set of strings, the node's source text must
   equal: `{:kind :identifier :parent :call :field :target :text #{"def" "if" "case"}}`.
   The walk checks it last, after every cheap constraint holds, and refuses on the node's
   byte length before reading a byte (the set keeps its shortest and longest). A held
   tree's rope lends the text without a copy when it lies in one chunk.
2. **`:parent` may be a selector map** the parent must satisfy, recursively, its own
   `:field`/`:nth` placing it in the grandparent:
   `{:kind :field_identifier :parent {:kind :field_expression :field :function}}`. A plain
   `:parent :call` is the map with a kind alone. At most three maps nest (the key, its
   parent's, its grandparent's), refused past that. The walk's `NodeContext` now holds the
   parent NODE and a reference to the parent's own context on the walk's stack, so a nested
   selector climbs the chain the walk already built — no tree-sitter `parent()` calls.
3. **Specificity** is a vector of level weights from the node outward, compared
   lexicographically. Each level's weight is its constraints as distinct powers of two:
   text 16, field 8, parent 4, nth 2, kind 1. The node's own constraints decide first, so
   `{:kind :identifier :text "b"}` beats `{:kind :identifier :field :method}`; when they tie,
   the parent selector's weight decides (a nested parent beats a parent kind), then the
   grandparent's. A remaining tie goes to the narrower `:text` sets (fewer strings), then
   to the face name that sorts first — so the map's hash order never decides. The table is
   sorted by this rank once per call, and the walk takes the first rule that holds, the
   by-kind and any-kind lists compared by their place in that order.

`face-table-problems` validates both: `:text`'s shape, `:parent` as a kind or a valid map,
and the depth bound. The text, held-tree and windowed paths share the walk, which starts at
the root, so a window's nodes see the whole document's ancestry.

**Rejected.** *A `:text` regex.* The cases are closed word lists; a regex per node is a
cost and a dependency the walk does not need. *Unbounded nesting.* A bound keeps the
specificity a fixed-size array and every real case fits in three. *Tree-sitter queries*,
for ADR-486's reasons: these two keys cover the missing cases within the existing walk.
*Matching `:text` in Brood after the walk.* The walk reports the OUTERMOST coloured node,
so a call coloured as a keyword must be decided before the walk descends.

**Callers.** bedit, for Elixir's keyword calls and method-call names in Rust, Go,
JavaScript, TypeScript, Python and C. As ADR-486: the mechanism is the kernel's span walk.

**Consequences.** Guards in `tests/treesit_module_test.blsp`: with built-in grammars,
Elixir `def`/`if` against calls, text over field, a nested parent over a flat one, the
narrower text set, a nested parent's own field, held-tree spans equal text spans over the
file and a window, and malformed `:text` / `:parent` / over-deep selectors refused by the
kernel and named by `face-table-problems`. With an installed Rust grammar: `s.bar()`
against `p.x`, through the text and a held tree.

## ADR-482 — An unchanged fragment's quads replayed, and damage narrower than a row

**Status:** implemented (2026-10-27).

**Context.** ADR-470 made an unchanged memoised fragment reach the window as last frame's
allocation, so the frame diff and the strip diff skip it by a pointer. Two costs it listed as
next steps were still paid per frame. The GPU target walked every op of every frame: each text
op hashed its string and face, found its run in the `RunCache` (ADR-440) and pushed its quads
one at a time through the builder. And the CPU painter's unit of damage was a cell row: a typed
character re-rasterised and presented the whole width of its row, every pane beside the one
typed in included.

**Decision.**

1. **The GPU target keeps each fragment's instances** (`gpu::FragmentCache`). A fragment
   expanded on a miss is recorded: the solid and textured instances it pushed, the batch
   segments they form (a `Segment` is a `Batch` without its start), the run hashes and nested
   fragments it used. A HIT is the same `Arc<[Op]>` (the entry holds a clone, so its address
   cannot be reused) in the same `FragmentContext`, compared whole: the grid (origin, cell
   size, scroll shift), the clip band and viewport (what was culled), the renderer's metrics
   and line height, the default family, the window background (the contrast lift's ground),
   the font generation, ligatures and subpixel order, the scale factor (hairline snap), a
   texture generation bumped by every upload and free (a sprite of a missing texture draws
   nothing), and — only for a fragment holding a blinking caret — the blink phase. A hit
   pushes the instances as blocks (`FrameBuilder::push_solids` / `push_texs`), each segment
   joining the open batch exactly when its first quad would have, so the batches equal an
   expansion's; its runs and nested fragments are carried into this frame's caches without
   being replayed, so a later frame that changes the fragment still finds its unchanged lines
   shaped. Like the run cache it holds what the last frame drew and nothing else. A fragment
   that moved the overlay point is never recorded (the expanders splice those anyway,
   `fragments::frame_global`). `BROOD_GUI_DAMAGE=0` turns it off with the run cache.
2. **Column damage on the CPU painter** (`paint::strip_columns`). A dirty strip that is not
   blitted is re-rasterised only in the columns its differing leaves can paint. The leaves
   that differ are those outside the strip's common prefix and suffix, compared position by
   position when what is left has one length in both frames (a typed character changes the
   line's text op and moves the caret; the divider and the other pane between them pair up
   equal). Each one's columns come from `leaf_columns`, conservative like `op_band`: a text
   op's cells (a unit's glyph canvas is exactly its cell block), a caret's cell, a rect's
   cells, a sub-cell or pixel-space op's float extent widened by four pixels; a clear, a cell
   region (whose width the painter does not clip) and anything non-finite have none, and the
   strip is repainted whole. A run of adjacent dirty strips is one rect over the union of
   their columns, so the frame is walked once per run as before. `Canvas` gained the column
   bounds every primitive now clips to (`Canvas::rect`, `cols`); the present copies and
   declares rects rather than full-width bands. `BROOD_GUI_COLUMNS=0` restores full rows.

**Why exact.** A pixel no differing leaf reaches is painted, in both frames, by the same ops
in the same order over the same cleared ground, so it is the pixel the canvas holds. Inside the
rect the raster is a full raster's: each primitive's per-pixel result depends only on the pixel
it writes, so cutting its loop to the rect changes nothing within it.

**Rejected.** *Keying fragments without position and translating on replay, as runs are*: the
clip and the cull depend on the absolute position, so a scrolled fragment would need re-culling
quad by quad — which is what the run cache already does under a miss. *A diff of each strip's
leaves by longest common subsequence*: the prefix, suffix and positional pairing cover typing,
deleting and caret motion; anything else costs a whole row, which is what it cost before.

**Next steps.** `display-broadcast` passing markers to the members that take them (ADR-470's
third) is still open: a broadcast display gets spliced frames, so neither cache applies there.

**Consequences.** Guard: `gpu::tests` (a replayed fragment's instances and batches equal
pushing its quads one by one after three different preludes; a theme's ground, a font size,
the cell metrics, a font registration, ligatures, the subpixel order, a scroll, a clip, a
resize, a scale factor and a texture upload each miss; the blink phase misses only a fragment
holding a blinking caret; equal ops in another allocation miss; a replay carries its runs and
nested fragments, and an entry unused for a frame is dropped); `paint::strip_diff_tests`
(typing repaints the changed cells, not the divider or the other pane; every op kind with
columns, changed one at a time, matches a full raster; a raster confined to a rect leaves
everything outside it untouched and matches a full raster inside it, through glyphs, scaled
and underlined text, rounded rects, a turned quad, each caret style and a cell region; a clear,
a cell region and an off-screen change fall back to the whole row; the blink flip repaints the
caret's cell). `backend::gpu_replay` drives `GpuWindow::expand_fragment` itself on every
hardware adapter the machine has, with no window: `GpuWindow::offscreen` draws into a texture
of a window's size and format through the same pipelines and passes, and `read_pixels` reads
it back. One sequence of 42 frames — unchanged lines, one line edited, a background and a
palette change, a scroll shift, a font size step, a blinking caret, a texture drawn before its
upload then replaced and freed, nested fragments in a moved cell region, fragments dropped and
re-added, new fragments in freed allocations, a resize — is drawn with replay on, with fragment
replay alone off, and with every reuse off, under grey and subpixel text, and the three must
match pixel for pixel. First run on an Intel Raptor Lake UHD and an NVIDIA RTX 5060 (Vulkan):
identical, and a key left out of `FragmentContext` (the scroll shift, the ground, the texture
generation, the blink) fails it. Intel draws grey text with the odd stray pixel between two
identical draws, every reuse off in both; up to three such pixels are tolerated
(`DEVICE_NOISE_PIXELS`). A machine with no hardware adapter (CI) skips it and says so. Its
ignored sibling times the frame build of a sixty-line page with one line changed per frame
(Intel, one shot, median of eight): 112 µs replayed, 148 µs with the run cache alone, 447 µs
with no reuse.

## ADR-488 — The reader-family form scans read a rope, and carry their table across edits

**Status:** implemented (2026-10-27).

**Context.** ADR-483 let `editor/treesit`'s indenter and motions take a rope. The Lisp side
had not followed: `reflect/scan-form-start` / `-2` / `scan-form-end` took only a string, so
`sexp/narrow` and every structural motion over it, `sexp/point-kill-end`,
`editor/highlight/closer-redundant?` and bedit's Lisp indenters were handed
`(buffer-text buf)` — the whole document flattened per C-M-f, C-M-k, `)` or RET. Worse, the
string was fresh each time, so the safepoint table cached on a string value (the thing that
makes `scan-form-start` O(stride) rather than O(pos)) missed on every call: each key paid a
native lexical pass from offset 0 on top of the copy.

A bounded scan from a column-0 `(` (Emacs's `beginning-of-defun`) was considered and is not
exact: Brood docstrings put `(` in column 0 (std's own module docstrings do), and a
mis-indented open inside an unclosed form is not a form start. Exactness needs the lexer state
at some point before `pos`, which only a forward pass can give.

**Decision.**

1. **The scans take `(or string rope)`.** The lexer is written once over a `ScanText` trait —
   a string's bytes, or a rope read through the chunk holding the last byte asked for (ropey
   splits on char boundaries, so a char never straddles chunks). A rope is never copied.
2. **A rope's safepoint table is carried across edits.** The process keeps the tables of the
   last four ropes it scanned (`HeapExtras::form_scan_ropes`). A new rope is compared with
   them (common prefix and suffix, chunk by chunk — `%rope-changed-range`'s comparison); an
   identical one reuses its table. Otherwise the nearest one's table is carried: safepoints
   before the change are kept, the scan resumes at the last of them, crosses the change, and
   stops at the first old safepoint past it whose state it reproduces — same depth, same byte
   offset, and the same last two form starts once moved by the edit. Same state over the same
   remaining text means the same remaining pass, so the old tail is taken, shifted. A
   keystroke inside a form re-scans from one stride before it to the next safepoint after the
   form ends. An edit that never rebalances (a lone `(`) re-scans to the end: one native pass,
   exact, and no worse than before.
3. **The callers follow.** `text/slice` and `text/length` accept a string as well as a rope.
   `sexp/narrow` slices only its ~3-form window out of a rope; the motion buffer commands
   (`sexp/forward` … `end-of-defun`) and `point-kill-end` pass `(buffer-rope buf)`;
   `closer-redundant?` reads the char at point, then only the top-level form up to it. The
   paredit EDITS (slurp, barf, raise, …) still take the whole text: they build the whole new
   text anyway, once per explicit chord.

**Rejected.** *Column-0 candidates*: inexact, above. *A table on the rope value*: the next
keystroke discards the value. *Per-node summaries inside the rope*: ropey has no hook for them,
and a fork of it is a larger thing to own than a carried table.

**Consequences.** Guard: `form_scan_tests` in `builtins/syntax_scan.rs` — every position of
the existing fixtures over a rope, with and without a table, and `scan-form-end` from every
offset; a table carried across eleven successive edits (typing in a form, opening and closing
a string, a lone `(`, a form at the start, trimming the end, multi-byte text, a column-0 `(`
inside a docstring) holds only true states and answers as a fresh scan; and one keystroke in a
128 KB document visits under an eighth of its states. `tests/sexp_test.blsp`: every scan,
motion, `point-kill-end` and `closer-redundant?` agree with the string at every point, on a
rope from a string and on one built by edits, and a document past the table threshold is
edited six times and re-asked. A held-in-process cache is new state in the kernel; it holds
Rust values only (rope clones and tables), so it is not traced and survives GC untouched.

## ADR-489 — Injections: another language's document inside this one

**Status:** implemented (2026-10-27). Extended by ADR-496: `:exclude`, and line breaks between pieces.

**Context.** `editor/treesit` parsed a whole document in ONE language. Code embedded in it
could not be coloured as itself: a Markdown fence's body, Elixir's `~H"""…"""` (HEEx), a
Dockerfile `RUN` line's shell, a Terraform heredoc. Emacs (`treesit-range-settings`), Neovim
and Helix all call this injection, and all build it on tree-sitter's included ranges: a
parser told to read only some byte ranges of a text parses them as one document, its nodes
carrying the outer text's offsets.

**Decision.** Two layers, both in the kernel's span walk.

1. **Ranges as one document.** `(%tree-sitter-range-spans text lang ranges table
   keywords?)` parses the char `ranges` of `text` (a rope read in place, or a string) as one
   `lang` document and answers `[start end reported]` for `table`, in the outer text's char
   offsets, clipped to the ranges. std's `fontify-ranges` resolves the faces. This is what a
   host with no tree calls (a line lexer). Ranges are sorted and merged. A missing grammar
   answers nil (std: `()`), never an error: an embedded language's grammar is optional.
2. **Declared injections for a tree-sitter host.** `%tree-sitter-spans`,
   `%tree-sitter-tree-spans` and `%tree-sitter-tree-changes` take an optional INJECTION SPEC
   (std: the optional last argument of `fontify`, `fontify-tree`, `tree-changes`):

   ```
   {:rules [{:content {:kind :quoted_content :parent :sigil}
             :lang-from :sigil_name :aliases {"H" :heex}}
            {:content {:kind :template_literal :parent :heredoc_template} :lang :bash}]
    :faces {:heex heex-table :bash bash-table}}
   ```

   `:content` is a face-table selector (ADR-486/487). A rule names its language with `:lang`,
   or with `:lang-from`: a node kind found among the content's siblings (else its children),
   whose text's first word (letters, digits, `_ - + #`) names it, through `:aliases` or
   lowercased as it is. `:faces` gives each injected language its face table.
   - **A parent's matching children are one document.** A heredoc split by `${…}` or `#{…}`
     interpolations is several content nodes under one parent, and they parse together.
     Different parents are different documents: two fences never share a parse, and an
     error in one stays in it. (Neovim's `injection.combined` joins every match in the
     file. That is not what a fence or a sigil means.)
   - **Over a document's pieces, the host's spans give way.** They are cut out of the host's
     spans, and the injected spans, clipped to the pieces, go in. Between the pieces (an
     interpolation) the host's colours stay. A document whose language has no table in
     `:faces`, or no grammar, keeps the host's colours. The table also gates the open
     `:lang-from` word: `~r` is not handed to an `r` grammar unless someone gave `:r` a
     table.
   - **The walk.** A second walk runs from the root only when a spec has rules. At each node
     it tests every child against the rules, so pieces outside the window still join their
     document. It enters only children that matched nothing and reach the window. A matched
     child is not entered, so injections do not nest (HEEx inside a fence is HEEx's own
     business, and stays uncoloured).
   - **Windowed and held-tree paths.** The text and held-tree paths share the walk and the
     splice, so they agree; a window's spans equal the whole text's clipped to it (tested).
     **Injected trees are not held.** Each call parses the documents that reach its window,
     using the outer text in place, with no copy. The cost is a parse of each visible
     embedded document per frame: a frame showing three 2 KB fences parses 6 KB of embedded
     code. That is cheap next to the host parse a held tree saves, and holding a tree per
     document would need the host tree's edit log mapped into every document. That mapping
     is the next step if a large embedded document shows up in a profile. Nothing here was
     measured.
   - **Bounded.** A document over 32 KB is cut to the window. Its colouring then loses what
     lies above the window, like a windowed fontify without a held tree, and without a
     window it keeps the host's colours. At most 128 KB of embedded text, 64 documents and
     256 pieces per document are parsed per call. `%tree-sitter-range-spans` drops ranges
     past 256 or 128 KB. A pathological file costs at most that per frame.
   - **Changes.** Typing a quote inside a fence can recolour the fence below the edit. The
     host tree's changed ranges cannot report that, because the host's syntax did not
     change. With a spec, `%tree-sitter-tree-changes` widens each changed range over the
     embedded documents it reaches, whole, so a band cache keyed on it drops the right
     bands. An edit to what names a document's language (a fence's info string) reaches the
     document's parent, so it widens too.
   - `injection-problems` validates a spec: rule shape, a valid selector, exactly one of
     `:lang` / `:lang-from`, `:aliases` shape, a fixed or aliased language with no table, and
     each table's own problems. The kernel refuses a malformed spec at the call.

**Rejected.** *Tree-sitter injection queries (`injections.scm`).* ADR-486's reasons apply: a
query compiled per grammar, and policy written as a source string instead of data. Selectors
already name the nodes. *Splicing in Brood.* The host spans would have to cross into Brood
with byte offsets, or be converted twice. The walk already holds both trees and the
splice is a merge of sorted intervals. *Holding injected trees.* See above: the cost of
re-parsing visible embedded documents is bounded, and the edit mapping is real work with no
measured need yet. *Injected spans layered over the host's (Neovim's highlight stacking).*
Spans here are a flat list a view paints once, so a layer would be an overlap every consumer
must resolve. Replacing is the documented contract.

**Callers.** bedit: Markdown fences (its line lexer calls `fontify-ranges`), Elixir `~H`,
Terraform/HCL heredocs and Dockerfile `RUN` lines. Nothing else in the tree calls it yet.
std's `markdown` renders fenced code unhighlighted, and its `->html` is the natural second
caller of `fontify-ranges`. It versions with the kernel: included ranges are the parser's, and the walk that finds
the content nodes is the kernel's span walk (question 3 of bedit's CLAUDE.md).

**Consequences.** Guards are in `tests/treesit_module_test.blsp`. With the built-in Ruby and
Elixir grammars: ranges with a gap parse as one Ruby document (a string across the gap, where
the second range alone reads `def` as a keyword); offsets are the outer text's; a rope equals
a string; unsorted ranges are merged; a missing grammar is nil and `()`. A pooled parser
comes back without the ranges (sabotaged red). Ruby inside an Elixir `~R` sigil (`:lang-from`
+ `:aliases`) and inside an interpolated heredoc (two pieces, one method across them;
sabotaged red by one document per piece). A missing grammar or table keeps the host's spans.
Held-tree spans equal text spans over the file and three windows, one of them ending before a
document's later pieces (sabotaged red by stopping at the window). `fontify` and
`fontify-tree` resolve injected faces. `tree-changes` widens an edit inside the sigil to its
body. A 40 KB heredoc keeps the host colour on the text path and is cut to a window on the
tree path. Eight processes injecting at once agree. A malformed spec is refused by the kernel
and named by `injection-problems`. With installed HCL and Python grammars: an HCL `<<-PY`
heredoc as Python, its string spanning the `${…}` interpolation.

## ADR-490 — Input before background: mailbox lanes, a fold budget, a watchdog

**Status:** implemented (2026-10-27).

**Context.** bedit froze, no scrolling and no clicking, while a language server indexed a
project. The server's connection process sent the editor one message per log line and per
diagnostic, hundreds a second. bedit batched that producer, but the cause is structural:
`gui-display`'s `:poll` was `(receive (m m) …)`, so the user's keys and every background
message share ONE FIFO mailbox, and `ui-drain-input` folded up to 1024 queued messages per
render with no regard for time. Any chatty producer (a test stream, git replies, collab, a
debugger trace) put the user's next key behind its whole backlog, and every background
message also counted as input, so an idle timer never fired during a flood.

**Decision.** Five parts.

1. **Mailbox lanes, in the kernel.** An envelope carries a lane.
   - `proc/send-priority` (and everything a window or a browser tab delivers:
     `host/gui/backend.rs` imports the priority delivery under the names it always used,
     `host/tab.rs` its one call) queues on the PRIORITY lane. `proc/take-priority` takes the
     oldest priority message as `[msg]`, or nil at once, without rebuilding a single
     ordinary message it passes; O(1) in a mailbox that holds none (`priority_queued`, an
     exact count kept by every push, removal and re-insert — at first an upper bound only
     `take-priority` lowered, so a loop that read its priority input with a plain `receive`
     made every later `take-priority` walk the queue). `proc/receive-lane ms` is `(receive (m m) (after ms nil))` answering
     `[msg :priority]` / `[msg :normal]`: a loop that parked learns whether the user woke it.
   - `proc/send-latest target key msg` queues on a LATEST lane: a newer message with the
     same key (compared by its printed form) removes the queued older one at delivery and
     queues at the back. A receive never hands over a LATEST message superseded while it was
     out of the queue for a pattern check: for a LATEST candidate only, the scan asks whether
     a newer copy of its key is queued before handing it over or putting it back, and drops
     it if so — an ordinary message pays only the lane test. Both questions are answered by an
     index of the queued LATEST envelopes by key (`latest_queued`, the seq of the one per
     key): the superseded one is found by a binary search on the seq-ordered queue, so a
     `send-latest` — which a peer can make over a link (ADR-492) — no longer walks the
     receiver's backlog under its lock.
   - A lane survives a locally registered name (`:editor`, or a `{:name :node}` address
     naming this node): it resolves to the local pid. A remote or dead target gets a plain
     `send`; lanes do not cross nodes. LATEST messages skip the L1 copy into a parked
     receiver's heap, so a delivery that supersedes one drops it without touching that heap.
   - *Why the kernel, not `ui-run`:* input cannot be told apart by shape (a key is any
     string or keyword, as are some background messages), and a Brood-level selective
     receive that tests types runs the matcher closure, with no tag prefilter, over every
     queued message: it rebuilds the backlog into the heap on every poll, O(backlog²) through
     a flood. The lane is decided where the message is MADE and costs one field per
     envelope. Conflation in the kernel bounds the QUEUE (memory, and the scan of every
     selective receive behind it), not just the folds, and serves any consumer — a REPL's
     output, the observer, a stream; a `ui-run`-only envelope would still queue every stale
     copy.
2. **Input first, defined once per frontend.** A display has two more entries.
   `:poll-input` answers the next queued user input or nil without waiting; `:poll-tagged`
   answers the OLDEST message of any kind, waiting up to `ms`, as `[message input?]`.
   `gui-display` takes its priority lane (motion coalesced) and parks on `proc/receive-lane`;
   `*term-display*` asks its keyboard (everything it returns is input); `display-broadcast`
   asks every member's queued input before any member's slice; `with-events` tags a pushed
   event as background; `editor/serve`'s remote displays take the client's `[:key …]`,
   `[:detach]` and death (all tag-led, so the scan skips a backlog by its tags). `:poll`
   keeps its meaning (`:poll-tagged` without the tag). A std display builds its polls with
   `display-polls`, which marks the `:poll` its `:poll-tagged` agrees with
   (`:poll-tagged-of`): `display-poll-tagged` asks `:poll-tagged` only while that is still
   the display's `:poll`, so the old wrapping idiom — `(assoc display :poll …)` to see a
   message first — is not silently bypassed. `ui-run` asks `display-poll-input`
   first, then parks on `display-poll-tagged`. A display with neither entry behaves as
   before; one with `:poll-input` and no `:poll-tagged` has what its `:poll` returns
   counted as background.
3. **A fold budget, and fairness.** A `:coalesce-input?` turn folds background only for
   `*ui-fold-budget-ms*` (8, the model's `:fold-budget-ms`), then renders and looks again.
   Half a 60 Hz frame: a flood shows its progress every frame or two, and a key typed into
   it waits about one budget plus one fold. Each drain step asks for input first and always
   folds it; once an input is folded the turn takes no more background, so its frame is
   next — except ONE arrival-order fold per turn, which keeps background moving while input
   never stops. Past the deadline even input waits for the render. A message the drain folds
   keeps its poll's tag: from a display that cannot tell input apart every message is the
   user's, so no background ceiling (ADR-491) stops the second key of a burst. A
   non-coalescing app keeps its documented once-per-input render, so its turn folds one message and needs no
   budget; its fairness is that a turn after one whose input jumped the queue takes the
   oldest message instead. `*ui-input-batch*` stays the ceiling; a due timer fires on every
   turn.
4. **Only input holds idle timers back.** A turn stamps `:last-input` only when it folded
   USER input (what `:poll-input` gave, a `:poll-tagged` result tagged input, or input the
   drain took). An idle beat therefore fires during a flood of background replies. A display
   that cannot tell (no `:poll-input`) keeps stamping on every message, as before.
5. **A watchdog.** An `update` fold or a `view` slower than `*ui-slow-ms*` (50, the model's
   `:slow-ms`) is reported as `{:phase :tag :ms}` to the model's `:on-slow` `(fn (report)
   …)`, or as one stderr line. `ui-input-tag` names the input without printing it: a key as
   itself, a vector by its leading keyword (and the second, when that is one too: `[:timer
   :idle]`), a record by its id. A slow view is reported at most every
   `*ui-slow-view-quiet-ms*` (5 s), since an app that logs the report into its model makes
   the next (slow) frame, and a slow update at most every `*ui-slow-update-quiet-ms*` (1 s,
   kept in a table bound for the loop's life): a stream of folds each just over the line
   reported once per fold. An interrupted one (ADR-491) is always reported.

**Also in this change.** `ui-coalesce-motion` matched only the 6-element mouse shape, and a
window adds the pointer's `{:at …}` after a nil 7th slot, so a window's drag was never
coalesced: every cell crossed cost a fold and a frame ahead of the next key. It matches all
three shapes now. The thin client ships its window's queued input before painting the
daemon's frames; the terminal client polls its keyboard first and draws only the newest of
the frames queued (a frame is the whole screen).

**Not done.** The window client still paints every queued frame: frames interleave with
texture and sound messages a later frame may depend on, so skipping one is not safe without
an ordering the protocol does not carry. A `view` has no budget — it is reported by the
watchdog, not bounded. A lane does not cross a node link.

**Tests.** `tests/ui_test.blsp`: a key after 5000 background messages folds first,
coalescing or not; inputs keep their order; background finishes under self-feeding input,
coalescing or not; an idle timer fires during a self-feeding flood, coalescing or not; a zero
budget renders per fold and a large one once; newest-wins keeps one per key and every unkeyed
message, through a registered name and a `{:name :node}` address too, and never hands over a
message superseded mid-match (optimistic and in-place candidates); both watchdogs, with their
tags and the view's rate limit; a window's motion with `{:at …}` coalesces.
`tests/serve_test.blsp`: the window client ships a queued key before painting 50 queued
frames. The `proc/*` docstring examples, and the mailbox unit tests (replacement keeps seq
order and the park gate's `scanned`; the lane bookkeeping — the PRIORITY count and the
LATEST index — stays exact through a plain receive's consume, a candidate out and back, a
supersession and a clear). The supersession and idle-timer guards were sabotaged red. Later:
a display without `:poll-input` folds a burst's slow second key unstopped by the ceiling; a
run of slow updates is reported once, an interrupted one still; a `:poll` replaced over a
`display-polls` display is the one asked, and `with-events` over one still sees its events
first (each red before its fix).

## ADR-491 — Quit: interrupting a running process at its next safepoint

**Status:** implemented (2026-10-27).

**Context.** After ADR-490 a key never waits behind background MESSAGES, but `update` and
`view` still run in the one loop process: one fold or one view that takes seconds (a
tree-sitter parse of a large file, a runaway loop in a command, a reply whose fold is
quadratic) freezes the editor, and nothing can stop it. Emacs has had the answer since the
start: `quit-char` sets `quit-flag`, and the next `QUIT` check signals `quit` wherever the
code is. Brood had a safepoint at every tier already (the reduction rollover, where
preemption, the mailbox bound and a hard `:kill` are checked) and an `(exit pid :kill)` that
uses it, but no way to stop a computation without killing its process.

**Decision.** An interrupt is a catchable error raised at the target's next safepoint.

1. **The interrupt window.** `(proc/interruptible ceiling-ms thunk)` runs `thunk` in the
   calling process's window and answers `[:ok value]` or `[:interrupted e]` (`e` what a
   `catch` would bind); any other error propagates. Only inside an open window can an
   interrupt land. The window, not "time since the process last left `receive`", is what
   the kernel measures: a stamp at every receive is reset by each `gen/call` a fold makes,
   so a slow fold that makes calls would never look busy; and an interrupt landing in a
   loop's own glue — between its receive and the fold — would crash the loop. No Brood code
   sits between a raise and the window closing. A window opened inside an open one is a
   plain call: the outer owns the interrupt and its ceiling. (The first cut was an
   `allow`/`inhibit` pair the caller placed inside its own `try`; the sticky rule below made
   its handler a place a re-raise could land, so it went.)

   **A REGION on the VM's own frame stack.** The bytecode driver does not call the builtin
   for a VM thunk: it runs the call as an interrupt region, a handler kind beside the inline
   `try` (ADR-400) on the process's `vm_handlers`, and pushes the thunk's frame as an
   ordinary call (`ChunkExit::Interruptible`). The thunk returning to the frame that opened
   the region closes it with `[:ok v]`; the driver's catch takes the interrupt there as
   `[:interrupted e]`, closing the window BEFORE the catch is noted, so the sticky re-raise
   is not armed; any other error, and every error at a region inside an outer window,
   passes through, closing what it owns; a driver left by an error or a kill closes the
   window of every region it drops. A region in tail position returns its answer from the
   caller's frame. It is found by its frame's INDEX, not its base: a frame with no slots
   and an empty operand stack shares its base with the frame it calls. Since nothing native
   sits under the thunk, a `receive` in an `update` or a `view` PARKS the process — run
   nested under the builtin, as at first, it blocked the worker thread. The JIT subset
   fences a call of `proc/interruptible` out (a native caller would run it nested). The
   builtin remains for every other path — the tree-walker, `apply`, a native or
   tree-walked thunk — where a `receive` blocks as any native-nested one does; there it
   never suspends (a nested driver does not capture), so the window is never closed and
   the thunk re-run by a replay.
2. **Three sources.** `(proc/interrupt pid)` from another process; the window's own
   CEILING (a per-process deadline the safepoint compares the clock against, so a process
   interrupts itself with no timer process); and the QUIT KEY.
3. **The quit key.** `(proc/set-quit-key key busy-ms)`, Emacs's `quit-char`, requests an
   interrupt when its message arrives while the owner is running in a window open for at
   least `busy-ms`. Two shapes, both compared at delivery under the mailbox lock it already
   holds, without a heap: an ATOM (keyword, string or integer — a key as a window or the
   terminal delivers it) matched on the PRIORITY lane only, where the frontend says it is
   input; and a VECTOR of atoms matched as the head of a vector message on ANY lane — a key
   as a wire frontend ships it (`[:key :ctrl-g …]` from a thin client), since lanes do not
   cross a node link and the message's own tag says it is input, as ADR-490's
   `:poll-tagged` reads it. With no quit key a delivery pays nothing. The message is
   QUEUED AS WELL as interrupting: it is never lost (a C-g that lands as the turn finishes
   is still an ordinary C-g), and the app folds it next, which is where its own
   keyboard-quit runs, as Emacs's quit leaves you at top level. A key DELIVERED FROM
   ANOTHER NODE (lanes cross a link since ADR-492, so an atom can too) counts only from the
   node of the pid given as `proc/set-quit-key`'s optional third argument — the client a
   served loop serves, which `ui-run` takes from the display's `:quit-from` and
   `remote-display` sets — or, with none given, from a full peer, never a GUEST link
   (ADR-415): a guest whose grant reaches a loop's pid must not stop its turn unless it is
   that loop's own client. A link's reader marks what it delivers with its origin in a
   thread-local (`interrupt::delivering_from`), so no envelope carries a field for it.
4. **A parked process is not running.** A request against a process blocked in `receive`
   (status `WAITING`) is a no-op that answers false and latches nothing, so it cannot fire
   later at a point nobody chose. A ceiling is checked only when the process runs.
5. **The error, and why it is sticky.** It is `ErrorKind::Interrupted` —
   `{:kind :interrupted :code "E0047" …}` to a `catch`, `interrupted: quit` (or `… the
   interrupt window's ceiling passed`) uncaught — and `try` sees it like any error: no new
   syntax, not a control signal. But Emacs's `condition-case` on `error` does not catch
   `quit`, and a Brood `catch` catches everything, so a catch-all inside the interrupted
   work would swallow it. So the interrupt is STICKY: once raised it stays raised until the
   window closes, and a `catch` that binds it (`Heap::note_caught`, every engine's catch
   path) ends the quantum, so the first safepoint after the handler raises it again. A
   catch-all only delays it by one handler; a raise inside a handler propagates outward.
   Immutability is what makes stopping safe at all — the code it stops was building new
   values, never changing old ones, so nothing is left half-written.
6. **Where it is checked — no new per-iteration cost.** The probe is one thread-local
   borrow and a relaxed load of the window's flag word, made where the once-per-quantum
   checks already are: the VM driver's loop top and an inline loop's back edge
   (`quantum_checks`), the capturing tree-walker's driver safepoint, the nested tree-walker's
   and passthrough tick (`tick_nested`, which replaced `tick_reporting_hard_kill`), and a
   native activation's poll on rollover, which LEAVES for the interpreter with the budget
   spent so the interpreter's next safepoint raises it. The root thread's native poll used to
   charge nothing; it now charges its budget and checks on rollover, or a JIT'd loop on the
   root could never be stopped. The clock is read only while a ceiling is armed. Latency: one
   quantum, about a millisecond of work. A pending hard `:kill` is checked FIRST at a quantum
   boundary: an interrupt raised ahead of it would run the interrupted code's handlers —
   the window's close and what follows it — before an untrappable kill.
7. **Builtins.** A builtin that calls Brood per element (`fold`, a comparator, a key fn) is
   interrupted at the callback's own nested safepoint and unwinds through the builtin. A
   builtin that iterates natively over a large input polls (`eval::InterruptPoll`: a
   counter decrement per item, the probe every 4096): `sort` without a callback (sorted in
   64K-item chunks with a probe between, then once more, which the standard sort merges as
   runs — no comparison pays for it; a small input is one plain sort), `string/split`,
   `%string-join`, `string/->codepoints`, `%codepoints->string`, `string/->graphemes`, the
   regex scans (`%regex-find-all` per match, `%regex-tokens` per token, the longest-match
   walk per window), the rope scans (`%rope-find` per leaf, `%rope-rfind` per 64K slice,
   `%rope-skip` per character), the plain JSON encoder per value (`json/decode` is Brood),
   `%diff-line-hunks` (the Myers search gives up as at its cost limit and the builtin raises),
   `%ui-harvest` per op, and a tree-sitter parse through its progress callback (a pooled
   parser is `reset` on return so a cancelled parse never resumes), the case maps
   (`string/upper`/`lower` a 4 KB piece at a time — a string holding a `Σ`, whose final form
   depends on its neighbours, is cut only after ASCII whitespace, so the answer is the whole
   string's), `string/normalize` per character, `%str-index-of` / `%str-last-index-of` in
   16 KB windows, the gzip / zlib / deflate / brotli coders in 64 KB pieces each way, and
   `%digest` / `%hmac` in 64 KB pieces with `%pbkdf2-sha256-bytes` per iteration. Rope
   EDITS need nothing: ropey's insert and remove are tree edits, O(log n) plus the text
   inserted. A regex search cannot be cancelled — regex-automata has none — but it is
   bounded: no backtracking, `meta`'s caps (a 10 MiB NFA, a 2 MiB lazy-DFA cache), one
   lazy-DFA pass or, past the cache, one Pike-VM pass at O(pattern × text). What the crate
   does offer is a search confined to a byte range (`Input::range`, look-around still seeing
   the whole text), so a pattern whose matches have a bounded length (read from its parse
   when it is compiled) is searched in 64 KB windows with a poll between; an unbounded one
   (`a+`) remains one search.
8. **`ui-run`.** It arms the quit key (`*ui-quit-key*`, `:ctrl-g` — what a window and the
   terminal deliver for C-g; the model's `:quit-key`, nil for none) with `*ui-quit-busy-ms*`
   (300, the model's `:quit-busy-ms`), in the shape the display ships keys in (its
   `:quit-message`; a served session's is `[:key k]`), and runs each `update`, and each
   `view` with its harvest, in a window. An interrupted `update` drops its input and keeps
   the previous model; an interrupted `view` keeps the last frame on screen, and the loop
   goes on to fold the C-g. The fold of a BACKGROUND message (a reply, a timer — anything not
   user input) runs under a ceiling, `*ui-event-ceiling-ms*` (2000, the model's
   `:event-ceiling-ms`, nil for none): no user asked for that work, so nobody is there to
   press C-g. A user's own command is never stopped by a ceiling — only C-g stops it, as in
   Emacs. Either is reported through the watchdog: `{:phase :tag :ms :input :interrupted
   true}`, `:input` true when the fold was the user's input (what came on the priority lane,
   or what `:poll-tagged` called input) — an editor says "Quit" for an interrupted INPUT turn
   only, and a tag cannot tell `:up` from `:lsp-diagnostics`. A view's report is `:input
   true`: only the quit key stops one. Without a hook: `ui-run: interrupted update 2000.4ms on
   :lsp-diagnostics`. An interrupted view's model never rendered, so it is not the
   rollback point: the loop's `last-good` stays the last model on screen.
9. **The terminal and served sessions.** `*term-display*` reads its keys in the loop
   process, so mid-turn nobody read the C-g. Now its `:enter` starts a reader thread
   (`term/forward-input`) that delivers every key and mouse event to the loop's priority
   lane, as a window does, and the terminal polls the mailbox like the window — input first,
   background tagged as such (a terminal app now sees its background messages, as the same
   app in a window always did). A served session's remote and shared displays declare
   `:quit-message (fn (key) [:key key])`, so the daemon's kernel matches the thin client's
   `[:key :ctrl-g held?]` on the ordinary lane. Polling the whole mailbox means a loop sees
   messages a protocol inside the same process waited for: the remote observer
   (`observe-connect`) found its `[:nodedown]` and late replies folded as keys, so its
   `update` now takes them as the link's (a nodedown marks the link down, sticky; a late
   reply is dropped).
10. **The busy cursor.** After an input, a window asks every 100 ms whether the loop that
   takes its input has been in one window past its quit key's busy-ms
   (`process::interrupt_busy`), shows the wait cursor while it has — the C-g that would stop
   it is live — and puts the hover shape back when the turn ends. It stops asking once the
   loop is idle, so a window at rest never wakes for it. A THIN CLIENT's window feeds a loop
   on the daemon, which it cannot ask, so the served session asks for it: the display's
   `:enter` starts a watcher beside the loop, each input the loop takes kicks it
   (newest-wins), and it asks `(proc/busy? loop)` — true past busy-ms in one window, nil
   when idle — every 100 ms until the loop is idle, telling the client each change as
   `[:busy on]` with `proc/send-latest` (a shared session tells its hub, which tells every
   client). The client hands it to its display's `:busy`, which `gui-display` maps to
   `%gui-busy`: the window shows the wait cursor while its own loop or the remote one is
   busy. A terminal client drops it.

**Not done.** An unbounded regex pattern's one search, and windows do not nest beyond "the
outer one owns it" (both lifted by ADR-493). A `proc/interruptible` reached through
`apply`, from native code or the tree-walker still runs its thunk nested, where a `receive`

## ADR-492 — A thin window client paints its newest frame, and lanes cross a node link

**Status:** implemented (2026-10-27).

**Context.** ADR-490 left two limits. The window thin client (`editor/serve`'s
`attach-display-loop`) painted every frame its daemon had queued, because texture, sound
and window-option messages sit between frames and a later frame may use them; a daemon
that renders faster than a client paints left the window painting stale screens while
the user's next key waited. And `proc/send-priority` / `proc/send-latest` to a pid on
another node fell back to a plain `send`, so neither the priority lane nor newest-wins
reached a served client across its link.

**Decision.**

1. **The window client paints a backlog once.** A `[:frame f]` starts a drain that takes
   the daemon's queued messages without waiting (`attach-display-backlog`). It keeps the
   newest frame, `latest`, and the seam messages that came after it, `after`. A newer
   frame first applies `after`, then becomes `latest`. When the queue is empty the client
   ships the window's queued input (keys still go first, ADR-490), paints `latest`, then
   applies `after`. A `[:bye]` paints the backlog and ends.
2. **One-shot ops are carried.** Two frame ops act once, when their frame arrives, rather
   than painting state: `[:sound …]` plays and `[:burst …]` emits. Every other op,
   `[:music …]` and `[:emitter …]` included, is state the next frame restates.
   `editor/display/frame-one-shots` lists a frame's one-shots at any depth. A skipped
   frame's one-shots are appended to the frame that is painted — unless a seam message came
   after one still to play: then that frame is painted in its turn instead of skipped,
   because applying the message first (`[:sound-free S]` after a frame playing `S`, a
   texture freed that a burst uses) would play a freed or reused sound. The first cut
   applied `after` and carried the one-shots past it.
3. **Frames conflate at the source.** `remote-display`'s `:draw` and the shared hub send a
   frame with `proc/send-latest client :editor/serve/frame …`, so one queued frame for a
   client is replaced by the next, in the client node's mailbox once lanes cross the link
   (part 4). A frame with a one-shot op goes as a plain `send`, which nothing supersedes.
4. **Lanes cross the link.** A send in the priority or latest lane is a new frame,
   `FRAME_SEND_LANE`: `Send`'s fields followed by a lane byte, and for latest the key's
   printed form. A normal send stays the `FRAME_SEND` every version knows. `Lane` is made
   crate-visible. `send_in_lane` routes a remote target through `dist::route_in_lane`,
   and the receiving node delivers with `process::deliver_in_lane`, queueing exactly as a
   local send does. A dead local target or an unregistered name drops the message, as
   `send` does.
5. **Frames conflate in the link's writer queue too.** A link's writer thread drains a
   bounded queue of encoded frames. A `send-latest` puts its payload in the link's slot
   for that target and key and queues a ticket. A later one to the same slot replaces the
   payload and queues its own ticket at the back. The writer writes a ticket's payload
   only while it is still the newest for its slot, and passes over a replaced one. So a
   slow link writes one frame per key, in the order the mailbox would hold it. This
   happens on the sending side, whatever the peer speaks.

**The ordering argument.** Messages from one session reach the client in the order sent,
over one link or in one runtime. Let a backlog be `m1 … mn` and let `F` be its last frame.
Painting every frame in order applies each seam message at its position. The drain
applies the same seam messages in the same relative order. The only change is that the
paints of the frames before `F` are dropped, and a paint changes nothing a seam message
reads. So the state when `F` is painted is the state painting in order would have, which
gives three cases:
- A texture uploaded before `F` was applied before `F` is painted, because it preceded
  `F` or a frame that `F` superseded, and a superseding frame applies `after` first.
- A texture freed after `F` is in `after` and is freed only after the paint. The daemon
  sent that free once `F` was drawn, so `F` may still use the texture.
- A texture freed between two skipped frames was freed when painting in order would free
  it. A later frame cannot use it unless the daemon uploads it again, and that upload is
  also applied in order.

The skipped frames' one-shots are the only effects a dropped paint loses, and part 2 puts
them back.

Source conflation keeps this. `send-latest` removes the older frame and queues the new one
at the back, behind every seam message sent since. That is the order the daemon sent them
in, and the order the client's own drain would have applied them.

**Protocol versioning: v11, and v10 peers keep linking.** The dist protocol versions by
its magic byte (`wire.rs`'s history), and until now every bump made the versions refuse
each other. This one does not strand older nodes. A v11 node advertises lanes with the
magic `b"BRD\x0b"` and still speaks v10 (`b"BRD\x0a"`), and the magic step is the
capability exchange (`handshake::agree_version`):
- A v11 **responder** reads the dialer's magic before writing its own, and answers in the
  dialer's version. A v10 dialer, which writes its magic and then requires the reply to
  equal it, hears v10.
- A v11 **dialer** offers v11. A v10 responder writes its own magic before reading, so the
  dialer hears v10 while the responder refuses v11 and closes. The dialer then redials
  offering v10 (`node_connect`). This costs one extra connection, only to an old node.
- The link records whether both ends speak v11 (`Conn::lanes`). On a v10 link, a
  priority or latest send goes as the plain `FRAME_SEND`, so the bytes are exactly what a
  v10 node writes, as before ADR-492.

The magic is not under the MAC, so an on-path attacker can force a link down to v10. That
costs only the lanes: the handshake after the magic is unchanged and authenticated.

Guest cookies (ADR-415) needed no wire change: the responder tries each grant's cookie
against the MAC. Lanes need a signal, and the alternatives were worse:
- `Hello` is strict about trailing bytes, so a field there breaks a v10 peer.
- A post-handshake capability message would leave the first sends racing it.
- Writing an unknown frame tag to a v10 reader tears the link down.

`BROOD_DIST_V10=1` makes a runtime speak exactly v10 (its magic written first, only v10
accepted, plain sends only), which is the old peer the mixed-version tests run.
**Costs.** The daemon walks each frame once in Brood (`frame-one-shots`) to decide how
to send it, which is O(ops) per frame. Nothing was measured. A drain's selective receive
uses an `or` pattern, so it has no tag prefilter; the client's mailbox holds window input
and daemon messages, not a background flood.

**Not done.** The terminal client (`attach-drain`) still ignores seam messages; a
terminal cannot show them anyway. A `view` still has no budget (ADR-490).

**Tests.** `tests/serve_test.blsp`:
- A backlog of 20 frames with interleaved texture uploads paints once, the newest frame,
  after every upload.
- A texture freed after the newest frame is freed after its paint, and one freed before
  it is freed before.
- A skipped frame's `[:sound …]` and nested `[:burst …]` ride on the painted frame, and
  its `[:music …]` does not.
- A key queued behind a backlog ships before the paint.
- A skipped frame's `[:sound 4 …]` followed by `[:sound-free 4]` is painted before the free
  is applied (red when the free was applied first and the sound carried past it).
- `remote-display` supersedes a queued plain frame, and keeps one with a sound, in order
  with a texture.

Painting every frame turns the four client tests red.

`crates/cli/tests/distribution.rs`, each with two runtimes:
- A remote `proc/send-priority` (by `{:name :node}`) is taken by `proc/take-priority`
  ahead of earlier plain messages.
- A remote `proc/send-latest` (by pid, then by name) replaces the queued one and queues
  at the back.
- A v11 node dials a v10 node (`BROOD_DIST_V10`), and a v10 node dials a v11 node. Plain,
  priority and latest sends cross in both directions and all arrive. Without the
  dialer's v10 redial, the first of these is red.

`dist` unit tests:
- The magic agrees v11, v10, or tells a v11 dialer to redial, for every pairing.
- A lane reaches the wire to a v11 peer, and becomes a plain `Send` to a v10 one.
- A `send-latest` replaces its unwritten frame in the writer queue, its replacement
  written after what was queued before it, while another target's slot, a plain frame
  and an already-written slot are left alone.

`wire_tests`: every lane round-trips, a normal send is v10's `FRAME_SEND` byte for byte,
and an unknown lane tag is refused. Docstring examples for `frame-one-shots`.

## ADR-493 — Interrupts reach every regex search, and interrupt windows nest

**Status:** implemented (2026-10-28).

**Context.** ADR-491 left two limits. An UNBOUNDED regex pattern (`a+`, `.*`, `zq.*`) over
a large text was one `meta` search: regex-automata has no cancellation, and ADR-491's
windows (`Input::range`) are sound only for a pattern whose matches have a bounded length —
a match starting in one window may end anywhere, and a later match inside the window would
be taken for the leftmost (`a+b|c` over `aaa…c…b`). And a window opened inside an open one
was a plain call: the outer window owned the interrupt. So a command that ran its own
`proc/interruptible` inside a `ui-run` turn never saw C-g — the turn did — and an inner
window could not keep its own ceiling.

**Decision.**

1. **An unbounded pattern is STEPPED.** The lazy DFA under `meta` is a state machine
   regex-automata lets a caller drive (`next_state` per byte, `start_state_forward`,
   `next_eoi_state`), so over a text longer than a window (64 KB) the search loop is ours
   (`regex_native::find_stepped`): forward to the match's end, backward from it to its start
   (`hybrid::regex`'s own two passes), the DFA's state carried across an `InterruptPoll`
   every window. It is `hybrid`'s `find_fwd` / `find_rev` minus the loop unrolling, with the
   same match delay, look-ahead past a range's end, look-behind before it, and `meta`'s
   rule for an empty match inside a character (skipped). A leftmost-first search carries
   the prefix prefilter `meta` would use (`Prefilter::from_hirs_prefix`, only when
   `is_fast`): in a start state with nothing found it jumps to the next candidate, never
   past the window's end, so a stretch with no candidate still polls. Every search goes
   through `find_polled` — bounded patterns in windows, unbounded ones stepped, a short text
   one `meta` search — including the lexer's multi-pattern `any_rule` and the anchored
   longest-match walk (`longest_at`, which `%regex-tokens` and `%regex-paint` run).
   - **What it costs.** Nothing when no interrupt is pending: the poll is a counter, the
     probe once per 64 KB. The stepped loop itself is `hybrid`'s without unrolling or
     `meta`'s other engines, so a long unbounded search runs the lazy DFA where `meta`
     might have run it unrolled — slower per byte by a constant, linear as before; a text
     under a window and every bounded pattern take the paths they took. The DFA is built
     the first time a pattern is stepped (`OnceLock`, NFA capped at `meta`'s 10 MiB, no
     capture states) and its search caches are pooled on the pattern, so `find-all` does
     not rebuild the DFA per match. It never gives up on a full cache
     (`minimum_cache_clear_count(None)`): a cache cleared again and again is slow, not
     wrong, and the poll still runs.
   - **Groups** are found by a second search anchored at the match and confined to it:
     the match is the highest-priority one starting there, so the confinement changes
     neither it nor its groups (`meta`'s own `search_captures` also finds the match first).
     A pattern with no groups of its own skips that pass.
   - **Where no DFA can go, a Pike VM of ours.** A lazy DFA cannot decide a Unicode `\b`:
     before non-ASCII text it QUITS, and `meta` would fall back to its Pike VM — one
     uncancellable search. The capture engines (`meta`'s Pike VM, bounded backtracker,
     one-pass DFA) have no step API either, and none can be resumed across `Input::range`
     windows: their thread lists live inside one call. But the Thompson NFA they all run is
     public data (`thompson::NFA::state`, `LookMatcher::matches`), so `regex_native::
     pike_search` simulates it in a loop of ours, `pikevm::search_imp` line for line — the
     same epsilon closure, thread priority, capture slots and slot restore — ticking the
     poll once per position. It takes the two cases that were left: a search the lazy DFA
     quit on (`find_pike`, and the anchored longest walk with `all`), and the groups of a
     match longer than a window (anchored at the match, confined to it). A shorter match
     keeps `meta`'s capture engines, which are faster (one-pass, backtracker). The NFA is
     built once per pattern, lazily, with every group, and used only when its slot layout
     is `meta`'s. Its cost is the Pike VM's, O(pattern × text), which is what `meta` paid
     in exactly these cases.
   - **Not a backtracker.** There is no catastrophic-backtracking pattern to stop: the
     engine is automata only.

2. **Windows nest; the innermost window that is catching gets the interrupt.** Emacs's
   `with-local-quit`: a quit is handled by the nearest code that asked to handle it, and a
   quit it handled is gone. Each open window has a DEPTH (1 the outermost; `proc/
   interruptible` opens one whatever is open already), and an interrupt is raised FOR one:
   - a REQUEST (`proc/interrupt`, the quit key) for the innermost window open when the
     safepoint raises it — the work nearest the user that chose to be stoppable;
   - a CEILING for the window it is the ceiling of: that window's budget ran out, not the
     inner one's. The kernel arms the earliest ceiling of the open windows (the outermost
     on a tie).

   Only that window's `proc/interruptible` answers `[:interrupted e]`. A window inside it
   lets the error pass and closes (a region's catch path checks `interrupt_raised_for`
   before it catches; the builtin checks before it closes); a window outside it never sees
   it: closing the window an interrupt was raised for CONSUMES it, so the outer runs on
   until a request of its own or its own ceiling. Stickiness is per target: a `catch`
   inside an inner window that swallows an outer ceiling's interrupt is interrupted again,
   and the inner window passes it on. A request that LANDED but was not yet raised when an
   inner window closes stays for the windows still open (Emacs's `quit-flag` is handled by
   whatever checks it next); closing the OUTERMOST drops it, as ADR-491 had it. The busy
   threshold (`busy-ms`, `proc/busy?`, the busy cursor) counts from the OUTERMOST window's
   opening — the turn — not the innermost.

   The window stack is `Interrupt::windows` on the mailbox (each window's absolute
   deadline), touched only by the owning process — on open, close, and a request's raise —
   so its lock is never contended; the safepoint probe stays one relaxed load of the flag
   word. `HandlerKind::Region` carries its `window` depth instead of `owner`, and a driver
   left by an error or a kill closes the outermost region it drops, which closes every
   window inside it.

**Not done.** Nothing on the regex side: every search, and every group search past a
window, polls. A `proc/interruptible` reached through `apply`,
native code or the tree-walker still runs its thunk nested (ADR-491's remaining limit).

**Tests.** `crates/lisp/tests/interrupt.rs`: an unbounded search is stopped INSIDE — no
match over a megabyte (`a+z`), a match the whole megabyte long (`a+`), a prefilter that finds
nothing (`zq.*`), a lexer whose one rule never matches, a lexer token the whole text long; a
stepped search answers what one search does across window edges after multi-byte text (a
prefiltered literal, groups, an empty match, a `\b` the DFA quits on). Nesting, on the
bytecode region AND the tree-walker's builtin: an outer ceiling passes through an inner
window (the code after the inner call never runs); an inner ceiling is answered by the inner
window and the outer runs to its end; a catch-all inside the inner window cannot keep an
outer ceiling; and `proc/interrupt` from another process lands in the innermost window, the
outer runs on, and a second request stops the outer. `regex_native` unit tests: the stepped
search agrees with `meta` for nineteen patterns (empty, `\B` before `é`, `(?-u:\b)`, `\z`,
`(?m)^.+$`, …) over ten texts at every start, a multi-pattern search likewise, the anchored
longest match at every start and limit, and a prefiltered literal across a window edge.
`process/interrupt.rs`: a request is the innermost window's and closing it consumes it; an
outer ceiling is the outer's and survives the inner closing; an inner ceiling leaves the
outer unarmed; an unraised request outlives an inner window and not the outermost; busy
counts from the outermost window. The `proc/interruptible` docstring runs a nested example.
The Pike VM: `regex_native` unit tests check it against `meta` — the match and EVERY slot
for twenty-two patterns over ten texts at every start, and the anchored longest match at
every start and limit; `interrupt.rs` stops a Unicode `\b` search and a lexer over half a
megabyte of `é` inside, and a 100 000-character match answers its groups and a `\b` search
over non-ASCII text answers its match, as one search does.
## ADR-494 — A `receive` in an interrupt window parks on every path that can capture

**Status:** implemented (2026-10-28).

**Context.** ADR-491 ran `proc/interruptible` over a VM thunk as a REGION on the bytecode
driver's own frame stack, so a `receive` in a ui-run `update` parks the process. It left the
builtin for every other path, where the thunk runs nested under the builtin's Rust frame and
a `receive` in it BLOCKS the worker thread: the tree-walker (`BROOD_TIER=0`, which CI runs the
whole suite under), `(apply proc/interruptible …)` (the VM's `dispatch` unfolds the `apply`
and calls the builtin), and a call made under a native frame (a builtin's callback). A fourth
turned up in testing: a thin wrapper, `(fn (c t) (proc/interruptible c t))`, is a passthrough
(ADR-069), whose redirect calls the builtin directly. A blocked worker is not a deadlock —
since ADR-100 §7.4 it leaves the executors, its queue moves to a live peer, and when none is
left an overflow thread starts (Go's handoff, the BEAM's dirty schedulers) — but each waiter
then holds an OS thread and its reserved stack, a fleet of them grows the overflow pool
without bound, and it cannot migrate. ADR-491's own region test (256 processes parked in a
window, the dirty-receive count flat) was red under the tree-walker for exactly this reason:
223 blocks.

**Decision.** Park wherever the continuation can be captured; hand the worker off where it
cannot. No new mechanism: each capturing engine already has the frame shape.

1. **The tier-0 machine runs the call as a frame.** ADR-416 made the tree-walker's pending
   work a frame stack a capturing machine parks with, and `%try`/`%binding` frames on it. A
   call of `proc/interruptible` with a closure thunk is now one more
   (`KontKind::Interruptible { window }`): it opens a window — nested inside any open one,
   ADR-493 — and keeps its depth on the frame, enters the thunk, and the thunk's value
   answers `[:ok v]`. An interrupt raised for this window (`interrupt_raised_for`) closes it
   BEFORE the catch is noted (so the sticky re-raise is not armed) and answers
   `[:interrupted e]`; any other error — an outer window's interrupt, a kill — closes it and
   passes through, as the VM's region does. A park
   leaves the frames as they are, and the window lives on the process's mailbox, so it
   migrates with them. The machine unfolds `apply` before it looks for a frame native, so
   `apply` at tier 0 is covered too. Keeping the thunk on the capturing machine exposed a
   gap of ADR-416's: the machine rooted and redid only `%receive`, but `proc/receive-lane`
   (ADR-490) waits the same way and suspends too, which surfaced as an empty `runtime
   error:` — at tier 0 a top-level `(proc/receive-lane 50)` failed, and ui-run's terminal
   poll did once its window became a frame. It is now parked and redone like `%receive`
   (its redo is safe: it clears its lane flag first).
2. **The VM's region sees through `apply`.** `interruptible_region` unfolds `(apply
   proc/interruptible … list)` when the head IS that builtin (any other `apply` pays one flag
   read) and the list is not a lazy seq-view (realising one runs Brood, which `dispatch`
   does; that call stays nested). The JIT subset fences a chunk that reads
   `proc/interruptible` as a VALUE, as it fences one that calls it, so native code never
   applies it nested.
3. **A wrapper over it is entered, not elided.** `compute_passthrough` refuses a body whose
   head is `proc/interruptible`, so the wrapper's VM arm runs and its call is a region. The
   test is by symbol, at closure creation — no per-call cost — like the JIT's fence; an alias
   bound to the builtin under another name is still a passthrough and runs nested
   (amended by ADR-505: the redirect gate refuses the builtin under any name).
4. **Under a native frame it still blocks, and that is the handoff, not a bug.** A builtin's
   callback (`reduce`, a comparator) runs Brood under the builtin's Rust frame, which no engine
   can capture; a window opened there runs its thunk in a nested driver whose `receive`
   blocks. Making that park would mean resumable builtins — every higher-order native
   rewritten as a frame kind — the cost ADR-416 declined for `receive` itself, and a window
   inside a callback is no different from a bare `receive` inside one. So the §7.4 handoff
   serves it: the blocked worker leaves the executors, its queue moves, and nothing on the
   pool waits behind it. A closure with no VM arm above tier 0 runs nested for the same reason
   (the VM cannot hold a tree-walked frame).
5. **Interrupts reach a waiter on every path alike.** A waiting process, parked or blocked,
   has status `WAITING`, so a request against it answers false and latches nothing (ADR-491
   §4); once a message wakes it, a ceiling that passed meanwhile lands at its next safepoint,
   and so does a request. The blocked path's safepoints are the nested driver's and the
   tree-walker's ticks, which already probe the window.

**Rejected.** Waking a waiter on an interrupt (ADR-491 §4 chose not to: it would fire at a
point nobody chose). A replacement thread started eagerly per blocked worker: §7.4 already
starts one exactly when the last executor goes, and an eager one costs a thread every wait.

**Not done.** A window inside a builtin's callback, over a thunk the VM cannot run, or
reached through an alias of the builtin, still holds its thread while it waits (points 3, 4).

**Tests.** `crates/lisp/tests/interrupt_one_worker.rs`, its own binary with a pool of ONE
worker: a process waiting in a window — opened through a wrapper, through `apply`, and inside
a `reduce` callback — leaves the worker to another process, answers `[:ok :went]` once
released, takes a ceiling that passed while it waited once it runs, refuses `proc/interrupt`
while waiting and takes it once running. Through the wrapper and through `apply` the
dirty-receive count stays flat; under the callback it rises (so the test still covers the
blocking path). Barriers, not guessed delays: the program polls `proc/info`'s `:status` until
the waiter is `:waiting`. Both tiers pass. Sabotaged red: without the tier-0 frame, the wrapper
and `apply` cases under `BROOD_TIER=0` and ADR-491's region test (223 blocks); without the
`apply` unfolding, the `apply` case at the default tier; without the passthrough refusal, the
wrapper case at the default tier. The same binary: `proc/receive-lane` in a spawned process,
inside a window and outside one, answers its message and lane and blocks nothing (under
`BROOD_TIER=0` red without the redo: both processes died). `tests/ui_test.blsp`'s terminal
C-g test under `BROOD_TIER=0` was the find. `compile/tests.rs`: a chunk applying `proc/interruptible`
stays out of the JIT subset and the same chunk applying `vector` is in it (red with the value
fence off). After ADR-493, its nesting tests' tree-walker runs go through the frame, and
`windows_nest_across_the_frame_and_the_builtin` nests a builtin's window (in a `reduce`
callback) inside the engine's, both tiers: the inner ceiling is the inner's, the outer's
passes through it.

## ADR-495 — A tree handle is owned by a process, never evicted by another's

**Status:** implemented (2026-10-28). Amends ADR-443.

**Context.** ADR-443's tree handles lived in one runtime-wide registry capped at 32, least
recently used dropped first. The cap was the only thing that freed a forgotten handle, and it
made every holder's handle hostage to every other process's allocations:

- bedit keeps one handle per tree-sitter buffer. With more than ~32 such buffers open (or
  fewer, plus the trees its off-loop tasks open), the oldest were dropped silently: an edit
  in that buffer reparsed the whole file where it should have reparsed the edit, and a
  structural query fell back to parsing the text.
- `nest test` runs a file's tests in parallel processes in one runtime. "an edit inside an
  embedded document widens the tree's changes over all of it" opens a tree, updates it and
  asks what changed. When the other tests in the file had opened enough trees in between,
  its tree was the least recently used one, `update-tree` from the dropped handle was a
  fresh parse, and `tree-changes` answered `true` instead of `[[12 13]]`. It failed once
  and passed on rerun. The code shows no other way it could fail: the rest is
  deterministic.

**Decision.** A handle is owned, the way a socket, a child process and a wasm instance are
(`host/owned.rs`, the `OwnedTable` already behind those three).

1. `%tree-sitter-tree` and `%tree-sitter-tree-reparse` register the new handle to the
   CALLING process. A reparse's handle is the caller's, whoever owns the tree it started
   from.
2. A handle goes away only when it is freed (`%tree-sitter-tree-free`, any holder) or its
   owner exits. The retirement path frees a dead process's trees beside its sockets,
   children and wasm instances, before its `[:down …]`s are sent, so a monitor that sees the
   death sees the trees gone. There is no cap and no eviction: memory is bounded by what
   live processes hold, as with every other owned resource.
3. `%tree-sitter-tree-give tree pid` (std `editor/treesit/give-tree`) hands a handle to
   another LOCAL process. Only the owner can give it (anyone else gets an error), and a remote
   pid is an error, because a tree lives in this runtime. A tree given to a process that has
   died is freed and the call answers `false`. The owner is moved before the target's
   liveness is read, so the retirement sweep either runs after the move, and frees it, or
   has already run, and the call sees the dead target. A tree is never left on a corpse.
. `%tree-sitter-owned-trees` (std `editor/treesit/owned-trees`) lists the handles the
   calling process owns. Without a cap nothing reclaims a handle its holder lost track of:
   bedit's model is rolled back when a turn throws, and a tree that turn opened is named
   by nothing. The holder sweeps instead: at a quiet moment it frees every owned handle it
   no longer references. That is the holder's policy, so the kernel only answers the
   question.

**Consequence: a task gives its tree back.** A task that opens or reparses a tree off the
loop exits right after replying, and its tree goes with it. It must
`(editor/treesit/give-tree tree editor-pid)` before it replies. bedit's `treewarm` and
`syntaxtree`'s off-loop reparse are the two such tasks.

**Rejected.**
- *A GC-managed heap value with a finalizer* (a `Value::Tree` like `Value::Rope`). It would
  free a tree when nothing references it. But it is a new heap type through the GC, promote,
  freeze, message copy, JIT and printer, and Brood has no finalizers. Owner death gives the
  same guarantee: a crashed or forgetful holder cannot leak past its own life. It is also
  the model every other native resource already uses.
- *Keep the cap and make eviction observable.* A larger cap only moves the cliff. And no
  failure value helps when the code that pays for the eviction is not the code that caused
  it: one test, or one buffer, pays for another's allocations.
- *A per-process registry with no hand-off.* Off-loop parsing is the reason handles are
  sendable (bedit warms a 250 KB file's tree in a task), so ownership has to move.

**Tests.** `tests/treesit_module_test.blsp`, "tree handles are owned":
- A held tree outlives 40 trees opened by another process, and `update-tree` from it is
  incremental (`[[12 13]]`, not `true`). Under the LRU, 41 handles evict the first, so this
  fails every run, where the old flake needed an unlucky interleaving.
- When that process exits its 40 trees are gone and the held one is not.
- A task's tree dies with the task unless it gives the tree to the process it replies to.
- Only a tree's owner can give it away.

The Rust unit test `a_handle_survives_other_owners_and_dies_with_its_own` checks the same
at the host level: other owners, the close sweep, a refused give, and a give to a dead
process.

## ADR-496 — Injections: `:exclude`, and the line breaks between pieces

**Status:** implemented (2026-10-28). Extends ADR-489.

**Context.** Two defects in ADR-489's injected documents, both seen in a Dockerfile:

- *No way to leave a descendant out.* The Dockerfile grammar puts a `RUN <<EOT` line's
  `heredoc_marker` INSIDE the `shell_fragment` that bedit injects as bash. bash's faces
  replaced the host's `:heredoc_marker` colour, and bash, given a lone `<<EOT` with no
  body, parsed it as an `ERROR`. Tree-sitter's own injection queries handle this case with
  `injection.include-children` false.
- *Pieces lost their line breaks.* A document's pieces become tree-sitter's included ranges,
  and the parser reads nothing of a gap between two ranges. So two pieces separated by a
  newline were one line to it. Given `heredoc_line` nodes, which stop short of their `\n`,
  bash read `echo a` / `echo b` as `echo a echo b`: the second `echo` was an argument.

**Decision.**
1. A rule takes an optional `:exclude` selector: a kind keyword or a selector map, the same
   shape as `:content`. The content node's descendants it selects (the outermost ones; a
   selected node is not entered) are cut out of the document's pieces. They are not parsed
   as the embedded language and keep the host's colours. Their context (`:parent`,
   `:field`, `:nth`) is read as in the host tree, from the content node down. The kernel
   refuses a malformed one, and `editor/treesit/injection-problems` names it.
2. Between two consecutive pieces, the LAST line break of the gap is handed to the parser
   as a one-byte range. It is only parsed, never coloured: injected spans stay clipped to the
   pieces, so the break keeps the host's colour. This applies to every injected parse, so
   `%tree-sitter-range-spans` (a lexer host's fence lines) gets the same fix. Only the
   last break is passed, because one is enough to end the line, and a gap is otherwise
   foreign text.
   Byte offsets and points are the original text's throughout, so line and column numbers
   inside the embedded tree are the host's.

bedit's Dockerfile rules become
`{:content {:kind :shell_fragment :parent :shell_command} :exclude :heredoc_marker :lang :bash}`
and `{:content :heredoc_block :exclude :heredoc_end :lang :bash}`.

**Tests.** `tests/treesit_module_test.blsp`:
- "injections: :exclude and line breaks" runs on the built-in grammars. An Elixir string
  injected as Ruby keeps the host's colour over an excluded `#{x}`, and a misspelt
  `:exclude` selector is named.
- "injections: a Dockerfile heredoc as bash" uses the Dockerfile and bash grammars from
  `$BROOD_TEST_GRAMMARS`, else bedit's grammar directory, and is skipped without them. The
  grammars are loaded at file load, because a load moves the grammar epoch under any held
  tree.
  - `<<EOT` / `<<EOF` and the closing `EOT` keep the host's faces, no `ERROR` appears, and
    `> /x` is a redirect.
  - Heredoc lines given as separate pieces parse as lines. That test was red before this
    change: the second `echo` was a `:word`.

Rust unit tests cover the piece subtraction and the line-break join.

## ADR-497 — Ranking: the optimal alignment, paths, term operators, history, and narrowing

**Status:** implemented (2026-10-28).

**Context.** `std/fuzzy` ranked with a greedy left-to-right walk plus one contiguous-run
second try (ADR-357, ADR-375, ADR-429). bedit's user asked for what Emacs gives with vertico +
orderless + prescient: typing `foo somet` finds `foo-bar-something.txt` (it already did), and a
*proper ranking* on large projects. Four gaps stood between the two. The greedy walk takes the
first letters it meets, so `somet` against `asoxmet/some-thing` scored the scattered letters and
missed `some` + `thing`. A path was a flat string: `view` ranked `view/model.blsp` above
`src/view.blsp`. A term could only be a subsequence — no exclusion, literal or anchor — and
case was always ignored. And ranking knew nothing of what the reader had chosen before, while
every keystroke re-ranked the whole set even when the new query could only narrow the last.

**Decision.** All in the Brood definition first, then the native pass to match, pinned by
`tests/fuzzy_native_test.blsp`:

- **Optimal alignment.** A fuzzy term is aligned by a dynamic programme over the SAME per-char
  rules (`fuzzy-char-bonus` + `fuzzy-step`): row i at j is the best alignment of the term's first
  i+1 chars ending at j, from either the run (j-1, +6) or a gap (p ≤ j-2, less the gap cost).
  The gap cost is linear in p, so the second maximum is a running prefix max: O(term ×
  candidate), two rows natively. Past `fuzzy-dp-max-cells` (16384) it falls back to the old
  greedy-or-first-run. It dominates both old alignments, so no candidate's score went down.
  Positions are traced in Brood only (`match`, the rows a UI draws); the native pass computes
  scores, so the two never have to break a tie between equal alignments the same way.
- **Paths are an option, not a global:** `{:category :file}`. A char in the last segment is
  worth +2, `^x` anchors at the file name, and a tie goes to fewer segments before the shorter
  candidate.
- **Orderless dispatch per term:** `!x` excludes (literal), `=x` literal run (best place), `^x`
  / `x$` / `^x$` anchored literal. Smart case per term: an upper-case letter makes it
  case-sensitive. No escape for a literal leading `!`/`=` (`=!x` covers it), as orderless's
  default.
- **History:** `top`/`filter`/`ranker`/`%fuzzy-top` take `:boost {cand n}`, added to a
  MATCHING candidate's score — it reorders, never admits. A candidate that IS the query (or for
  a path, whose file name is) gets +10⁹: it ranks first, as prescient's exact match. Both are
  `top`'s, applied over whatever scorer is in force.
- **Narrowing in the session.** `ranker` holds the options with the set (sent once), and keeps
  the previous query's terms and EVERY index it matched (`%fuzzy-top … {:indices true}`), not
  the capped rows. A query whose every old term is implied by a new one (`fuzzy-refines?`:
  same case, a containing text, same anchors, an exclusion unchanged) ranks only those
  (`:subset`). Replacing the set forgets them. Default rules only — a custom scorer's matches
  need not shrink as the query grows.

`*fuzzy-scorer*` is now `(query options) -> (cand) -> score | nil`, so a custom scorer sees the
category. Greenfield: every in-tree scorer was updated.

**Allocation.** Per call: the parsed terms, the result (and the index vector a session asks
for). Per candidate: nothing — its chars, lowered chars, bonuses and the two DP rows live in
scratch vectors reused across the set, and a subsequence check of every term rejects most
candidates before a bonus is computed. Storing lowered copies at session creation was
considered and not done: the pass must decode each candidate into chars anyway (the DP indexes
them), lowering ASCII in that same loop is one instruction, and a stored copy would double the
session's memory for nothing measurable by reasoning. Nothing was benchmarked.

**Consequences.** A user scorer written `(fn (q) …)` must take the options. `FB` no longer
matches `foo-bar` (smart case). Tests: `tests/fuzzy_ranking_test.blsp` (what a reader sees:
`foo somet`, the alignment, basenames, each operator, smart case, boost, exact, narrowing equal
to a fresh ranking), `tests/fuzzy_native_test.blsp` (the native pass equal to the Brood
definition over operator queries, each option, and candidates past the DP's size).

## ADR-498 — One doctest engine: `;=>` asserts in docstrings and in markdown

**Status:** implemented (2026-10-28).

**Context.** ADR-308's argument reorder survived in `docs/language.md` because prose examples
were never executed. Docstring examples were, but by two engines with opposite conventions:
`nest test` (`std/tool/doctest`) ran `form → result` and treated `form ;=> result` as an
unrun illustration, while `nest doctest` (a collector in `docs.blsp`) evaluated `;=>`, its
expected side included. A reader could not tell from a line whether it was checked.

**Decision.**
- **One engine, one marker.** `std/tool/doctest` is the only engine. `form ;=> result` is a
  case: the form is evaluated and the result, a comment so the line stays pasteable, is read
  as a value. `form ;~> result` is an illustration: read, and its head must exist with an arity
  that takes the arguments, but it is not run. An indented `→` is reported as an old marker,
  and a second marker or an empty result as malformed, never skipped.
- **Examples take the full namespace.** An example runs at the top level, as an Elixir doctest
  does, so it is written `(myapp/parse "x")` and pastes into any REPL. Only public names are
  checked, so the qualified name is always callable. No "evaluate inside module M" capability
  was added; a bare call to the documented module's own name fails naming the spelling to use.
- **Markdown blocks are executed, opt-out.** ```` ```clojure ````, ```` ```lisp ```` and
  ```` ```brood ```` blocks run; ```` ```clojure fragment ````, untagged blocks and other
  languages do not. Unmarked lines are setup, run in order, and setup that raises fails the
  block; a marked line may close a form the setup opened.
- **A block is a process.** Each block runs in a child (`nest run --no-check`, so a project's
  sources are reachable) under a 10 s timeout. In one process a block's `def` reaches every
  later block, and a block that serves or sleeps stalls the run. About 0.3 s a block.
- **The project chooses the documents.** `:doc-paths` in `project.blsp` names files,
  directories and `!` exclusions; the default is `README.md` when there is one, and a named
  path that does not exist is a failure. Brood names `README.md` and `docs` without the ADRs,
  the devlog and the archive: they record what was true when written.
- **On demand, not in CI.** `nest doctest` runs it all; `nest test` still gates a project's
  docstrings. The markdown run is not a CI gate: a document run takes a minute, and its
  failures are editorial before they are urgent.

**Consequences.** Every std and Rust builtin docstring moved to the markers in one sweep. A
documentation block that cannot run says so (`fragment`) instead of silently not running. The
first full run over Brood's docs found 184 failures in 252 blocks; most were prose after a
result or snippets naming values defined elsewhere, and some were real drift. Tests:
`tests/doctest_test.blsp` (markers, namespace hint, fenced-block selection, block setup,
isolation between blocks, a block that exits), `tests/docs_test.blsp` (`doc-files`),
`crates/nest/tests/blsp_dispatch.rs` (`nest doctest` in a scaffold).

## ADR-499 — Following a line through a diff: `diff/map-line`, and a parsed hunk's changes

**Status:** implemented (2026-10-28).

**Context.** ADR-468 gave `std/diff` a native line diff (`line-hunks`) and the change-gutter
reading of it (`line-status`). Two questions a tool asks of a diff were still answered by
hand in bedit. *Where did this line go?* Its time machine (`C-x v t`) mapped point from one
revision to the next with a private `tm-map-line` over `line-hunks`; its auto-revert and
format-on-save did not ask at all and kept point's character OFFSET, so a formatter that
sorted an import in above point, or a `git pull` that added lines, left point on some other
line. *Which lines of the new side did this diff change?* The time machine tinted a
revision's changed lines with a private `tm-changed-lines`, a second reading of a git hunk
beside `line-status`'s reading of two texts — the same rule (`+` lines that replace `-` lines
are modified, the rest added) written twice, once per input shape.

**Decision.**
- **`diff/map-line old new line`** — the 0-based line of `new` that line `line` of `old`
  became, strings or ropes, through one `line-hunks`. An unchanged line is exact. A changed
  line lands on the line that replaced it at the same offset in its block (the block's last
  line when fewer replaced it), so reindenting or editing a line keeps you on it; a deleted
  line lands on the line that followed the deletion. The answer is clamped to `new`'s last
  line a cursor can be on — the empty one after a final newline counts — so the end of `old`
  maps to the end of `new` and a caller never checks.
- **`diff/map-lines old new lines`** — the batch form: one diff serves every position (an
  editor's point in each pane, a REPL's marks), since the diff is the cost.
- **`diff/hunk-changes hunk`** — the change runs inside a PARSED unified-diff hunk
  (`parse-unified`'s, with context) as zero-context hunks in `line-hunks`' shape. That is the
  bridge, rather than a second status function: everything written for `line-hunks` reads a
  diff git printed through it.
- **`diff/hunks-status hunks`** — `line-status`'s gutter reading, split off so it takes
  hunks from either source. `line-status` is now `(hunks-status (line-hunks old new))`, and a
  parsed diff's gutter is `(hunks-status (mapcat hunks hunk-changes))`.

**Callers besides bedit.** None calls it yet; the ones that want it: the eval server and the REPL keeping marks (a form's result note, an
error's location) in a buffer reloaded from disk, the observer keeping a selected source line
across a hot reload of the module it shows; `nest`'s doctest and check reports name lines
of a file that may have changed since. Each is a line of an old text found in a new one.

**Consequences.** bedit drops `tm-map-line` and `tm-changed-lines`; its revert and
format-on-save keep point on its line and column. A deletion now appears in the time
machine's status map as `:deleted` (it has no line of its own to tint, so the tint skips
it). Tests: `tests/diff_test.blsp` ("map-line / map-lines", "hunk-changes / hunks-status").
