# Design decisions: numbers 700 to 799

One of the files the ADR log is split across by number; the index, and the notes that
apply to every entry, are in [../decisions.md](../decisions.md).

## ADR-710 — `string/scripts` and `string/mixed-script?`: the Script property, and TR39's single-script test

**Status:** implemented (2026-11-11).

**Context.** A Cyrillic `а` (U+0430) looks like a Latin `a`, so `pаypal` reads as `paypal`. An
editor wants to mark an identifier or a URL that mixes scripts the way a homoglyph does (Emacs's
`textsec.el`, VS Code's ambiguous-character highlight); a package registry wants to refuse a
package name that imitates another; a mail reader wants to flag a sender's display name. Each
needs the Unicode Script property of a character, which is table data Brood did not have.

**Decision.** One native and one std function.

- `(string/scripts s)` (`builtins/string.rs`, over the `unicode-script` crate already in the tree
  through cosmic-text) — the scripts of `s`'s characters as keywords (`:latin`, `:cyrillic`,
  `:old-italic`), in order of first appearance, none twice. Common (digits, punctuation, spaces),
  Inherited (combining marks) and Unknown are left out: they belong to every script, so
  `(string/scripts "v1.2")` is `[:latin]`.
- `(string/mixed-script? s)` (`std/string.blsp`, Brood) — UTS #39's "highly restrictive" level:
  false for one script, for Han with kana, Hangul or Bopomofo (its augmented script sets), and
  for any of those with Latin; true for the rest, Latin with Cyrillic or Greek above all. The
  rule is policy over the property, so it is Brood; the property is data, so it is native.

**Not done.** UTS #39's *confusables* (`confusables.txt`, the skeleton that makes the whole-script
`раураl` — all Cyrillic — compare equal to `paypal`) need the `unicode-security` crate's tables
or a generated std table; a word in ONE script is not flagged. Script_Extensions (a character
several scripts share, U+30FC) are read as the character's single Script value.

## ADR-711 — `mcp-server`: the MCP protocol out of `nest mcp`, for any program that serves tools to an agent

**Status.** Accepted (2026-11-11).

**Context.** `std/tool/mcp.blsp` held the whole Model Context Protocol server — the JSON-RPC
dispatch, the handler run in a monitored process of its own with stdout captured, the deadline,
the projection of Brood data onto JSON — bound to stdio and to `nest mcp`'s catalogue, in a DEV
module a shipped runtime does not carry. An editor that hands a coding agent its own tools (its
buffers, diagnostics, the tests it can run) needs exactly that dispatcher, served from inside
its own event loop and shipped with it; so does an agent harness exposing its file tools to a
CLI agent. `docs/mcp.md` had foreseen it: "the Brood half ports unchanged; only the transport
re-hosts".

**Decision.**
1. **A runtime module, `mcp-server`** (`std/mcp-server.blsp`), holds the protocol. A SERVER is a
   plain map: `:catalogue` (a fn answering `{:name :description :schema :handler}` entries, read
   on every request), `:info`, `:capabilities`, `:methods` (more JSON-RPC methods, `name -> (fn
   (params server) [status payload])`, answered before the built-in ones), `:emit` (where a
   progress notification goes), `:deadline-ms` and `:deadline-tools`. `handle` and `respond`
   answer one message; `json-data`, `pretty-json`, `listed-tool`, `rpc-error` and `progress` are
   public, so a server built elsewhere shapes its results the same way.
2. **Two transports.** `serve-stdio` — newline-delimited JSON, with an optional per-reply step
   (`nest mcp` carries its staleness warning on it). `http-handler` / `start-http` — MCP's
   streamable-HTTP transport with JSON responses only: a POST carries one message and gets one
   reply (202 for a notification, 405 for anything but POST), on loopback only and only with a
   secret token (`http/loopback-only`, `http/require-token`). `start-http` listens on an
   OS-assigned port in a process of its own and answers `{:pid :port :token :url}`.
3. **`nest mcp` is one server spec over it**: its catalogue, the reference documents as
   resources, the `brood-task` prompt (as `:methods`), the deadline on `eval` / `load`. Its
   behaviour is unchanged; `mcp/progress` is `mcp-server/progress`.

**Rejected.** *Leave it in `nest mcp` and let applications copy it*: the handler isolation and
the JSON projection are the subtle parts, and they would drift. *A stdio-only server, with a
relay process an agent launches to reach an application's port* (what an agent harness had
built): one more process and one more protocol hop for every call, when an agent CLI that
speaks MCP speaks HTTP too. *Server-sent events on the HTTP transport*: no client this serves
needs a notification mid-call yet; a JSON response is the smaller transport the spec allows.

**Consequences.** `mcp-server` ships in every runtime; `mcp` stays a dev module. A progress
report over HTTP goes to the server's `:emit`, not to the client. Guards: `tests/mcp_test.blsp`
(nest's server, through the shared dispatcher), `tests/mcp_server_test.blsp` (a spec of its own,
`:methods`, the deadline, HTTP with and without the token, a notification, GET).

## ADR-712 — `insert-program-output`: text a program writes, which undo steps over

**Status.** Accepted (2026-11-11).

**Context.** `std/editor/buffer`'s undo restores whole snapshots (`{:rope :point :mark …}`).
In a buffer that a program writes into while a person types (a shell's output above its
prompt, an agent's reply above the message being written), undoing what the person typed
restored a snapshot from before the program's later output, and so took that output away
(redo brought it back). bedit's agent chat turned undo off to avoid this; bshell and a
line-mode terminal had the same problem.

**Decision.** `(insert-program-output buf at text &optional properties)` inserts `text` as though it
had always been there:
- into the buffer, and into every snapshot of its history (`:undo`, `:pending-undo`), at the
  same position;
- recording nothing;
- point, mark, markers, narrowing and text properties move as any insertion moves them;
- a read-only or narrowed buffer takes it, because the text is the program's, not an edit.

Each snapshot goes through the same insertion as the buffer itself (restored into a widened,
unrecorded copy, inserted into, snapshotted again), so there is no second implementation of
how an insertion moves things.

**Rejected.**
- *Delta undo, Emacs's `buffer-undo-list`:* the whole undo model replaced, for one case that
  this covers exactly.
- *Turning undo off in such buffers:* a person loses undo of their own typing.
- *Re-applying the output after each undo:* the history would still hold states the buffer
  never had.

**Consequences.**
- The result is exact when the text before `at` is the same in every snapshot, which is how
  every program buffer is laid out (output above input). Elsewhere a snapshot gets the text at
  the same offset, clamped.
- The cost is one insertion per snapshot, bounded by the undo limit. `:undo-size` does not
  count the output.
- Guards: `tests/buffer_output_test.blsp`. It covers undo, a run of undos, redo, point,
  markers, narrowing and properties.
