# Design decisions: numbers 600 to 699

One of the files the ADR log is split across by number; the index, and the notes that
apply to every entry, are in [../decisions.md](../decisions.md).

## ADR-602 — A test run says so, and gets a scratch home of its own

**Status:** implemented (2026-11-05).

**Context.** A test that calls a command which persists something writes wherever the
program keeps its files — and under `nest test` that was the user's real home. bedit's shell
test pressed RET and overwrote the user's `~/.config/bedit/state/bshell-history.blsp`; its
`check-modes` tool filled their recent files. bedit then guarded itself by asking whether the
test framework's registry happened to be bound — a guess from what is loaded, which every
other program would have had to repeat, and which said nothing to a process a test started.

**Decision.**

- **The runner says it is a test run.** `nest test` sets `BROOD_TEST_RUN=1` before the
  interpreter exists (`cli_support::arm_test_run`, from `arm_test_env`). `test/running?`
  answers from it. It is an environment variable on purpose: a program a test starts — an
  eval server, a subprocess under test — is part of the run, and inherits it. A program that
  must not load the test framework to ask (an editor deciding where its config lives) reads
  the variable itself.
- **The run gets a private scratch home.** Unless `nest test --real-home` or
  `BROOD_TEST_HOME=keep`, the runner makes `<temp>/brood-test-home-<pid>-<time>/` and points
  `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_DATA_HOME` at its `config/`, `state/` and
  `data/`; `BROOD_TEST_SCRATCH` (`test/scratch-dir`) names it. A program that keeps its files
  under the XDG homes needs no test-mode code at all. The directory is removed when the run
  ends, and an earlier run's left behind by a run that died is purged when the next starts
  (by liveness, not age: ADR-608). The REPL's history, which is not under an XDG home, is
  pointed there too (`BROOD_HISTORY`, ADR-608).
- **`XDG_CACHE_HOME` is left alone.** Brood's own caches — the stdlib image, the prelude
  image, compiled grammars, the check cache — live there, keyed so sharing is only a
  speed-up; a fresh cache per run would cost every run a cold start. A cache is regenerable;
  a config, a history or a data file is not.
- **`nest`'s own preferences stay the user's.** `BROOD_USER_CONFIG_HOME` keeps the real
  config base, and `project`'s user config (`~/.config/brood/config.blsp`: the registry, its
  token, `git init`) reads it first — those are the person's tool settings, not the program
  under test's state. A run started inside another keeps the base the outer run kept
  (ADR-608). Nothing else reads it: a publisher's signing key, a node cookie and
  everything a program keeps go to the scratch home under test.

Not covered: `brood --test`, which runs after the interpreter (and its threads) exist, where
setting the environment is not safe; it is a single-file runner.

**Callers beyond bedit.** Every project's suite — a hive package with a history, a cache of
its own or a config file is protected without knowing it; Brood's REPL history (since
ADR-608, which points `BROOD_HISTORY` into the scratch home) and `node`'s cookie under std's
own tests; any tool that wants to keep a test away from something real
(`test/running?`).

**Consequences.** Guards: `crates/nest/tests/test_scratch_home.rs` (a project's test writes
under `$XDG_CONFIG_HOME`; with `HOME` at a stand-in, the write lands in the scratch home, the
scratch home is gone after the run, and `--real-home` puts it under `HOME/.config`) and
`tests/test_run_test.blsp` (`running?`, `scratch-dir` and the three homes inside it).

**Amended by ADR-608 (2026-11-05).** As first written, only `nest test` armed — so bedit's
`C-c t`, which runs a project's tests through a generated script under `nest run` (cold) or in
a warm eval-server child, ran them with the real home, and the tests bedit guards skipped their
checks. A runner that is not `nest test` now asks for the run with `BROOD_TEST_ARM=1`; bedit's
both runners do. The REPL history moved into the scratch home, a purge goes by liveness, and a
nested run keeps the user's config base.

## ADR-603 — What a load bound, and the impls a module registered: `reflect/rebound-since`, `registry/impls-by`

**Status:** accepted (2026-11-05).

**Context.** A plugin host that unloads a plugin has to know what the plugin's load defined and
which ability impls it registered. bedit found the first by reading EVERY global's value before
the load and the source site of every global after it (11,495 globals: 55 ms to apply a package,
80 ms to remove one), and had no way at all to find the second: `registry/written-by` leaves the
impl tables out (ADR-582), and `reflect/undef` retires only the impls of a type it removes — so a
plugin's `impl` of a core ability for a core type outlived it, calling a helper that was gone.
The runtime already knew both: every `def` and removal stamps the global with the runtime's
generation (`RuntimeCode::global_generations`, read by `%global-generation`), and every impl is
kept by precedence tier with the namespace that registered it (`*impl-tiers*`, ADR-432).

**Decision.**

- **`reflect/generation`** answers the runtime's generation now; **`reflect/rebound-since g`**
  every global defined, redefined or removed after it — one pass over the stamps in Rust, no
  value read. A host takes the generation before a load and asks after it.
- **`registry/impls-by writers`** lists every impl a namespace in `writers` registered and that
  is still registered (`{:ability :op :key :rank :from}`); **`registry/retract-impl impl`** takes
  one back while its tier still holds that namespace's registration, the highest tier left
  winning again (or the slot unclaimed). An impl from code of no module is nobody's.
- **The root escape names a global exactly in `reflect/source-location` and `reflect/undef`**:
  `/org/f` is the global `org/f` even inside a project whose own `org` module would root
  `org/f` to `bedit/org/f`. A host asking about a plugin's module that shares a short name with
  one of its own got the host's function's site — and would have removed it. (Inside a project
  a `def` target is still rooted, root escape or not; ADR-604 is what keeps a plugin's module
  out of the host's.)
- **`registry/put-new!`** registers an entry only when the key is free, in one locked step — a
  runtime-wide slot (bedit's one package job across every window).

**Callers beyond bedit.** `nest`'s dev server and `tool/reload` (what a reload rebound, an impl
a module no longer declares), the observer's extensions, a REPL undoing an experiment.

**Amended by ADR-606:** the generation says WHICH globals a load bound; what each held before it
is `reflect/global-values`, taken before the load. Keeping old values only for the names the
plugin's source spells missed a name the project rooted and one a macro built.

**Consequences.** Guards: `tests/registry_writers_test.blsp` "reflect/rebound-since" and "ability
impls a module registered"; bedit's package tests.

## ADR-604 — A plugin's modules load apart from the host project's; same-tier impls stack

**Status:** accepted (2026-11-05).

**Context.** Inside a project every `mod/name` of one of its modules roots to
`project/mod/name` (ADR-070), at compile time and on a global lookup's miss. A plugin loaded at
run time — bedit's packages — loads in the host's process, so in the host's package context:
a plugin module named `org` beside bedit's `org` declared `bedit/org` and redefined bedit's
functions. A root-escaped `(def /org/f …)` bound the ROOTED `bedit/org/f` while its definition
site was recorded under `org/f`, so the site said the plugin's file and the binding was the
host's. And an `impl` registered at the same precedence tier as another namespace's replaced it
outright: taking the plugin back left the slot empty rather than the impl it replaced.

**Decision.**

- **`reflect/with-modules-apart modules thunk`** runs `thunk` with `modules` removed from the
  active project's module set: inside it `org/f` is the global `org/f`, while every other
  project module roots as before — the plugin still reaches the host's `model`, `commands`, ….
  The context comes back on the way out, a throw included; a process spawned inside inherits it.
- **A name bound exactly whose rooted spelling is not bound is not rooted** (`root_qualified_ref`,
  checked outside its memo): a late-bound `'org/only-in-plugin` — a keymap command, a hook —
  reaches the plugin's. A name BOTH bind is ambiguous when spelled short; the host's compiled
  code names its own in full (`bedit/org/f`), and the short spelling finds the exact global.
- **A definition's site is recorded under the global the definition binds** — the same rooting
  the `def` arm applies — never under a name nothing binds.
- **`*impl-shadowed*`**: a same-tier registration from another namespace keeps the one it
  replaced (newest first, per `[ability op id]` and tier). `registry/retract-impl` puts it back;
  `registry/impls-by` lists the shadowed ones too, so a plugin whose impl was itself replaced
  can be taken back without the newer one ever restoring it. The stdlib image carries tiers as
  before; a std module replacing another std module's impl at the same tier (a warned conflict)
  is not imaged with its shadow.
- **`%registries-written-by writers`** answers the registries the writer journal credits to
  `writers`; `registry/written-by` walks those instead of every registry.

**Callers beyond bedit.** Any host that loads plugins into its own project process (the
observer's extensions, a `nest` dev server loading a scratch module), and any tool unloading
one.

**Consequences.** bedit loads each package's files apart from its own modules and binds a
retired layer back the same way; its removal is proportional to what the package wrote (80 →
18 ms at ~11,500 globals). Guards: `tests/modules_apart_test.blsp`; `tests/registry_writers_test.blsp`;
bedit's `tests/package_safety_test.blsp` ("a package module named like one of bedit's", "two
packages implementing one ability for one type, at the same tier").

**Addendum (2026-11-05).** `reflect/project-modules` answers the running project's module short
names (ADR-606: registered by `setup` and by a release bundle's boot, not read off the package
context, which a bundle never sets), so a host can refuse a plugin whose module would share one (bedit refuses a package
whose module is named like one of bedit's or a std module, at install and at load: a short
late-bound `'org/…` in its own keymaps could otherwise reach the plugin's). And the project
image's prune no longer exempts registrations made before the project loaded: ownership is the
journalled writer, so the prelude's never were a module's (KI-106), while a std module the build
loaded from source before the project — `nest`'s toolchain, with no stdlib image yet — had its
record ids baked into the image, and the next run started with `:http/response`,
`:log/line-backend` … and no constructors. Reproduced on an empty cache with nest 77f15601 and
this branch; guard: `crates/nest/tests/project_image_registries.rs`
`a_cold_first_run_without_a_stdlib_image_images_no_foreign_record_ids`.

## ADR-605 — A restarted served loop is given only the hand-overs no loop handled; a new client starts a fresh ledger

**Status:** accepted (2026-11-05). Follows ADR-593.

**Context.** ADR-593's session keeps the manager's hand-overs to its loop (`[:adopt …]`,
`[:claim …]`, `[:client-can …]`) and gives them to a restarted loop again, on the reasoning that
replaying one the dead loop had taken is harmless. A review found it is not. The session only
appended them (the newest six), so every restart replayed every one it had ever passed on: a claim
DECLINED long ago (the old client answered; the claimant got a session of its own), replayed to a
restarted loop whose client had since gone and whose session had parked, adopted the claimant
without a ping — the claimant's window then fed two sessions, and the manager, still holding the
first one parked, could no longer hand it to its user. A claim that SUCCEEDED, replayed to the
loop now serving the claimant, pinged the claimant and could `[:bye]` it. Three more seams leaked
the same way: the key LEDGER kept the old client's last key number when a new client adopted or
claimed the session, so a restart before the new client's first key was taken told it
`taken=N` and it dropped its own first N keys; a restarted parked loop parked afresh, so a loop
dying every half-minute kept a parked session alive forever; and each restarted loop that
watched a buffer registry left its dead predecessor among the registry's watchers, as the session
kept every death it ever had.

**Decision.**

- **Only unhandled hand-overs replay.** The loop's display tells its session each hand-over it
  HANDLED, whatever came of it (`[:editor/serve/handled message]`, sent after what handling it
  sent, so it is folded before the loop's `[:EXIT]`), and the session forgets it. A restarted
  loop is given only what was passed on and never handled — a hand-over the dead loop had not
  reached yet. A claim the loop was mid-way through (waiting on its ping) when it died is
  unhandled, and is asked again.
- **A new client starts a fresh ledger.** Adopting or claiming the session clears the ledger's
  last-taken number: the new client numbers its keys from 1, so until the new loop takes one, a
  restart tells it none was taken and it sends them all again.
- **A parked session's time to live runs from when it parked.** The display reports `:parked-at`
  with its client and size; a restarted parked loop starts parked at that time.
- **Nothing dead is kept.** A buffer registry monitors each watcher and drops one that ends
  (`registry-unwatch` demonitors). A session keeps only the deaths its restart budget counts
  (those inside `:window-ms`); `:restarts` in the `death` map is a counter of its own.
- **A browser tab's input has one owner.** The tab's event-stream process owns its input log: a
  `POST /input/<id>` is handed to that process (`[:editor/web/input m]`), which numbers, keeps and
  ships it in mailbox order with the session's `[:reattached …]`. Before, the request process
  and the stream both read-modify-wrote the tab's entry: a post during a restart could go to the
  dead loop and be wiped from the log by the resend, its number reused. No new primitive: one
  owner process is Brood's way to make a table entry's update atomic.

**Callers beyond bedit.** Every `serve` app's sessions, and every buffer registry's watchers (a
frame, a mirror, a collab host).

**Consequences.** A restart no longer asks or adopts anyone the manager did not just ask it to.
Guards: `tests/serve_test.blsp` "serve: a restarted loop is given only the hand-overs no loop
handled (ADR-605)" — a declined claim not replayed to a restarted parked loop, a successful claim
not replayed to the claimant, the adopter's fresh ledger, a parked session's restarted loop
ending on the original time, the pruned deaths; `tests/buffer_registry_test.blsp`
"buffer-registry — a watcher that ends is dropped (ADR-605)"; `tests/editor_web_test.blsp` "a
tab's input across a restarted loop (ADR-605)".

## ADR-606 — The running project's modules and what a load replaced, in every configuration: `reflect/project-modules`, `reflect/global-values`, `reflect/source-locations`

**Status:** accepted (2026-11-05).

**Context.** Two answers ADR-603/604 gave a plugin host were only true under `nest run` /
`nest test`. `reflect/project-modules` read the active package context — but a `nest release`
bundle loads the root project's own modules UNROOTED and never sets one (`bundle-boot-load`
registers only the dependencies' rooting), so in bedit's installed editor it answered `[]`: a
package module `org` passed the collision check, loaded into bedit's `org`, and its removal took
bedit's own `org` rows and namespace with it. And a host undoing a plugin learned WHICH globals
the load bound from `reflect/rebound-since`, but kept the value each held before only for the
names the plugin's source spelled. Inside project `bedit` a plugin's `(defn keyhelp/f …)` binds
the rooted `bedit/keyhelp/f`, and a macro can build any name; neither was kept, so removing the
plugin left the patch live — calling the plugin's helpers, now unbound.

**Decision.**

- **`reflect/project-modules` is the running project's registered module list** (the prelude's
  `*project-modules*`, `%register-project-modules!`), not the package context. `setup`'s
  rooting registers the `(defmodule …)` names it roots; `bundle-collect` bakes the same names
  into the release manifest as `:project-modules`, and a bundle's boot registers them before any
  module loads (a bundle built before the field falls back to its embedded keys that are no
  dependency's). The answer is the same inside a dependency's load or `with-modules-apart`. The
  project image does not carry it: it is true of the run, set before the image installs.
- **`reflect/global-values`** answers every global a `def` may rebind — none the language
  reserves (ADR-166) — as a map of exact name to value, read in one pass under the table's lock.
  Taken before a load, it holds what each global `reflect/rebound-since` names afterwards held
  before it, however the load spelled or generated the name. Reserved names are left out: a load
  cannot rebind them, and they are most of the table.
- **`reflect/source-locations`** is its companion — every rebindable global's definition site,
  `{sym [file line col]}` — and **`reflect/set-source-location name loc`** puts one back (nil
  forgets it). A global given back its old value otherwise still read as defined in the
  removed plugin's file, so `M-.` and `C-h f` on a restored function went to a file that is
  gone.

**Callers beyond bedit.** `nest`'s dev server and `tool/reload` (what a reload replaced, to roll
it back), a REPL undoing an experiment, any released Brood program that loads plugins and checks
their module names against its own.

**Consequences.** bedit's package removal restores every core global a package rebound, by the
rooted name, and refuses a package module named like one of bedit's in the released editor as in
`nest test`. Guards: `crates/cli/tests/release_bundle.rs` `a_bundle_answers_its_own_project_modules`
(a booted bundle, baked manifest and the fallback); `tests/project_test.blsp` "bundle-collect bakes
the project's own module names into the manifest"; `tests/modules_apart_test.blsp`
"reflect/project-modules"; `tests/registry_writers_test.blsp` "reflect/global-values" (both cases); bedit's
`tests/package_safety_test.blsp` ("in the released editor", "a core function a package patched").

## ADR-607 — One resolver finds the program for `os/which` and every spawn

**Status:** implemented (2026-11-05).

**Context.** `os/which` searched `PATH` in Brood, Windows's `PATHEXT` included, while every
spawn left the search to the platform. On Windows the two disagreed. `std::process::Command`
with a bare name finds only `name.exe`, so `os/which "mix"` answered `mix.bat`, and an npm shim
answered `tsc.cmd`, and then `os/spawn` and `os/cmd` failed on the same name. bedit's LSP client
never connected, its formatter raised, and its Elixir sandbox did not start. The ConPTY spawn
handed `CreateProcessW` the bare name with no application name. That search tries the current
directory first, so a `bash.exe` planted in a cloned repository ran. It also never reads an
`:env` `PATH`.

**Decision.**

- **One resolver, in Rust** (`host::subprocess::program`). `os/spawn`, `os/spawn-pty`
  (ConPTY and Unix), `os/cmd`, `os/run-process` and `os/detach` all start the absolute path it
  answers. `os/which` is the same resolver too (`%program-path`): a yes from it is a program a
  spawn starts, because it is the same code. It lives in Rust because the ConPTY spawn needs an
  absolute path whoever calls `%pty-spawn`, and a raw builtin is no safer than its weakest
  caller.
- **The child's view.** It resolves with the spawn's `:cwd` and `:env`. The `PATH` searched is
  the `:env` one when the spawn sets it, ours otherwise, and no `PATH` finds nothing. A
  relative name, or a relative `PATH` entry, is taken against the child's working directory.
  `os/which` takes the same options (`(os/which "mix" {:env …})`).
- **`execvp`'s rule everywhere.** A name with a separator is used as given, and a bare name is
  looked for in each `PATH` entry, an empty entry meaning the working directory. On Windows a
  program is a file with a `PATHEXT` extension. Windows's own extra places (the current
  directory, the system directories, the executable's directory) are not searched. On Unix
  the child still sees the name it was given as `argv[0]`.
- **Batch files run under the system's `cmd.exe`, never `COMSPEC`.** `cmd.exe` re-parses the
  arguments (BatBadBut, CVE-2024-24576). For the pipe spawns, `Command` given a `.bat` path
  already escapes them (Rust 1.77.2 and later). The ConPTY spawn writes its own command line,
  using the same escaping (`batch_command_line`): `cmd.exe /e:ON /v:OFF /d /c ""SCRIPT" ARGS"`.
  An argument is quoted unless it holds only letters, digits and `#$*+-./:?@\_`. A `"` in it is
  doubled, a `%` becomes `%%cd:~,%`, and an argument holding a line break is refused.

**Callers beyond bedit.** Every program that asks `os/which` before it spawns: `nest`, the
REPL's tools, a test helper.

**Consequences.** A not-found spawn now fails before anything starts, with
`not found on PATH`. Guards: the resolver's and the batch escaping's unit tests
(`host::subprocess::program::tests`, which test the Windows rule on every platform);
`tests/platform_test.blsp` "a spawn finds its program as os/which does", which runs a `.bat`
by its bare name from an `:env` `PATH` through `os/cmd`, `os/spawn` and `os/spawn-pty` on the
Windows runner.

## ADR-608 — Any test runner can ask for the test run; the scratch home is purged by liveness

**Status:** implemented (2026-11-05). Amends ADR-602.

**Context.** ADR-602 armed the test run in `nest test` alone, keyed on the subcommand. A test
runner that is not `nest test` got nothing: bedit's `C-c t` writes a script that installs its
report sink and runs it with `nest run` (the cold path), or keeps an eval-server child that loads
the project and runs tests on request (the warm path). Under either, `BROOD_TEST_RUN` was unset,
so the guards bedit's own suite relies on skipped their checks, and a run from inside the editor
wrote the user's real savehist, save-place, transient memory, tutorial progress and slow-turn
log — the exact accident ADR-602 was written for. Three smaller gaps: ADR-602 said Brood's REPL
history was protected, but the history is `$BROOD_HISTORY` or `$HOME/.brood_history` and the
scratch home moves only the XDG homes; the purge called a scratch home stale once its directory
was an hour old, so a second `nest test` deleted a long first run's home under it; and a `nest
test` started inside a run took the outer run's scratch config as the user's config base.

**Decision.**

- **The request is an environment variable on the child: `BROOD_TEST_ARM=1`.** Every Brood
  entry point — `nest` (every subcommand) and `brood` — reads it before its interpreter exists
  (`cli_support::arm_requested_test_run`) and arms exactly as `nest test` does: `BROOD_TEST_RUN`,
  a scratch home, `BROOD_TEST_HOME=keep` honoured. It then removes the request from its own
  environment, so what it starts inherits the armed run (one scratch home, the way a program a
  `nest test` test starts shares it) instead of arming one of its own. Not a `nest run` flag:
  the editor's runtime may be `nest` or `brood`, and an environment variable means the same to
  both — and to a bundle, should one ever host a runner. Not in-process arming from std's test
  runner: the environment cannot be changed safely once the runtime's threads are up, and the
  code a runner loads before its tests could already have read the real paths.
- **`BROOD_HISTORY` points into the scratch home** (`state/brood_history`). An audit of std's
  writers keyed on `HOME` rather than the XDG homes found this one; `~/.broodrc.blsp` is only
  read, and every other file std keeps (`node`'s cookie, a publisher's signing key, `project`'s
  user config) is under `XDG_CONFIG_HOME`. Caches stay under `XDG_CACHE_HOME`, as ADR-602 said.
- **A scratch home is purged by liveness.** The run that makes one holds an exclusive lock on
  its `run.lock` for as long as the process lives — released by the operating system however
  it ends. A purge removes a home whose lock it can take, and keeps one whose lock is held,
  however old. A home with no lock file (made by an older binary, or caught between its
  directory and its lock being made) is removed only past an hour.
- **A nested run keeps the user's config base.** `BROOD_USER_CONFIG_HOME`, when already set (an
  outer run kept it), wins over `XDG_CONFIG_HOME` — which inside a run is the outer run's scratch
  config, no one's preferences.

**Callers beyond bedit.** Any tool that runs tests by some other road than `nest test`: an
editor's in-image or warm runner (bedit's two), an MCP client running a suite through `nest run`,
a CI wrapper that drives `brood` directly, a hive package's own test harness.

**Consequences.** bedit's cold runner starts `nest run` with `BROOD_TEST_ARM=1`, and its warm
test child is spawned with it (`sandbox/spawn-runtime-on`'s `:env`) — so the child is armed
before its first line; the warm child keeps one scratch home for its life, its runs sharing it.
Guards: `crates/nest/tests/test_scratch_home.rs` (an armed `nest run` is a test run with its own
home, `BROOD_HISTORY` inside it, the request consumed and the home gone after; a nested run keeps
the user's base; a purge keeps a live run's ancient home and takes a dead run's),
`cli_support`'s `test_scratch_liveness_tests`, `tests/test_run_test.blsp` (the REPL history path
under a run), and bedit's `tests/testrun_test.blsp` ("a C-c t run gets a scratch home": the cold
runner's `nest run` and the warm child each arm a home of their own).

## ADR-609 — A frame can be painted into memory by the window's own painter: `gui/render-frame`, `gui/capture`, headless painting

**Status:** implemented (2026-11-05).

**Context.** A layout bug in bedit — a strip of window background between the title bar and
the header line showing the file's name — survived three fixes, because nobody could see what
a window paints. There is no screenshot tool on the machine it was worked on, and brood could
not hand back a frame as pixels: a headless window (`BROOD_GUI_HEADLESS=1`) draws nothing and
has no font engine, and a real one paints straight to its surface. It was fixed on 2026-11-05
by a change to the layout rule (`Renderer::grid_origin` is `(inset, 0)`: row 0 starts at the
top edge; ADR-508's addendum), checked only by a geometry unit test — which tests the rule as
the test's author understood it, not what reaches the screen.

**Decision.**

- **A picture is the window's paint, called without a window.** `backend/offscreen.rs` bleeds
  the frame as `RedrawRequested` does (`bleed::edge_bleed` over `Margins::of`), rasterises it
  with `paint::raster_frame` (`force`), and reads the canvas back as RGBA. The layout rule
  (`grid_origin`, `grid_cells`), the inset, the background, the edge bleed and the glyph
  rasteriser are all the window's; there is no second painter whose picture would prove
  nothing about the first. A layout change in the renderer changes the picture.
- **`gui/render-frame frame spec`** paints a frame as a window described by `spec` would
  (`:width` `:height` in physical px, `:font` — an installed family's name or a family
  keyword —, `:size`, `:line-height`, `:inset`, `:bg`, `:scale`, `:text-aa`, `:ligatures`;
  every default a window's). It needs no window and no display, so it runs in `nest test`,
  headless or not. The answer is `{:width :height :rgba :cell :grid :origin :inset}` —
  `gui/image-thumb`'s shape plus the geometry it was painted at, so a test finds row 1 or a
  cell without re-deriving the rule it is testing.
- **`gui/capture id`** is a window's current frame. A real window's is rasterised on the GUI
  thread by its own renderer from its own bled frame (a GPU window's by the CPU painter, its
  sprites absent), the retained frame then forgotten so the next paint repaints whole.
- **Headless painting is opt-in: `BROOD_GUI_HEADLESS=paint`.** Under it a headless window is
  painted offscreen: it keeps its font, inset, background, line height and the frames drawn
  to it, measures its grid with the real cell metrics (and tells the app `[:resize …]` when
  a font change moves it), answers `gui/cell-size` and `gui/font-info`, and `gui/capture`
  paints it — so an app's real loop, its own startup and timers included, can be looked at
  with no display. `gui/windows` lists the open windows, so a driver finds the one the loop
  opened. A plain `=1` window is unchanged: the fixed nominal 8×16 grid and no font engine.
  Every headless window measuring real metrics was the alternative; it would change the grid
  every existing headless test and app run sees, and start a text engine (and, for a family
  asked for by name, a system font scan) in each — a cost those runs never asked for.
- **The painter is a thread of its own (`brood-offscreen`)**, as the window's is the GUI
  thread: the text engine is not `Send`, and one engine keeps its glyph cache and its
  registered families across pictures. Its requests mirror the GUI thread's events, so a
  headless painting window takes the same settings in the same order a real one does.
- **`gui/write-png image path opts`** writes any `{:width :height :rgba}` map as a PNG;
  `:crop [x y w h]` and `:scale n` (nearest neighbour) make a few pixels of spacing visible.
  `gui/pixel image x y` reads one pixel, for a test.

**Callers beyond bedit.** Golden-image and geometry tests of brood's own renderer (the layout
rule, edge bleed, glyph placement — `offscreen`'s tests and `tests/gui_test.blsp` are the first);
any brood GUI app's tests (`examples/`, pong) asserting on what its view paints rather than on
its ops; an agent or a person reviewing a UI change, who can now look at the frame (bedit's
`tools/screenshot.blsp` writes one from the real editor).

**Consequences.** A test can say "the header's colour starts at y = 0" and mean the screen.
Not covered: what the compositor does after the window presents (scaling on a HiDPI output
the window was not told about, a decoration drawn over the surface), and a GPU window's
sprites and shader effects, which `capture` paints with the CPU painter. Guards:
`backend/offscreen.rs`'s tests (row 0 at y = 0, the inset margin left, right and below, a
full-width band bleeding to the window's edges, a glyph's ink inside its cell), and
`tests/gui_test.blsp` (the same through `gui/render-frame`, a PNG round trip with crop and
scale, `gui/pixel`, `gui/capture` of a window that is not open).

## ADR-610 — An app declares the seam row: rows above it are top-anchored, rows from it down bottom-anchored, the leftover sits between

**Status:** implemented (2026-11-05). Refines ADR-508 (its 2026-11-05 addendum).

**Context.** A window is rarely a whole number of rows tall. Since ADR-508's last addendum the
grid sat at `(inset, 0)` and the leftover height (the window less the margins, mod one row,
0..cell_h-1 px) went under the last row. In bedit the last row is the echo area, a chrome band,
so the gap under it moved with the window's height: 11 px at 600 px tall, 24 px at 613. Every
earlier policy (leftover on top, split above and below, centred) put the leftover beside a
chrome band too — bedit shipped each failure in turn. Editors with chrome answer it the other
way: Emacs pins the minibuffer to the frame's bottom and each mode line to its window's bottom,
and the surplus is a partly visible line of text in a window's body; VS Code's status bar is a
fixed band and the editor area absorbs the rest. The research is in bedit's
`reports/Editor UI design for bedit.md`, "The layout decision".

**Decision.**
- **A frame op `[:seam row]`** (`editor/display/seam`) names the SEAM. Rows `0..row-1` are
  anchored to the top (`top + k·ch`), rows `row..last` to the bottom (the last row ends exactly
  at `h - inset`), and the leftover `r` lies between row `row - 1` and row `row`. bedit names its
  bottom mode line, so the echo area sits on the window's bottom inset at every height and the
  leftover is the text body's partial line. No seam (or one at or past the grid) is the old
  layout exactly: other programs are untouched. A seam of 0 anchors every row to the bottom.
- **`[:seam row {:top-band false}]`** says row 0 is not a full-width band: the top then gets the
  inset the sides have. Left out, row 0 is a band (bedit's header line, a tab bar) and starts at
  y = 0, as before. The research found no source for this; it is judgement, made by looking at
  both (bedit sets it from whether its header line is on).
- **One row map, `backend::rows::RowMap`**: `y(k) = top + k·ch + (k ≥ seam ? r : 0)`, a span of
  rows is `y(end) - y(start)`, and its inverse `row_at` gives the gap's pixels to row `seam - 1`.
  Every consumer goes through it — both painters (`render_ops`, the GPU `expand` via its `Grid`),
  the CPU painter's damage strips (`Strips`, row `seam - 1` is one strip with its gap), the scroll
  blits (a translation is accepted only between spans of equal height), the edge bleed's margins,
  the offscreen picture, the mouse hit-test (`px_to_cell`, `px_to_cell_frac`), the cursor zones
  and the IME caret area (taken to and from the grid's uniform space with `uniform_y` /
  `window_y`). Nothing else computes `origin + row·cell_h`.
- **Phase 1 painting: the row above the seam paints the gap.** A rect or frect whose bottom edge
  is the seam reaches through it by the map itself (its bottom is `y(seam)`), and so do the edge
  bleed's side pieces beside it — the gutter, a pane divider and the body background continue
  into the partial line. The cost: a current-line highlight on the last visible body line grows
  by `r`. Text backgrounds and the caret stay one cell tall (a run's background is the shaper's;
  the bleed leaves text alone for the same reason). Phase 2, content drawn in a clipped partial
  row at the seam (Emacs's half-visible line), is ADR-615 (`[:above-seam ops]`).
- **The seam rides the frame; the top band too.** The seam moves pixels, not cells, so it is
  frame state — pure data from the app's view, carried to a thin client or a browser with the
  frame, and a split, a taller echo area or a header toggled at run time is just the next frame.
  The top band changes the row count, so a frame that changes it makes the window re-publish its
  size (`[:resize …]`), and the app lays out again; one frame is painted for the old count. A
  window setting (`gui/inset … {:top-band …}`) was the alternative, but an attached client's
  window settings come from its own machine while the header line is the daemon's model: the two
  would disagree. Read at the top level, first wins; a memoised fragment holding one is spliced
  (`frame_global`). `gui/render-frame` and `gui/capture` return `:seam` and `:row-tops` (every
  row's pixel top, then the last one's end), so a test reads the map instead of re-deriving it.
- **The edge bleed gains a top piece, for bands taller than one row**: with a top margin, a
  gutter or a pane background on row 0 continues up to the window's edge, so the frame stays
  finished (Rule 1: the inset is painted by the band that touches it). A band ONE row tall —
  the current-line highlight on line 1 — does not: bled up, its text would sit low in a taller
  band, which is the header-line fault ADR-508's last addendum removed. The bottom keeps
  bleeding one-row bands: the last row is an app's bottom chrome (bedit's echo area, a status
  bar), and a strip of window under it is the band floating off the edge that this ADR exists
  to stop; the inset there is the band's own margin, as on the sides, while the top margin is
  the TEXT's breathing room.

**Callers beyond bedit.** Any brood GUI program with a bottom status line under `gui-display`:
the REPL, the observer, a TUI-style app, `examples/` with a status bar.

**Consequences.** The layout is a property proved over every window height, not checked one
screenshot at a time. Guards: `backend/rows.rs`'s tests (the map, its inverse, saturation),
`offscreen::tests::the_seam_holds_the_leftover_at_every_height` (every height in a row's span,
two font sizes, band and not: the last row ends at `h - inset`, row 0 at 0 or the inset, the gap
painted by the row above, no bare pixel row, `px_to_cell` of every row's centre is that row) and
`without_a_seam_the_leftover_stays_under_the_last_row`, `bleed::tests::a_band_on_row_zero_covers_the_top_margin_when_there_is_one` (and a one-row band
not), and `tests/gui_test.blsp`'s "the seam holds the leftover at every height" and "a one-row
band on row 0 stays out of it; a taller band reaches the top edge" through `gui/render-frame`.

## ADR-611 — Text sits by CSS's line box, and blends in linear light at the encoded lerp's weight

**Status:** implemented (2026-11-05).

**Context.** Two things about how a GUI window draws text were measured against the design
review of bedit (its "Type and rendering" section, items 7 and 8).

*Placement.* The baseline came from cosmic-text's line layout of an 'M': half-leading around
the font's ascent/descent box, where that box is the hhea one unless the font sets
`USE_TYPO_METRICS`. DejaVu Sans Mono (the bundled `:mono`) and Hack do not, and their hhea
box is 1.16 em, stretched to clear every accent in the font, so text sat low: at 16 px in a
20 px cell the caps had four pixels above them and the descenders none below, and lowercase
ink was centred up to two pixels under the row's middle. ADR-516 centred geometric marks in
the whole cell, which put a status dot visibly off the text it marks.

*Weight.* ADR-358 moved text to a lerp of the ENCODED colours, because a plain linear-light
lerp makes every anti-aliased rim glow. That lerp has two faults. Light text on a dark ground
reads thin: a stem straddling two pixels at half coverage keeps 43% of its light. And a lerp
of two hues in the encoded space darkens between them. `gui-text-contrast!` (ADR-337) existed
to lift light text, but defaulted to no lift.

**Decision.**

- **Vertical metrics are read from the grid font's tables** (`FontVertical::read`): the OS/2
  typographic ascender and descender when they are plausible (a box of 0.6–2.5 em), the hhea
  ones otherwise, as CSS Inline 3 recommends; and the OS/2 x-height.
- **The baseline is CSS's half-leading, rounded once** (`line_box`): `L = cell − (A + D)`,
  `baseline = round(L/2 + A)` with the cell height already a whole number of pixels, so every
  row of every region (and every per-buffer zoom size) puts its baseline on the same pixel.
  One guard: where the font's hhea ascent (where its accents reach) would leave the cell, the
  baseline moves down ONE pixel, while the cell has room for it and the descent. DejaVu's
  accents reach 0.93 em, so at a line height of 1.25 the pure half-leading baseline cuts off
  an É's tip; going further than a pixel puts the lowercase visibly low again.
- **A geometric mark is centred on the lowercase beside it** (reconciling ADR-516, not a
  second rule): `centre_ink_vertically` targets `x_middle`, half an x-height (rounded as the
  hinter rounds it) above the baseline, instead of the cell's middle, as near as the cell
  allows. Check marks and crosses (`✓ ✔ ✗ ✘`, U+2713–2718, a gutter's pass and fail marks)
  join the Geometric Shapes.
- **Text blends in linear light with the encoded lerp's weight** (Ghostty's
  `linear-corrected`). The alpha is chosen so the linear-light result has the luminance a
  lerp of the encoded luminances at that coverage has (`text_alpha`): the hue mixes in linear
  light, the weight stays the encoded blend's, and for a neutral pair the two are identical,
  so ADR-358's numbers (white on black at half coverage = 128) still hold. The CPU painter does
  it per pixel (`TextInk`, decoding the ground once per distinct pixel, encoding through a
  table); the GPU draws text through the swapchain's sRGB view with the same formula in the
  shader (`fs_tex_linear`, `fs_tex_lcd_linear`, the per-channel variants), against the ground
  each glyph is given — its run's `:bg`, or the window background — carried as one more
  instance word. Text and translucent geometry now share the linear pass, so a frame of text
  and fills is one render pass. Without an sRGB view the GPU keeps the encoded lerp, which has
  the same weight. Subpixel text corrects each channel's coverage the same way.
- **`gui-text-contrast!` is the perceptual gamma light-on-dark text is weighted at**, not a
  parallel knob: coverage is lifted to `cov^(1/γ)` before the correction where the text is
  lighter than its ground (luminance, no longer Rec. 601 luma), so 1.0 is the encoded lerp's
  weight and about 2.2 linear light's. The runtime default goes from 1.0 to **1.4**, and
  bedit's `:text-contrast` default with it: white on black at half coverage lands at 155/255,
  between the encoded weight (128) and the linear glow ADR-358 removed (188, and 205 with the
  old 1.4 on top).

**Consequences.** At bedit's 15–16 px and 1.25 line height, text moves up one pixel in its
row and lowercase is centred within a pixel; a dot or check mark sits on the text's middle.
Light text gains weight by default, a little — in side-by-side screenshots the stems read
fuller and the rims do not glow, but it is a modest change, not a different look. Guards:
`line_box_tests` (the typo/hhea choice; the half-leading baseline and its guard; "Hxg" on five
rows at three sizes through `offscreen::picture`, the painter `gui/render-frame` uses, with
the cap top and baseline on the same pixel of every row and the `H` standing on the baseline;
lowercase ink centred within a pixel of the row's middle and of `x_middle` at 10–30 px and line
heights 1.25–1.6, which DejaVu's hhea box failed by up to 1.5 px), `tests/gui_test.blsp` (the
same through `gui/render-frame`), `a_geometric_symbol_is_centred_on_the_lowercase_beside_it`,
`text_mixes_hue_in_linear_light_at_the_encoded_lerps_weight`,
`the_contrast_gamma_moves_light_text_from_the_encoded_weight_to_linear_lights`, and
`backend/gpu_ink.rs`: a page of bedit's text on its ground carries the same ink on the GPU as on
the CPU painter (within 3%; 0.1% on Intel's Raptor Lake UHD, gray and subpixel, γ 1.0 and 1.8),
and γ 1.8 carries more than 10% more ink than 1.0 on both.

**Alternatives rejected.** *The hhea box with no change*: the low text this fixes. *Pure
typo half-leading with no accent guard*: accented capitals lose their tips at 1.25. *Stem
darkening or synthetic emboldening*: changes glyph shapes and advances and would put the
setting in the glyph cache's key. *A plain linear-light blend*: ADR-358's glow. *A separate
gamma setting beside text contrast*: the lift already is a gamma; two knobs for one quantity.
*A baseline-adjust setting* (Ghostty's `adjust-font-baseline`): not added; the half-leading
rule centres the fonts measured, and an app can pick its line height.

## ADR-612 — What a calm editor needs from the host: input→present as a distribution, which press is a repeat, the desktop's reduced-motion switch

**Status:** implemented (2026-11-05; `host/gui.rs` `LatencyHistogram` / `LatencyLog`,
`backend.rs` `record_latency`, `backend/keyboard.rs` `PressReceipt`; `gui/latency-histogram`,
`gui/latency-percentiles`, `gui/latency-merge`, `gui/latency-since`, `gui/key-repeat?`,
`gui/reduce-motion?`, `gui/reduce-motion-from`).

**Context.** bedit's UI review (2026-11-05) found three things a calm editor needs and no
program on brood could express. *Latency*: ADR-440 timed each input to the present of the
frame that answered it and kept the last 64 samples. A ring of 64 has a median and a worst,
but no tail: at ten keys a second one input in a thousand comes every hundred seconds, and
that p99.9 is what typing feels (Dan Luu's terminal measurements; Fatin's jitter finding).
Nor did the ring tell a key from a wheel step. *Key repeat*: a held key under `{:key-repeat
:os}` (ADR-441) arrives as presses identical to a fresh one, so an app could not keep
animation off a held key — bedit's pulse flashed behind every repeat of a held C-v. The
GUI thread already tells a repeat from a press by transition; the app could not ask which
press it was folding (`gui/held-key` says a key is down, which is true during a single tap
too). *Reduced motion*: every desktop has a switch asking apps for less animation, and none
of it is a window property winit reports.

**Decision.**

- *A distribution per kind of input.* Each window counts every input-to-present sample since
  it opened into a fixed log-linear histogram — exact below 16 µs, then 16 buckets per power
  of two, so a bucket is at most 6.25% wide; 432 counters; recording is an index and an add
  on the GUI thread — one for keys (a press, an OS repeat, an input method's commit) and one
  for the pointer (a button, a wheel step). The input stamp carries its kind to the paint.
  The 64-sample ring stays (`gui/latency`, each sample now saying its `:input`).
  `gui/latency-histogram` hands it over as plain data, `{:count n :max-us n :buckets
  {upper-us n}}`, a bucket keyed by the largest value it holds. Percentiles are Brood:
  `gui/latency-percentiles` reads p50 / p99 / p99.9 and the maximum off a histogram,
  integer ranks, a percentile reading as its bucket's top (never under the samples it stands
  for, never above the maximum). Because the data is buckets, two sessions add
  (`gui/latency-merge`) and a window of time is a later reading less an earlier one
  (`gui/latency-since`) — which is how an app keeps a distribution across sessions without
  the host keeping anything on disk. Rejected: percentiles computed in Rust (a fixed window
  the app cannot merge or persist), and a bigger ring (memory that grows with the tail it
  wants and still cannot span sessions).
- *Which press is a repeat, exactly.* The OS repeat already rides a mailbox credit (ADR-441's
  `RepeatGate`), released as the message leaves the mailbox. A fresh press now carries a
  credit too, a receipt costing nothing (`PressReceipt`). As a press leaves the mailbox its
  credit marks the window's `received_repeat`: a repeat's sets it, a fresh press's clears
  it, and a repeat taken back at the release marks nothing. Since the app folds a press after
  receiving it and before receiving the next, `gui/key-repeat?` asked during that fold
  answers for that press. Rejected: a repeat flag in the key message (every app's key
  vocabulary would change for a fact few need); inferring it in `ui-run` from the presses
  and `[:key-up …]`s it folds (the drain folds several inputs per turn, and the state would
  have to thread through all of them); inferring it in the app from `[:key-up …]` (a release
  would change the model and cost a view per keystroke).
- *The desktop's preference, read where each desktop keeps it.* `gui/reduce-motion?` runs
  the platform's settings tool once — GNOME's `gsettings get org.gnome.desktop.interface
  enable-animations`, KDE's `AnimationDurationFactor` in kdeglobals, macOS's `defaults read
  com.apple.universalaccess reduceMotion`, Windows' `MinAnimate` (what the "Animation
  effects" switch turns off) — and `gui/reduce-motion-from` is the pure reader over what each
  said, tested on any machine. Brood, not Rust: it is a subprocess and a file read, it needs
  no window and no GUI build, and a missing source counts as not asking. Not a live
  subscription: an app reads it at startup.

**Callers beyond bedit.** Any brood GUI app's latency report and CI performance gate (the
histogram is the number to gate on, with the tail in it); a game that wants a held key to
auto-fire differently from a tap; a terminal emulator or REPL with any animation, and any
program honouring the platform's accessibility switch.

**Consequences.** bedit records the key histogram in its slow-turn log and shows p50 / p99 /
p99.9 in M-x latency and M-x slow-turns; a held key starts no pulse; `:reduce-motion :auto`
follows the desktop. Measuring is for CI or a machine set aside for it: the tests here feed
the percentile functions synthetic histograms and check the receipt with dropped credits,
and nothing measures a real frame. Not covered: the time from the present to the panel
lighting (up to one refresh), which no API reports; a preference changed while the program
runs. Guards: `host/gui.rs` `latency_histogram_tests` (bucket bounds within 1/16, the last
bucket, a log counting each kind apart), `backend/keyboard.rs`
`each_press_marks_whether_it_was_a_repeat_as_the_app_takes_it`, and `tests/gui_test.blsp`
(percentiles, merge and since, the readers per desktop, a window not open).

## ADR-613 — A window has a default text colour, `gui/fg`, as it has a background

**Status:** implemented (2026-11-05; `host/gui/backend/render.rs` `Renderer::fg` /
`set_fg`, `backend.rs` `fg` and `UserEvent::Foreground`, `offscreen.rs`
`Request::Foreground`, `%gui-fg!`, `gui/fg`, `gui/render-frame`'s `:fg`).

**Context.** A text op whose face names no `:fg` was drawn in a colour the renderer
hardcoded: Catppuccin Mocha's text (`#cdd6f4`) in the CPU painter, `#e5e5e5` in the GPU
one — the two did not even agree. A program could set the window's background
(`gui/bg`) but not this, so a light theme painted its plain text — bedit's
identifiers with no syntax face, its echo line — light grey on a light ground, nearly
invisible in Catppuccin Latte. The program's only way out was to stamp an `:fg` on every
text op it emits, its own copy of "the default face" threaded through every view; a
terminal already has the default face (`term/bg bg fg`, ADR-586) a window lacked. The
same defaults gave a reversed face with no colour a near-black ground on any background.

**Decision.** `gui/fg` (`%gui-fg!`) sets the window's default text colour beside
`gui/bg`: what a `:text` / `:text-px` op whose face names no `:fg` is drawn in, on every
open window and the default for ones opened later, `nil` restoring the renderer's. Both
painters read it from the renderer (`Renderer::fg`), and a face with no `:bg` takes the
window background (`Renderer::bg`) instead of a constant, so a reversed face with neither
colour is the window's colours swapped. `gui/render-frame` takes `:fg` as it takes `:bg`;
a headless painting runtime (`BROOD_GUI_HEADLESS=paint`) keeps it as a window setting.
The renderer's fallback stays for a program that sets nothing.

**Callers.** bedit sets it from each theme's code-text colour when the theme is applied;
any GUI program with a light theme (a Brood REPL window, a viewer, a game's text layer)
needs the same, and a program that offers both a dark and a light theme cannot do without
it.

**Consequences.** One more window setting, a pure repaint. A program that relied on the
renderer's light default under a light `gui/bg` now gets that default still (it did not
call `gui/fg`); the GPU painter's default text and reversed ground now match the CPU
painter's. Guards: `tests/gui_test.blsp` "text whose face names no :fg is drawn in the
window's text colour" (a full block's ink and a reversed blank's ground are the `:fg`).

## ADR-614 — A definition's name and punctuation are faces of their own; a face-table selector can read the sibling before a node

**Status:** implemented (2026-11-05; `std/editor/highlight.blsp` `:syntax/definition`,
`:syntax/punctuation`, `hl-name-place?`; `std/editor/lexer.blsp` roles; `host/treesit.rs`
`Selector::after`, `TokenRules`; `std/editor/treesit.blsp` `token-rules`).

**Context.** bedit's UI review (2026-11-05) proposed a calm syntax theme on Tonsky's rules
(his Alabaster): colour definitions and literals, leave keywords and calls plain, dim
punctuation. None of the three highlighters could say it. The face vocabulary had ONE face
for a call's head and a definition's name (`:syntax/function`), so a theme colouring one
coloured both; the Lisp lexer did not mark a `def…` form's name at all; brackets had no
face, painted only by the rainbow option; and a tree-sitter face table could not find an
Elixir `def`'s name: `def main(x)` parses as a call whose argument is the call `main(x)`,
the same shape as `foo(bar(x))` — what differs is the identifier the `arguments` follow, a
sibling, and selectors read only a node's own kind, field, position, text and ancestors.

**Decision.**

- *Two faces in the shared vocabulary.* `:syntax/definition` is the name a definition binds,
  `{:inherit :syntax/function}` by default, so a theme that names neither sees no change in
  any table that moved a definition to it. `:syntax/punctuation` is brackets, commas and
  semicolons, `{}` by default — and a face with no attributes paints no span, so the default
  costs nothing per bracket. They are std's, beside the other `:syntax/*` faces, because the
  terminal REPL's line editor, the observer and any program fontifying text through
  `editor/highlight`, `editor/lexer` or `editor/treesit` read the same registry.
- *The Lisp lexer marks the name place.* A head in the pass's special-form set that starts
  with `def` is a definer — Brood's `defn` / `def` / `defmacro` / `defmodule`, elisp's
  `defun` / `defvar`, Clojure's `defn`, Scheme's `define` — as is a docstring-carrying head
  (`defn-`, `(reflect/doc-forms)`) and the private `-` form of a special one (`def-`); the
  form right after it is the name; when that form is a list (Scheme's `(define (f x) …)`), its head is. A bracket takes
  the rainbow depth face when that option is on, else the punctuation face when it paints.
  `editor/lexer` grammars may name `:definition` and `:punctuation` roles.
- *A selector's `:after`.* `{:kind :arguments :after {:text #{"def" "defp"}}}`: the named
  sibling right before the node must satisfy a map of `:kind` and `:text` alone. The walk
  already stands on the parent's cursor, so the previous named child is carried in the
  node's context for nothing. It weighs 32 in a level's specificity, above `:text`. The
  nesting bound rises from three maps to four, which is what reaches the name a GUARDED
  clause defines (`identifier` in `call` in `binary_operator` in `arguments`).
- *Punctuation as a token rule.* A span query's `keywords?` may be a set, `#{:keywords
  :punctuation}`; `:punctuation` reports an anonymous token made only of `()[]{},;` as
  `:__punctuation__`, the way an alphabetic one is `:__keyword__`. An anonymous token's kind
  is its text, so the test reads no text. `true` still means keywords alone. `fontify`,
  `fontify-tree` and `fontify-ranges` ask for it only while `:syntax/punctuation` paints
  anything, read per call.

**Rejected.** *A definition flag on the call face* (`:syntax/function` with a `:definition`
variant): a face is a name, and a theme restyles by name. *Punctuation entries in each
language's table*: every grammar spells its brackets as different anonymous kinds, a table
naming a kind its grammar lacks is reported as a grammar mismatch (ADR-583), and the default
would pay a span per bracket. *A general sibling selector* (any sibling, any constraint): the
case is "what this node follows", and the previous named child is what the walk has in hand.
*Colouring Elixir definitions in bedit after the walk*: the walk reports the outermost
coloured node, so the decision has to be made inside it.

**Callers beyond bedit.** The REPL's line editor (`editor/lineedit` reads `highlight-spans`),
any theme a brood program defines over `:syntax/*`, and any tree-sitter host that wants a
language's definitions apart from its calls.

**Consequences.** In a theme that leaves the two faces alone, every tree-sitter language
looks as it did; the Lisp lexer now paints a `def…` form's name in the call colour where it
painted nothing. Guards: `tests/highlight_test.blsp` (a definition apart from a call in
Brood, Scheme and elisp; the line lexer across a line break; punctuation off by default, on
with a face, the rainbow over it), `tests/lexer_test.blsp` (the roles),
`tests/treesit_module_test.blsp` (`:after` by text and by kind, a guarded `def` four maps
deep, a held tree, punctuation by token rule and through `fontify`, malformed `:after`
refused by the kernel and named by `face-table-problems`).

## ADR-615 — The leftover strip shows the next line: `[:above-seam ops]` lays the text out past the seam and cuts it off there

**Status:** implemented (2026-11-05). Phase 2 of ADR-610.

**Context.** ADR-610 put the leftover height (0..cell_h-1 px) at the seam, between the text
body and the bottom mode line, and filled it by stretching the backgrounds of the row above
— padding the size of up to a line. Emacs shows a window's partly visible last line there,
clipped; so does every editor whose text area absorbs the surplus. bedit's design review
(`reports/Editor UI design for bedit.md`, "The layout decision") asked for that: the strip as
content. Three shapes were weighed.

- **The strip as a short grid row** (`[:seam row {:partial true}]`, the grid one row taller,
  that row `gap` px high). The app would paint its last body row there unchanged and the
  hit-test would need no flag. Rejected: every overlay that crosses the row (a transient menu
  anchored above the mode line, a popup) gets a row squashed to a few pixels, its text cut in
  half; the row count would change with the window's height mod a cell; and the app would
  have to keep its scroll logic from counting the row as visible.
- **A group painted only in the strip** (`[:partial-row ops]`, the next row's ops alone).
  Clean to paint, but the app must produce the next row's ops apart from the rest of its
  text: an editor builds a pane's gutter, bands, text and notes for a range of rows, and
  multi-row rects (the gutter wash) would have to be cropped. Or the pane is painted twice.
- **A group laid out past the seam and cut off at it** — chosen.

**Decision.**
- **`[:above-seam ops]`** (`editor/display/above-seam`, `Op::AboveSeam`): the ops are laid out
  on the rows above the seam carried on as if the grid had no seam — `top + row·ch`,
  `RowMap::uniform_rows` — and clipped where the seam's row begins (`RowMap::seam_top`).
  Above the seam the two maps agree, so the group's rows paint where they always did; what it
  puts on the seam's own row number lands in the strip, its top `gap` px showing; nothing of
  it reaches the bottom-anchored rows. So an editor wraps a pane's scrolling layers, rendered
  ONE ROW TALLER, in the block, and the strip shows the next line — text, gutter number,
  bands — clipped, with no second pass and no cropping. A group's rows do not stretch (a
  current-line band on the last whole line stays one row, curing ADR-610's cost); what shows
  under the group in the strip is what the frame painted before it.
- **One row map still.** The group is a scope with another `RowMap` (`uniform_rows`) and a
  clip, like a `CellRegion` without the metrics: both painters (`render_ops`, the GPU
  `expand`), the CPU strip diff (each leaf of a group carries `above_seam` and its band is
  computed on the group's rows and cut at the seam; a blit never pairs a leaf in a group with
  one outside), the edge bleed (descends, the pieces clipped with the rest), the zones (cut at
  the seam), the IME caret walk, the memo harvest, the fragment splice, the effects walk.
  Without a seam the ops paint as they are; inside a cell region too; the terminal and the
  browser frontend draw them in place.
- **The hit-test follows the content.** A frame that carries an `AboveSeam` anywhere a painter
  reaches it with the window's rows (top level, fragments, scroll regions — `frame_layout`)
  makes the map `partial` (from half a row, above): a pointer in the strip is reported on the SEAM's row, the row its
  ops were laid out on, with `:partial true` in the trailing map (`Mouse::partial`), and its
  `:at` row is `seam + f`, f the fraction into that row (so `floor(:at)` is still the row).
  Without the flag the strip stays row `seam - 1`'s, stretched, as in ADR-610. The flag is
  needed because the seam's row number is also the bottom-anchored row's (the mode line); an
  app that paints the strip reads it. Pointer-shape zones fold the strip into the row above
  still (`uniform_y`): in uniform space the strip's row is the mode line's.
- **Only from half a row.** The strip shows the next line only when it is at least half a row
  tall (`gap * 2 >= cell_h`, decided in `RowMap::window`); under that the block paints on the
  window's own rows (`RowMap::above_seam_rows`), so the strip is phase 1 exactly — the row
  above's backgrounds stretched through it, the block's seam row landing on the
  bottom-anchored row where the cut removes it — and a click in it is row `seam - 1`, not
  `:partial`. The reason is legibility, seen in bedit at 600 / 607 / 613 px (cell 19 px): a
  5 px strip shows only the tops of the tallest letters, a row of specks on the mode line,
  worse than the plain band; 12 px and up reads as a line cut short, which is what Emacs
  shows. The renderer owns the rule because only it knows the leftover in pixels; the app
  paints the block at every height and never learns which side of the rule it is on.
- **A seam with no leftover is kept in the map** (`RowMap::window`), so a group is cut off at
  the seam at every height, not only where there is a strip.

**Callers beyond bedit.** Any GUI program with a bottom status line under a scrolling text
(the REPL, the observer, a log viewer): wrap the text in `above-seam`, paint one more line.

**Consequences.** bedit's bottom panes show their next line in the strip (`view/ed-partial-row-pane`)
and a click there lands on it and scrolls it in (`panes/ed-mouse-unstrip`), as Emacs does; the
scroll logic is untouched, since the pane's whole rows are still its text rows. During a smooth
scroll's glide the group holds one extra row only, so the bottom of the strip can show the
window's ground for the frames of a glide. Guards: `backend/rows.rs`
`a_painted_strip_is_the_seams_row_to_the_hit_test` and `a_seam_with_no_leftover_is_kept`;
`a_strip_under_half_a_row_stays_phase_one`;
`offscreen::tests::the_strip_shows_the_next_line_from_half_a_row_at_every_height` (every height
in a row's span, two font sizes: from half a row the strip's pixel rows are exactly the next
line's top as it paints with no seam and its pixels hit-test to the seam's row, flagged; under
half a row, and everywhere outside the strip, the picture is phase 1's pixel for pixel and the
strip hit-tests to the row above); `tests/gui_test.blsp` "from half a row the strip shows the
next line clipped; under it, phase 1" through `gui/render-frame`; bedit's
`tests/window_paint_test.blsp` (600 px: a 5 px strip, plain; 607 and 613 px: the line's ink).

## ADR-616 — A keyword literal and a named constant are faces of their own, apart from a language's keywords

**Status:** implemented (2026-11-06; `std/editor/highlight.blsp` `:syntax/symbol`,
`:syntax/constant`, `hl-faces`; `std/editor/lexer.blsp` roles).

**Context.** bedit's "Catppuccin Mocha Calm" theme follows Tonsky's rules (ADR-614): keywords
plain, literals coloured. `:syntax/keyword` named two things. The tree-sitter tables report a
language's KEYWORDS there — Python's `def` and `return`, Rust's `fn`, Elixir's `do` / `end`, every
anonymous keyword token (`face-of-syntax`) — and the Lisp lexer painted its `:keyword` token kind
there: `:foo`, and `nil` / `true` / `false`, which the reader classifies with them, LITERALS. A
theme colouring `:foo` as a literal coloured `def` with it. The tree-sitter and lexer tables, for
their part, coloured their literal constants (`True`, `null`, an Elixir atom, a Ruby symbol) as
`:syntax/special`, the face the Lisp lexer paints special forms in — a keyword again — so a theme
leaving keywords plain left those literals plain too.

**Decision.** Two faces beside the others in std:

- `:syntax/symbol` — a symbol used as a value: the Lisp lexer's `:keyword` token kind (`:foo`,
  `nil`, `true`, `false`) and a data format's key (a JSON / YAML / TOML / INI key, a name written
  as data). `{:inherit :syntax/keyword}`.
- `:syntax/constant` — a constant a language names: `true` / `false` / `nil` / `None` / `null`, an
  Elixir atom, a Ruby symbol. `{:inherit :syntax/special}`.

Each inherits the face its tokens were painted in, so a theme that names neither sees nothing
move. `editor/lexer` grammars may name `:symbol` and `:constant` roles. `:syntax/keyword` is
now only a language's keywords, and `:syntax/special` the Lisps' special forms plus what a
table still files there (types, attributes, decorators).

**Rejected.** *One literal face for both.* The default palette paints the Lisp's `:foo` in the
keyword colour and the other languages' constants in the special colour; one face could keep
only one of them, and changing a default theme's colours was not the point. *Moving Lisp's
`nil` / `true` / `false` to `:syntax/constant`*, where the other languages' constants are: the
same reason — their default colour is the keyword one. A theme that colours literals names both
faces, which is two entries, not a loss. *Retargeting `:syntax/keyword` at the literals and adding
a face for language keywords*: every tree-sitter table and `face-of-syntax` name the keyword face
for keywords, and the anonymous-keyword rule is the cross-language default (ADR-487); the
literals are the smaller set to move.

**Callers beyond bedit.** The REPL's line editor and the observer (`highlight-spans`), and any
program that themes `:syntax/*`.

**Consequences.** Under a theme that leaves the new faces alone, every highlighter paints what it
did. Guards: `tests/highlight_test.blsp` ("a :keyword literal takes the symbol face": styled
apart, `:foo` / `nil` / `true` / `false` leave the keyword face; the line lexer agrees; by default
the faces are equal), `tests/lexer_test.blsp` (the roles, and a grammar's keyword / symbol /
constant painted apart under a theme).

## ADR-617 — A failure carries fields beside its message; the HTTP clients and the registry answer with one

**Status:** implemented (2026-11-06; `builtins/errors.rs` `%failure` / `%failure-fields`,
`failure/with` in `prelude/control.blsp`, `fields` in `prelude/abilities.blsp`; callers in
`net/http.blsp`, `tool/package.blsp`, `tool/update-brood.blsp`).

**Context.** ADR-310 gave expected failure its own kind, but a failure carried only a message.
A caller that had to tell one failure from another — the registry's 404 from its 500 — could
not without parsing text, so the code that most needed to branch kept its own encodings: the
HTTP clients answered a transport failure as a response, `{:status 0 :error msg :headers {}
:body #b""}`, and `registry-get-json` answered `[:ok data]` / `[:error status msg]`. Three
conventions for one idea (`docs/archive/failure-encoding-cleanup.md` step 4). The storage was never the
obstacle: a failure is a CHAMP map under its own tag, and printing, equality, messaging and the
wire format already handle any number of fields; only the constructor took one string.

**Decision.**

- `(failure/with fields & parts)` returns a failure whose fields are the map `fields` plus
  `:message`, the concatenated parts, as for `failure`. The fields may not name `:message`
  (raises): the message is always the one the parts spelled, so `error-message` cannot be made
  to disagree with what was written.
- `fields` — already the way into a record (ADR-542) — reads a failure's fields as a plain map,
  `:message` among them. A failure stays not-a-collection: `get` on one still raises, so a
  caller asks `failure?` first and the checker narrows on it.
- The kernel change is one optional argument on `%failure` and a `%failure-fields` accessor.
- `http/request`, `fetch`, `post` and `request-on` answer a transport failure (no connection,
  a dropped read, the connection process not answering) with a `failure`; a response with any
  status is still a response. A `:status 0` response was a response that did not exist, and
  every caller had to remember to test for it before reading `:body`. The checker now types the
  result `failure | http/response`, so a caller that reads the response without asking is told.
- `registry-get-json` answers the decoded object, or a failure: `(failure/with {:status s} …)`
  for an answer the registry gave, a plain failure when it could not be reached. The callers'
  404 test is `(= (get (fields f) :status) 404)`.

**Rejected.** `failure` taking a map as its first argument (an overload that changes the
meaning of `(failure some-map)`, which prints the map today); a separate `failure-data`
accessor (`fields` already names "the fields of a kind that wraps a map"); keeping `:status 0`
(a sentinel inside the success type is what ADR-310 exists to remove); a `:status` field on a
transport failure (there was no status — the field would be the sentinel again).

**Consequences.** Every failure-shaped result in std now uses one encoding. `nest check
--strict` found the 18 test reads of a client response and one in `package.blsp` that assumed a
response; the tests go through a local `answered` helper that raises on a failure.

## ADR-618 — A macro's error is placed at the call, or at the sub-form it names

**Status:** implemented (2026-11-06; `eval/macros.rs` `macroexpand`, `builtins/errors.rs`
`%raise`'s `:at`, `reflect/error-at` in `prelude/control.blsp`). Finishes ROADMAP "What the
other Lisps have", item 6 (ADR-434 left "an error located at the offending sub-form" open).

**Context.** ADR-434 said a macro's error sat at the macro call. It did not: the compile pass
expands a whole top-level form before running it, and an expander's error carried no position
of its own, so it took the position of the top-level form — `(defn f () … (for (x xs y) …))`
reported the `defn`, however far down the `for` was. And nothing let a macro say *which part*
of the call was wrong; Racket's `syntax-parse` is the bar for that.

**Decision.**

- `macroexpand` keeps the call it was handed rooted, and an error with no position of its own
  is placed there (`or_form_pos`, so an inner position still wins). This covers an expansion
  the macro *built* — `match` expands to a `match*` call with no reader position, whose errors
  now land on the user's `match`. The tree-walker's lazy expansion already did this.
- `%raise` takes an optional `:at form` entry: the error is placed at `form`'s recorded position
  and file, and the entry is removed from the map — it is a place, not part of what a handler
  is handed. `(reflect/error-at form & parts)` is the surface, `error` with a place. It sits in
  `reflect/` beside `gensym` and `macroexpand`, the other macro-writing tools.
- The prelude's own checks use it where the offending piece is a list: `for`/`fold-for`'s
  binding list, `dotimes`/`dolist`'s bind, `binding`'s pairs, `receive`'s misplaced `after`,
  `try`'s clauses, `match`'s guardless `:when` and dead clause, `defmodule`'s unknown filter.
  `dotimes` and `dolist` moved onto pattern clauses (ADR-434), one per shape.

**Rejected.** Positions on vectors and atoms (the form-position table is pair-keyed by design —
`read_vector`); a `:hint`/`:at` clause syntax on `defmacro` (a function call does it, ADR-011);
moving every hand-rolled prelude check onto clauses in one sweep (most check a list's contents,
which a clause head cannot say; they move as they are touched).

**Consequences.** Guard: `tests/macro_error_position_test.blsp` (each half sabotaged red). An
error map the language raises can now carry a position the raise did not have; `:at` is the only
way to get one, and it never reaches a handler.

## ADR-619 — One grammar for every `fn` head; clauses run in order, and a shadowed clause is refused

**Status:** implemented (2026-11-06; `core/value.rs` `select_arm_by`, `eval/macros/patterns.rs`
`shadowed_clause_error` / `lower_fn`, `prelude/match.blsp` list patterns, `hygiene.rs`,
`resolve.rs`). Supersedes ADR-047's arm-selection rule and ADR-152/226/434's refusals of
`&optional` in pattern and guarded clauses. Closes the matrix ROADMAP § D's closing note named.

**Context.** A `fn` head obeyed three rules that interacted: arity clauses did not mix with
pattern clauses (any pattern sent every clause to the match engine, where `&optional` was
refused), an `&optional` slot could not be a pattern, and `:when` did not combine with
`&optional`. Worse, the two kinds of multi-clause `fn` had different dispatch: arity clauses
picked the most specific arm whatever the order (ADR-047), pattern clauses went in order. Each
rule was defensible alone; together they were a table users had to look up.

**Decision.**

- *One head grammar.* Required slots are patterns; after `&optional`, a slot is `name`,
  `(name default)` or `(pattern default)` — a default runs only when its argument is absent
  and sees the names bound before it; after `&`, a name or a pattern; a `:when` guard first in
  the body, a single-clause `fn` included. `match`'s list patterns take the same `&optional`
  slots, which is what lets a pattern clause — a list pattern over the arguments — take them.
- *One dispatch rule.* Clauses are tried in order and the first that matches runs, by count
  and by shape. `select_arm_by` takes the first accepting arm, so the native arity path and
  the match engine agree; plain-symbol heads still bind natively.
- *A shadowed clause is a compile error.* A clause whose every call an earlier one takes — the
  earlier accepts every argument count the later does, has no guard, and every slot is a plain
  name (a repeated name is an equality test, so it is not) — can never run, and the `fn` is
  refused, naming both. Checked in `lower_fn` (the compile pass) and where arity arms are built
  (a `fn` the compile pass never saw). This is what keeps order from deciding silently, the job
  ADR-047's most-specific rule did; partial overlap stays legal and runs the first.

**Migration.** A temporary audit compared ADR-047's choice with first-match for every
arity-only `fn` across std, tests, examples and bedit (`nest check` expands them all): no
function chose differently, and no clause was shadowed but one test of the old tie-break.

**A single clause's guard.** `(defn f (x) :when (string? x) …)` keeps its native parameters:
the guard wraps the body (`(if guard body <the match error a failed clause raises>)`), so the
checker still reads the parameters and the guard's domain (`(f 5)` is "argument 1 expects
string"). Only a pattern `&optional` slot or a pattern rest lowers a single clause to `match*`.
Before, a single clause's `:when` was not a guard at runtime at all — it evaluated as two body
forms and the body ran on any argument — while the checker already read it as one; no program
in std, tests or bedit wrote one.

**Found on the way.** Hygiene read an `&optional` default in a macro template as a pattern, so
its names were renamed as binders: `` `(fn (a &optional (b (+ a 10))) …) `` raised `unbound
symbol: +__733` (the plain native `fn`, before this ADR too). Name resolution likewise took a
default's names for binders, leaving a module-private call in one unqualified. Both now treat
the default as an expression.

**Rejected.** Keeping most-specific-first for arity clauses (two rules); making partial
overlap an error too (`((0) …) ((n) …)` is the point of pattern dispatch); `&key` (still
ADR-163's options map).

**Consequences.** Guard: `tests/fn_heads_test.blsp` (the order, the refusal at both check
sites, the slots, hygiene and resolution across modules — each sabotaged red). A macro that
generates clauses in a computed order meets the same refusal at expansion.

## ADR-620 — `()` stays `nil`; a truthiness test on a list-or-other-collection is a lint

**Status:** implemented (2026-11-06; `types/check/walk/binders.rs` `check_if`, the
`:list-truthiness` category). Decides `docs/archive/empty-list-truthiness.md`; amends ADR-003.

**Context.** `()` reads as `nil` (ADR-003), so the empty list is the one collection whose
empty value is falsy: `(if () …)` takes the else branch, `(if [] …)` the then. ADR-003 chose
it as a consequence of classic cons lists, never on its own merits. The scoping weighed three
options: Clojure's split (only empty *results* become a truthy `()`, `nil` still ends a
chain), a strict split (`()` its own value, `nil` never a list), or keeping it with a lint.

**Decision.** Keep it, and lint the case that bites.

- *Why keep it.* Lists are mostly code in Brood — data is vectors and maps, whose empties are
  already truthy — so the asymmetry meets a value in exactly the place where `(if xs (f (first
  xs) (rest xs)) done)` is the idiom of Common Lisp and Emacs Lisp, and where the checker's
  narrowing (`(if xs …)` makes `xs` a `pair`) pays. Clojure's split is its worst ergonomic
  wart: two list terminators, `rest` against `next`, and `(seq x)` as a ritual. A strict split
  is clean but costs one to two weeks and turns every missed end-of-list test into a silent
  infinite loop that no address-space cap catches, for the collection users are told not to
  use for data.
- *The lint.* A truthiness test — `if`, and everything that lowers to it: `when`, `and`, `or`,
  `cond` — whose type positively admits a list that can be empty (`pair` and `nil`) and a
  vector, map, set or string is reported: that test answers by kind when the value is empty.
  A list alone, `nil` as absence beside a vector, a list known non-empty (the
  constant-condition lint's case), and `any` are not. `(check-allow :list-truthiness …)`
  keeps one on purpose.

**Measured.** No finding across std, tests, examples or bedit when it landed — the habit
`empty?` already carried the code; the lint is for the next program.

**Consequences.** `docs/language.md` §Truthiness gives the reason with the asymmetry.
Reopen only with a program whose workaround costs more than a split would.

## ADR-621 — `file/replace`: the write for a file a person keeps

**Status:** accepted (2026-11-06).

**Context.** `file/spit` is `fs::write`: it truncates, then writes. An editor's save went through
it, so a crash, a power cut or a full disk in that window destroyed the file being saved, and
Emacs's mail shows how that is felt (#21612, #15902). `file/spit-atomic` is no answer: a temp file
and a rename give the file a new inode, and with it the default mode and this user's ownership,
and a symlink at the path becomes a plain file.

**Decision.** `(file/replace path content)` writes a sibling temp file, `fsync`s it, renames it
over the path and syncs the directory. It follows a symlink and replaces the target. It gives the
temp file the old file's owner, group and mode. A write that fails leaves the old file and no
temp file, and raises.

It writes in place, with `file/spit`'s risk, when a rename would change what the file is: a file
with other hard links, one whose owner this user cannot keep, extended attributes (a
`security.selinux` label excepted, since the directory gives the new file the same one), a
device, a directory that takes no new entries, a rename the filesystem refuses (a bind mount), a
dangling symlink. That is Emacs's own rule for when to back up by copying. A full disk is never
one of these: the bytes that did not fit do not get a second try on the only copy.

It is a builtin because `fsync`, `fchown` and the extended attributes have no Brood surface, and
none of them is wanted apart from this. `save-buffer` and `nest`'s codemod use it.

**Limits.** A write in place is not atomic, and nothing says so: the file ends up right. On
Windows it was always a write in place: a rename there loses the DACL. ADR-671 (2026-11-09)
replaced that with `ReplaceFileW`, which keeps it. A rename changes the inode, so a process
following the old file keeps the old text. A
crash between the temp file's creation and its rename leaves a `.brood-replace-*` file behind.

## ADR-630 — The editor toolkit split along its seams

**Status:** accepted (2026-11-06).

**Context.** `editor/buffer` said it was pure and held the buffer process. `editor/serve` was both
ends of a protocol, so a thin client loaded the daemon, and `editor/ui` was the frontends and the
loop, so that client loaded the loop too. Reviewed by reading calls rather than `:use` clauses, the
cost was the same each time: a caller that wanted one half paid for the other, and a change to
either had to be read against both.

**Decision.** A module holds one layer and a move goes to the module of the layer it belongs to.
No aliases: every public name that moved has a `renames.rs` entry, and each caller adds a `:use`.

- `editor/span-properties`: text-property spans as pure data. It takes no buffer.
- `editor/buffer-server`: the process that owns a buffer, and the client calls of its protocol.
  `editor/buffer` is pure. `splice-transform` stays there: it is arithmetic over splices and the
  client's fold needs it without a process.
- `editor/buffer-file`: a buffer and the disk. `buffer-replace-text` stays pure and `revert-buffer` is
  a read plus that.
- `editor/serve-protocol`: what a daemon and its client share. `editor/attach`: the client, which
  loads no daemon.
- `editor/frontend`: displays and their input. `editor/ui` is the loop that drives one, and a thin
  client needs no loop.
- `editor/line-cache`: the line-state cache, which takes its lexer as data.
- `editor/grammar-install`: fetching and building a grammar. `editor/treesit` touches no git, compiler
  or file, and only asks the runtime.

Inside `editor/buffer` the sections are layered too: spans, then the splice log, then undo, then
the editing commands, with no calls back up.

**Consequences.** A caller adds a `:use` for each home its names moved to. The ledger's entries
are qualified, so `nest check` names the new home of a qualified spelling; a bare name under the
old `:use` reads as plainly unbound. `editor/lineedit` still loads the Brood highlighter: the REPL
wants it.

**Addendum: the text commands leave for bedit.** The same review found paragraph and sentence
motion, `whitespace-run-at`, `collapse-whitespace`, `fixup-whitespace`, `join-line` and the
rectangle operations in `editor/buffer`, about 380 lines. Only bedit and their own tests called
them, and they are features over public buffer calls, so by ADR-417 they are bedit's: its
`bufferops`, tests included. `back-to-indentation` stays, with the word motions. Each name has a
ledger entry pointing at `bufferops/`, which nothing in this repository binds, so
`tests/renames_test` checks only that the old name is gone for a name that left Brood.

## ADR-631 — A window whose display goes away tells its app: `[:hangup :display-lost]`

**Status:** accepted (2026-11-08).

**Context.** When the Wayland compositor or the X server dies, the GUI thread's event loop cannot
go on, and an app was told nothing. On Wayland winit's `run_app` returned an `ExitFailure` that
`run_gui` dropped (`let _ =`): the GUI thread ended, every window's app sat in `receive` waiting for
input that would never come, and a draw raised `gui thread is gone`. On X11 it was worse: winit
reads events through Xlib and installs no I/O error handler, so Xlib's default one called `exit(1)`
on the GUI thread and the whole runtime ended mid-turn. An editor lost every unsaved buffer either
way. The terminal had the answer already (ADR-586): SIGHUP and SIGTERM reach the loop as
`[:hangup sig]`, `ui-run` runs the app's `:on-hangup` (bedit auto-saves) and ends.

**Decision.** The window uses the terminal's vocabulary. Once the display is gone, every open
window's subscriber is sent `[:hangup :display-lost]` on the priority lane, once, and `ui-run` acts
on it as on any hang-up: `:on-hangup` with `:display-lost` as the signal, then the end of the loop,
then `:leave`. From then on `gui/draw`, `gui/settle` and the window ops are no-ops (there is
nothing to paint on, and the loop must reach the message rather than die raising), and
`gui/open` fails with `the display is gone`. It is detected in two places:

- `run_app` returning, by error or by a panic inside winit (caught): nothing in Brood asks the loop
  to exit, so a return is always the display going away.
- An Xlib I/O error handler, installed after the event loop is built when libX11 is already
  loaded (`dlopen` with `RTLD_NOLOAD`, so a Wayland session loads nothing and no new crate is
  linked). Xlib calls `exit` when a handler returns, so this one tells the apps and parks the GUI
  thread for good; the rest of the runtime saves and exits on its own terms.

A new message (`[:display-lost]`) was the alternative. It would have needed its own predicate, its
own arm in `ui-run` and its own hook in every app, for the same response a hang-up gets. An app
that cares which it was reads the signal.

`(%gui-lose-display why)` runs the same path from Brood, so it is tested headless
(`tests/gui_display_lost_test.blsp`). bedit handles it with the terminal's handler: every unsaved
buffer to its sidecar, no restart.

**Limits.** Not tried against a real compositor crash in CI, which has no display server to kill;
the detection is winit's behaviour as read in winit 0.30.13. macOS and Windows have no display
server to lose; their `run_app` returning is handled the same way. A Wayland compositor that
survives a client disconnect (a reconnecting one) is not followed: the windows are gone, and a new
`gui/open` fails. An X11 session whose GPU path loaded libX11 for Vulkan also takes the handler,
which is right: that connection failing is the display failing.

## ADR-632 — Bidirectional text: not yet; the cell grid is left-to-right, and what reordering would take

**Status:** not yet (2026-11-08). Records the gap and the shape of a fix; nothing is decided to
build.

**Context.** The display seam is a grid of cells in logical order. A string's characters are
grapheme clusters laid left to right, each 0, 1 or 2 cells (`text_width`, ADR-342), and the three
layout primitives — `string/display-width`, `string/width->index`, `string/expand-tabs` — are
monotonic: a later character is never left of an earlier one. Everything above them assumes it:
bedit's row tables (`panes`), its wrap (`wrap.blsp`, which breaks a line into `[from to]`
segments in logical order), the scroll clamp, the caret, a click, a highlight range
(`[start end face]`, one span of cells). Brood implements none of UAX #9, the Unicode
Bidirectional Algorithm.

What IS done, for the bidi controls only:
- They are glyphless (ADR-556): zero cells by default, shown as `<202e>` when
  `*glyphless-display*` is `:hex-code`, and bedit's `glyphless.blsp` paints U+202A–202E,
  U+2066–2069, U+200E/F and U+061C with a hazard face — Emacs's
  `highlight-confusing-reorderings`, against Trojan Source (CVE-2021-42574).
- Because nothing reorders, a Trojan Source line is shown in the order the compiler reads it.
  That is the safe reading of code, and it is so by omission, not by design.

**What breaks for right-to-left text today.**
- *The GUI.* Each grapheme cluster is shaped alone (`render::shape_cluster`) and drawn in its
  cell, in logical order. Hebrew therefore reads backwards: the first letter of a word is the
  leftmost. Arabic reads backwards *and* unjoined: shaping one cluster at a time gives every letter
  its isolated form, so no word looks like Arabic. Diacritics stay on their base (they are in its
  cluster). Digits inside RTL text are not reordered either (UAX #9's weak types).
- *The terminal* (`-nw`). Brood writes each row's cells in logical order. Most terminal emulators
  (xterm, Alacritty, kitty) draw them as given, with the GUI's result. One that applies bidi itself
  (mlterm, Konsole, VTE with BiDi on) reorders the row it was given, so the screen no longer
  matches the cell grid Brood keeps: the caret, a click and a partial repaint (ADR-586 writes only
  the cells that changed) land on the wrong characters.
- *Point and columns.* `C-f` moves to the next character, which is the next cell to the right.
  That is right for the logical order the screen shows, and wrong for any reading of RTL text.
- *Wrapping and truncation.* A wrapped RTL paragraph puts its first words on the left of the
  first row. The `…` of a truncated line (`wrap/one-row`) cuts the logical end, which in RTL
  text is the visual left.

**What an implementation would need.**
1. *UAX #9 as a primitive.* The algorithm per line (a buffer line is the paragraph, as for code;
   prose may want Emacs's paragraph separation), with a base direction that is `:ltr`, `:rtl` or
   `:auto` (rules P2–P3, the first strong character), giving the embedding levels and the visual
   runs. The `unicode-bidi` crate is already in the tree through cosmic-text; the primitive would
   return `[[from to level] …]` in visual order, so the policy above stays Brood.
2. *Wrap before reordering.* UAX #9 reorders each line *after* it is broken (rule L1–L2 apply per
   display line). So the wrap keeps its logical segments and each screen row is reordered alone —
   which keeps bedit's `wrap` and the row table's logical `[from to]` as they are.
3. *A non-monotonic cell map.* Per screen row, a logical index ↔ visual cell permutation. The three
   layout primitives stay the logical measure; a fourth answers "which cell shows index i" and
   "which index is at cell c". The caret, a click, the mouse drag and the scroll clamp go through
   it. At a direction boundary one logical position has two visual places; Emacs draws the caret
   at the one belonging to the character after point, and so should this.
4. *Logical and visual motion.* Emacs's default is logical (`C-f` is the next character, which
   may jump across the screen), with `visual-order-cursor-movement` for the arrows. The same choice
   here: commands stay logical; the arrow keys can be visual behind a setting.
5. *Ranges become several spans.* A region, a search hit, a highlight `[start end face]` covering a
   direction change is one logical range and several visual spans on its row. The view's span
   painting would split each range per row through the map in 3.
6. *Shaping a run, not a cluster.* An RTL run must be shaped as a whole so Arabic letters take
   their joining forms, then each cluster's glyphs placed in that cluster's cells. Joining strokes
   only meet at cell edges with a font whose Arabic is monospaced; with any other the result is a
   compromise every grid editor makes (Emacs's is per glyph, not per cell). The glyph cache keys on
   the cluster today; it would key on the cluster *and* its joining form.
7. *The terminal.* Turn the emulator's own bidi off where it can be (ECMA-48 BDSM, `CSI 8 l`,
   which VTE honours) and send each row in visual order, so the grid Brood keeps is the one shown.
   A terminal that reorders regardless cannot be supported.
8. *Trojan Source again.* Once reordering is real, an override *does* reorder what is shown, which
   is the attack. The hazard face stays; a prog mode should either not honour explicit
   embeddings and overrides (show logical order inside them) or mark the whole reordered span, as
   Emacs's `highlight-confusing-reorderings` does.

**Why not now.** No bedit user writes RTL text yet, and every item above touches the seam ADR-342
and ADR-556 keep simple: a cluster has a width and sits after the one before it. Doing 3, 5 and 6
halfway would leave a screen that disagrees with its caret, which is worse than today's consistent
logical order. When it is taken up, 1–3 come first (a primitive and a map, with tests), then the
GUI's run shaping, then the terminal.

## ADR-633 — A bare type name means what it means in the module that wrote it

**Status:** accepted (2026-11-08). `builtins/type_scope.rs`; `annot::scoped_ty`.

**Context.** hatch's `web/conn` declares `(sig parse-body (conn -> conn))` over its own record
`conn`. Under `nest test` the contract rejected that record: `store-postgres` declares
`(deftype conn (record &open :buf bytes :off int))`, and a contract, which checks a value wherever
the call happens, holds only the type-form. It looked the bare `conn` up as an alias first, across
every loaded module, and found `store-postgres`'s. The checker had the same order with a narrower
reach: a record ahead of an alias, each the ONE across all modules, so a second record named
`conn` handed the name to the alias. ADR-327 said an alias is module-scoped; neither reader
treated it so.

**Decision.** A bare type name in a `sig` or a `deftype` body resolves, nearest first: a base type
(never rebound by any module); the declaring module's own `deftype` or `defrecord`; the ONE
`(:use …)`d module declaring it; then the global rules as before (an ability by its name, the one
record, the one alias). The checker reads it in that order. The runtime cannot carry a scope into
a check, so the declaration is SCOPED where it is stored: the names that resolve in the module
are written qualified in the declared-sig store (`web/conn/conn`), and the contract, its alias
lookup and its verdict memo, all keyed by the form or a qualified name, need no scope.

- A name the module has not declared yet (a `sig` above its `defrecord`) is remembered; the
  declaration is scoped again when `deftype` / `defrecord` declares it.
- While a module loads under `require`, a used module's name is not taken: the module may still
  declare its own. `provide` settles those.
- A declaration whose stored form changes is offered to the contract hook again, so a shim built
  from the bare form is rebuilt.
- `%refer` records which modules a module uses (`Heap::module_uses`); the per-file import table
  is gone by the time a contract asks.
- `%declared-sig` and `%type-aliases` undo the scoping, so an editor shows the declaration as
  written.

**Consequences.** Two modules may each declare `conn` and mean their own, at runtime and in
`nest check`. A name resolved through a used module at a REPL re-evaluation of a `sig` (no
`provide` follows) keeps the global rule. An ability has no module of its own in the registry, so
it keeps its global name and an alias of the same name elsewhere still answers first at runtime.

## ADR-634 — HTTPS trusts the platform's certificate store, the bundled roots its fallback

**Status:** accepted (2026-11-08).

**Context.** Every TLS client connection (`tls/request`, `tls/connect`, so `http/fetch` and the
SSE client) trusted exactly the Mozilla roots compiled in from `webpki-roots` (ADR-062). A machine
whose administrator added a CA — a company proxy, a private registry, a distribution that ships a
newer root — could reach it with curl and a browser but not from Brood, short of passing `:ca`
on every request; and a root the machine had removed stayed trusted until Brood was rebuilt.

**Decision.** The default client config reads the platform's store once, through
`rustls-native-certs`: the system CA bundle on Linux and the BSDs (honouring `SSL_CERT_FILE` /
`SSL_CERT_DIR`), the keychain on macOS, the certificate store on Windows. When it yields no
certificate rustls can use, the bundled Mozilla roots are trusted instead — a container without
`ca-certificates` still reaches the web. It is one or the other, not their union, so a root the
machine removed is not brought back. An explicit `:ca` still replaces both. The store is read on
the dialler thread of the first TLS connection, never on a scheduler thread (the keychain can be
slow).

**Consequences.** One new crate and the platform pieces it uses (`openssl-probe`, `schannel`,
`security-framework`), host-only like the rest of the TLS stack. A store changed while a runtime
is up is seen by the next runtime. `rustls-platform-verifier` (the OS verifying each chain itself,
revocation included) would be the next step; it changes the verifier rather than the roots, and
was not needed for this.

## ADR-635 — A runtime that dies on a signal leaves a record for the next start

**Status:** accepted (2026-11-08).

**Context.** The panic hook appends a panic to `.brood_crash_dump` in the working directory, but a
runtime that dies on SIGSEGV, SIGBUS, SIGILL, SIGFPE or SIGABRT runs no hook: a segfault in a
grammar, a stack overflow, a panic that aborts. Such a crash left nothing behind unless a terminal
kept stderr, and an editor's report-bug had nothing to offer the user the next time it started.

**Decision.** `brood` and `nest` (so every released bundle) install handlers for those five
signals at startup (`cli_support/fatal_signal.rs`). Everything that allocates is done then: the
record's path, `$XDG_STATE_HOME/brood/crashes/crash-<pid>.blsp` (else `~/.local/state/…`), the
directories to make, and the fields that do not change (version, sha, pid, argv). The handler
runs on the thread's alternate stack, formats the signal, the time, the thread's name, the fault
address and the signal's code into a buffer on that stack, adds the last panic's message (kept in
atomics by the panic hook, so an abort after a panic is named), and writes it with `mkdir`, `open`
and `write` — the async-signal-safe calls only. The record is one Brood map literal, so the reader
reads it back: `crash-report/previous-crashes` lists the records, `describe-error` makes a report
of one, `forget-crash` removes it. The handler then gives the signal back: a fault to the handler
before it (Rust's stack-overflow check), which sees it re-raised as before; a signal sent by
`kill` or `abort` to the default action. The process dies as it would have, with the same status
and core dump. Nothing is created on disk unless a runtime crashes. A test run's arming
(`arm_test_run`) installs it again over the scratch home, so a test that crashes a runtime never
writes the user's state directory.

**Consequences.** No backtrace: unwinding is not async-signal-safe, and a core dump or gdb remains
how to see the stack. The first fatal signal writes; a second (Rust's overflow handler aborting)
does not overwrite it. Unix only; Windows has no record. A record is any brood program's, so a
caller that wants its own filters by `:argv`. `.brood_crash_dump` stays for panics, which a
program survives.

## ADR-636 — A display that falls back tells the app, as an event

**Status:** accepted (2026-11-08).

**Context.** The GUI keeps a window up where it can rather than failing: the CPU painter when the
GPU target will not start or offers only a software adapter, the bundled DejaVu when a font named
by `:family-name` is not installed, an unregistered family (the default font) when a font file
does not parse, grey text when the driver rejects both subpixel pipelines, FIFO when `{:vsync
false}` asked for a mode the compositor does not offer. Each said so on stderr at most, which a
desktop launch discards; only the font was queryable (`gui/font-info`'s `:not-found`), and only
by an app that knew to poll it. An editor could not tell its user why the text looked wrong.

**Decision.** Each of those is reported through one function, `report_degraded(what, reason,
to)` in `host/gui/backend.rs`, which still logs the line and sends
`[:display-degraded {:what :gpu|:font|:lcd-text|:vsync :reason "…"}]` to the app's mailbox, as
input arrives. A window's own fallback goes to that window's app. A runtime-wide one (a font) goes
to every open window's app, and when none is open — fonts are registered before the first
window — it is held and handed to the next window opened, once. The offscreen painter registers
fonts through the same code, so a headless run is told as a window is. `ui-run` passes the event
to the app's update like any input it does not act on.

**Consequences.** An app that ignores unknown input is unaffected. Left as log lines: a glyph no
installed font covers (per cluster, too frequent to be news), a swapchain with no non-sRGB 8-bit
format and a surface with no sRGB view (blending in the encoded space — a slight difference, not
a failure), and the display going away, which is already `[:hangup :display-lost]` (ADR-631). No
query of past degradations: the event is the one channel.

## ADR-637 — Regex: `\n \t \r \f \v` and the hex escapes mean what every other engine means

**Status:** accepted (2026-11-08). Amends ADR-389, which read `\n` as the letter `n`.

**Context.** ADR-389 kept an escaped letter as that letter ("write a newline as a newline").
That is consistent, and it silently breaks every pattern carried over from another dialect:
`[ \t]*` matched spaces and the letter `t`, and `[^\n]+` stopped at every `n`. Both were in
the tree, in `std/tool/grammar.blsp` and in bedit's playground, and a crash-report redaction
rule hit it during the KI-377 fix. The comment beside `\S` already called the same trap a bug.

**Decision.** In a pattern, in a set or out of one, `\n \t \r \f \v` are newline, tab, carriage
return, form feed and vertical tab. `\xHH`, `\x{H…}`, `\uHHHH` and `\u{H…}` name a code point, as
in Rust's regex, PCRE and JavaScript. A malformed hex escape, a number past Unicode or a
surrogate is the letter, as any other unknown escape still is, so the parser keeps raising only
where it raised before. An escaped character in a set is the end of a range like a plain one:
`[\x00-\x7F]`, `[\--/]`.

**Consequences.** `\0`, `\a` and `\e` stay letters. Engines disagree on `\0` (octal in PCRE, an
error in Rust), and `\x00` says it plainly. `]` first in a set still closes it, the one divergence
left from the Fowler corpus. A pattern that meant the letter must now write it bare.

## ADR-638 — `/name` is the root binding under any local; a local callee is named

**Status:** implemented (2026-11-08).

**Context.** A playground report: `(fn (((x y & rest) "+") …) ((acc val) …))` raised
`cannot call non-function: nil`, at the guard, about nothing the user wrote. The pattern compiler
walks the argument list with `first`/`rest` and tests it with `pair?`/`nil?`, and that walk runs
inside the binders the CALLER's pattern names, so a pattern variable called `rest` captured the
generated `(rest tl)`. A probe found `first`, `rest`, `pair?`, `nil?`, `vector?`, `get` and
`contains?` all broke `match`, pattern `fn`, destructuring `let` and `receive`. ADR-236's `/name`
escape and ADR-423's escaped template heads defended against a MODULE defining the name; a
LOCAL still captured the escape, because the resolver stripped `/name` to a bare `name` before
the code was compiled. Six prelude helpers that build code (`%for-fold`, `%with-build`,
`%ok-thread-build`, `%receive-binds`, `%receive-dispatch`, `%condp-clauses`) and two that build
it with `list` (`%impl-args-expr`, the `defmodule` clauses) emitted bare root names, outside the
gate, which scanned only `defmacro` templates.

**Decision.**
1. **`/name` means the root binding, whatever is in scope.** The compile pass renames any local
   binder (`let`, `letrec`, `fn`, `defmacro`; patterns are lowered by then) that a code-level
   `/name` in its scope would be captured by, before the escapes are stripped
   (`eval/macros/escape_capture.rs`). Renaming a binder with every reference it binds preserves
   meaning, so the pass is sound whatever it renames; the fresh name is a gensym, which reads as
   written in arglists and errors. Code that never passes through the compile pass — a form a
   macro expanded lazily, a pattern lowered at run time — reads `/name` from the global table on
   its lookup miss (`derive::root_escape_value`); no local can be named `/name`, so the read is
   immune to locals too. The root strip now also strips an escape in a template's `~` hole.
2. **The prelude's code builders write `/name`**, and `tests/prelude_capture_test.blsp` scans
   every prelude `defn` (opening `check-allow`) for all three emission shapes.
3. **A local callee is named.** `cannot call non-function: \`list\` is [1]`, with a hint when the
   local shadows a root function. The engines raise where only the value is known, so the error
   carries the printed value (`LispError::uncalled`) until a site that knows the head names it:
   the tree-walker from its call form; the VM at its dispatch, by the call's position in
   `CompiledArm::local_call_heads`; native code through the slow call's otherwise-unused head
   argument, or — for a tail call, whose exit is shared — a heap field the arm stores before
   exiting (`Heap::jit_tail_local_head`) and every tail dispatcher takes. Only a call whose
   CALLEE is uncallable is named, so a callable local whose own callee failed (`(h f xs)`,
   `h` = `map`) is not blamed. A call with no source position is not named on any tier, so the
   tiers agree on the prelude's code.
4. **Generated code is located at the piece it came from.** `%stamp-form-pos` gives a template the
   position of the source form it implements, through the expander's own stamping pass;
   `%copy-form-pos` lets a rewriter keep a rebuilt form's record. The pattern compiler locates
   each list pattern's walk at that pattern, which the fail-splice used to strip. Positions are
   metadata about forms; no value changes. The eval server's error reply carries `:line`,
   `:col` and `:hint`, and bedit's playground shows the place and the hint.

**Consequences.** A pattern variable may be named like any root function. A local named like a
root function is still a local: calling it is the user's mistake, and the message now says so.
A native local-headed tail call pays one 32-bit store; no other call path changes.

**Addendum: the review that followed.** Reading for the same shape found more of each:
- *Capture.* `gen`'s `defserver` clause builder (`send`, `nth` inside the caller's pattern
  variables), `string/interp`'s `(cons 'str …)`, the `next-impl` default's `'(empty? next-args)`,
  `defability`'s `(cons 'list …)`, and the Rust source rewrites: the fold pipeline and counted
  loop (`nth`, `failure?`, `+`, comparisons, `count`, `first`/`rest`), linmap's
  `(= :table (type-of r))` — under which a module's own `type-of` handed user code the live
  in-place table — and a failed guard's `(append (list …) rest)`. All now emit `/name`; the
  builder gate scans every std file, not only the prelude.
- *Positions.* The static-quasiquote pass rebuilt every enclosing list with no position and
  left its builder unlocated; the threading macros, `try`'s clauses, `debug/spy`,
  `postwalk`/`prewalk` and `defserver` rebuilt user forms without theirs. Each now keeps the
  original's record.
- *Errors.* `seq`'s "expected a collection" was a thrown string — no kind, no code, no
  position — reached by every collection walker; it is a raised `:type` error (`%raise` now
  admits `E0030` for the prelude's own argument checks), with an argument-order hint when a
  function stands where the collection belongs. Two keyword-accessor hints carried runs of
  spaces from joined string literals.

**Addendum: the follow-ups (same day).**
- *The fold rewrites respect a module's own names.* They read `fold`, `reduce`, `range`, `get`,
  `assoc`, `+`, `-`, `inc`, `dec` by spelling before namespaces resolve; in a module that defines
  or imports any of them, they (and linmap's defn split) now step aside, so a module's own `fold`
  is never replaced by the root fold's loop.
- *Positions.* A macro whose expansion is a form with a position of its own — the user's form it
  returned, or one it located — keeps that position, where the rebuild used to copy the call's;
  `(-> x (inc) (/ 0))` and `(w (+ 1 "x"))` report the failing call. A global read is located at
  its enclosing form (`CompiledArm::staged_head_pos` now holds every read), and the tree-walker
  tags a positionless argument with its call, so an unbound name in argument position reports
  where it is written on every tier.
- *Errors inside std are reported at the program* (`LispError::relocated_out_of_std`, applied by
  the program runner): the headline is the innermost trace frame in the program's file, else
  the running top-level form; the message names the library function called; the std raise
  site stays in the trace.
- *Messages name what was called.* A shared reader's unnamed type error is named by the
  primitive `call_native` was running (`named_by`), `apply` and `string/join` name themselves,
  `sort`/`take` check their collection (`%expect-collection`), `assoc` replaces
  `%vector-assoc`, and a string reaching a fold says it is not a sequence. A non-function
  called from code with no source position — library code calling a value the caller passed —
  gets an argument-order hint instead of "write (f x), not f(x)", on every tier (the JIT is
  told such a call by `POSITIONLESS_CALL`).
- *Pattern functions* name themselves in their no-match error (`pf: …`, from the `def` they are
  the value of), and a call no clause takes by COUNT is said as an arity error, in the words an
  arity-only multi-clause function uses.
- *Raised, not thrown*: `defn`'s name check, `sig`'s type check, `case`'s test check, `spawn`'s
  shape checks, `node/spawn-sync`, `%no-impl`, `%no-method` and regex's repeat limit are
  located error maps with a code.
- *The checker reads resolved code*: the `check` builtin (and the checker's test harness)
  strips root escapes as the compile pass does, so `/vector?` narrows like `vector?`.
- *The last three.* The pattern lowerings emit `/match*`, so a module defining its own
  `match*` no longer breaks its destructuring `let`s and pattern `fn`s (the checker's source
  walkers and the template passes read `/match*` as `match*`); the capture gate also scans a
  quoted list handed to `list`/`cons`/`append` (`'(empty? next-args)`); and an unbound global
  read in native code is located by the arm's error block (`Heap::jit_miss_gsite`), which has
  the arm the callback lacks.

## ADR-650 — A character no font has is drawn as a box holding its code point in hex

**Status:** implemented (2026-11-08).

**Context.** ADR-442 draws a glyph the window's family lacks from an installed font that has
it. When no installed font has it — an unassigned code point, a private-use icon from a font
that is not installed, a script with no font on the machine — the cluster went to cosmic-text
anyway, which drew the primary font's `.notdef` (DejaVu's is an empty rectangle) or nothing.
Either way the reader cannot tell one missing character from another, nor look it up: every
missing glyph is the same rectangle, and a blank is worse, a hole in the text. Emacs's
`glyphless-char-display` draws a character no font covers as `hex-code`, a box holding its
code point, and so do many terminals.

**Decision.** `FontShared::glyph_source` says who draws a cluster: its family (or a bundled
face), an installed fallback, or — `Missing` — nothing this runtime can reach. A `Missing`
cluster that takes a cell is baked (`Renderer::build_cluster`, `render::hex_box`) as a box
filling the cells the layout gave it (a wide character's two), its top and bottom lines a
pixel inside the cell so stacked boxes stay apart, holding the first character's code point
in hex on two rows: `03`/`78` for U+0378, six digits `03F`/`FFD` beyond the BMP. The digits
are a built-in 3×5 bitmap face scaled by whole pixels to the cell (a HiDPI cell gets bigger
digits), so the box never needs a font itself; a cell too narrow for three digits and the
box's side lines drops the sides, and one too small for any digits keeps the empty box. The
canvas is coverage like any monochrome glyph, so it takes the face's foreground. Both
painters bake through `build_cluster` — the CPU painter directly, the GPU atlas through
`cluster_glyph` — and `gui/render-frame` (ADR-609) is the CPU painter, so the box is the same
everywhere and testable from pixels. A zero-width cluster (a joiner, a format character the
glyphless display left as it is, ADR-556) and a control character are not boxed: they take no
cell to hold one, and drew nothing before. The terminal display (ADR-586) leaves the
character to the terminal, which has its own rule.

**Why not `.notdef`.** It is the font's, so it looks different under every family and says
nothing about the character, and a font may draw it as nothing. The hex box names the
character: a user can tell a private-use icon (`E0A0`) from an unassigned code point, find
the font that would draw it, or see that a file holds a character it should not.

**Consequences.** The check costs nothing on the hot path: printable ASCII in the bundled
family asks nothing, and a cluster's answer is baked once into the glyph cache. A font that
covers everything (macOS's last-resort font) answers before `Missing` is reached, so there the
font's own glyph still draws; GNU Unifont, common on Linux, likewise draws unassigned BMP code
points its own way. Guards: `render::missing_glyph_tests` (the digits read back from
the canvas at one cell, two cells and HiDPI; an empty box when nothing fits; the renderer's
bake is the box) and `tests/gui_test.blsp` "a character no font has is a box in its own
cells" (render-frame pixels, U+3FFFD and U+10FFFD: a wide box's four lines across its two
cells, digits inside, nothing beside it; a narrow six-digit one keeps its top and bottom
lines; Linux only).

## ADR-660 — A grammar library is vetted in a child before it is loaded, and a crash in one quarantines it

**Status:** accepted (2026-11-08).

**Context.** A tree-sitter grammar loaded at runtime (`%tree-sitter-load-grammar`, a declared
grammar's first use — ADR-481) is native code dlopened into the process: a parser table and,
often, a hand-written C external scanner. bedit builds them from git (`grammar-install`) and
loads them into the editor itself, so a scanner that dereferences null, loops forever, or a
corrupt build took down the editor and every unsaved buffer's process. Emacs's bug archive
has this report again and again. Moving parsing to another process is not the answer: an
editor holds a tree per buffer (ADR-443), reparses it per keystroke and queries it constantly
(indent, brackets, folding, crumbs, injections), so a round-trip per query is a cost every
healthy grammar would pay for the rare bad one. ADR-635 already leaves a record when a runtime
dies on a signal, but it could not say whose code was running.

**Decision.** Two defences, neither on the per-keystroke path.

- **Vet before the first load.** `load_library` — every runtime load of a grammar, eager or
  declared — reads the library, hashes it (SHA-256, the identity ADR-583's manifest records)
  and asks for a VERDICT on those bytes before any of its code runs here. A quarantined
  library is refused with an ordinary error naming the reason; with none, the runtime starts a
  CHILD — this very binary, `/proc/self/exe`, with `BROOD_GRAMMAR_VET_CHILD` set, which
  `cli_support::grammar_vetting_entry` (the first line of `brood`'s and `nest`'s `main`, so
  every bundle) hands to the vetter before any runtime, panic hook or signal handler exists.
  The child checks the bytes are the ones hashed, dlopens the library, calls its entry point,
  sets it on a parser and parses a corpus: the caller's (`%tree-sitter-vet-grammar`'s
  `:corpus` — `editor/grammar-install/grammar-corpus` reads a grammar's `test/corpus/*.txt`)
  and inputs it makes for every grammar — its own anonymous tokens spaced, packed, reversed,
  on lines, with CRLF and NULs; nesting 1,500 deep; a 64 KB line; invalid UTF-8; fixed noise;
  every common unterminated string or comment opener — each tree walked and reparsed after an
  insertion and a deletion, where a scanner's serialised state is read back. It reports each
  stage on stdout. A child that dies on a signal or fails is QUARANTINED, with the stage it
  died in ("it crashed (SIGSEGV) parsing input 8 (nesting-parens)"); one that reports nothing
  for the timeout (10 s, `:timeout-ms`) is killed and quarantined as hung. A parse cut short
  by its own budget (a quarter of the timeout, through tree-sitter's progress callback) is
  slow, not a fault, and moves on — only a scanner that never returns starves the watchdog. A
  library that fails as an ordinary load would (no entry point, an ABI out of range) is
  `:refused`, keeps no verdict, and the parent's load reports it as before.
- **Attribute a crash anyway.** Input no corpus covered can still crash the runtime. Each
  loaded library gets a MARK built at load (and leaked, as the library is): the fragment
  ` :grammar {:lang :library :sha256}` and the path of its quarantine. Every call into grammar
  code — the dlopen and entry point, `set_language`, each parse (whole-text, held-tree and
  injected), dropping a stale parser — runs with the mark in a const-initialised thread-local
  (`cli_support::enter_foreign_code`: two thread-local writes per parse). ADR-635's handler
  splices the fragment into the crash record and, with `open` and `write` alone, writes the
  quarantine — `{:verdict :quarantined :by :crash :reason … :signal … :time … :pid …}` — so
  the next start refuses the grammar without reading crash records at all, and
  `crash-report`'s message says which grammar it was.

Verdicts are one flat map literal per library, `<sha256>.blsp`: a quarantine is STATE, in
`$XDG_STATE_HOME/brood/grammar-verdicts` beside the crash records (a test run's scratch home
moves it, ADR-602); a pass is a CACHE, in `$XDG_CACHE_HOME/brood/grammar-verdicts`, since it
follows from the bytes and losing it costs one vetting. A test run (`BROOD_TEST_RUN`) writes
neither under the user's home: its passes go to `<scratch>/cache/brood/grammar-verdicts` in the
run's scratch home (its quarantines are already there, through `XDG_STATE_HOME`), while
`XDG_CACHE_HOME` itself stays the user's, since the stdlib image is shared there; a run that
kept the real home keeps its passes with its quarantines. A healthy library is vetted once per
machine (once per run under test); a reinstalled one is new bytes, vetted afresh, so reinstalling is how a quarantine
ends, and `%tree-sitter-forget-grammar-verdict` is how to give the same bytes another try.
Brood sees it as `editor/treesit/vet-grammar`, `grammar-verdict`, `forget-grammar-verdict`,
`editor/grammar-install/grammar-vet` (an install's own corpus), and `grammar-status`
answering `{:quarantined reason :library :sha256 :by}` for a declared quarantined library —
which `languages` also leaves out.

**Alternatives.** *Parse in a server process* — isolation for every crash, but a round-trip
per query of a tree held per buffer; the cost lands on every keystroke of every healthy
grammar. *`fork()` without `exec` for the child* — cheaper to start, but a multithreaded
process (GUI, scheduler workers) may fork while another thread holds the loader's or the
allocator's lock, and a deadlock would read as a hang and quarantine a healthy grammar; macOS
forbids much after a fork in a process using Cocoa. *Vetting in Brood* (std spawning `nest`) —
std cannot find "this binary" reliably for a bundle, and the gate has to sit in front of the
dlopen in the kernel anyway. *Reading crash records at the next start to find the grammar* —
an editor adopts and deletes its records (bedit's report-bug), and might before the grammar's
first load; the handler writing the quarantine itself needs no reader.

*Which binaries can vet* (amended after CI): `brood`'s `main` (so every `nest release` bundle,
whose executable is the `cli` runtime with the app appended — the child exits at the first line,
before the bundle is mounted), `nest`'s, and the cargo suite harness (`crates/lisp/tests/suite.rs`),
whose one test calls the hook first: started again as the child with no arguments, the harness
runs that test, which vets and exits. The child writes its stages and its complaint to the
streams directly, never through the print macros a test harness captures, and sets its core
limit to zero, since its crash is the expected answer.

**Consequences.** The first load of each new library costs a child: ~0.1–0.4 s for the
grammars bedit installs, once per machine, on whichever process first parses it (an editor
that would rather not pay it on its loop vets after installing, in a task). That first load
held the declared-grammar lock, so other parses waited for it (no longer: ADR-672). A host that never calls
`grammar_vetting_entry` (an embedder, `cargo test`) cannot start a child and loads unvetted,
as before; `BROOD_GRAMMAR_VET=0` turns automatic vetting off, never a quarantine. A crash the
corpus missed still ends the process once — the point is that it cannot twice. Attribution
names the grammar whose code was marked, so a tree-sitter bug that a grammar's input
triggers is laid at the grammar's door; forgetting the verdict undoes it. A record buffer too
full for the fragment (a very long argv) omits it, but the quarantine is still written. No
Windows crash record (ADR-635 is Unix-only); vetting itself works there, and since ADR-672
a crash in a grammar quarantines it on Windows too. Guards: `tests/grammar_vet_test.blsp` builds grammars with `cc` — null tables (crash in
the parse), an aborting entry point, a spinning one (the watchdog), one with no entry point
(refused), a healthy shim over an installed JSON grammar — and runs a child runtime that loads
the crashing one unvetted, dies, and leaves a record naming it and a quarantine the next
runtime honours; Rust tests cover the verdict literal (including the handler's bytes), the
store, the corpus framing and the thread-local mark.

## ADR-670 — A `defmemo` store is per process and keeps the caller's own cells

**Status:** implemented (2026-11-09).

**Context.** `defmemo` (std/memo, ADR-522) kept its last few `[key value]` calls in a global,
re-bound with `def` on each miss. `def` promotes what it binds: a deep copy into the shared,
append-only RUNTIME region (`Heap::promote_global`). So a remembered key was never the cell
the caller passed. `=` answers at once for the same cell (its identity fast path), but the
next call with the very same value compared it against a copy, element by element, and every
miss copied the whole key again — into a region only a runtime compaction reclaims. Only a
key that was a handle (a rope) or already a shared value (a global's own map) compared at
once. bedit's render memos were keyed on buffer-sized values; one keyed on a pane and the
buffer cost 4.6 s a frame beside a 150,000-line diff, and bedit cut its keys down to what a
frame shows (bedit 79ddbbc1) rather than fix the store. A memo that walks its keys is not a
memo for big values, which is what it is for.

**Decision.** Each process keeps its own `defmemo` stores in its own heap, uncopied.

- **Two kernel primitives** over a new per-process field (`HeapExtras::memo_stores`, a short
  vector of `{slot version entries}`): `(%memo-store slot version)` reads the entries and
  `(%memo-store! slot version entries)` replaces them. The entries are held as they are —
  never promoted — so a key is the caller's cell, the next `=` with the same value is a
  pointer test, and a miss costs a cons. A value only `=` to a remembered one still hits,
  after a walk, as before.
- **A GC root**, traced exactly where the dynamic-binding stack and the caught-error origins
  are: relocated by the LOCAL collector's root flush (minor and major), walked by the debug
  heap verifier (`BROOD_GC_VERIFY`), seeded in the RUNTIME drain's generation probe and
  rewritten by a RUNTIME compaction (a store may hold a shared handle, a registry table
  say). `reset_local_to` — the
  nursery truncation a tooling eval does at a top-level boundary, which assumed no root
  points into the nursery — forgets every store.
- **`slot`** is the memo's qualified name, computed as the `defmemo` form expands, so two
  modules' memos of one name never share. **`version`** is a symbol the `defmemo` form mints
  (`reflect/gensym`) into a `NAME--memo-version` global each time it runs: a store kept under
  another version reads as empty, so a redefinition (a hot reload) never answers with the old
  body's value in any process, and its first call replaces the stale store (bounded: one store
  per memo per process).
- **`memo/entries`** reads the caller's store, for a test; `name-recent` globals are gone.

**Alternatives.** *Keep the global, store keys without promoting them* — a global is read by
every process, and a LOCAL handle in it would be a dangling pointer in all but one; the
promotion is what makes a global sound. *An identity cache in Rust keyed by handle, with the
structural fallback* — the same per-process field, plus a second lookup structure that every
collection must rekey, for a store of eight entries a linear `=` scan already serves. *A
`table`* — shared, so its writes copy too. *Leave it to callers* (bedit's fix) — every memo
author must know that a key is copied, which is exactly the trap that cost 4.6 s.

**Consequences.** The store follows the process: a short-lived process starts empty and its
store dies with it, and two processes no longer share answers (nor race to re-bind a global).
The editor's render memos run on its loop, so they keep theirs. The remembered values stay
alive in that process's heap until pushed out (`capacity` entries per memo) — before, they
stayed in the RUNTIME region until a compaction. Memo misses no longer promote, so they leak
nothing into the shared region. What this does NOT change: a miss compares the arguments with
each remembered call's, and `=` on two different big values walks them until they differ (two
ropes by their text), so a memo keyed on a whole buffer still pays for the buffer on the call
after an edit. Identity makes the hit free; keeping a key to what the answer reads keeps the
miss cheap. `editor/ui`'s `ui-memo` already had this property (its table is
the loop's own value, bound for the view) and is unchanged; its docstring now says so. Guards:
`tests/memo_test.blsp` — a 20,000-row key holding a NaN (equal to itself only as the same cell)
hits, the store holds the caller's own value, survives two collections, a structurally equal
key hits, a spawned process has its own store, and a redefinition starts empty.

## ADR-671 — `file/replace` on Windows: `ReplaceFileW`, and a file held open is refused, not torn

**Status:** implemented (2026-11-09). Amends ADR-621's Limits.

**Context.** ADR-621 made `file/replace` a synced temp file renamed over the path on Unix and
left Windows a write in place (`fs::write`: truncate, then write), because a rename there gives
the file the temp file's security descriptor, not its own. An editor's save went through that,
so a crash, a power cut or a full disk between the truncate and the last byte left bedit's file
on Windows empty or cut short. Windows has two other things Unix does not: another program may
hold a file open in a way that refuses a rename or a delete (a sharing violation), and an
indexer, a virus scanner or a backup tool does so for a moment after every write.

**Decision.** On Windows, `file/replace` writes a temp file beside the file, flushes it
(`FlushFileBuffers`, which `File::sync_all` is), and puts it in the file's place with
`ReplaceFileW`, which keeps what the old file had: its ACL, attributes (hidden, system),
creation time, short name and alternate streams. A file not there yet, or a filesystem without
`ReplaceFileW` (FAT, some network shares: `ERROR_INVALID_FUNCTION`, `ERROR_NOT_SUPPORTED`,
`ERROR_INVALID_PARAMETER`), takes `MoveFileExW(MOVEFILE_REPLACE_EXISTING |
MOVEFILE_WRITE_THROUGH)` instead.

Another program holding the file (`ERROR_SHARING_VIOLATION`, `ERROR_LOCK_VIOLATION`, and from
`ReplaceFileW` `ERROR_UNABLE_TO_REMOVE_REPLACED`, `ERROR_UNABLE_TO_MOVE_REPLACEMENT`,
`ERROR_ACCESS_DENIED`) is waited on for about a second (10 ms doubling to 250 ms, ~1.06 s in
all), then the replace RAISES, saying another program has the file open and that the file is
unchanged. It never falls back to a write in place for that: the old file and no temp file are
left. A temp file whose bytes could not all be written or flushed (a full disk) is removed and
the old file left, as on Unix.

The cases ADR-621 writes in place for keep their Windows form: a file with other hard links
(`GetFileInformationByHandle`'s link count; a replace would leave them the old text), something
that is not a plain file, a directory that takes no new entries (the temp file refused with
access denied), a dangling symlink (written through). A symlink is followed and its target
replaced. A file this user may not write (the read-only attribute, its ACL) is refused, as a
write would be: the check opens it for writing first, without truncating. A file the user may
write but whose ACL grants no DELETE, which `ReplaceFileW` needs, answers `ERROR_ACCESS_DENIED`
after the wait and is written in place — the Unix rule for a file whose owner cannot be kept.

`ERROR_UNABLE_TO_MOVE_REPLACEMENT_2` (the old file moved aside and the new one could not take its
name) leaves the temp file as the only whole copy: it is finished with `MoveFileExW`, and if
that fails too the error names the temp file, which is kept.

**Alternatives.** *A rename with the DACL copied over by hand* (`GetSecurityInfo` /
`SetSecurityInfo`) — `ReplaceFileW` is that, plus the attributes, streams and creation time, in
one call the filesystem does. *A write in place when the file is held* — safe against the
sharing case itself (`CreateFile` refuses before anything is truncated) but it brings back the
torn file for the crash or full disk that follows; a save that says why it failed is the better
answer, and bedit keeps the buffer modified and the text in its sidecar. *Waiting longer* — a
program that keeps a file open (Excel, a log tailer without `FILE_SHARE_DELETE`) does not let go
in ten seconds either, and the editor's save queue waits behind the call.

**Consequences.** A save on Windows survives a crash mid-write, and keeps the file's ACL and
attributes; a hidden file, which `fs::write`'s `CREATE_ALWAYS` refused, is saved. A file another
program holds open without sharing delete is not saved, after about a second, with that reason
(bedit says it and leaves the buffer modified). A reader that shares delete (most do: Rust's and
.NET's defaults, a tail with `FILE_SHARE_DELETE`) does not stop it. The replace gives the file a
new file index, as a rename gives a new inode on Unix. A crash between the temp file's creation
and the replace leaves a `.brood-replace-*` file behind, as on Unix. Guards:
`windows_replace_tests` in `crates/lisp/src/builtins/filesystem.rs`, run by CI's
`windows-smoke` job — an existing file replaced (a new file index, its hidden attribute kept), a
missing file made, a file held open refused with the reason and left whole, one let go of within
the wait replaced, one a reader shares fully replaced under it, a read-only file refused, a
failed write leaving the old file and no temp, a hard-linked file written in place.

## ADR-672 — Vetting holds no lock, can run ahead of first use, and a crash quarantines on Windows too

**Status:** accepted (2026-11-09). Amends ADR-660.

**Context.** ADR-660 left three gaps. The first load of a declared grammar vetted its library
while holding the declared-grammar table's lock, so for the child's 0.1–0.4 s every parse of
every other language, every `grammar-status` and every declaration waited on it — an editor
asking a status question per buffer froze with it. Nothing could vet ahead of time, so the
first keypress in a file of a newly installed language paid for a child on the editor's loop.
And a grammar that crashed the process on Windows was never quarantined: the crash file is
written by ADR-635's signal handler, which is Unix-only.

**Decision.**

- **The vetting runs outside the lock; one child per library.** A declared grammar's first use
  reads the declaration under the lock, releases it, reads and vets the library, then takes the
  lock again and dlopens only if the declaration is still the one it vetted — loaded by another
  thread meanwhile, failed there, or declared anew, it asks again. The dlopen itself stays under
  the lock, which is what makes it happen once. Two threads that need the same library meet in
  `vet_once`: a table of vettings in flight keyed by the library's SHA-256, where the first
  thread runs the child and every later one waits on a condition variable for its verdict
  (checking for its own kill while it waits). A vetting that ends without a verdict — its caller
  killed — sends the next waiter to vet in its place. `%tree-sitter-vet-grammar` goes through the
  same table unless `:force`, so a host's background vetting and a load's never start two
  children for one library or race to write its verdict file.
- **Vetting ahead of first use is the host's call, off its loop.** `%tree-sitter-declared-grammars`
  answers the pending declarations, `{lang path}`, and std's `editor/treesit/vet-declared-grammars`
  vets each one without a verdict, one after another, answering `{lang verdict}`. A host calls it
  in a spawned process after declaring its grammars (bedit's startup does). A kept verdict is
  answered from the store, so a machine that vetted once pays a hash per library; a parse that
  arrives while its library is being vetted waits for that vetting rather than starting another.
  It is a std function over two primitives, not a kernel thread: when to spend a child's CPU is
  policy, and the runtime has no loop of its own to protect.
- **Windows quarantines on a crash through an unhandled-exception filter.** `fatal_signal::install`
  sets `SetUnhandledExceptionFilter` there (and a C-runtime `SIGABRT` handler for a grammar's
  `abort()`), which runs on the faulting thread, reads the same thread-local mark the Unix handler
  reads, and writes the grammar's crash file with `CreateDirectoryW` / `CreateFileW` / `WriteFile`
  over UTF-16 paths built at load — `:signal` naming the exception (`EXCEPTION_ACCESS_VIOLATION`,
  `abort`). It then hands the exception to the filter before it, so the process dies as it would
  have. The quarantine directory falls back to `%USERPROFILE%` when `HOME` is unset, as
  `boot::cache_dir` does, or the mark had nowhere to write. Still no crash RECORD on Windows;
  only the quarantine, which is what keeps the next start alive. The vetting parent names a
  crashed Windows child by its exit status (an NTSTATUS, or 3 for `abort()`), and the child's own
  refusal codes moved to 73 / 74, clear of `abort()`'s 3.
- **The crate's unit tests cannot reach the user's cache.** The crate's own Rust unit tests are
  not an armed test run, so their verdict directories are a temporary directory of the test
  process, by `cfg(test)`, rather than read from the environment.

**Alternatives.** *Vet in the kernel in a background thread at declaration* — every declaration
would start a child whether the language is ever used, on a schedule the host does not control;
the std function lets a host choose when, and an editor already has a place to run it. *A
vectored exception handler on Windows* — it sees first-chance exceptions, including ones a
library raises and catches itself, so a healthy grammar using SEH internally would be
quarantined; the unhandled filter sees only what would end the process. *An in-progress marker
file per parse* — a write per keystroke, the cost ADR-660 refused.

**Consequences.** No parse, status question or declaration waits on a vetting child; only a
thread that needs the very library being vetted does, and it shares the child. A declaration
replaced while its predecessor was being vetted costs that vetting, and the new library is
vetted afresh. A `__fastfail` (Rust's own abort, a CRT built to fail fast) bypasses every filter
on Windows, and an `abort()` in a grammar linked against another C runtime raises its `SIGABRT`
there, unseen — those still end the process without a quarantine. Another library that installs
its own unhandled-exception filter after ours replaces it. The Windows path is verified only by
CI's compile and its Windows jobs; the crash itself is not exercised there. Guards: Rust tests
for the shared vetting (one child for two threads, a waiter vetting after a verdict-less
leader), the unit tests' verdict directories and the Windows exit-status names;
`tests/grammar_vet_test.blsp` covers `declared-grammars` and `vet-declared-grammars` (a
quarantined declaration answered and kept, under the run's scratch home).

## ADR-673 — The 1.0 compatibility promise: what is covered, for how long, and what is not

**Status:** accepted (2026-11-10). Proposed 2026-11-09. The owner settled four points:
nodes link within one `major.minor`, and the handshake can be widened later; a project opts
into new lints through a manifest key; there is no `:beta` carve-out, because everything is
covered and the release candidates are where the surface settles; and the deprecation window's
minimum time is decided closer to 1.0. Closes gap 1 of `general-purpose-gaps.md` once accepted.
The checklist that turns it into a release is `docs/road-to-1.0.md`.

**Context.** The README disclaims all stability. CHANGELOG.md uses the word "breaking" on 35
lines across about fourteen weeks, and the Unreleased section has four more breaks. The
playbook's only rule is that before 1.0 a break bumps the minor version
(`ecosystem-playbook.md` §1). The language surface was made freeze-ready in July (ADR-165..169)
and its absences were ratified in ADR-170. What has never been written is the promise itself:
which surfaces 1.0 covers, what "compatible" means for each of them, and how long a deprecated
name lives. Many of the mechanisms exist already: `:since`/`:deprecated`/`:beta` (ADR-283), the
rename ledger with `--fix-renames` (ADR-304), the `:brood` constraint gate (ADR-209), and magic
numbers on the image, bundle and wire formats. Each of them, though, was built for the
greenfield phase. The wire protocol bumps "with no back-compat kept" (`dist/wire.rs`). The lock
file has no version field. `nest check` fails on any new gating lint, and it tells gating
warnings from advisory ones by matching substrings of the message
(`std/tool/project-check.blsp`).

**Decision (proposed).**

1. **Semantic versioning from 1.0.0.** A break that a covered program can observe requires a
   major release. A minor release adds things. A patch release fixes things.

2. **Covered: changes only at a major release.** From `1.0.0-rc.0` to 1.0.0 these surfaces
   still move; a break between release candidates is allowed but goes in the changelog and
   the ledger.
   - **The language.** The reader and its reservations (ADR-169), the eight special forms,
     evaluation semantics (truthiness, tail calls, immutability, equality), the pattern
     grammar, the `fn` head grammar, the module header clauses, and ADR-170's refusals.
     Relaxing a restriction is a minor change (the freeze asymmetry, ADR-166).
   - **Public std names.** Everything bare (ADR-506) and every qualified public name in `std/`
     with its arity and the documented meaning of its arguments.
     Everything public at 1.0 is `:since "1.0"` implicitly, so only a name added later carries
     `:since`.
   - **The project formats.** The `project.blsp` keys, and the lock file, which gains a format
     version before 1.0. A newer `nest` reads every older lock file of the same major.
   - **The `nest` and `brood` command lines.** The documented subcommands and flags, and the
     exit-status meanings of `nest check`/`test`/`run`.
   - **Error codes.** A code is never reused, as `error-codes.md` already says, and an error
     keeps its code.

3. **Versioned, refused or rebuilt on mismatch, never silently misread.**
   - The startup and prelude images are rebuilt on mismatch, as today.
   - The release bundle format is unaffected, because a release binary carries its own
     runtime.
   - **The dist wire protocol.** Nodes of the same `major.minor` always link. Across minors,
     the handshake refuses with a message that names both versions. This is the narrow promise
     on purpose. Widening it later, for example to every minor of one major, is a relaxation
     and breaks no one; narrowing it would break every cluster that relied on it. A wider
     promise has two costs. The wire format would become a covered surface, so every new
     encoding would need negotiation and every old one kept for the life of the major. And
     closures travel as data in a remote spawn (ADR-034), so a closure from a newer node can
     name a std function an older node lacks, which a wire promise alone does not solve. The
     day someone needs a rolling upgrade, that is the widening.

4. **Not covered.**
   - `%`-prefixed primitives, `-internals` modules and `:use-internals`.
   - The JIT ABI (`brood_rt_*`) and every `BROOD_*` flag.
   - Performance, and the exact text of error and warning messages.
   - What the checker can infer. A more precise type is not a break.
   - No module is carved out. Everything public in `std/` is covered at 1.0, `std/editor/*`
     included. The release candidates are where the surface settles (`road-to-1.0.md` §E). A
     name added *after* 1.0 may still ship as `:beta` (ADR-283) until it settles.

5. **Warnings are not breaks, so new lints cannot redden a passing CI.** Proposed: warnings
   carry a structured severity rather than being matched on their message text. A lint new in
   a minor release is advisory in batch `nest check` until the next major, unless the project
   opts in with a key in `project.blsp`. A manifest key and not a flag, because CI and every
   developer read the same manifest. A per-run flag can be added later if someone asks for
   it (ADR-011). This needs the project- and file-level warning controls in handoff's open
   thread 1.

6. **Deprecation.** A name to be removed is marked `(meta name :deprecated "1.x" :use 'new)`
   and stays working, with an advisory warning, until at least the next major. **Deferred:**
   whether a minimum time is added on top of that; the owner decides closer to 1.0. It is
   removed only at a major release. Every removal and
   rename has an entry in the rename ledger, so that `nest check --fix-renames` applies it.
   Every reordering of arguments or change of meaning ships a codemod or names the manual step
   in CHANGELOG's migration section.

7. **Greenfield ends at 1.0.0, not before.** The rule "make breaking changes freely"
   (CLAUDE.md) holds through the 0.x releases and the release candidates. Pre-1.0 breaks should
   be spent now: open thread 6 ("reduce before adding") removes forms, which this ADR would
   otherwise forbid until 2.0.

**Alternatives.** *Calendar versioning with a rolling deprecation window*, as some editors do.
It reads honestly for a live-programming system, but it gives a downstream `:brood`
constraint nothing to say "compatible" with. *A covered "core" plus everything else
unstable.* That is simpler to promise, but std is where users live, and ADR-506 already drew
the bare/qualified line a promise can follow. *No wire promise at all.* That is honest today,
but it makes a rolling upgrade of a cluster impossible, and that is the use case distribution
exists for.

**Consequences.** CLAUDE.md's greenfield section and the README's warning are rewritten at
1.0.0. The rename ledger, `:deprecated` and `--fix-renames` stop being conveniences and become
the release process: a break with no ledger entry is a release blocker. The checker's
message-matching classification has to be replaced before 1.0. The lock file and the wire
protocol need a version they do not have today. Each of these is an item in
`road-to-1.0.md`.

## ADR-674 — Reduce before adding: one iteration form for effect, staged out through `nest format --migrate`

**Status:** accepted (2026-11-10). Stage 1 implemented; stage 2 (removal) is a 1.0 blocker in
`docs/road-to-1.0.md`. Stage 2 implemented (2026-11-11).

**Context.** ADR-673 forbids a removal after 1.0 until 2.0, so every form the language means to
lose has to go in 0.5x. The open thread "reduce before adding" listed the candidates: four
forms iterate for effect (`for` collects; `doseq`, `dotimes` and `dolist` do not), three forms
match (`match`, `case`, and the public engine `match*`), and `unless` is `when` over `not`.
`doseq` was `(do (for …) nil)`: it built `for`'s whole list and threw it away, so the forms that
did not (`dotimes`, `dolist`) existed partly because the general one was slow. `case` was
reviewed and stays: it is not a synonym for `match`, because it refuses a bare symbol test,
which is the one trap `match` has. `with-out-str` and `with-err-str` stay too: the names match,
but they capture different things (stdout and everything spawned, against the `*err*` port).
The owner settled `unless` against the precedent of another language in the same family, which
soft-deprecated it in favour of `if` over a negation and ships a formatter migration for it.

**Decision.**

1. **`doseq` is the one form for effect.** It takes `for`'s bindings (several pairs, the last
   varying fastest, `:when` guards, destructuring) and walks them as `fold-for` does, with a nil
   accumulator, so nothing is collected. A counted loop is `(doseq (i (range n)) …)`. Measured
   (ms, 3M iterations over a table put, best of 3): tier 2 — old `doseq` 560, new 368, `dotimes`
   328; tier 1 — 1333, 951, 716. Over a 1M list: `dolist` 149, new `doseq` 157 (tier 2). The
   ~12% left against `dotimes` at tier 2 is the range fold's per-step cost against a hand loop,
   and the fix for it is in the fold, where every `range` walk benefits, not in a second form.
2. **`dotimes`, `dolist`, `unless` and `match*` are deprecated, in two stages.** Stage 1 (now):
   each still works, carries `:deprecated "0.51.0"` with its replacement, and `nest check` warns
   at every use. Stage 2, before `1.0.0-rc.0`: each is removed, with a rename-ledger entry so
   the unbound error names the replacement.
3. **`match*` becomes `%match`.** It is the engine `match`, `case`, the destructuring `let` and
   the pattern `fn` lower to, not a form for users. Under ADR-673 a `%` name is not covered by
   the 1.0 promise, so the engine can keep changing. The compile pass emits `/%match`.
4. **`nest format --migrate` rewrites the deprecated forms** (`std/tool/migrate.blsp`), then
   formats. The rewrites walk the lossless CST, so strings, comments and layout are kept, and
   quoted data is never touched; a quasiquote template is code a macro emits, so it is
   rewritten. `(unless (not x) …)` becomes `(when x …)` rather than a double negation. Only a
   call is rewritten: `(defmacro match* …)` and `'match*` name the old form.
5. **A deprecated macro warns where it is called.** The checker reads expanded code, where a
   macro's call no longer exists, so a `:deprecated` mark on a macro warned nowhere. A pass over
   the unexpanded forms (`types/check/deprecated_macros.rs`) gives a call of a deprecated macro
   the diagnostic a deprecated function's call gets, with "`nest format --migrate` rewrites it"
   appended. `(check-allow :deprecated …)` silences it; a module's own definition of the name is
   its own.

**Alternatives.** *Remove at once* — the greenfield rule allows it, and the codemod exists
either way. Staging costs one release and buys a rehearsal of the post-1.0 process (deprecate,
warn, migrate, remove) on forms whose users are all known, before it has to work on strangers.
*Keep `dotimes` for speed* — it would be a second spelling kept for a constant factor the fold
can lose. *A ledger rename for `dolist`* — `--fix-renames` could swap the name, but `dotimes`
and `unless` change shape, and one tool for all four is simpler than two.

**Consequences.** Every program written so far needs `nest format --migrate` once; std, the
tests and the downstream projects were migrated with it. `nest format` gains a mode, and
`migrate` holds a rewrite only for as long as its form exists — stage 2 deletes both. A
`doseq` whose body is a bare name now draws the "evaluated and discarded" lint, correctly. The
`for`-shaped binding grammar is now the only iteration grammar for effect, so `doseq` inherits
every future change to `for`'s bindings. Guards: `tests/reduce_forms_test.blsp` (the warning
test is red with the pass disabled).

## ADR-685 — Property testing shrinks over a recorded choice sequence

**Status:** accepted (2026-11-10).

**Context.** `check-property` (in `test`) took a `seed -> [value next-seed]` function and
stopped at the first counterexample, reporting it whole: a property over vectors that broke on
a 42 printed a 60-element vector of random numbers, and the reader did the minimising by hand.
There were no combinators either, so every test built its generator from `rand/int` and
threaded the seed itself. bedit wanted properties over edit sequences and file encodings,
where an unshrunk counterexample is a page of noise.

**Decision.** A new DEV module, `property` (`std/tool/property.blsp`, beside `test`, never
shipped), with integrated shrinking over a **choice sequence**, Hypothesis's design in its
small form (minithesis):

1. **A generator draws integers, not values.** Every random decision is one non-negative
   integer below a bound, recorded as it is drawn. A generator is `{:generator f :label s}`,
   `f : source -> [value source]`; the source is a map holding the recorded prefix, the
   choices drawn so far, a PRNG seed or nil, and a limit. A draw takes the prefix first
   (clamped to its bound), else the seed, else 0. Each generator is written so that choice 0
   is its simplest value: `int` draws a sign then a magnitude when its range holds 0, a
   collection draws a "one more?" flag before each element past its minimum, `character`
   draws a class (ASCII first, offset so 0 is `a`) then an offset.
2. **Shrinking edits the sequence and replays the generator.** Passes delete chunks of 8,
   4, 2 and 1 choices from the end back, zero chunks, and binary-search each choice toward
   0, repeated until a round finds nothing. A candidate is kept when the predicate still
   fails and the choices it actually CONSUMED are smaller in shortlex order (shorter, then
   lexicographically less). The work is bounded by `:max-shrinks` predicate runs (1000).
3. **The surface:** `choice`, `constant`, `int`, `bool`, `elements`, `one-of`, `frequency`,
   `tuple`, `vector-of`, `map-of`, `character`, `string`, `string-of`, `fmap`, `bind`,
   `such-that`, `from-rng`; `check` (a result map), `report` (its lines), `replay`,
   `generate`, `sample`. Collection first, function last, as everywhere.
4. **`check-property` keeps its name and shape,** `(check-property n gen pred [opts])`, and
   takes a generator; a bare function is refused with a pointer to `property/from-rng`, which
   wraps one (it shrinks by trying smaller seeds only). The callers in the repository
   (`tests/prng_test.blsp`, the docs) were migrated.
5. **Seeds.** The start seed is `:seed`, else `nest test --seed`'s (read off the active
   filter), else 1, so the suite is deterministic and a `--seed` explores. Each trial draws
   from its own seed (the previous one plus the golden-ratio constant, renormalised: chaining
   through the PRNG's next state would make each trial the last one shifted by one choice),
   and the report names the FAILING trial's seed, so `{:seed S}` or `--seed S` replays it as
   trial 1 and shrinks to the same value.

**Alternatives.** *QuickCheck's rose trees* (each value carries a lazy tree of smaller
values): integrated shrinking needs the trees to compose through `fmap` and `bind`, and
`bind`'s does not (the inner generator's tree is lost when the outer value shrinks — the
known weakness of Hedgehog-style monadic shrinking). Brood has no laziness to build the trees
on demand, so each node would be a thunk closure, and every combinator would carry shrinking
code. The choice sequence needs none: one shrinker over integer vectors serves every
generator, and `bind` shrinks through both stages because both draw from the same sequence.
*Type-directed shrinking* (a shrink function per generator, QuickCheck's original): the
generator and shrinker drift apart, and a shrunk value can break an invariant the generator
kept (a sorted vector shrinking to an unsorted one); a replayed value is always one the
generator could have made. *Keep the old seed-function protocol and add shrinkers beside it*:
the counterexamples it reports cannot be shrunk without knowing how they were made.

**Consequences.** A failure reports the shrunk counterexample, the original draw, what the
predicate raised and the replay seed. A generator built on `from-rng` reproduces but does not
shrink meaningfully; the docs say to build values from the combinators when a small
counterexample matters. Shrinking quality rests on each generator's "choice 0 is simplest"
discipline: a new generator has to keep it. Guards: `tests/property_test.blsp` (a vector
holding 42 shrinks to `[42]`, an integer bound to the boundary, a sum to a short vector at
the bound, strings to `"aa"` / `"b"`, through `bind`; determinism; the seed replays the
failing trial; the shrunk choices rebuild the shrunk value) and every public name's executed
docstring example.

**Addendum: edge bias and growing sizes (2026-11-10).** Uniform draws found the values bugs live
at (0, -1, a range's ends, an empty or one-element collection, `"\n"`, NUL, the codepoints
beside the surrogate gap, U+10FFFF) only by luck: `x ≠ 0` over `(int -1000000 1000000)` passed
100 trials. Each random choice now comes, one draw in 8 (`edge-odds`), from its bound's edges —
0 and the bound three eighths each, 1 a quarter, bound − 1 an eighth, plus edges a generator
names (`character`'s BMP class adds U+D7FF and U+E000; its whitespace class gained NUL) — and a
"one more element?" flag stops the collection one draw in 8. The bias is a *sampler*: it acts
only on the random half of a draw, never on a replayed prefix, so shrinking, `replay` and
"choice 0 is simplest" are untouched and a seed still fixes every draw. Sizes grow over the
trials: a source carries `:size` in (0, 1], which scales `vector-of`'s `:average`, rising
linearly to 1.0 by the halfway trial, so early trials try small collections. Because trial *i*
now draws at its own size, a failure reports `:size` beside `:seed` (and the run's
`:start-seed`); `{:seed S :size Z}` replays it as trial 1, and the report's `--seed` hint names
the start seed, which reruns the whole sequence. `check` takes `:size` to fix it. Guards:
`tests/property_test.blsp` "edge bias finds edge values in a few trials" (0 within 100 trials,
each end of a range within 200, -1, `[]` and a one-element vector, the boundary characters,
each over several seeds) and the size test (small sizes draw shorter vectors).
## ADR-686 — A picture is a display op: `[:image row col w h source opts]`, painted at pixel resolution, half blocks in a terminal

**Status:** implemented (2026-11-10).

**Context.** bedit's PDF doc-view rasterises a page with `pdftoppm` and paints it the only way
the display protocol allowed: decoded by `gui/image-thumb` and drawn as half-block cells, `▀` in
its top pixel's colour over its bottom pixel's — two pixels a cell. Body text at that resolution
is unreadable; bedit's image viewer has the same ceiling. The op set had no way to say "this
picture, in this rect". The pixel-space `[:sprite …]` op (games) needs a texture uploaded to a
window first (`gui/texture`, a per-window handle the app frees), takes physical pixels from the
window's corner — so an app laying out in cells has to know the inset, the seam's row map, a
cell region's metrics and a scroll region's shift — has no clip and no fit, and draws nothing in
a terminal. None of that is what a page or a photo in a pane wants. Other callers want the same
thing: any `ui-run` app with a picture, the observer, a Markdown preview with images.

**Decision.**

1. **One op, in cells.** `(editor/display/image row col w h source opts)` builds
   `[:image row col w h source opts]`. The rect is in cells, the grid every other cell op uses,
   so the op scrolls in a `scroll-region`, sits in a `cell-region`, is placed by the seam's row
   map and is diffed by rows like a `:rect`; only the painting is in pixels. The picture is
   placed in the block by `:fit` — CSS's `object-fit` words, `:contain` (default), `:scale-down`,
   `:fill`, `:none` — and `:align` (`:center`, default, or `:top-left`), and clipped to the
   block.
2. **The source is the picture, not a handle.** `source` is the encoded bytes (PNG; JPEG / GIF /
   WebP / BMP with `image-formats`) or the `{:width :height :rgba}` map `gui/image-thumb`
   returns. There is no upload and nothing to free: the op is plain data, so it crosses to a thin
   client like any other.
3. **Decoded once per content.** The op is parsed every frame (a memoised fragment is not
   guaranteed), so `%gui-draw` hashes the bytes (BLAKE3, read in place in the heap) and looks the
   key up in a process-wide decode cache (`host::picture::DECODED`, 256 MB, least recently used
   dropped); a miss decodes under `image-thumb`'s limits. A frame naming the same bytes again
   costs a hash. The op carries the decoded picture as an `Arc`, and two ops are equal when their
   keys are, so an unchanged frame is not repainted.
4. **Resampled once per size, by both painters.** Each window's `Renderer` keeps the picture
   resampled (Catmull-Rom) to the size it was drawn at (`ScaledPictures`, 128 MB). The CPU
   painter blends those pixels into the canvas, clipped to the block, the band and the grid top
   a scrolled op stops at; the offscreen painter is the CPU painter, so `gui/render-frame` and
   `gui/capture` show it. The GPU painter uploads the same pixels once per size as a texture of
   exactly the drawn size (`PictureTextures`, 128 MB) and draws one textured quad texel for
   pixel, clipped to the block; an upload or a free bumps the texture generation, so a memoised
   fragment holding a picture expands again rather than replaying a freed texture.
5. **The terminal draws the same op in half blocks**, the rendering apps did by hand: the block
   taken as `cols` × `2·rows` square pixels, the picture placed by the same `:fit` and `:align`,
   a partly transparent pixel blended over the terminal's background, a transparent half left as
   the terminal's own (`▄` / `▀`), and a cell the picture does not cover left untouched.
6. **No capability query.** The fallback is automatic, so an app emits one op and need not ask
   which display it has. The one thing an app may want to adapt — how many pixels to rasterise a
   page at — it can already compute from the cells it gives the op and `gui/cell-size`.

**Alternatives.** *Sprites in Brood* — expand the op in `editor/frontend` into a `gui/texture`
upload plus a `[:sprite …]`: the frontend would have to turn cells into window pixels (inset,
seam, cell regions, scroll shifts — all renderer state), manage per-window texture lifetimes, and
the sprite has no clip; the picture would also cross a thin client's wire as a texture upload
beside the frame. *A handle the app uploads once* (`gui/texture`-style) — cheaper per frame than
a hash, but it makes the op stateful and per window, which the display protocol's frames are
not; the content cache gets the decode-once property without the state. *A terminal graphics
protocol* (kitty, sixel) — real pixels in a terminal that has one; left for later (below).
*A `gui/pixel-images?` query* — rejected in (6).

**Consequences.** bedit's image view and PDF doc-view emit one op and get readable pages in a
window, cells in a terminal. A frame carrying a picture pays a hash of its bytes per parse (well
under a millisecond for a page-sized PNG) unless it is inside a reused `ui-memo` fragment; the
first paint at a new size pays a resample on the GUI thread (tens of milliseconds for a large
page), which a window resize repeats per size. A thin client is sent the picture's bytes in every
frame that carries it (the frame protocol has no content dedup yet). The resample filters
straight alpha, so a picture with soft transparent edges can fringe slightly. Follow-ups: the
kitty graphics protocol and sixel for terminals that have them; dedup of picture bytes on the
remote-display wire. Guards: `host::picture` unit tests (placement, the decode cache, half
blocks), `offscreen::an_image_paints_at_pixel_resolution_inside_its_block` (one-pixel stripes
survive; red with the painter's arm disabled), `terminal::native::image_tests`, and
`tests/gui_test.blsp`'s `editor/display/image` block through `gui/render-frame`.

**Amended (2026-11-10, ADR-695).** Each follow-up above is done: a terminal that speaks the kitty
graphics protocol shows the picture in pixels (cells stay the fallback, still with no capability
query for the app); the first paint at a new size no longer resamples on the GUI thread; a thin
client's link carries a picture's bytes once; and the per-parse hash is gone for a bytes value
reused across frames, its digest kept on the heap blob. ADR-695 has the decisions.

## ADR-695 — A picture's follow-ups: the kitty graphics protocol in a terminal, resampling off the GUI thread, large bytes once per link

**Status:** implemented (2026-11-10).

**Context.** ADR-686 left four costs of its `[:image …]` op. A terminal always drew half blocks,
two pixels a cell, though kitty, Ghostty, WezTerm and Konsole can show real pixels. The first
paint at a new size resampled the picture on the GUI thread — tens of milliseconds for a page, on
every step of a window resize. A thin client (`editor/serve` / `editor/attach`, frames sent as
messages over a node link) was sent the picture's encoded bytes in every frame that showed it. And
every parse of a frame hashed the bytes again.

**Decision.**

1. **The kitty graphics protocol, detected by asking.** `term-enter` (once per process) writes a
   kitty graphics query for a 1×1 picture (`a=q`, image 31) followed by DA1, and reads the tty
   until the DA1 answer or 500 ms: every terminal answers DA1, in order, so an `OK` for image 31
   before it means the protocol. `BROOD_TERM_GRAPHICS=kitty|cells` decides without asking. With
   the protocol AND a cell pixel size from `TIOCGWINSZ`, a picture is resampled to the pixels its
   cells cover, cropped to what shows, PNG-encoded and transmitted once under an image id keyed
   by those pixels, then PLACED at its cell (`a=p`, a pixel offset into the cell, `C=1`) after
   the frame's cells are written, inside a cursor save / restore. An unchanged frame writes
   nothing; a moved picture deletes its placement and places the stored image again; a whole
   repaint deletes every placement and re-places without retransmitting; images no frame shows
   are kept (a page flipped back to) and the least recently shown freed past 64 images or
   192 MB (under kitty's 320 MB quota); leaving the screen frees them all. The cells under a
   picture are left as the frame painted them — kitty draws the image over them. The decoder now
   swallows an APC answer (`ESC _ … ESC \`), so a late reply is never typed.
2. **Resampling off the GUI thread.** A real window's `ScaledPictures` hands a size it does not
   have to a worker thread of its own (the newest size per picture when requests pile up — a
   resize drag asks for many) and returns a stand-in: the nearest size resampled before, else the
   decoded picture. The CPU painter stretches it nearest-neighbour, the GPU uploads it at its own
   size and lets the sampler stretch the quad. When a resample lands the worker sends
   `PicturesLanded`; each window keeps what landed for it, forgets its retained frame, bumps its
   GPU texture generation (so memoised fragments expand again) and repaints. The offscreen painter
   resamples in place, so `gui/render-frame` and `gui/capture` stay deterministic.
3. **A large bytes value crosses a link once.** In the distribution layer, not the display
   protocol: any repeated large value (a texture, a sound, a file) is the same waste, and the
   link already orders everything. On a current link a bytes value of 16 KiB or more is left out
   of a queued `Send` payload at encode time and spliced back in by the link's writer thread when
   the frame's turn comes — whole (`M_BYTES_NEW`: digest, bytes) the first time, by its BLAKE3
   digest (`M_BYTES_SEEN`) after. Both ends keep the same bounded LRU ledger (64 values, 64 MiB)
   and apply it to the same sequence — the writer in queue order, the reader in arrival order —
   so the sender knows exactly what the receiver holds: no acknowledgement, no re-request, and a
   new link (reconnect, restarted peer) starts both empty. A reference the reader cannot resolve
   or bytes that do not hash to their digest fail the decode and tear the link down; the receiver
   hashes what it is sent, so a peer cannot make a reference resolve to other bytes. The new tags
   bump the protocol to **v13**; a v12 node no longer links (as v12 did to v11), and a v10 link
   never carries them.
4. **A bytes value keeps its digest.** `SharedBlob` caches its BLAKE3 digest on first use; the
   picture cache keys a heap bytes value by it, so a frame naming the same value again (an app
   holding its page in its model) hashes nothing. The link's dedup uses the same digest, and a
   value received whole arrives with it computed.

**Alternatives.** *Sixel* (foot, WezTerm, mlterm, `xterm -ti 340`): a sixel image becomes cell
content with no ids, so it must be re-sent whenever a cell under it changes and a vanished picture
needs its cells repainted, and the picture must be quantised to a palette first — not the "once
per content" this decision is about. Left out; DA1's attribute 4 says which terminals have it,
should a later decision want it. *Kitty's own scaling* (send the source, place with `c=`/`r=`) —
stretches to whole cells and cannot keep the aspect or offset within a cell; resampling here keeps
the window's exact placement. *Unicode placeholders* (kitty's `U=1`, which survive tmux) — a
later step for tmux. *Dedup in the display protocol* (`editor/serve` swapping sources for keys) —
a walk of every frame in Brood, blind inside memo fragments, and only for pictures; the link sees
every value. *An acknowledgement or a "send it again" request* — mirrored ledgers make both
unnecessary. *Resampling with a GPU blit* — a per-backend path for what one worker thread does for
both painters.

**Consequences.** In kitty, Ghostty, WezTerm or Konsole a picture in bedit's image view or PDF
doc-view shows at the terminal's pixels; tmux and screen, which answer DA1 themselves, keep half
blocks (so does a terminal whose tty reports no pixel size, and Windows' console). The answer is
waited for up to 500 ms at the first `term-enter` when a terminal never answers DA1. A picture
transmitted is encoded on the drawing process (once per content and size). A resize shows a
nearest-neighbour stand-in for a frame or two before the exact size lands. A thin client holds up
to 64 MiB of received large values per link. A v12 runtime cannot link with this one. Untested
here: a real kitty-protocol terminal (the escapes, the detection parse and the paint plan are unit
tests; the user's check is to run bedit `-nw` in kitty or Ghostty on an image). Guards:
`terminal::native::graphics::tests` (detection parse, plan geometry, transmit-once / place /
delete / whole-repaint / farewell escapes, chunking, eviction),
`image_tests::an_image_op_through_the_kitty_protocol_leaves_the_cells_alone`, the decoder's
APC case, `picture::tests::a_new_size_is_resampled_off_the_thread_and_a_stand_in_painted_meanwhile`,
`dist::shared_bytes::tests` (once then by digest, both ends forget alike — red with the reader's
eviction disabled — unknown references and wrong digests refused), `cli`'s
`distribution::a_large_bytes_value_sent_repeatedly_arrives_intact_every_time` (red, a 30 s
timeout, with the reader keeping nothing), and `blob::tests::a_digest_is_the_bytes_blake3_and_is_kept`.

## ADR-687 — The three largest std files split along their layers: `package-manifest`, `package-publish`, `test-select`, `editor/undo-region`

**Status:** implemented (2026-11-10).

**Context.** `std/editor/buffer.blsp` (2 334 lines), `std/tool/package.blsp` (2 316) and
`std/tool/test.blsp` (1 991) were the largest std files. A module is one file (a second
`defmodule` of the same name is rejected), so a split means new module names, and every moved
public name changes its qualified spelling.

**Decision.** Split each along a layer the rest of the file does not call back into, so the new
module depends on the old one and never the reverse (no require cycle):

1. **`package-manifest`** — `nest add` / `nest remove` (`add`, `remove-dep`) and the CST edits
   of the manifest's `:dependencies` behind them. **`package-publish`** — `nest search`,
   `publish`, `release`, `key-gen`, `bump-version`, `publish-brood-constraint`, the tarball
   build and the signing. Both are toolchain modules; `package` (resolution, fetching, the lock
   file, runtime install) stays in the core list because a bundle with dependencies sets up
   through it. `registry-search-url` and `package-signing-payload` stay in `package`, which
   uses them too.
2. **`test-select`** — the selection pipeline (`test-make-filter`, filtering, sharding,
   ordering), each test's recorded tags / file / line, and `label`. Pure functions of the units
   and the spec; the two readers of the `test/*filter*` global (`test-filter-seed`,
   `test-filter-narrows?`) stay in `test`.
3. **`editor/undo-region`** — `undo-in-region` and its diff helpers, which read a buffer's
   history and record through the buffer's own entry points.

A moved name keeps its spelling under the new module (no renames beyond the module), and each
public one is in the rename ledger, so a caller on the old spelling is told where it went.

**Alternatives.** *A module spanning several files* — an `(:include …)` or a second
`defmodule` of the same name allowed: it keeps every spelling, but adds loader semantics (file
order, where a private is visible, what an image section holds) to the language for a
file-length concern, against ADR-011. *Splitting the cores further* — the buffer's splice log,
narrowing and editing operations, and the test runner's phases and reporting, are each called
from the rest of their file and call back into it; a split there is a mutual dependency, which
the loader allows only through `(:use-internals m :only […])` refers.

**Consequences.** `package.blsp` 1 688 lines, `test.blsp` 1 770, `buffer.blsp` 2 106. Callers
that reach a moved private qualify it with the new module (`package-publish/registry-build-tarball`).
A private of the old module that a new one uses is reached qualified
(`package/package-in-project`) through `(:use-internals package :only [])` — the grant with
nothing referred, so `(:use package :exclude [update])` stays the only refer. (The split found
that the checker read `(:use-internals m :only […])` as a refer-all of the publics, so a private
named in `:only` was "unbound" though the runtime referred it; fixed the same day, guard
`use_internals_only_refers_exactly_the_names_privates_included`.) bedit's one caller of `undo-in-region` moved with it.

## ADR-696 — `os/pipeline` and `os/spawn-pipeline`: children joined by OS pipes

**Context.** Brood could run one child (`os/cmd`, `os/spawn`) but could not connect one child's
stdout to another's stdin. bedit's `/ssh:` copy between two machines needed exactly that —
`ssh A cat X` into `ssh B sh R` — and had to write `/bin/sh -c "ssh A cat X | ssh B sh R"` through
`os/cmd`: Unix only, every argument quoted for the shell by hand, and one exit status for the whole
line, so a failing `cat` on A was invisible behind a succeeding `sh` on B. Moving the bytes through
Brood instead (read one child, `os/write` the other) puts every byte through the heap and a mailbox
for no gain. The OS already has the mechanism; Brood had no way to ask for it.

**Decision.** Two natives over one chain builder (`host::subprocess::spawn_chain`), which starts the
stages with each one's stdout handed to the next as its stdin (`Stdio::from(ChildStdout)`, portable
to Windows), the parent's copy of each read end gone as each `Command` drops.

- `(os/pipeline stages opts)` — `os/cmd` for a pipeline. A stage is an argument vector
  `["prog" "arg" …]` or `{:argv [...] :cwd :env :raw-args}`; `opts` are `os/cmd`'s, `:cwd` /
  `:env` / `:raw-args` every stage's defaults, `:stdin` the first stage's, `:timeout-ms` the whole
  pipeline's. The answer is `os/cmd`'s shape plus `:stages`: `:stdout` the last stage's, `:stderr`
  every stage's in order, `:exit` bash's `pipefail` (the last stage that did not exit 0), and
  `:stages [{:exit :stderr} …]`. `pipefail` rather than the last stage's code because the caller's
  question is "did the bytes arrive", and a failing upstream stage means they did not; the shell
  default is what hid bedit's failing `cat`.
- **`os/cmd` is now a pipeline of one**: the same runner (`run_stages`), so the timeout, the
  caller-killed kill (ADR-514), the dirty-blocked worker (KI-280) and the responsive report
  (ADR-517) are one code path. A pipeline reports once, `:native "os/pipeline"`, its detail the
  stages joined by ` | `.
- `(os/spawn-pipeline stages opts)` — `os/spawn` for a pipeline, ONE subprocess handle: `os/write`
  feeds the first stage, the last stage's stdout arrives as `[:proc …]`, every stage's stderr as
  `[:proc-err …]`, `[:proc-exit h code]` once every stage has exited (`pipefail`, nil for a
  signal). The upstream stages ride the last stage's registry entry (`ChildSlot::upstream`), so
  `os/close`, `os/signal`, the owner's death and the reap reach every stage without a second
  registry.
- Every stage leads its own session (Unix) or Job Object (Windows), as every pipe child does; a
  stop kills each stage's group. Stages cannot share one group: `setsid` in the first stage puts
  its group in a new session, which a later stage forked from the runtime may not join.

**Callers beyond bedit.** `std/tool/package` approximates `git archive | sha256sum` in Brood
because it could not pipe; `git archive HEAD | tar -x -C dest` is the vendoring step it wants.
Anything moving a large artefact between two programs — `pg_dump | gzip`, `tar c | ssh host tar x`,
`git diff | patch` in `std/vcs` — is the same call, and it is what a shell-like REPL helper's `|`
would lower to.

**Rejected.** *A Brood relay* (read stage 1, write stage 2): every byte through the heap and two
mailboxes, and the pipe's backpressure replaced by the reader budget's. *`os/shell-cmd` with a
`|`*: the shell's quoting and Unix only, which is what this replaces. *Stages sharing one process
group*: not possible across sessions (above). *Per-stage tags on a spawned pipeline's stderr*: a
caller that must tell them apart can `os/spawn` each stage; the common case reads them as one
stream, as a terminal shows them.

**Consequences.** A pipeline moving gigabytes holds only what its last stage prints. `yes | head -1`
reports a failure (SIGPIPE ended `yes`) — `pipefail`'s known price; `:stages` says which stage and
how. On Windows the chain is std's portable pipe; the CI platform jobs exercise it, the desktop
does not. Guards: `tests/os_pipeline_test.blsp` (three stages, `:stdin`, per-stage env/cwd, a
failing middle stage, 256 MB through three stages with the runtime's peak memory flat, a timeout
and a killed caller each killing every stage, the responsive report, a stage that cannot start,
`os/spawn-pipeline`'s messages, pipefail and close).

## ADR-697 — `file/read-link`, `file/symlink`, `file/chmod`: links and permission bits, refusals as failures

**Context.** `file/stat` reported `:symlink?`, `:mode` and `:exec?`, and nothing could change
them or say where a link points. bedit's dired could not print `-> target`, and its writable dired
could not redirect a link or edit permissions (Emacs's `wdired-allow-to-redirect-links` /
`wdired-allow-to-change-permissions`); an installer had no way to make what it unpacked
executable; a bundler or a sync tool could not recreate a link. Each is a syscall, so each is a
native.

**Decision.** Three natives in `builtins/filesystem.rs`, each `watched!` (ADR-517's file addendum:
a call that held a responsive process is reported as `[:blocking-call …]`).

- `(file/read-link path)` — the stored target (`readlink`, never resolved), or nil when `path` is
  missing or not a link, as `file/stat` answers nil for a missing path. Asking whether something is
  a link is a question, so "no" is not an error.
- `(file/symlink target path)` / `(file/symlink target path {:replace true})` — nil, or a
  **failure** saying why: the name is taken (a dangling link takes it too), the directory is
  missing or refuses entries, the privilege is missing. The older file natives raise on I/O
  errors; these answer failures because every refusal here is one the caller expects to meet and
  act on — wdired reports a link it could not redirect and goes on to the next line — the
  convention ADR-310 set and `file/trash` follows. A wrong argument TYPE still raises.
  `:replace` makes the link under a temp name beside `path` (`.brood-link-PID-N`) and renames it
  over, so a reader sees the old entry or the new link, never neither. A real directory at `path`
  is refused rather than replaced: the rename would fail on Unix anyway, and replacing a tree with
  a link is not what redirecting a link means.
- `(file/chmod path mode)` — nil or a failure (missing, not the caller's file). `mode` is an int
  0..0o7777 (setuid/setgid/sticky included); outside that raises, as a type error does. It follows
  a symlink, as chmod(1) does (Linux cannot chmod a link itself). No symbolic `"u+x"` form: a
  caller that wants one reads `:mode` from `file/stat` and sets the bit, one `bit/or` in Brood.

**Windows.** A link is made as a directory link (`symlink_dir`) when its target — read from the
link's own directory, as the link will read it — is a directory, and a file link (`symlink_file`)
otherwise, a missing target included. Making either needs Developer Mode or
`SeCreateSymbolicLinkPrivilege`; `ERROR_PRIVILEGE_NOT_HELD` becomes a failure naming both. No
junctions. A Windows file has no permission bits, only a read-only attribute, so `file/chmod` sets
it when `mode` lacks the owner-write bit (0o200) and clears it when `mode` has it, ignoring the
rest; `file/stat`'s `:mode` stays 0 there. Chosen over a failure saying "unsupported" because the
one bit Windows has is the one a caller most often means (make a file read-only, make it writable
again), and a portable caller then needs no OS test for that case.

**Rejected.** *Raising on every refusal*, like `file/rename`: wdired, the first caller, would wrap
every call in a `try` to carry on. *A `:no-follow` option for chmod*: Linux has no `lchmod`.
*Replacing a directory with `:replace`*: deleting a tree is `file/rmdir`'s business, said out loud.

**Consequences.** `file/chmod` and `file/symlink` join the world effects a live evaluator holds
back on a half-typed form (`tooling.rs` `WORLD_EFFECTS`). `platform_test` uses `file/chmod` in
place of the `chmod` / `attrib` programs it ran. Guards: `tests/file_test.blsp` "file: symlinks
and permission bits" (a link, a plain file and a missing path read; a dangling link; a taken name
refused and kept; `:replace` over a link and a file with no temp left; a directory refused; chmod
round trips through `file/stat`, follows a link, refuses a missing path and raises on a bad mode),
`tests/platform_test.blsp` (the Windows behaviour, run by CI's Windows job) and Rust unit tests in
`filesystem.rs`.

## ADR-698 — Every checker warning has a category; `nest check` gates on the category, under the project's `:check` key

**Context.** `nest check` fails on any gating warning, and it told gating from advisory by matching
substrings of the message ("recursive call in non-tail position", "checker gave up:", "is
deprecated since", "is beta —"), and `nest run`'s launch gate found an unbound symbol the same way.
ADR-673 §4 leaves the text of a warning free to change, and §5 needs warnings that carry a
structured severity, with project- and file-level controls (handoff open thread 1,
`road-to-1.0.md` §B3). The only control was `check-allow` around one form.

**Decision.**
1. **A finding is `(position, category, message)`.** `types/check/lint.rs` lists the categories
   (30 today), each a kebab-case keyword. Where `check-allow` already took a name for a lint, the
   category is that name (`:type-mismatch`, `:non-tail-recursion`, `:unbound`, …), so one word
   names a lint everywhere. The structured builtins (`reflect/check-file-structured`,
   `check-string-structured`, `check-file-deps`) give `{:file :line :col :category :message
   :text}`; `reflect/check-categories` lists every name. The GNU strings of `reflect/check-file`
   and the Rust tuple API are unchanged.
2. **Severity is policy, so it is Brood** (`project-check.blsp`). Advisory by default:
   `:non-tail-recursion`, `:gave-up`, `:deprecated`, `:beta`. Everything else gates. The launch
   gate counts `:unbound`.
3. **Project level: `:check` in `project.blsp`**, a map of `:advisory`, `:gating` and `:allow`
   to category lists. `:allow` silences; it wins over the other two, which win over the defaults.
   A manifest key and not a flag, because CI and every developer read the same manifest (ADR-673
   §5). A name the checker does not know is a warning, not a manifest error: a newer checker may
   know it.
4. **File level: a `(:check-allow :category …)` clause in a `defmodule` header.** The checker
   drops the named categories for that module's lines; an unknown name is a `:check-allow`
   finding. The runtime `defmodule` accepts the clause and ignores it.
5. **`nest check` prints each warning's category** after it (`… [type-mismatch]`, `… [non-tail-
   recursion, advisory — not gating]`), so the name to write is on the line that needs it.

**Rejected.** *Severity in Rust*: which lint fails a project's CI is policy, and policy is Brood
(ADR-006). *Keeping the text match for the launch gate*: the same fragility. *A per-run flag*:
ADR-011 — added the day someone asks. *Severity per finding site rather than per category*: a
project could not name it.

**Open.** ADR-673 §5's "a lint new in a minor release is advisory until the next major" needs a
lint's `:since`; no lint is newer than 1.0 yet, so the rule waits for the first that is.

**Consequences.** The incremental check cache is v5 (its entries hold the maps). The verdict
replay is keyed on the `:check` policy too, since project.blsp is not among the fingerprinted
files. "Special form used as a value" is `:unbound`, so the launch gate now refuses it, as the
runtime would; an evaluated-and-discarded name is `:suspicious`. Guards:
`crates/nest/tests/check_warning_policy.rs` (defaults, `:advisory`, `:allow`, `:gating`, a typo
and the header clause, cache on and off; red with the `:advisory` lookup broken),
`crates/lisp/src/types/check/tests/categories.rs`, `crates/lisp/tests/check_string_structured.rs`.

## ADR-699 — The dist handshake carries the Brood `major.minor`; another minor is refused, and the v10 fallback goes

**Context.** ADR-673 §3: nodes of one `major.minor` always link, and across minors the handshake
refuses with a message naming both versions. The handshake carried only a protocol magic, and
ADR-492 kept a fallback to protocol v10 for runtimes from before mailbox lanes — runtimes of an
older minor by construction, which §3 says must be refused.

**Decision.** Wire **v14**. Step 1 is an 8-byte greeting: the magic `BRD\x0e`, then `major` and
`minor` as big-endian `u16`s. The dialer writes first. The responder reads; on a wrong magic it
closes without a byte, so a port scanner learns nothing. Otherwise it answers with its own
greeting even when the versions differ, and both ends refuse with "the peer runs Brood X.Y and
this node Brood Z.W: nodes link only within one major.minor" — before the `Hello`, so no key
exists and neither end has learned more than the other's version. The magic bumps so a v13 node,
which would read the version as the start of a `Hello`, is refused as a magic mismatch. The v10
dialect goes: `Offer`, the redial, the plain-`Send` downgrade, the record refusal
(`Message::holds_record`), the `lanes` flag on a link and `BROOD_DIST_V10`. A later protocol
change needs no magic byte of its own, since a node of another minor is refused by version.
`BROOD_DIST_VERSION` makes a node claim another `major.minor`, for the test.

**Rejected.** *Keeping v10 interop*: it is cross-minor linking, which §3 refuses. *Comparing the
patch level*: a patch release never changes the wire. *The version inside the `Hello`*: the
refusal would come after keys were agreed, and the dialer of another minor could not parse the
responder's `Hello` to learn why.

**Consequences.** A cluster upgrades a minor at a time, all nodes together (§3's widening is the
day someone needs rolling upgrades). Guards: `dist::handshake::tests` (one minor links, three
mismatches refused at both ends naming both versions — red with only the major compared; a wrong
magic gets no answer), `crates/cli/tests/distribution.rs`
`*_another_minor_*_refused_naming_both_versions` (the error `node/connect` raises, whichever end
is the other minor).
