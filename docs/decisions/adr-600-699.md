# Design decisions: numbers 600 to 699

One of the files the ADR log is split across by number; the index, and the notes that
apply to every entry, are in [../decisions.md](../decisions.md).

## ADR-602 — A test run says so, and gets a scratch home of its own

**Status:** implemented (2026-11-05).

**Context.** A test that calls a command which persists something writes wherever the
program keeps its files — and under `nest test` that was the user's real home. bedit's shell
test pressed RET and overwrote the user's `~/.config/bedit/state/bshell-history.blsp`; its
`check-modes` tool filled their recent files. bedit then guarded itself by asking whether the
test framework's registry happened to be bound — a guess from what is loaded, which every
other program would have had to repeat, and which said nothing to a process a test started.

**Decision.**

- **The runner says it is a test run.** `nest test` sets `BROOD_TEST_RUN=1` before the
  interpreter exists (`cli_support::arm_test_run`, from `arm_test_env`). `test/running?`
  answers from it. It is an environment variable on purpose: a program a test starts — an
  eval server, a subprocess under test — is part of the run, and inherits it. A program that
  must not load the test framework to ask (an editor deciding where its config lives) reads
  the variable itself.
- **The run gets a private scratch home.** Unless `nest test --real-home` or
  `BROOD_TEST_HOME=keep`, the runner makes `<temp>/brood-test-home-<pid>-<time>/` and points
  `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_DATA_HOME` at its `config/`, `state/` and
  `data/`; `BROOD_TEST_SCRATCH` (`test/scratch-dir`) names it. A program that keeps its files
  under the XDG homes needs no test-mode code at all. The directory is removed when the run
  ends, and an earlier run's left behind by a run that died is purged when the next starts
  (by liveness, not age: ADR-608). The REPL's history, which is not under an XDG home, is
  pointed there too (`BROOD_HISTORY`, ADR-608).
- **`XDG_CACHE_HOME` is left alone.** Brood's own caches — the stdlib image, the prelude
  image, compiled grammars, the check cache — live there, keyed so sharing is only a
  speed-up; a fresh cache per run would cost every run a cold start. A cache is regenerable;
  a config, a history or a data file is not.
- **`nest`'s own preferences stay the user's.** `BROOD_USER_CONFIG_HOME` keeps the real
  config base, and `project`'s user config (`~/.config/brood/config.blsp`: the registry, its
  token, `git init`) reads it first — those are the person's tool settings, not the program
  under test's state. A run started inside another keeps the base the outer run kept
  (ADR-608). Nothing else reads it: a publisher's signing key, a node cookie and
  everything a program keeps go to the scratch home under test.

Not covered: `brood --test`, which runs after the interpreter (and its threads) exist, where
setting the environment is not safe; it is a single-file runner.

**Callers beyond bedit.** Every project's suite — a hive package with a history, a cache of
its own or a config file is protected without knowing it; Brood's REPL history (since
ADR-608, which points `BROOD_HISTORY` into the scratch home) and `node`'s cookie under std's
own tests; any tool that wants to keep a test away from something real
(`test/running?`).

**Consequences.** Guards: `crates/nest/tests/test_scratch_home.rs` (a project's test writes
under `$XDG_CONFIG_HOME`; with `HOME` at a stand-in, the write lands in the scratch home, the
scratch home is gone after the run, and `--real-home` puts it under `HOME/.config`) and
`tests/test_run_test.blsp` (`running?`, `scratch-dir` and the three homes inside it).

**Amended by ADR-608 (2026-11-05).** As first written, only `nest test` armed — so bedit's
`C-c t`, which runs a project's tests through a generated script under `nest run` (cold) or in
a warm eval-server child, ran them with the real home, and the tests bedit guards skipped their
checks. A runner that is not `nest test` now asks for the run with `BROOD_TEST_ARM=1`; bedit's
both runners do. The REPL history moved into the scratch home, a purge goes by liveness, and a
nested run keeps the user's config base.

## ADR-603 — What a load bound, and the impls a module registered: `reflect/rebound-since`, `registry/impls-by`

**Status:** accepted (2026-11-05).

**Context.** A plugin host that unloads a plugin has to know what the plugin's load defined and
which ability impls it registered. bedit found the first by reading EVERY global's value before
the load and the source site of every global after it (11,495 globals: 55 ms to apply a package,
80 ms to remove one), and had no way at all to find the second: `registry/written-by` leaves the
impl tables out (ADR-582), and `reflect/undef` retires only the impls of a type it removes — so a
plugin's `impl` of a core ability for a core type outlived it, calling a helper that was gone.
The runtime already knew both: every `def` and removal stamps the global with the runtime's
generation (`RuntimeCode::global_generations`, read by `%global-generation`), and every impl is
kept by precedence tier with the namespace that registered it (`*impl-tiers*`, ADR-432).

**Decision.**

- **`reflect/generation`** answers the runtime's generation now; **`reflect/rebound-since g`**
  every global defined, redefined or removed after it — one pass over the stamps in Rust, no
  value read. A host takes the generation before a load and asks after it.
- **`registry/impls-by writers`** lists every impl a namespace in `writers` registered and that
  is still registered (`{:ability :op :key :rank :from}`); **`registry/retract-impl impl`** takes
  one back while its tier still holds that namespace's registration, the highest tier left
  winning again (or the slot unclaimed). An impl from code of no module is nobody's.
- **The root escape names a global exactly in `reflect/source-location` and `reflect/undef`**:
  `/org/f` is the global `org/f` even inside a project whose own `org` module would root
  `org/f` to `bedit/org/f`. A host asking about a plugin's module that shares a short name with
  one of its own got the host's function's site — and would have removed it. (Inside a project
  a `def` target is still rooted, root escape or not; ADR-604 is what keeps a plugin's module
  out of the host's.)
- **`registry/put-new!`** registers an entry only when the key is free, in one locked step — a
  runtime-wide slot (bedit's one package job across every window).

**Callers beyond bedit.** `nest`'s dev server and `tool/reload` (what a reload rebound, an impl
a module no longer declares), the observer's extensions, a REPL undoing an experiment.

**Amended by ADR-606:** the generation says WHICH globals a load bound; what each held before it
is `reflect/global-values`, taken before the load. Keeping old values only for the names the
plugin's source spells missed a name the project rooted and one a macro built.

**Consequences.** Guards: `tests/registry_writers_test.blsp` "reflect/rebound-since" and "ability
impls a module registered"; bedit's package tests.

## ADR-604 — A plugin's modules load apart from the host project's; same-tier impls stack

**Status:** accepted (2026-11-05).

**Context.** Inside a project every `mod/name` of one of its modules roots to
`project/mod/name` (ADR-070), at compile time and on a global lookup's miss. A plugin loaded at
run time — bedit's packages — loads in the host's process, so in the host's package context:
a plugin module named `org` beside bedit's `org` declared `bedit/org` and redefined bedit's
functions. A root-escaped `(def /org/f …)` bound the ROOTED `bedit/org/f` while its definition
site was recorded under `org/f`, so the site said the plugin's file and the binding was the
host's. And an `impl` registered at the same precedence tier as another namespace's replaced it
outright: taking the plugin back left the slot empty rather than the impl it replaced.

**Decision.**

- **`reflect/with-modules-apart modules thunk`** runs `thunk` with `modules` removed from the
  active project's module set: inside it `org/f` is the global `org/f`, while every other
  project module roots as before — the plugin still reaches the host's `model`, `commands`, ….
  The context comes back on the way out, a throw included; a process spawned inside inherits it.
- **A name bound exactly whose rooted spelling is not bound is not rooted** (`root_qualified_ref`,
  checked outside its memo): a late-bound `'org/only-in-plugin` — a keymap command, a hook —
  reaches the plugin's. A name BOTH bind is ambiguous when spelled short; the host's compiled
  code names its own in full (`bedit/org/f`), and the short spelling finds the exact global.
- **A definition's site is recorded under the global the definition binds** — the same rooting
  the `def` arm applies — never under a name nothing binds.
- **`*impl-shadowed*`**: a same-tier registration from another namespace keeps the one it
  replaced (newest first, per `[ability op id]` and tier). `registry/retract-impl` puts it back;
  `registry/impls-by` lists the shadowed ones too, so a plugin whose impl was itself replaced
  can be taken back without the newer one ever restoring it. The stdlib image carries tiers as
  before; a std module replacing another std module's impl at the same tier (a warned conflict)
  is not imaged with its shadow.
- **`%registries-written-by writers`** answers the registries the writer journal credits to
  `writers`; `registry/written-by` walks those instead of every registry.

**Callers beyond bedit.** Any host that loads plugins into its own project process (the
observer's extensions, a `nest` dev server loading a scratch module), and any tool unloading
one.

**Consequences.** bedit loads each package's files apart from its own modules and binds a
retired layer back the same way; its removal is proportional to what the package wrote (80 →
18 ms at ~11,500 globals). Guards: `tests/modules_apart_test.blsp`; `tests/registry_writers_test.blsp`;
bedit's `tests/package_safety_test.blsp` ("a package module named like one of bedit's", "two
packages implementing one ability for one type, at the same tier").

**Addendum (2026-11-05).** `reflect/project-modules` answers the running project's module short
names (ADR-606: registered by `setup` and by a release bundle's boot, not read off the package
context, which a bundle never sets), so a host can refuse a plugin whose module would share one (bedit refuses a package
whose module is named like one of bedit's or a std module, at install and at load: a short
late-bound `'org/…` in its own keymaps could otherwise reach the plugin's). And the project
image's prune no longer exempts registrations made before the project loaded: ownership is the
journalled writer, so the prelude's never were a module's (KI-106), while a std module the build
loaded from source before the project — `nest`'s toolchain, with no stdlib image yet — had its
record ids baked into the image, and the next run started with `:http/response`,
`:log/line-backend` … and no constructors. Reproduced on an empty cache with nest 77f15601 and
this branch; guard: `crates/nest/tests/project_image_registries.rs`
`a_cold_first_run_without_a_stdlib_image_images_no_foreign_record_ids`.

## ADR-605 — A restarted served loop is given only the hand-overs no loop handled; a new client starts a fresh ledger

**Status:** accepted (2026-11-05). Follows ADR-593.

**Context.** ADR-593's session keeps the manager's hand-overs to its loop (`[:adopt …]`,
`[:claim …]`, `[:client-can …]`) and gives them to a restarted loop again, on the reasoning that
replaying one the dead loop had taken is harmless. A review found it is not. The session only
appended them (the newest six), so every restart replayed every one it had ever passed on: a claim
DECLINED long ago (the old client answered; the claimant got a session of its own), replayed to a
restarted loop whose client had since gone and whose session had parked, adopted the claimant
without a ping — the claimant's window then fed two sessions, and the manager, still holding the
first one parked, could no longer hand it to its user. A claim that SUCCEEDED, replayed to the
loop now serving the claimant, pinged the claimant and could `[:bye]` it. Three more seams leaked
the same way: the key LEDGER kept the old client's last key number when a new client adopted or
claimed the session, so a restart before the new client's first key was taken told it
`taken=N` and it dropped its own first N keys; a restarted parked loop parked afresh, so a loop
dying every half-minute kept a parked session alive forever; and each restarted loop that
watched a buffer registry left its dead predecessor among the registry's watchers, as the session
kept every death it ever had.

**Decision.**

- **Only unhandled hand-overs replay.** The loop's display tells its session each hand-over it
  HANDLED, whatever came of it (`[:editor/serve/handled message]`, sent after what handling it
  sent, so it is folded before the loop's `[:EXIT]`), and the session forgets it. A restarted
  loop is given only what was passed on and never handled — a hand-over the dead loop had not
  reached yet. A claim the loop was mid-way through (waiting on its ping) when it died is
  unhandled, and is asked again.
- **A new client starts a fresh ledger.** Adopting or claiming the session clears the ledger's
  last-taken number: the new client numbers its keys from 1, so until the new loop takes one, a
  restart tells it none was taken and it sends them all again.
- **A parked session's time to live runs from when it parked.** The display reports `:parked-at`
  with its client and size; a restarted parked loop starts parked at that time.
- **Nothing dead is kept.** A buffer registry monitors each watcher and drops one that ends
  (`registry-unwatch` demonitors). A session keeps only the deaths its restart budget counts
  (those inside `:window-ms`); `:restarts` in the `death` map is a counter of its own.
- **A browser tab's input has one owner.** The tab's event-stream process owns its input log: a
  `POST /input/<id>` is handed to that process (`[:editor/web/input m]`), which numbers, keeps and
  ships it in mailbox order with the session's `[:reattached …]`. Before, the request process
  and the stream both read-modify-wrote the tab's entry: a post during a restart could go to the
  dead loop and be wiped from the log by the resend, its number reused. No new primitive: one
  owner process is Brood's way to make a table entry's update atomic.

**Callers beyond bedit.** Every `serve` app's sessions, and every buffer registry's watchers (a
frame, a mirror, a collab host).

**Consequences.** A restart no longer asks or adopts anyone the manager did not just ask it to.
Guards: `tests/serve_test.blsp` "serve: a restarted loop is given only the hand-overs no loop
handled (ADR-605)" — a declined claim not replayed to a restarted parked loop, a successful claim
not replayed to the claimant, the adopter's fresh ledger, a parked session's restarted loop
ending on the original time, the pruned deaths; `tests/buffer_registry_test.blsp`
"buffer-registry — a watcher that ends is dropped (ADR-605)"; `tests/editor_web_test.blsp` "a
tab's input across a restarted loop (ADR-605)".

## ADR-606 — The running project's modules and what a load replaced, in every configuration: `reflect/project-modules`, `reflect/global-values`, `reflect/source-locations`

**Status:** accepted (2026-11-05).

**Context.** Two answers ADR-603/604 gave a plugin host were only true under `nest run` /
`nest test`. `reflect/project-modules` read the active package context — but a `nest release`
bundle loads the root project's own modules UNROOTED and never sets one (`bundle-boot-load`
registers only the dependencies' rooting), so in bedit's installed editor it answered `[]`: a
package module `org` passed the collision check, loaded into bedit's `org`, and its removal took
bedit's own `org` rows and namespace with it. And a host undoing a plugin learned WHICH globals
the load bound from `reflect/rebound-since`, but kept the value each held before only for the
names the plugin's source spelled. Inside project `bedit` a plugin's `(defn keyhelp/f …)` binds
the rooted `bedit/keyhelp/f`, and a macro can build any name; neither was kept, so removing the
plugin left the patch live — calling the plugin's helpers, now unbound.

**Decision.**

- **`reflect/project-modules` is the running project's registered module list** (the prelude's
  `*project-modules*`, `%register-project-modules!`), not the package context. `setup`'s
  rooting registers the `(defmodule …)` names it roots; `bundle-collect` bakes the same names
  into the release manifest as `:project-modules`, and a bundle's boot registers them before any
  module loads (a bundle built before the field falls back to its embedded keys that are no
  dependency's). The answer is the same inside a dependency's load or `with-modules-apart`. The
  project image does not carry it: it is true of the run, set before the image installs.
- **`reflect/global-values`** answers every global a `def` may rebind — none the language
  reserves (ADR-166) — as a map of exact name to value, read in one pass under the table's lock.
  Taken before a load, it holds what each global `reflect/rebound-since` names afterwards held
  before it, however the load spelled or generated the name. Reserved names are left out: a load
  cannot rebind them, and they are most of the table.
- **`reflect/source-locations`** is its companion — every rebindable global's definition site,
  `{sym [file line col]}` — and **`reflect/set-source-location name loc`** puts one back (nil
  forgets it). A global given back its old value otherwise still read as defined in the
  removed plugin's file, so `M-.` and `C-h f` on a restored function went to a file that is
  gone.

**Callers beyond bedit.** `nest`'s dev server and `tool/reload` (what a reload replaced, to roll
it back), a REPL undoing an experiment, any released Brood program that loads plugins and checks
their module names against its own.

**Consequences.** bedit's package removal restores every core global a package rebound, by the
rooted name, and refuses a package module named like one of bedit's in the released editor as in
`nest test`. Guards: `crates/cli/tests/release_bundle.rs` `a_bundle_answers_its_own_project_modules`
(a booted bundle, baked manifest and the fallback); `tests/project_test.blsp` "bundle-collect bakes
the project's own module names into the manifest"; `tests/modules_apart_test.blsp`
"reflect/project-modules"; `tests/registry_writers_test.blsp` "reflect/global-values" (both cases); bedit's
`tests/package_safety_test.blsp` ("in the released editor", "a core function a package patched").

## ADR-607 — One resolver finds the program for `os/which` and every spawn

**Status:** implemented (2026-11-05).

**Context.** `os/which` searched `PATH` in Brood, Windows's `PATHEXT` included, while every
spawn left the search to the platform. On Windows the two disagreed. `std::process::Command`
with a bare name finds only `name.exe`, so `os/which "mix"` answered `mix.bat`, and an npm shim
answered `tsc.cmd`, and then `os/spawn` and `os/cmd` failed on the same name. bedit's LSP client
never connected, its formatter raised, and its Elixir sandbox did not start. The ConPTY spawn
handed `CreateProcessW` the bare name with no application name. That search tries the current
directory first, so a `bash.exe` planted in a cloned repository ran. It also never reads an
`:env` `PATH`.

**Decision.**

- **One resolver, in Rust** (`host::subprocess::program`). `os/spawn`, `os/spawn-pty`
  (ConPTY and Unix), `os/cmd`, `os/run-process` and `os/detach` all start the absolute path it
  answers. `os/which` is the same resolver too (`%program-path`): a yes from it is a program a
  spawn starts, because it is the same code. It lives in Rust because the ConPTY spawn needs an
  absolute path whoever calls `%pty-spawn`, and a raw builtin is no safer than its weakest
  caller.
- **The child's view.** It resolves with the spawn's `:cwd` and `:env`. The `PATH` searched is
  the `:env` one when the spawn sets it, ours otherwise, and no `PATH` finds nothing. A
  relative name, or a relative `PATH` entry, is taken against the child's working directory.
  `os/which` takes the same options (`(os/which "mix" {:env …})`).
- **`execvp`'s rule everywhere.** A name with a separator is used as given, and a bare name is
  looked for in each `PATH` entry, an empty entry meaning the working directory. On Windows a
  program is a file with a `PATHEXT` extension. Windows's own extra places (the current
  directory, the system directories, the executable's directory) are not searched. On Unix
  the child still sees the name it was given as `argv[0]`.
- **Batch files run under the system's `cmd.exe`, never `COMSPEC`.** `cmd.exe` re-parses the
  arguments (BatBadBut, CVE-2024-24576). For the pipe spawns, `Command` given a `.bat` path
  already escapes them (Rust 1.77.2 and later). The ConPTY spawn writes its own command line,
  using the same escaping (`batch_command_line`): `cmd.exe /e:ON /v:OFF /d /c ""SCRIPT" ARGS"`.
  An argument is quoted unless it holds only letters, digits and `#$*+-./:?@\_`. A `"` in it is
  doubled, a `%` becomes `%%cd:~,%`, and an argument holding a line break is refused.

**Callers beyond bedit.** Every program that asks `os/which` before it spawns: `nest`, the
REPL's tools, a test helper.

**Consequences.** A not-found spawn now fails before anything starts, with
`not found on PATH`. Guards: the resolver's and the batch escaping's unit tests
(`host::subprocess::program::tests`, which test the Windows rule on every platform);
`tests/platform_test.blsp` "a spawn finds its program as os/which does", which runs a `.bat`
by its bare name from an `:env` `PATH` through `os/cmd`, `os/spawn` and `os/spawn-pty` on the
Windows runner.

## ADR-608 — Any test runner can ask for the test run; the scratch home is purged by liveness

**Status:** implemented (2026-11-05). Amends ADR-602.

**Context.** ADR-602 armed the test run in `nest test` alone, keyed on the subcommand. A test
runner that is not `nest test` got nothing: bedit's `C-c t` writes a script that installs its
report sink and runs it with `nest run` (the cold path), or keeps an eval-server child that loads
the project and runs tests on request (the warm path). Under either, `BROOD_TEST_RUN` was unset,
so the guards bedit's own suite relies on skipped their checks, and a run from inside the editor
wrote the user's real savehist, save-place, transient memory, tutorial progress and slow-turn
log — the exact accident ADR-602 was written for. Three smaller gaps: ADR-602 said Brood's REPL
history was protected, but the history is `$BROOD_HISTORY` or `$HOME/.brood_history` and the
scratch home moves only the XDG homes; the purge called a scratch home stale once its directory
was an hour old, so a second `nest test` deleted a long first run's home under it; and a `nest
test` started inside a run took the outer run's scratch config as the user's config base.

**Decision.**

- **The request is an environment variable on the child: `BROOD_TEST_ARM=1`.** Every Brood
  entry point — `nest` (every subcommand) and `brood` — reads it before its interpreter exists
  (`cli_support::arm_requested_test_run`) and arms exactly as `nest test` does: `BROOD_TEST_RUN`,
  a scratch home, `BROOD_TEST_HOME=keep` honoured. It then removes the request from its own
  environment, so what it starts inherits the armed run (one scratch home, the way a program a
  `nest test` test starts shares it) instead of arming one of its own. Not a `nest run` flag:
  the editor's runtime may be `nest` or `brood`, and an environment variable means the same to
  both — and to a bundle, should one ever host a runner. Not in-process arming from std's test
  runner: the environment cannot be changed safely once the runtime's threads are up, and the
  code a runner loads before its tests could already have read the real paths.
- **`BROOD_HISTORY` points into the scratch home** (`state/brood_history`). An audit of std's
  writers keyed on `HOME` rather than the XDG homes found this one; `~/.broodrc.blsp` is only
  read, and every other file std keeps (`node`'s cookie, a publisher's signing key, `project`'s
  user config) is under `XDG_CONFIG_HOME`. Caches stay under `XDG_CACHE_HOME`, as ADR-602 said.
- **A scratch home is purged by liveness.** The run that makes one holds an exclusive lock on
  its `run.lock` for as long as the process lives — released by the operating system however
  it ends. A purge removes a home whose lock it can take, and keeps one whose lock is held,
  however old. A home with no lock file (made by an older binary, or caught between its
  directory and its lock being made) is removed only past an hour.
- **A nested run keeps the user's config base.** `BROOD_USER_CONFIG_HOME`, when already set (an
  outer run kept it), wins over `XDG_CONFIG_HOME` — which inside a run is the outer run's scratch
  config, no one's preferences.

**Callers beyond bedit.** Any tool that runs tests by some other road than `nest test`: an
editor's in-image or warm runner (bedit's two), an MCP client running a suite through `nest run`,
a CI wrapper that drives `brood` directly, a hive package's own test harness.

**Consequences.** bedit's cold runner starts `nest run` with `BROOD_TEST_ARM=1`, and its warm
test child is spawned with it (`sandbox/spawn-runtime-on`'s `:env`) — so the child is armed
before its first line; the warm child keeps one scratch home for its life, its runs sharing it.
Guards: `crates/nest/tests/test_scratch_home.rs` (an armed `nest run` is a test run with its own
home, `BROOD_HISTORY` inside it, the request consumed and the home gone after; a nested run keeps
the user's base; a purge keeps a live run's ancient home and takes a dead run's),
`cli_support`'s `test_scratch_liveness_tests`, `tests/test_run_test.blsp` (the REPL history path
under a run), and bedit's `tests/testrun_test.blsp` ("a C-c t run gets a scratch home": the cold
