# Design decisions: ADR-500 onward

One of the six files the ADR log is split across by number; the index, and the notes that
apply to every entry, are in [../decisions.md](../decisions.md).

## ADR-500 — Hygiene at every binding site of the one pattern grammar

**Status:** implemented (2026-10-28).

**Context.** The ADR-066 amendment made a quasiquote template's own binders hygienic, but
only plain-symbol `let`/`letrec`/`fn` binders. A destructuring pattern, a `match` or
`receive` clause, and every standard binding macro (`when-let`, `for`, `doseq`, `with`,
`try`'s `catch`, a template `defn`'s params, …) left the template's binder literal, so it
captured caller code spliced into its scope — silently, exactly where the docs said
hygiene was automatic. A typed binder was worse: `(fn (x:int) …)` was renamed to
`x:int__609`, which kept neither the annotation nor the binding of the body's `x`.

**Decision.**
- The rename runs before the macros in a template expand, so it is told where each form
  binds. It follows the one pattern grammar in `let`/`letrec`/`fn` binders and in clause
  patterns: a symbol binds; a pin's expression, a dynamic `bytes` size and an `:or` default
  are references; a quoted symbol, a literal and a `record` name are neither; a name
  repeated in one pattern (an equality constraint, `or`'s alternatives) keeps one
  replacement.
- The standard library's binding macros are described by shape in the hygiene pass:
  binding pairs (with keyword modifiers, and `if-let`/`if-some`'s else branch outside the
  binding), pattern clauses (`match`, `match*`, `receive` with its `after`), `catch`,
  `as->`, and the params of `defn`, `defmethod` and `impl`.
- A typed binder renames its name and keeps its annotation: `x__12:int`.
- The resolver reads the same shape table (`hygiene::shaped_binders`). It qualifies a
  template's free names when the macro is defined, before these macros expand, so without
  the table it qualified their binders under a runtime `eval` (`a` → `my-module/a`). A
  qualified name is never renamed, so those binders escaped hygiene and their arglists read
  `(my-module/a)`.
- A renamed binder is shown as written. Every place a parameter list reaches a person — an
  arglist, `reflect/arglists`, the runtime arity error, the checker's arity warning — reads
  it through `ClosureArm::source_params`, which shows a gensym by its prefix
  (`value::source_symbol`). A template `defn`'s params are renamed like any other binder;
  before this, `map`'s doc read `(map coll__60 f)` (bedit's doc pane caught it).
- No user-facing way to declare a macro's binding shape. Every knob is a tax on every macro
  author (ADR-011); a user's own binding macro used in a template stays literal, with
  `#`/`gensym` as before.
- `{:keys [a]}` stays literal: its names are the keys looked up, and the grammar has no
  spelling of "key `:a`, bound as something else" that keeps `:keys`' never-fails meaning.
- A computed binder (`(fn ~params …)`) stays literal: the macro builds those names, so it
  names them.

**Consequences.** Any template containing a binding form now takes the runtime expansion
path (fresh names per expansion), not only one with a plain-symbol binder. A macro that
relied on a literal binder in one of these sites being visible to the caller's code was
relying on the capture; it must say so with `~'name`. The shape table names standard
macros in the kernel — a rename of one of them must update it. Tests:
`tests/hygiene_test.blsp` ("hygiene at every binding site", across processes).

## ADR-501 — Every error is a map; `catch` takes a pattern

**Status:** implemented (2026-10-28).

**Context.** A `catch` handler saw four shapes. A built-in error was a
`{:kind :message :code :file :line :col :trace}` map; `error` and `assert` raised a plain
string; a failed `match`, refutable `let` or pattern `fn` raised the vector
`[:match-error ctx value patterns]`, which also printed as that vector when uncaught; and
`throw` raised its argument as it was. `error-message` hid the difference, but anything
that branched had to know all four, and `catch` could not choose: one bare binder, and
handlers rethrew by hand.

**Decision.**
- **Every error the language raises is an error map**, `{:kind :message …}`, with a code,
  position and trace: `error` raises kind `:error` (`E0090`), `assert` kind `:assert`
  (`E0091`), and a pattern nothing matched kind `:match` (`E0092`) with `:context`,
  `:value` and `:patterns`. One primitive, `%raise`, raises a Brood-built error map with a
  code the language owns; the catch site enriches it as it already did for a contract
  violation (`LispError::caught_value`). Uncaught, these render as `error: <message>`.
- **`throw` raises any value as it is** — a keyword for a non-local exit, a program's own
  error written as a map with `:kind` and `:message`. Wrapping thrown values was rejected:
  `(throw :found)` would have to be read back as `(:value e)`, and a program's own error map
  would nest.
- **`catch` takes a pattern** from the one pattern grammar, with an optional `:when` guard,
  and a `try` may have several after its body. The first that matches runs; when none does,
  the error is raised again from where it was first raised. `(catch e …)` is a pattern that
  matches anything, so every existing handler keeps its meaning. A guard-only form was
  rejected as a second way to test a shape the language already tests with patterns.
- The no-match branch lowers to `(%raise (%match-error 'ctx target 'patterns))`. The
  checker's exhaustiveness lint, `:total` check, parameter domains and clause recovery find
  it through one recogniser (`guards::match_failure_parts`), with the arguments where the
  vector's elements were.

**Consequences.** Code that read a caught `error` as a string, or matched
`[:match-error …]`, changed — `error-message` reads every shape. A `catch` clause list that
ends in a catch-all compiles without a rethrow; one that does not rethrows what nothing
matched. Tests: `tests/try_catch_test.blsp`, `tests/pattern_matching_test.blsp`, the
checker's exhaustiveness and inference tests.

## ADR-502 — A fold calls a closure reducer from Brood, so a `receive` in it parks

**Status:** implemented (2026-10-28). Amends ADR-494 §4 and ADR-403. Amended by ADR-505: a builtin hands its kernel dispatch back to the engine, so most of "What still blocks" below now parks.

**Context.** ADR-494 left one path where a `receive` in an interrupt window blocks its worker
instead of parking: a window opened inside a builtin's callback, which runs under the
builtin's Rust frame that no engine can capture. It is wider than windows: any `receive` in a
callback blocks, and in a `ui-run` turn the window is OUTSIDE, so a synchronous call (a
`buffer-query`, a `gen-call`) in a `map` or `fold` callback of `update` blocks too. ADR-494
judged the fix to be resumable builtins — every higher-order native rewritten as a frame kind.

So which higher-order builtins are there? Taken one by one, almost none. `map`, `filter`,
`reduce`, `mapv`, `each`, `sort-by` (`%merge-sort`), `every?`, `any?` and the rest are Brood,
and all of them that walk a collection walk it through `fold`. `fold` over a list is Brood
(`%fold-loop`). Only `fold` over a VECTOR or a RANGE called into Rust: `%vector-fold-span` and
`%range-fold-span` (ADR-403), each calling the reducer per element from a native loop. The
other natives that call Brood are once-per-call (`%try` and `%binding`, already frames on both
capturing engines; `isolate`; contract wrapping) or a kernel dispatch from inside a builtin (a
record's `num/add` under `+`, `compare-to` under `<`, `->seq` under `first`, the `apply`
builtin taken as a value, a `*err*` port's warning write).

**Decision.** A span folds only a reducer it INLINES — `+` and `*` (`reduce_prim_op`), whose
step runs no Brood. Any other reducer is declined before an element is folded: the span
answers `:%fold-walk`, and `fold` walks the collection in Brood (`%vector-fold-walk`,
`%range-fold-walk`, self-tail loops beside `%fold-loop`), calling the reducer from the
process's own engine, where a `receive` in it parks — on the VM, on the tier-0 machine, and
through a window it opens (ADR-491's region or ADR-494's frame). The walk yields at its back
edge like any loop, so ADR-403's between-element stop now matters only to an inlined
reducer's fallback (a bignum, a record's `Num` method). The span's higher-order fast path
(`hof_resolve` per span) is gone from it; the mailbox matcher still uses it.

Option (b), a continuation frame for the span's loop state in the bytecode driver and the
tier-0 machine, was not needed: once only `fold` was left, a Brood loop IS that frame, on
both engines, with nothing new in either. Option (c), bounding the dirty handoff, would bound
the cost of blocking without parking anything.

**Native code.** A walk the JIT has compiled is native; a `receive` under a native activation
still cannot be captured, so the FIRST one blocks, and the suspend-host latch (ADR-410) takes
the walk arm off native code; every later one parks. That is what `%fold-loop` over a list has
always done. After that latch the walk runs on the VM, calling its reducer (native or not)
through the VM's own call path.

**What it costs — reasoned, not measured.** Nothing for `(fold v 0 +)` and the other inlined
reducers: same span. A closure reducer over a vector or range now costs a VM or native
self-tail loop per element where it cost a Rust loop calling the reducer's arm through the
higher-order fast frame: per element, a bounds compare, `%vector-ref` and a closure call,
against a native-entry gateway per call. ADR-360 §7 records the gateway as what the counted
loop rewrite removes. The shared walk is one call site for every reducer, so its call is
megamorphic, and once a callback anywhere has parked under it, it is interpreted. To check on
the benchmark machine: `nqueens`, `pipeline`, `json`, `reduce` (`make ab`).

**What still blocks.** Brood a builtin calls back into under its own frame: a record's
`Num`/`Ord` method under `+`/`<` (and a record reducer under an inlined `+`), `->seq` /
`->count` reached from `first`/`rest`, `apply` taken as a value by a native, a contract
wrap, `isolate`'s thunk, a `*err*` port. These are kernel dispatches, not iteration; the
§7.4 handoff serves them as before, and an interrupt reaches the waiter once it runs. Also
the first park under a native walk (above), a closure with no VM arm above tier 0, and an
alias of `proc/interruptible` (ADR-494 §3).

**Tests.** `crates/lisp/tests/interrupt_one_worker.rs` (one worker, `proc/info` barriers),
at the default tier and `BROOD_TIER=0`: a window opened in a `reduce` callback over a vector
(ADR-494's blocking case), a `fold` over a range, `map` and `mapv` callbacks, a `ui-run`-shaped
turn (the window outside, the `receive` in a `map` callback), and a window in a callback in a
window — each waits, lets the next process run, answers, takes a ceiling that passed and a
`proc/interrupt` once running, and leaves the dirty-receive count flat. A walk the JIT has
compiled blocks at most once in a program of three waits. What still blocks is pinned by a
window opened in a record's `num/add` under `+`: the count rises.

ADR-493's capture pass gets its test too: `regex_native`'s
`the_group_pass_over_a_match_longer_than_a_window_stops_inside` finds a 100 000-character
match with its groups, then hands the group pass (`groups_polled`, split out of
`search_captures_polled`) a poll that finds an interrupt due — `InterruptPoll::raising`, a
`cfg(test)` constructor — and the Pike VM stops at its first probe. End to end, a pending
interrupt stops the search first, so the pass could not be reached otherwise. Sabotaged red:
the group pass given a fresh poll.

## ADR-503 — Quasiquote has levels

**Status:** implemented (2026-10-28). Replaces item 4 of ADR-152.

**Context.** ADR-152 made a template inside a template an error: levels were not tracked,
so an inner `~x` was filled by the outer template. That kept the door open — every template
it accepted keeps its meaning under level tracking — at a price: a macro whose expansion
defines a macro had to build the inner template with `list`/`quote`, or move it into a
public function the generated macro could call. Nothing in std or downstream needed it yet;
the rule is what a reader of any macro-writing example expects, and the error met them on
the first try.

**Decision.**
- **Levels.** The template being built is level 1; each `` ` `` raises the level, each
  `~`/`~@` lowers it. A hole that reaches 0 is filled; anything deeper is rebuilt as
  written, markers included. So `~~x` fills `x` at the outer level and leaves the inner
  `~`, `~'~x` makes the outer value a constant of the inner template, and `~@~xs` /
  `~~@xs` splice at the levels they name.
- **Names resolve where the macro was written, at every level.** The resolver qualifies
  the inner template's free names when the outer macro is defined, so the macro it
  generates calls the defining module's `helper`, not one the user's module defines. A
  hole lowers the level by one instead of returning to code; a quote inside a template
  still resolves its holes (`'~(helper x)` was left unqualified before this, at any level).
- **Binders belong to the template that runs them.** The hygiene pass renames only the
  outermost template's binders. An inner template's binders are renamed each time the
  macro it builds expands — renamed once, every use of the generated macro would share
  them. A hole back to level 1 inside the inner template is the outer template's code and
  takes its renames: in `` `(let (x 1) `(f ~x)) `` the inner `~x` reads the `let`'s `x`.
- **`x#` belongs to the template that directly holds it**: replaced at level 1 only, so
  `` `(a `(b c#)) `` leaves `c#` for the inner template and `` `(a `(b ~c#)) `` takes the
  outer gensym.
- **A nested template takes the runtime expansion path**, like a template with a binder:
  its holes back to level 1 may bind.
- The root escapes ADR-423 writes into a macro's templates are written at every level: a root
  call head in the inner template comes out `/name`, so the generated macro cannot be
  captured by a module that defines the name. As data, `(/list 7)` is not `(list 7)`.

**Consequences.** Macro-writing macros are written as templates. The `~'~x` and `~~x`
spellings take two moments of expansion to read; the docs show them on a working example
(`def-tagged`). The checker already walked templates by level, so it needed no change.
Tests: `tests/nested_quasiquote_test.blsp` (levels, splices, three levels, `x#`, generated
macros and their hygiene, the defining module's names, across processes).

## ADR-504 — `tcp-send` waits on its peer: outbound backpressure

**Status:** implemented (2026-10-28). Amends ADR-143's "`tcp-send` is asynchronous".

**Context.** ADR-143 made `tcp-send` queue its bytes to the reactor and return, bounding a
stuck reader with a 16 MiB per-socket cap past which the connection is dropped. Nothing
slowed the producer. A server streaming a response (`stream-resp`, a release file, an
archive made while it is sent) therefore made the whole of it as fast as it could read its
sources, whatever the client's pace: the queue held all of it, up to 16 MiB a connection,
and a response larger than that was cut off for any client slower than the server, which on
the internet is every client. The mur forge met it with a 21 MB archive of Brood's own
trunk. `tcp/send`'s doc said "blocking" all along. Inbound had flow control since the
`InboundFlow` work; outbound had none.

**Decision.**
- **A send waits past a high-water mark.** Each stream has an `OutboundFlow`: the bytes
  handed to `tcp-send` and not yet written to the kernel (for TLS, the plaintext not yet
  fully flushed as records). `%tcp-send` charges it, queues, and returns whether the caller
  must wait: true once the queue is at 1 MiB or more. `tcp/send` then waits for
  `[:tcp-drained sock]`, parked like any `receive` (no worker held). A producer runs at its
  peer's pace and holds about a megabyte, not what it sends. Overshoot is one `tcp-send`.
- **Exactly one wake per wait, by the first of two events.** The reactor sends
  `[:tcp-drained sock]` when the queue falls below 256 KiB, or when the connection is gone
  by any route: the reactor holds the flow in a `SendGuard` whose drop closes it (a write
  failure, the cap, a stall, an idle or linger deadline, owner death, the reactor's own
  death unwinding); a send for a connection already gone closes it at once; the reactor's
  death hook closes every registered socket's flow. A closed flow parks no one again. The
  park decision and the wakes are taken under one lock, so a release cannot slip between a
  sender's check and its parking. Waiters are whichever processes sent, not the owner: a
  helper writing to a socket another process owns parks itself, and the owner's mailbox
  never sees `[:tcp-drained]`.
- **A stall bound ends a wait on a peer that stopped reading.** With sends waiting, a peer
  that never reads would park its sender forever; the cap used to end that. Output that
  makes no progress for 60 s now drops the connection, as an idle reap does (`[:tcp-closed]`,
  or `[:tcp-error]` for a one-shot TLS client), which wakes the sender.
  `tcp/set-stall-timeout` changes it per socket, and 0 disarms it. Only a peer whose kernel
  buffers are full can stall, so an idle stream (SSE, long-poll) is never touched; that is
  why it is on by default where the idle timeout is not.
- **The cap stays, as the backstop** for a single `tcp-send` larger than 16 MiB.

**Consequences.** A process that sends a lot and reads only afterwards, to a peer doing the
same, now waits where it used to buffer: two such ends deadlock until the stall bound drops
the connection. A request-response protocol never does this (each side reads before it
answers), and buffering instead was only ever deadlock deferred to 16 MiB. A test that
queued a large payload to a peer not yet reading and then went on (the backpressure and
lingering-close tests) sends it from a writer of its own. `tcp/close` still flushes for
the 5 s linger; a writer parked on the socket wakes once that flush has drained it or given up.

**Guard.** `tests/tcp_send_backpressure_test.blsp`: a writer to a peer reading nothing
parks well short of the 32 MiB it is given and every byte arrives once the peer reads (red
before: the writer queued all of it and the cap dropped the connection); a writer parked on
a peer that closes, and one on a peer that stalls past a 500 ms bound, are woken; a small
reply to a peer not reading never stalls; a listener has no stall timeout.

## ADR-505 — A builtin hands its Brood call back to the engine that called it

**Status:** implemented (2026-10-28). Amends ADR-502's "What still blocks" and ADR-494 §3.

**Context.** After ADR-502 the Brood a builtin still ran from Rust, under its own frame, was a
kernel dispatch: a record's `num/add` under `+` (and `num/sub`, `num/mul`, `num/div`), its
`compare-to` under `<`/`<=` (and through them `>`/`>=`), its `->seq` under
`first`/`rest`/`empty?`, its `->count` under `empty?`. Each was one `apply_engine` call nested
under the builtin, so a `receive` in the method blocked the worker. One more ran nested
without a builtin choosing to: `count`, `first` and friends on a map are `PrimOp1`s whose
fallback ran a closure head (the prelude's `count`) with `dispatch(…, false)` and then
`force`, a nested driver. And a wrapper over `proc/interruptible` bound under another name
was a passthrough the VM elided to the builtin, which ran its thunk nested (ADR-494 §3).

What these share is that the builtin's whole result IS the Brood call's result, or is one
small step from it. So the builtin need not make the call at all.

**Decision.**
- **A redirect.** A builtin whose slow path would call Brood returns
  `Control::Redirect` instead, with the call it would have made waiting in
  `Heap::take_redirect`. The engine that called it makes that call in its place, as an
  ordinary call: `dispatch` loops on it (so with `tail` a VM closure comes back un-run as
  `Step::Tail` and its caller pushes the frame), and the tier-0 machine continues its
  dispatch loop on it (a closure's body becomes the frame's). A `receive` in the method then
  parks, on both engines.
- **Only when offered.** A builtin is called from many places, most of which cannot take a
  redirect: another builtin calling it from Rust (`add_values` for `table/add`, the JIT's
  fallbacks, `extremum` for `math/max`). So an engine that can take one OFFERS it for the
  call it is making — `Heap::offer_redirect` records the address of the argument slice it
  hands the builtin, `call_native_redirectable` — and the builtin takes the offer only if
  its own `args` is that slice (`Heap::redirect_offered`). A builtin another builtin called
  has a slice of its own, sees no offer, and makes its nested call as before. No other code
  ever sees the signal. The offer costs a store before and after a native call through
  `dispatch` and the tier-0 machine; the inlined arithmetic and comparisons never reach one.
  Not measured: this desktop runs no benchmarks. On the benchmark machine, `make ab` with a
  native-call-heavy row beside ADR-502's (`nqueens pipeline json reduce`).
- **Where the result needs a step, a prelude shim.** `num/add` & co. ARE the result, so `+`
  hands back the multimethod itself. `<` needs the sign of `compare-to`, and `first` the head
  of `->seq`: the builtin hands back `%ord-lt` / `%ord-le` / `%record-first` /
  `%record-rest` / `%record-empty?`, which do that step in Brood. A shim the prelude has not
  defined yet (during boot) is no offer taken; the builtin compares or asks here, as before.
- **A map operand takes the call path in the bytecode.** `Prim1` / `Prim2` fallbacks with a
  map operand — every record is one — dispatch with `tail` and turn a `Step::Tail` into the
  frame push a non-tail `Call` makes (`prim2_dispatch_step`); `first`/`rest`/`empty?`'s direct
  builtin call is skipped for a map so the redirect can happen. Every other operand keeps the
  nested path it had, so the change is confined to records and plain maps.
- **`proc/interruptible` under any name is never a passthrough target.** The shared
  `passthrough_redirect_ok` refuses a native marked `is_interruptible`, so a wrapper over an
  alias is entered and its call is the VM's region (ADR-491). The tier-0 machine already
  framed it by the native's own name.

**What still blocks.** `isolate`'s thunk: making it a frame means the global snapshot and
restore, the isolate stamp and the reap running on return, on unwind and across a park and a
migration, on both engines — far more than a redirect, for a builtin only the test runner's
`:isolated` tests use. The §7.4 handoff serves it. A contract wrap, macro expansion, the module
loader and a `*err*` port's write are left as they were (none is on a running program's
update path). A builtin's callback reached from native JIT code: the JIT's fallbacks offer no
redirect and call nested, so the first `receive` blocks and the suspend-host latch takes the
arm off native code (ADR-410), as for ADR-502's walk; a JIT arm's staged tail call goes through
`dispatch`, which takes a redirect as a tail call. The JIT's fence still names
`proc/interruptible` by symbol, so an alias called from a hot JIT-compiled arm runs its thunk
nested. `apply` taken as a value never blocked from Brood: every engine unfolds it where it is
called. A builtin calling `apply` from Rust is a builtin calling Brood, the case above.

**Tests.** `crates/lisp/tests/interrupt_one_worker.rs`, default tier and `BROOD_TIER=0`:
ADR-502's pinned case — a window opened in a record's `num/add` under `+`, whose dirty-receive
count rose — now stays flat, as do a window in `num/sub` under `-` through a function's
locals, in `compare-to` under `<`, in `->seq` under `first`, in `->count` under `count` and
under `empty?`, through `apply` taken as a value, and through a wrapper over an alias of
`proc/interruptible`. Sabotaged red, per case: with `redirect_offered` always false, `+`, `-`,
`<`, `first` and `empty?` block at both tiers (3 blocks each); with the map operand's frame
push and the gate's refusal taken out, `first`, `count`, `empty?` and the alias block at the
default tier (tier 0 already framed `count` and the alias). Record arithmetic, ordering and
sequences answer as before at both tiers (`record_test`, `ability_test`, `counted_test`,
`multimethod_test`, `sorted_test`, `queue_test` and ten more files).

## ADR-506 — The bare namespace is the language: syntax, a measured core, and nothing else

**Status:** accepted (2026-10-28); moves landing family by family (ROADMAP B4).

**Context.** 302 names were bare. ADR-227's rule ("core stays bare, derived helpers move")
was overridden name by name by a second constraint — anything the prelude needed while
booting had to be bare, because the prelude cannot `require` — so `mapv` was bare and
`filterv` was not, `inc` bare and `even?` not. The boot constraint was never real: the
prelude can define a qualified name itself (`seq/lmap`, `string/->symbol` already are), so
where a function is defined says nothing about what it is called. A usage count over the 37
Brood projects beside this repo (comment lines skipped) showed the shape: 39 names in 25+
projects, 155 in fewer than 5 — 75 of the 77 dynamics among them.

**Decision.** A name is bare only when it is one of:
1. **Syntax** — every special form, and every macro that defines, binds or branches: the
   `def…` family, `impl`, `sig`, `fn`, `let`, `if`/`when`/`unless`/`cond`/`case`/`match`,
   the `if-let`/`when-let` family, `for`/`doseq`/`dotimes`/`fold-for`, the threading forms,
   `try`/`throw`, `receive`, `spawn`, `binding`, `with`, `comment`, `assert`, `include-str`.
2. **A measured core** — a function used in at least 15 of the projects counted, and the
   partner of a pair whose other half is core (`any?` with `every?`, `dec` with `inc`,
   `vals` with `keys`, `unlink` with `link`, `failure?` with `failure`).
3. **The built-in kinds** — the predicates and coercions of the language's own value kinds
   (`int?`, `keyword?`, `bytes?`, `record?`, `table?`, `->string`, `keyword`, `symbol`, …).
   A library type's predicate is its module's: `queue/queue?` (`queue?` again under
   `(:use queue)`). This reverses ADR-236's "every type predicate is bare" for library types.
4. **Operators**, `not=` among them.

Everything else is qualified by its family. Boot is not a reason: a function the prelude
needs is defined there under its qualified name.

| Module | Names moving |
|---|---|
| `combinator/` (new) | `complement` `constantly` `juxt` `fnil` `memoize` — `identity`, `partial` and `comp` stay bare: the language's own vocabulary, passed as values far more than a project count shows |
| `list/` (new) | the twelve `caar` … `cdddr` |
| `seq/` | `but-last` `drop-while` `take-while` `mapv` `partition` `repeat` `sort-by` — `seq` (a coercion, like `->string`) and `third` (with `first`, `second`) stay bare |
| `set/` | `disj` |
| `map/` | `assoc-in` `dissoc-in` `get-in` `update-in` — `hash-map` stays bare: the constructor of a built-in kind, and what the quasiquote expander emits for a map template |

## ADR-507 — The callback is last, and only its own arguments follow it

**Status:** accepted (2026-10-29); ROADMAP B5.

**Context.** ADR-308 put the collection first and the callback last, and named one deliberate
exception (a reducer's own parameters stay `(fn (acc x))`). It did not say what may follow a
callback, or what the "subject" is when the call is about a function. The language design
pass listed three suspected exceptions: `map/merge-with` takes the function first, `condp`
takes the predicate first, and a transducer `comp` reads left to right while plain `comp`
reads right to left. An audit of every public `defn` and `defmacro` in `std/` (parameter
lists with a function-named parameter that is not last) found these, and more:

| name | shape | why |
|---|---|---|
| `map/merge-with` | `(f & maps)` | variadic maps pushed the function forward |
| `condp` | `(pred expr & clauses)` | the predicate before the subject, unlike `case` and `match` (ADR-379 already made the predicate's call value-first) |
| `seq/transduce` | `(coll xform rf init)` | the seed after the reducer, where `reduce` and `fold` put it before |
| `seq/iterate-times` | `(f x n)` | function first, beside `seq/iterate`'s `(x f)` |
| `seq/times` | `(n f x)` | function in the middle |
| `stream/fn->` | `(f init)` | function first, beside `seq/iterate`'s `(x f)` |
| `editor/buffer/buffer-edit`, `buffer-edit-reply` | `(bp f &optional origin)` | an optional tag after the callback |
| `editor/buffer/buffer-edit-value` | `(bp f &optional origin (timeout 5000))` | two optional slots after the callback |
| `update`, `map/update-in`, `proc/offload`, `partial` | `(… f & args)` | the arguments after `f` are `f`'s |
| `combinator/fnil`, `combinator/complement`, `partial`, `gen/start`, `log/fn-backend`, `dev/jit-state`, `dev/why-not-native` | `(f …)` | the function is what the call transforms or runs |

None of the rows to reshape is the checker's: no curated signature, result inference or
callback synthesis reads their positions (ADR-308's silent-degradation trap does not apply).

**Decision.** One rule: **the subject comes first, a callback comes last, and only the
callback's own arguments may follow it.** The subject is what the call is about: a
collection, a map, a process, a seed. When the call transforms or runs a function, that
function is the subject (`(combinator/fnil f 0)`, `(gen/start server state)`), and it comes
first like any other subject.

Reshaped, every caller in the tree moving in the same change:
- `(map/merge-with maps f)` — the maps are one collection, so `(-> maps (map/merge-with +))`
  threads and a two-map merge is `(map/merge-with [a b] +)`. `nil` entries are still skipped.
- `(condp expr pred t1 r1 … [default])` — the subject first, as in `case` and `match`, and each
  clause reads in the order its test runs: `(condp line string/starts-with? "#" :heading …)`
  tests `(string/starts-with? line "#")`. The predicate's call stays value-first (ADR-379).
- `(seq/transduce coll xform init rf)` — `reduce`'s `(coll init f)` with the transducer added.
- `(seq/iterate-times x n f)` and `(seq/times x n f)` — the seed, how many times, then the step,
  as `seq/iterate`'s `(x f)`.
- `(stream/fn-> init f)` — the seed, then the generator.
- `buffer-edit` and `buffer-edit-reply` take two arities, `(bp f)` and `(bp origin f)`, as
  `reduce` has `(coll f)` and `(coll init f)`: the optional slot moves before the callback,
  and no name is added. `buffer-edit-value` adds a third, `(bp origin timeout f)`.

Kept, under the rule as written:
- **A function's own arguments.** `(update m k f & args)` calls `(f old & args)`;
  `update-in`, `proc/offload` and `partial` do the same. The arguments are the callback's,
  not the call's, and putting them first would separate them from the function they feed.
- **A function as the subject.** `fnil`, `complement`, `partial`, `gen/start`,
  `log/fn-backend` and the `dev/` probes take the function they transform or run first.
- **Transducer `comp`.** There is one `comp`, and it composes right to left. A transducer is a
  function from a reducing function to a reducing function, so in `(comp (seq/xfilter odd?)
  (seq/xmap inc))` the filter is the outermost wrapper and sees each item first: items flow
  through the stages in the order they are written *because* composition runs right to left.
  Nothing to reshape; language.md says it where transducers are taught.
- **The reducer's parameters** stay `(fn (acc x))` (ADR-308).

**How a stale caller fails.** ADR-308's test: a reorder should fail loudly. Every reshape
here does, at once or under the checker: the old `merge-with`, `transduce` and `times` calls put
a function where a number or a collection belongs, and the old `condp` puts the predicate
where the subject was, so the first clause calls a value. One reorder can fail silently: an
old `(seq/iterate-times inc 0 4)` read as `(x n f)` has `n` = 0, never calls `f`, and answers
`(inc)`. Its `f` (and `times`', `stream/fn->`'s and `merge-with`'s) is therefore annotated
`f:fn`, and the `buffer-edit` family declares `(sig … (and (any fn -> any) (any any fn -> any)))`,
so the checker rejects a non-function in that slot and an armed contract raises at the call.
An old `(buffer-edit bp f me)` would otherwise send the pid as the transform, and the buffer
process would fail calling it.

**Found on the way.** `iterate-times` called `f` once more than its result shows (fⁿ⁺¹(x),
computed and dropped), so `(iterate-times x 0 f)` called `f`: it now runs `f` exactly `n`
times. And a *documented* multi-clause `defn` with a typed parameter — `(defn f "doc" ((x:int)
…) ((x y) …))` — bound a variable literally named `x:int`: the refusal ADR-420 promises read
`(fn "doc" clause…)` as single-clause. It now peels the docstring as the `fn` lowering does,
and refuses.

**Rejected.** A variadic `merge-with` with the function last (`(merge-with a b & more+f)`):
the function would have to be found by position from the end, which no other function does.
A second name for the tagged `buffer-edit`: arities already say it, as for `reduce`.

**Consequences.** A library author has one rule to apply and one to look up (the subject,
when it is a function). `docs/language.md` states it beside the threading macros, where
argument order is taught. The stale "Brood has no `condp`" hint in the evaluator's
foreign-name table is gone: `condp` has existed since ADR-379.

## ADR-508 — A background at the grid's edge continues to the window's, and LCD text is filtered

**Status:** accepted (2026-10-30).

**Context.** Side by side with Emacs on the same panel, font and size (Hack 16 px, subpixel,
scale 1), a GUI window looked softer and unfinished in two ways. First, the cell grid rarely
fills the window: the inset sits on every edge and the sub-cell remainder (up to a cell less a
pixel) lands on the right and bottom, and both were painted with the window background. Every
full-width band (a mode line, a current-line highlight, a gutter) stopped a few pixels short of
the frame. Emacs paints its mode line and fringes through the same leftover pixels. Second,
subpixel text went through swash's `Format::Subpixel`, which is zeno drawing the glyph three
times at whole-pixel resolution, shifted ±0.3 px, one copy per channel: no 3× raster and no LCD
filter. A stem edge that covers one stripe of a pixel lit that stripe alone, a saturated orange
or blue fringe, where FreeType (under Cairo, under Emacs) spreads it over five stripes.

**Decision.** *Edge bleed:* an opaque, square background op (`Rect`, or `FRect` at full
opacity) that touches an edge of the grid gains `FRect`s covering the margin beside it, inserted
right after it. This is a frame rewrite (`host/gui/backend/bleed.rs`), run once per frame and
window geometry before either painter sees the frame, so the CPU and GPU painters, the CPU's
strip damage and the GPU's fragment cache treat the margin as frame content without knowing
about it. Text backgrounds do not bleed (a run's width is the shaper's), nor rounded or
translucent fills (a pill is not a band). Inside a `ScrollRegion` only the sides bleed, since
its rows move; a `CellRegion` paints at its own metrics and is left alone. A `Fragment`
(ADR-336, how bedit draws its mode line and gutter rows) is bled inside, and its bled ops are
kept by the fragment's address across frames, so an unchanged fragment stays one allocation
and the GPU fragment cache, which matches by address, keeps hitting. No setting: a
background that stops short of the frame for want of a few pixels is never what an app drew.

*LCD text:* the outline is rasterised as an alpha mask at 3× horizontal resolution, filtered
with FreeType's default LCD weights (`[8 77 86 77 8]`/256, which keep a solid run solid), and
each channel takes its own stripe (`lcd_filter`). Both painters bake glyphs through the same
function.

**Consequences.** `gui/inset` becomes padding in the edge bands' colours rather than a blank
frame. An app that wants a band to stop short of the edge leaves a cell free. A subpixel glyph
carries the same ink as its gray twin (a test holds the ratio), with lighter, near-neutral
edges. Hinting is unchanged: swash still hints the outline before the 3× stretch.

**Addendum (2026-11-02): a line bleeds sideways only.** A band one row tall is a line of text
(a header line, a mode line, a highlighted row), and carried up or down into the margin it stood
off-centre around its text: bedit's header line on the top row read as a strip a quarter-row
taller above its text than below. Such a band now gains its side pieces only; a taller band (a
gutter, a pane's background) still bleeds every way it touches. Emacs paints its header line
inside the frame's internal border the same way.

**Addendum (2026-11-02): the vertical remainder is split.** The margin under the grid was the
inset plus the whole vertical remainder (up to a row less a pixel), which under bedit's echo
area read as a band of empty window up to a row and a half tall. `grid_origin` now puts half of
the remainder above row 0 and half below the last row, so neither margin exceeds the inset plus
half a row. This gives up row 0 staying put across font sizes (1518e4b0 anchored the grid at the
top for that): a zoom step can move it by up to half a row, as it moves every other row. The
horizontal remainder stays on the right. Guard:
`the_vertical_remainder_is_split_above_and_below_at_every_size`.

**Addendum (2026-11-02): a line on an edge row bleeds into the margin after all.** The first
addendum left the top margin as a strip of window between the frame and bedit's header line,
and that strip read as a gap above the filename, which is worse than the header's text sitting
a little low in a taller band. A band one row tall now bleeds every way it touches, as a taller
one does, which is what Ghostty's `window-padding-color = extend` does with every edge row. A
current-line highlight on row 0 takes the margin above it too. Guard:
`a_line_on_the_top_row_fills_the_margin_above_it`.

## ADR-509 — A collection is due on the bytes a process makes, not only on its object count

**Status:** accepted (2026-10-30); KI-307.

**Context.** The collector's trigger counted objects: a minor collection was due when the
nursery held `max(floor, 2 × live)` of them (64K for a lone process), a major when the old
generation had grown 4×. An object's size never entered it, but one object can own any
number of bytes. A vector is flat and immutable, so `(conj v x)` copies `v`'s elements into
a fresh buffer: building a 60 000-element vector one `conj` at a time makes 60 000 vectors
owning 43 GB of element arrays between them, at two objects per step. In
`scripts/gc-contention-repro.blsp` a process doing that in a loop reached 12.4 GB resident in
three seconds, and the run then died on a 16 GB address-space cap. That was KI-307: a
neighbour of such a process ran 2.5× slower, all of it in its own CPU time (no waiting on a
worker, no extra collection), because the machine's memory was being churned at gigabytes a
second. Under the system allocator the same background reached 11 GB, so the allocator was
not the cause.

**Decision.** A minor collection is also due once the process has allocated enough **fresh
buffer bytes** since the last minor: spilled vectors (their element buffers), string text,
and byte blobs that no other handle holds. The budget is `max(byte floor, growth × retained
buffer bytes)`, capped at 512 MiB, where the byte floor is 32 MiB for a lone process and
shrinks with the live process count to 1 MiB, exactly as the object floor does. A major is
also due once the old generation's buffer bytes reach `max(64 MiB, 4 × what the last major
kept)`.

- **Fresh bytes, not retained bytes.** The counter resets at every minor. Survivors scale
  the next budget instead; counting them would make one large live young vector due a
  collection at every safepoint.
- **Only the kinds one object cannot bound.** A map node, pair, closure or env frame is
  bounded per object, and the object count already covers it. A rope or a shared blob is a
  reference-counted view onto data that may already exist: bedit makes a new rope on every
  edit of a large buffer, and counting each in full would collect on every few edits.
- **O(1) on the allocation path, O(copied) in the collector.** Allocation adds one number.
  A tenure measures only the entries it appended to the old generation, from a mark taken
  before it, and a major measures the generation it has just copied.
- **No per-process cost.** A parked process is held to a memory floor (`process_floor`), and
  four `usize` fields on the heap broke it by 31 bytes on the first push. The minor budget is
  one `u32` countdown in 16-byte units (64 GiB), which sits in the heap's existing padding;
  the old generation's two figures live in the extras a collection boxes anyway.
- **A pinned floor stays pinned.** `BROOD_GC_FLOOR` and `BROOD_GC_STRESS` fix the object
  trigger for an A/B or a stress run; with either set, the minor byte trigger stands down so
  the pinned floor means what it says.

**Consequences.** Memory for a buffer-heavy loop is bounded by its live data plus the byte
budget, not by its object count. A process that allocates large buffers collects more often
than before; each such minor costs what survives it, so the cost per byte allocated stays
constant. `(conj v x)` is still linear in `v`, so a loop of `conj` onto a vector is still
quadratic in time; it is no longer quadratic in memory. Guards:
`tests/gc_byte_trigger_test.blsp` (a `conj` loop, a `str` loop, and four processes at once;
all three red with the byte half of `gc_due` removed) and the collector test
`an_old_generation_of_dead_large_vectors_is_compacted_on_its_bytes` (144 MB of dead vectors
kept without the major's byte half).

## ADR-510 — A Lisp is coloured a line at a time, from the state the line above ended in

**Status:** accepted (2026-10-30).

**Context.** An editor colours a large Lisp buffer by lexing a window: the visible lines plus a
fixed lead-in above them (200 lines in bedit), restarted at a top-level form start found by
`safe-restart`. `safe-restart` scans its input from the input's own first character, and so
assumes that character is outside any string. The lead-in starts wherever 200 lines up
happens to be. In a file with a docstring longer than one line, some scroll positions put
that start inside the docstring: the docstring's closing `"` reads as an opening one, every
quote after it pairs the wrong way, and the whole window colours as string. Reported in bedit
on wos's `rp2350.blsp`, where the windows starting at two lines in 560 were inverted. Markdown,
org and the config formats had already left windowed lexing for the line-state cache
(ADR-471); the Lisp modes, the oldest, had not.

**Decision.** `editor/highlight/lisp-line-lexer` is `highlight-spans` as a `line-lexer`: a
line starts in the state the line above ended in, which is everything the walk carries, the
form stack (head and docstring position) plus, when the line ends inside a string, that
string's face. A line that starts inside a string colours up to its closing quote in the
carried face and lexes the rest as code. The walk (`hl-walk`) is shared with `highlight-spans`
and returns the stack it ended with. `specials` is the head-symbol set, as for
`highlight-spans`, so every dialect gets it by passing its own.

A line cannot see the line below it, so one decision differs: a string in a docstring
position that ends its line, with the next form or the close on a later line, is a docstring
(more body may follow), where a lex of the whole source sees a lone last body string and
calls it a value. The faces are resolved when the lexer is built, as every line lexer's are;
the cache rebuilds it when a `:syntax/*` face changes.

**Consequences.** Nothing is guessed, so no scroll position inverts the colours. An edit
re-lexes from its line until a line starts in the state it started in before, which for most
edits is the end of the enclosing top-level form, against a 200-line lead-in plus the band on
every keystroke before. `safe-restart` stays for callers that lex a slice. Guards:
`tests/highlight_test.blsp` checks every window of a source with multi-line docstrings, escaped
quotes, a quote in a comment and a regex literal against a whole-source lex (red with the
carried string state ignored); bedit's `modes_test` checks a 250-line docstring above a deep
window (red without the mode's `:line-lexer`).

**Addendum (rainbow brackets).** `lisp-line-lexer` takes an options map; `{:rainbow true}`
colours each bracket by its depth in `:syntax/delimiter-1` … `-9` (Emacs's rainbow-delimiters),
cycling past the ninth. The depth is the form stack the lines already carry, so it is exact
across lines where a windowed lex would have to guess it. The faces are registered empty, so
nothing changes until an app names their colours. Guard: the rainbow test in
`tests/highlight_test.blsp` (red with the spans dropped).

## ADR-511 — A `conj` onto a vector appends in place when it can

**Status:** accepted (2026-10-30).

**Context.** A vector is flat — its elements in one buffer, which is what makes `nth` O(1)
and lets native code read an element with two loads — and immutable, so `(conj v x)` copied
all of `v`. A loop of `conj` was quadratic: building a 60 000-element vector that way copied
43 GB of elements, which is how KI-307's background reached 12 GB before ADR-509 bounded the
memory. ADR-509 left the time quadratic. A persistent trie would make `conj` O(log n) but
`nth` too, and every native element read would become a walk or a deopt.

**Decision.** A vector may share its element buffer with the vectors appended from it. The
buffer (`AppendBuf`) is a `Vec` whose length is how far it is **claimed** — the longest
vector built over it — and whose spare capacity is room for the next. A vector over it
(`VecStore::Shared`) reads its own first `len` elements. `Heap::vector_append`, behind `conj`
and `into` on a vector, writes `x` past the claimed length only when the vector appended to
ends exactly there and the room is there; anything else copies: exactly sized for a first
append, so a one-off `into` wastes nothing, and with room for as many again when the source
was itself an append, so a chain is amortised O(1). Two `conj`s onto one vector cannot both
claim a slot — the second finds it claimed and copies.

No value ever changes. A write lands only past every existing vector's length, once per
slot. What keeps that true:

- **One heap.** The buffer is LOCAL-only: promotion, messages and a `VecStore` clone copy the
  elements out, and the shared regions build their own stores. So one thread touches it.
- **Copy-on-write for every other write.** `VecStore::as_mut_slice` gives a vector a buffer
  of its own first unless it already holds it alone, so a builder, or the collector
  rewriting relocated handles, never writes into a buffer another vector reads.
- **The collector.** The last vector over a buffer takes it and rewrites its elements in
  place, cut to its length; while others hold it, a vector copies its elements out — into a
  buffer as roomy as the old one for the newest vector over it, the one a `conj` loop is
  building, or the garbage versions behind it in the nursery would cost it its room at every
  collection. An old buffer can hold a young element past the old vector's length, which
  only the young vector reads; the generational invariant concerns what a value can reach,
  and the old vector cannot reach that slot.
- **The JIT.** `Shared` keeps `ptr` and `len` where `Spill` has them, so the native element
  read serves both, with the tag order pinned by a `const` assertion.

**Consequences.** A `conj` loop is linear: 200 000 `conj`s run in a fraction of a second where
the copy each step would move about 480 GB. CLAUDE.md's immutability rule names the append
buffer, so it is not mistaken for the mutable buffer the rule forbids — and so its two
properties are kept. Guards: the heap tests `an_append_writes_in_place_only_past_the_newest_vector`,
`a_collection_keeps_every_vector_over_a_shared_buffer`,
`a_write_never_reaches_another_vector_over_the_same_buffer`,
`the_vector_a_loop_is_building_keeps_its_room_across_a_collection` and
`a_buffer_the_collector_holds_alone_is_cut_back_to_its_vector`, each red with its guard
removed, and `tests/vector_append_test.blsp` (every version read back, the native path, and
vectors built by `conj` across processes).

## ADR-512 — Every parameter list is a list; a vector is data

**Status:** accepted (2026-10-30); ROADMAP B6.

**Context.** "Lists for code, vectors for data" (ADR-010) had four apparent exceptions:
ability op specs `(area [self] :-> float)`, `impl` methods `(area [c] …)`, `defmethod`'s
`[money money]` dispatch tuple and `{:keys [a b]}`. ADR-149 had made a vector parameter list
an error in `defn` and `fn`, because a vector in a parameter position already means
something — it destructures — so a second meaning read Clojure-shaped code as a different
program. The ability forms kept the vector, and so did `defbehaviour`'s op specs. The two
dispatch forms even disagreed with each other: `defmethod` took its parameters as a list.

**Decision.** Sort the four by what the vector *is*.

- **Parameter lists take a list, everywhere.** An op spec is `(area (self) :-> float)`, an
  `impl` method `(area (c) body…)`, a `defbehaviour` op `(mount (params))` — the spelling of
  `defn`, `fn` and `defmethod`. A vector there is an error whose hint is the list it should
  be: `impl Shape: method \`area\` takes its parameters as a list, as defn does — write
  (area (c) …), not [c]`. No alias: the old spelling is refused, not accepted twice.
- **A vector that is data stays a vector.** `defmethod`'s `[money money]` is a tuple of
  dispatch ids matched against the arguments' identities, not parameters (those follow it as
  a list). `{:keys [a b]}` names the keys a map pattern binds. `:sealed [circle rect]` and
  `:requires [Eq]` are member lists.

`defability` now finds its op specs by position — past the docstring, every keyword takes the
form after it as its value — because "a list whose second element is a vector" no longer
marks one, and a `:derive-record` recipe `(fn (fields) …)` is a list too. The checker reads
parameter lists only as lists, so a typed parameter `(scale (self (factor float)))` is still
checked at every call; the one reader that still took only a vector (`spec_param_types`)
would otherwise have stopped checking typed op parameters silently.

**Consequences.** The rule is one sentence: a parameter list is a list; a vector is data.
Every first-party use moved: about 550 parameter lists in `std/`, `tests/`, `docs/`, the Rust test
fixtures and the LSP's method skeleton (`(op (self …) body)`), by a tool that changes only
those brackets, wherever the form is written — code, docstrings, comments, Markdown, Rust
string literals. Downstream projects move the same way; an unmigrated one fails at load with
the hint. Guards: `robustness_limits_test` (a vector op spec is refused with the list
spelling), `ability_test` (typed op parameters still checked), `behaviour_test`, and the LSP
completion tests.

## ADR-513 — An underline can have its own colour and a wave

**Status:** accepted (2026-10-30).

**Context.** A face's `:underline` was a flag: a rule in the text's own colour. bedit's spell
checker (Emacs's jinx) and its diagnostics want what Emacs draws, a red wavy line under a word
that keeps its own colour. With only the flag, the spell checker had to turn the word itself
red, which reads as syntax, not as a mark about the word.

**Decision.** `:underline` takes a flag as before, a colour (`"#ff5f59"`, `:red`, `[r g b]`),
or `{:color c :style :wave}`. `gui::Face` carries `underline_rgb` and `underline_wave`, decoded
in `gui_face`. Both GUI painters draw it through one function, `gui::underline_rects`: one rule,
or a zigzag of thickness-square steps a thickness either side of the rule, its phase the
absolute x so a wave stays continuous across the cells and runs of one word. The terminal
sends the extended underline (crossterm's `Undercurled` and `SetUnderlineColor`), which kitty,
foot and wezterm draw and others show as a plain underline.

**Consequences.** A face map that used `:underline true` is unchanged. Guards:
`underline_takes_a_flag_a_colour_or_a_wave_spec` (red with the wave decode dropped) and the two
`underline_rect_tests`.

## ADR-514 — A command run by `os/cmd` dies with the process waiting on it

**Status:** accepted (2026-11-02).

**Context.** `os/cmd` waits for its child on the calling worker's thread, in native code
(KI-280 made that wait dirty-blocked). An exit signal sent meanwhile only set the caller's
flag: the caller died when the command returned, and the command ran to its end with nobody
to read its answer. `task/cancel` is a hard kill, so a cancelled task did the same. bedit's
live project search cancels the previous search on every keystroke, and each cancelled `rg`
ran on through the whole project; bedit had to run its searcher through `os/spawn` instead,
whose child already dies with its owner (ADR-100's port rule). The rule belongs to `os/cmd`
too: a command is part of the process waiting on it.

**Decision.** `%os-cmd`'s wait polls in slices of at most 20 ms and, between slices, asks
whether its caller has been sent an exit signal it will die of, hard or soft
(`process::capture_kill_pending`: the running green process's `kill_pending`, as a blocked
native-nested `receive` asks when it wakes; never true on the root thread, which is not
killable). The deadline and the kill are one `Stop`, handled alike: the child's process group
is killed and reaped. A deadline returns `:timed-out true` as before; a kill raises the kill
signal, so the caller dies with its own reason, as it would in a `receive`. The reap after the
pipes close polls under the same two stops, since a child that closed its output can still
run. The portable fallback checks the same `Stop`s.

**Consequences.** A killed caller's command is gone within about 20 ms, with the group it
started. A command that finishes is unchanged; one with no deadline now wakes every 20 ms to
look, which costs nothing measurable beside a process start. Guard:
`a_command_dies_with_the_process_waiting_on_it` (`crates/cli/tests/blocking_native.rs`), a
caller stopped by `:kill`, a soft exit and `task/cancel` on tiers 0 and 2, red with the check
disabled.

## ADR-515 — A block caret shows the character under it

**Status:** accepted (2026-11-02).

**Context.** A GUI block caret washed its cell in the caret's colour at half strength and
rimmed it solid. Over a light caret colour the character under it lost most of its contrast,
and the caret read as a smudge rather than as Emacs's box, which fills the cell solid and
draws the character in the background colour on top. The painter cannot do that by itself:
the frame paints the text, then the caret over it, and the caret op carries no text, so a
solid fill would hide the character.

**Decision.** `[:cursor row col style colour blink under face]` takes a seventh element, the
text in the caret's cell (one character or cluster), and an eighth, that cell's face;
`editor/display/cursor` takes them as its sixth and seventh optional arguments.
`gui::Op::Cursor` carries them as `under: Option<(String, Face)>`. With it a `:block` caret
is drawn by both painters, the CPU `render_ops` and the GPU `expand`, as a solid fill in the
caret's colour over `unit_cells(under)` cells, so a wide character's block covers both, with
`under` drawn over the fill as an ordinary text op in `Face::under_caret`: the cell's face, so
bold, italic, family and underline survive, coloured the window background, with no
background or reverse of its own and scale one, since the box is one cell tall. The damage
comparison counts `under`, so a caret moving onto another character in the same column, or
onto one in another face, repaints. Without
it, and for the other shapes, nothing changes; the terminal ignores it, since a terminal
cursor already inverts its cell.

**Consequences.** An app that wants the box passes the character at point; one that passes
nothing keeps the wash; one that passes no face gets the default face over the fill. A
scaled cell's character is drawn at scale one under the caret.

## ADR-516 — A geometric mark is centred in its cell

**Status:** accepted (2026-11-02).

**Context.** A glyph sits on the grid baseline wherever its font's design puts it (ADR-442
keeps a fallback glyph on the shared baseline). For text that is right. For a geometric mark
it is not: bedit's VCS state dot `●` at the end of the mode line read as dropped below the
text, three rows above its ink and one below at 12 px in the bundled DejaVu, and worse at a
taller line height. Fonts disagree about where these shapes sit, so no choice of font fixes
it, and an app cannot correct it per glyph without knowing the font.

**Decision.** After a monochrome cluster is baked, a single character from the Geometric
Shapes block (U+25A0–U+25FF) or the large circles and squares of Miscellaneous Symbols and
Arrows (U+2B1B–U+2B2F, U+2B55) has its canvas rows moved so its ink's top and bottom margins
are equal, the odd pixel below (`is_centred_symbol`, `centre_ink_vertically`). Ink is measured
from the coverage, so the gray and subpixel bakes are treated alike; colour emoji were already
centred. Both painters draw from this bake, so both get it. Letters, box drawing and block
elements are untouched.

**Consequences.** A status dot, a bullet `▪` or a marker `◆` is centred at every size and line
height, in whatever font draws it. Guards: `a_geometric_symbol_is_centred_in_its_cell` (six
shapes, 10–30 px, line heights 1.0 and 1.4, gray and subpixel; red before the change, `●` at

## ADR-517 — A responsive process is told when a native call blocks it

**Status:** accepted (2026-11-02).

**Context.** Some processes exist to keep answering: an editor's loop, a REPL's reader, an
observer's window. Brood gives every way to keep slow work off them (a task, a port, a
worker), and the mistake is not knowing it happened. bedit's `M-x project-task` ran `mix help`
inside the keypress, seconds of frozen window on an Elixir project; its git actions run a
command before refreshing, fine on a small repository and not on a large one. Each looks like
any other call in the source, the checker cannot know a program is slow, and the watchdog
(ADR-490) reports a slow TURN without naming the call that held it.

**Decision.** `(proc/flag :responsive mode)` marks the calling process. A native that waits on
the outside world calls `process::responsive::enter_blocking` before the wait: for an ordinary
process it does nothing; with a truthy mode it times the wait and afterwards sends the process
`[:blocking-call {:native "os/cmd" :detail "mix help" :ms 2300}]`, behind whatever it already
has; with `:refuse` it raises a catchable `E0048` naming the call before anything starts, so a
test can make every such call a failure. The read answers `nil`, `:report` or `:refuse`. The
mode lives on the heap's extras with the other per-process flags, so a spawned process starts
ordinary. `os/cmd` and `run-process` are hooked, the two natives that wait on a program; a
native-nested `receive` is not, since a synchronous call to another process is a round trip
the program chose, not a wait on the world.

**Consequences.** A responsive process learns which call held it and for how long, in the
place it already handles events: bedit routes the message into its slow-turn log. A new
blocking native has one call to make. Guards: `tests/responsive_process_test.blsp` (the flag's
reads, a refused command that never ran, the report's facts, silence for an ordinary
process) and `process::responsive`'s unit tests.

## ADR-518 — `cond` refuses a constant test; `else` is the one catch-all, and it comes last

**Status:** accepted (2026-11-03).

**Context.** The language-design pass (ROADMAP item 9) found `cond`'s catch-all working by
accident. `else` is the special case; `(cond … :else x)` also caught, but only because a
keyword is truthy, exactly as `true` or `42` would. ADR-154 had stopped special-casing `:else`
and kept it working that way on purpose, so 111 sites in brood and 279 in bedit spelled it so.
Two more shapes were accidental too: a falsy constant test (`(cond false a …)`) names a clause
that can never run, and an `else` before other clauses returned at once, silently dropping
every clause after it. The user's rule: accidental logic must not work; handle it by design
first, by lint only where design cannot reach.

**Decision.** By design, in the macro. `cond` raises at expansion on a test that is neither a
symbol nor a call — a self-evaluating constant or a vector/map literal — with a hint for
`:else` (`write else`), and on an `else` that is not the last test. `else` is unchanged. `if`
keeps literal tests: `(if true …)` pins a branch deliberately (ADR-373), and the compiler's
constant fold stays for it and for macro output.

**Consequences.** One catch-all spelling, enforced where the form is built: the REPL, a
load, `nest check` (which reports the expansion error) and a running program all see it.
Every `:else` test in brood and bedit is rewritten to `else`; the docs (`language.md`,
`spec.md`, `brood-for-claude.md`, `writing-brood-skill.md`) say so. `:else` as data (coverage's
branch states, a pattern's literal keyword, `with`'s marker) is untouched. Guards:
`tests/macro_harden_test.blsp` (each refusal and its message, `else` still catching) and
`tests/const_test_fold_test.blsp` (the refusal, and the `if` fold the old cliff needed).

## ADR-519 — A served session can outlive its client

**Status:** accepted (2026-11-03).

**Context.** `serve` (ADR-090) ran one session per attached client and ended it the moment
the client went: a `[:detach]`, or a monitor `[:down …]` when the client died or its link
dropped. For an editor that is the wrong default. bedit's private sessions hold their buffers
in the session's own model, so a dropped ssh tunnel or a laptop lid took every unsaved edit
with it — or, since bedit folds `:close` as its quit command, stranded the session on a "Save
file?" question no window could answer. Emacs's daemon keeps the buffers when an
emacsclient's terminal goes, and that is what a remote editor is for.

**Decision.** `serve` takes an optional `opts`; `{:resume-ms N}` (or `:forever`) makes the
session of a NAMED client (one that attached with `{:name …}`, or a guest whose grant names
it) PARK when that client dies, instead of closing. A parked session keeps running with
nothing to draw to (`remote-display` keeps its client in a table, nil while parked), tells
the manager `[:parked session token]`, and its app folds `[:client-lost]`. The manager hands
the next attach under the same identity the parked session (`[:adopt token client cols
rows]`): the session monitors the new client, sends it `[:attached session]` and the window
as it stands — the options asked for so far, the textures and sound data still live, the
last frame without the sounds and bursts it already played — re-arms its quit key for it,
takes its size, and the app folds `[:client-back]`.

The user attaching again usually notices a dead link before the network does: a laptop that
slept, a tunnel that dropped without a FIN. So an attach under an identity whose session
still HAS a client asks that session (`[:claim token client cols rows]`); it pings its client
(`[:ping session ref]`, which both client loops answer `[:pong ref]`) and waits
`serve-claim-ms` (1.5 s). An answer means two windows on purpose, and the newcomer gets a
session of its own; silence or the client's death hands the session over, the old client
demonitored and told `[:bye]` in case its link comes back. Several sessions under one
identity are asked in turn.

An adopt or a claim is honoured only with the manager's token — and an adopt only while
parked — so a stray message cannot take a live session's screen. A session parked past
`:resume-ms` ends with reason `:client-gone`. A `[:detach]` — the client's own close — still
ends the session, and an anonymous client's session is never parked, since it could be
handed to anyone. Without `:resume-ms` nothing changes.

**Consequences.** A served app survives a dropped link with all its state, and can make its
work safe on `[:client-lost]` (bedit writes auto-save sidecars). Two kernel defects surfaced
on the way and are fixed with it: a soft `exit` was honoured only by a `receive` that parked
or blocked, not one whose scan matched or whose `(after 0 …)` expired (now checked on entry
to every receive), and a receive with only an `after` clause took a message (ADR-520).
Guards: `tests/serve_test.blsp` › "a session outlives a dropped client" (park and adopt,
another name, an anonymous client, expiry, a stray adopt, the default unchanged), "an attach
while the old client's death is not yet known" (an answering client keeps its session, a
silent one hands it over and is told bye, both client loops answer the ping) and "a client
that takes a session over is given the window as it stands"; `tests/exit_test.blsp` › "a
soft exit lands at a receive that does not park".

## ADR-520 — A receive with only an `after` clause waits

**Status:** accepted (2026-11-03).

**Context.** `(receive (after ms body))` compiled to a receive with no patterns, which the
macro read as `(receive)`'s "take the next message as-is" — with a timeout. So it returned
the next queued message, not `body`, and only waited when the mailbox was empty. Everyone
who wrote it meant a pause: the module loader's yield (`%require-after-break`), bedit's startup
and run-stats waits, pools and upkeep loops in other projects, and a dozen tests. Each ate
whatever message happened to be queued. `proc/sleep` existed because of it, and its comment
and `spawn_monitor_test` warned against the form rather than fixing it.

**Decision.** A receive whose only clause is `after` matches nothing: it waits `ms`, leaves
the mailbox alone, and answers `body`. `(receive)` with no clauses at all still takes the
next message. The macro emits a matcher that answers nil for every message, with no native
spec and no tag filter.

**Consequences.** Every existing pause is correct as written, and `proc/sleep` is a named
spelling of the same thing (it keeps its argument check). Code that wanted "the next message
or a timeout" writes a catch-all clause, `(receive (m m) (after ms …))` — no such use was
found. Guards: `tests/receive_spec_test.blsp` › "a receive with only an after clause waits"
(red before the change).

## ADR-521 — `reduce` with no start value raises on an empty collection

**Status:** accepted (2026-11-03).

**Context.** ROADMAP's design pass item 13: `(reduce [] +)` answered `nil`. With no start
value there is nothing to return, and `nil` — absence — was a result nobody asked for, which
the caller then carried on with. `reduce` was also `(coll x & more)`, so a fourth argument was
silently ignored. Both are accidental logic, and the rule is to remove it by design first.

**Decision.** `reduce` has two clauses, `(coll f)` and `(coll init f)`. The first raises on an
empty collection, naming the fix (`(reduce coll start f)`); the second is `fold`. An argument
past the reducer is an arity error by construction. Not a `failure` (ADR-310): a failure is
for input that could not be interpreted, and calling a seedless reduce on an empty collection
is a program error, which raises.

**Consequences.** The checker's `reduce` inference already took a seedless reduce's result to
be an element, never `nil`; that is now true by construction. Nothing in `std/`, `tests/` or
`examples/` relied on the `nil`. Guard: `tests/prelude_seq_test.blsp` "reduce without a start
value".

## ADR-522 — No `memoize` function: memoisation lives at a definition

**Status:** accepted (2026-11-03).

**Context.** ROADMAP design pass item 12, lifetime traps. `combinator/memoize` (ADR-379) made a
fresh, unbounded table on every call and handed back a closure over it. Under a `def` that is
one table for the runtime; anywhere else — a function body, a loop — every call made another,
owned by the calling process and kept until it exited. Its docstring said so, and nothing
stopped it. Its only callers were its own tests: all real memoisation (bedit's 20, brood's 5)
already used `memo/defmemo`, which is a definition — bounded, compared by `=`, its store a
global. The second trap, a table dying with the process that created it (ADR-418), already
fails loudly (`no such table`), but the error did not say why.

**Decision.** By design, not by lint: remove `combinator/memoize`. Memoisation exists only as
`defmemo`, so there is one cache per definition by construction and none can be made per call.
The rename-ledger entry that pointed `memoize` at `combinator/memoize` goes too (`defmemo` is not
a drop-in replacement, so `--fix-renames` must not rewrite to it). A dropped table's error now
names both causes, a `drop` or its creating process exiting, and the hint gives the two fixes.

**Consequences.** `language.md`, `brood-for-claude.md` and `writing-brood-skill.md` point at
`defmemo`. Guards: `tests/library_gaps_test.blsp` (the name is unbound) and
`tests/table_test.blsp` (the dead table's error names its creator's exit).

## ADR-523 — Ability or `defmulti`: one rule, and a lint for the wrong choice

**Status:** accepted (2026-11-03).

**Context.** ROADMAP design pass item 7. Brood has two polymorphism mechanisms: abilities
(ADR-168/172) dispatch on the first argument's identity; `defmulti` (ADR-179) on the tuple of
every argument's identity. Nothing told a library author which to pick. In practice abilities
carry everything (87 in brood, 55 impls in bedit, 38 in hatch) and `defmulti` only the binary
operators it was built for (`num/add` … `num/div`, `compare-to`); no downstream project uses it.

**Decision.** Both stay, each for its job, and the rule is stated once (`language.md`
§Polymorphism): an ability unless the choice depends on more than the first argument. The
checker reports the one way to pick wrong — a `defmulti` this file declares whose methods all
agree past the first position (a one-argument multimethod, or methods that differ only in the
first argument), which is single dispatch without an ability's provided ops, `:requires` or
checker support. A `:commutative`/`:antisymmetric` multimethod's mirrors vary the second
position, so it is never reported. `(check-allow :single-dispatch …)` opts out.

**Consequences.** No user code changes; nothing in `std/` or bedit is reported. The mechanism's
own tests, which use one-argument multimethods on purpose, opt out. Guard:
`tests/multimethod_test.blsp` "defmulti that is single dispatch" (red with the lint off).

## ADR-535 — A key's Emacs spelling reads both ways: `key-parse` and `key-description`

**Status:** accepted (2026-11-03).

**Context.** A key is what the frontends deliver (`host::gui::character_chord` /
`named_key`, ADR-328, ADR-441): a 1-char string or a keyword such as `:ctrl-x`,
`:ctrl-meta-i`, `:ctrl-shift-left`, `:f5`. A person writes the same key the way Emacs prints
it, `C-x C-f`. Only the printing direction existed, and it lived in bedit (`keyhelp`'s
`ed-key-label`); nothing could turn `"C-c t f"` back into a key sequence, so no config file,
REPL binding or test could name a key the way help shows it. The first caller is bedit's
`init.blsp` `:keys`, the Emacs `global-set-key` question.

**Decision.** `std/editor/keymap` owns both directions. `single-key-description` and
`key-description` are the printer, moved from bedit unchanged. `key-parse` is its inverse:
one key per word, modifiers `C-` `M-` `S-` `s-`, Emacs's words `RET` `TAB` `SPC` `ESC` `DEL`,
named keys in angle brackets with Emacs's aliases (`<return>`, `<prior>`, `<backtab>`, the
older `<C-return>`), and every bare name the printer writes (`C-S-left`). The modifiers fold
into the key the way the frontends fold them: Ctrl lower-cases a character, Shift upper-cases
one without Ctrl, Shift+Tab is `:back-tab`. Anything else returns a `failure` naming the word
(ADR-310): a key description comes from a person, so a typo is input, not a bug.

**Consequences.** Every key the frontends deliver reads back from its description, which
`tests/keymap_test.blsp` checks over one key of every shape. The printer keeps bedit's
spelling (`C-x backspace`, not Emacs's `C-x DEL`) so no help text changes; `key-parse` takes
both. `H-` and `A-` are rejected: no frontend delivers Hyper or a separate Alt.

**Addendum (2026-11-03): layers merge prefixes deeply.** A config binding `C-c f` globally
was hidden in every buffer whose mode bound anything under `C-c`, because `editor/layers`
merged layers shallowly: a prefix key belonged wholesale to the highest layer binding it.
Emacs looks a key sequence up through every active map, so a mode map's `C-c C-p` and the
global map's `C-c f` both work. The layers now do the same. `keymap-merge` lays one keymap
over another, sub-keymaps merged all the way down; `active-keymap` folds the layers through
it; `layer-binding` (what dispatch asks per key) merges the prefix keymaps of every layer
below the one that binds a prefix (memoised, since a prefix key asks it on every press);
`scope-bindings` reports a binding shadowed only when a higher layer binds the same sequence,
or binds a prefix of it to a command or to nil. A higher command or nil still takes a key
whole, which is how a user unbinds one. `tests/layers_test.blsp` replaces the tests that
pinned the shallow rule; nothing in bedit relied on a mode hiding a global prefix.

**Addendum (2026-11-03): one rule for dispatch and help.** The first cut folded the layers
pairwise with `keymap-merge` for the merged map, while dispatch merged a prefix's lower
keymaps itself, skipping commands. With a MIDDLE layer binding a prefix key to a command the
layers on either side use as a prefix, the two disagreed: help dropped the bottom layer's
chord that dispatch ran. Now `keymap-stack-binding` is the rule for one key in a stack of
keymaps (the first that binds it decides; a prefix there merges the prefixes of every keymap
binding the key to one, a command beneath it passed over, as Emacs does), and
`keymap-merge-stack` applies it to every key, all the way down. `active-keymap` is
`keymap-merge-stack` of the layers; `layer-binding` resolves a prefix key with
`keymap-stack-binding`; `keymap-merge` is the two-keymap stack. Guard: `tests/layers_test.blsp`
"help and dispatch agree on every key sequence of a mixed stack", which walks every bound
sequence, each prefix and one key past each through dispatch and through the merged map.

## ADR-536 — A clipboard read is a blocking call

**Status:** accepted (2026-11-03).

**Context.** ADR-517 hooked the two natives that wait on a program, `os/cmd` and
`run-process`. A clipboard READ waits on one too: the app that owns the selection
serialises what it holds — an X11 conversion round trip (arboard opens a fresh display
connection for each read and gives an owner up to four seconds), a Wayland data offer read
through a pipe. bedit's yank called `os/clipboard-get` inside every `C-y` keypress, so a
slow or wedged owner froze the window, and neither the responsive flag nor the slow-turn
log could name the call. Moving the read into a task had a second cost: the native did not
mark its worker dirty-blocked, so a task waiting on a hung owner held a scheduler worker
the way `os/cmd` did before KI-280's fix.

**Decision.** `os/clipboard-get` and `os/clipboard-image` call `enter_blocking` before the
read (`:native` `"os/clipboard-get"` / `"os/clipboard-image"`, `:detail` `"text"` /
`"image"`) and hold a `dirty_block` guard across it, one helper in
`builtins/clipboard.rs`. Writing (`os/clipboard-set`, `os/clipboard-set-image`) is not
hooked: it hands the data to this process's own selection owner and waits on nobody.

Two more pieces make reading in a task safe and sufficient:

- A read can wait for good — a Wayland offer whose pipe is never written has no deadline in
  arboard — and while one handle served both sides, that read held the lock every later
  read AND every write waited on: a kill the editor mirrors to the clipboard, on its loop,
  would have frozen behind it. Reads now go through a handle of their own (`READER`), taken
  with `try_lock`; a read that finds another still waiting raises at once ("another
  clipboard read is still waiting on the clipboard's owner") instead of queueing, and
  writes keep the owner's handle, which no read holds.
- An editor reads the clipboard when its window regains the keyboard, so the terminal
  frontend must say when that happens too. `term-enter` turns on focus reports
  (`CSI ?1004h`; `term-leave` and the abnormal-exit restore turn them off), and `term-poll`
  and the input forwarder deliver `CSI I` / `CSI O` as `:focus-in` / `:blur`, the window's
  spelling, through one converter (`polled_value`). The inline seam (`term-raw-enter`, the
  REPL's line editor) turns them off, and its reader drops any that still arrive: a
  full-screen app that died without `term-leave` leaves the terminal sending them.
- A read that never returns would hold even its own handle for good, so every later read
  answered busy until a restart. The reader is replaced once a read has held it past
  `READ_DEADLINE` (two seconds; reads take milliseconds and arboard's own X11 wait ends at
  four): the stuck read keeps the handle it is inside, the next read makes a fresh one. A
  wedge costs one stuck thread, and reads recover.

**Consequences.** A responsive loop is told when a clipboard read held it, and a test that
refuses blocking calls catches a yank that reads the clipboard on the loop; bedit reads it
in a task when its window or terminal regains focus instead. `language.md` and
`error-codes.md` list the clipboard reads beside `os/cmd`. Guards:
`tests/responsive_process_test.blsp` (both reads refused, the text read reported, a write
never refused), `host::clipboard`'s tests (a read behind a stand-in that never answers is
`Busy` at once), the terminal's `focus_reports_are_delivered_in_order_with_the_keys` and
`a_focus_report_reads_as_a_windows_focus_event`.
## ADR-537 — The tab width is a dynamic variable, `*tab-width*`

**Status:** accepted (2026-11-03).

**Context.** The cell-layout primitives — `string/display-width`, `string/width->index`,
`string/expand-tabs` (ADR-342) — take an optional tab width and default to 8. An editor's tab
width is a property of the BUFFER (Emacs's buffer-local `tab-width`, an `.editorconfig`'s
`tab_width`), and bedit measures text in some sixty places across its view, wrap, pane and
scroll code, plus std's own callers (`string/clip-cells`). Threading a width argument through
every one of them, and through std functions that do not take one, was the only way to show a
Go file's tabs at 4: a missing capability, not a missing call.

**Decision.** The prelude declares `(defdyn *tab-width* 8)`, and the three primitives read it
— through the calling process's binding stack — whenever they are not handed a tab width. An
explicit argument still wins; a value below 1 is 1, as an argument is; an unbound or non-int
value (a heap without the prelude) is 8. An editor binds it once around a pane's render and its
row-table computation, and every measure inside agrees on the buffer's stops.

**Consequences.** No caller changes: unbound, everything is 8 as before. The GUI painter's own
advance for a RAW tab (`host/gui`) stays 8 — it never sees one from a view that expands tabs
first, which is what `string/expand-tabs` is for. Guard: `tests/strings_test.blsp` "the ambient
tab width" (red without the kernel read).
## ADR-539 — A served session's clipboard is its client's

**Status:** accepted (2026-11-03).

**Context.** `serve` (ADR-090) runs the app on the daemon and paints it on a client's
window, often on another machine. An editor's kill and yank go through the OS clipboard, and
the only one a served session could reach was the DAEMON's — a machine its user is not
sitting at, and, on a shared host, someone else's. bedit's served sessions therefore had no
clipboard at all: a copy in the window never reached the user's other apps, and a yank never
saw what they had copied. Nothing in the protocol let a session ask anything of its client's
machine.

**Decision.** Three messages, all plain data (so a guest link, ADR-415, carries them):
`[:clipboard-set text]` session → client, a cast; `[:clipboard-get session ref]` session →
client, answered `[:clipboard ref text]` (`text` nil when the clipboard is empty or not
text). Both client loops (`attach`'s terminal one, `attach-display`'s) handle them, through
the display's `:clipboard-set` / `:clipboard-get` entries when it has them and the OS
clipboard otherwise, and always answer a get — read by a process beside the client loop, so a
slow clipboard owner never stops it painting or shipping keys. The session side is three public functions
that work in the process a session runs in — found through a dynamic var `serve-session`
binds for the session's life to `remote-display`'s new `:served-client` entry (the client it
draws to NOW, so an adopted session, ADR-519, asks its new client): `served-client`,
`client-clipboard-set` (returns the text, or nil having sent nothing) and
`client-clipboard-ask` (returns the ref, or nil having asked nothing). Outside a served
session, while parked, and in a `serve-shared` session (no one client) they do nothing.

Nothing waits. The answer is not received by the asker; it reaches the app's `update` as an
event, as every background message does, so the loop draws and takes keys through the round
trip. A client whose link dropped without anyone knowing yet (ADR-519's case) never
answers, so the ask also schedules its own answer (`timer/send-after`), `[:clipboard ref
nil]` after `ms` (500 by default): every ask is answered, and the app takes the first answer
for a ref and ignores the rest. A blocking get with a timeout was the first shape; it stalled
the loop for the round trip on every yank, and for the whole timeout against a dead link.

**Consequences.** An app reaches its user's clipboard by a function and an event; it never
names the OS clipboard for a served session, and the daemon's clipboard is never touched by
one. Not done: images (`os/clipboard-image`) and the X11 primary selection — text only.
Guards: `tests/serve_test.blsp` › "serve: the session's clipboard is its client's" — a copy
reaches the client, a paste gets the client's answer as an event while the session keeps
taking keys, a client that never answers is answered for at the timeout and its late answer
is the app's to ignore, nothing is sent outside a session, and the window client sets and
answers through its display.

## ADR-540 — A rope is searched by regex in place

**Status:** accepted (2026-11-03).

**Context.** bedit's incremental search grew regexp search, a match count and highlighting of
every visible match (Emacs 27's `isearch-lazy-count` / `lazy-highlight`). `std/regex` searched
only a string, so each of those needed the buffer flattened — a copy of the document per
keystroke, per frame, per count — which is the cost `%rope-find` (literal search) was written
to remove. A count over a 50 MB buffer also cannot run on one key; it has to be taken in slices,
and slices of a regex search are not obviously exact (a match can straddle a slice's end).

**Decision.** Four primitives in `crates/lisp/src/builtins/rope_regex.rs`, under
`regex/rope-find`, `rope-find-backward`, `rope-count` and `rope-spans`. They drive the
pattern's lazy DFAs (regex-automata's `hybrid`) a byte at a time over the rope's leaves: forward
to a match's end, the reverse DFA back to its start; backward, the reverse DFA unanchored from
`before` meets the largest start first and the forward DFA confirms it — Emacs's
`re-search-backward` (the match starting last and ending by `before`). Groups come from `meta`
over the match's own text. A bounded scan (a count's slice, a window's spans) stops past its
limit only where the forward DFA is back in a START state with nothing found — the one point
where no match is in progress — so slices add up to exactly the whole count. Matches are
non-empty, except that a search may ask for an empty one (`:empty?`), as Emacs's isearch stops
on `x*` before the first character; a count and a window's spans never include one. Where the lazy DFA quits (a Unicode `\b` before non-ASCII text) the search runs
`meta` over the materialised text it needs, the one copying path — a window at a time
(forward: the next 64 KB of starts and as far past them as a match can reach; backward: windows
doubling from `before`, a search per match start, not per byte), so a window's spans copy the
window.

The rope functions read a pattern as a buffer search does, Emacs's way: `^`/`$` are a line's
ends and `.` stops at a newline (`{:lines? false}` for the string meaning); `{:fold? true}` is
`(?i)`. Two helpers a search box needs: `regex/escape` (text as a literal pattern) and
`regex/incomplete?` (an unclosed group or set, or a trailing backslash — the dialect reads such
a pattern leniently, so nothing else can say it is unfinished).

**Consequences.** bedit's isearch searches, counts (on the idle beat, a slice at a time) and
highlights by regex without flattening the buffer. Guards: `rope_regex.rs`'s unit tests (the
answers agree with `meta` over the flattened text across leaf boundaries; slices add up) and
`tests/regex_test.blsp` "regex over a rope".

## ADR-541 — A chord is read by the key's US identity when the layout's character is not Latin; Option composes unless it is Meta

**Status:** implemented (2026-11-03).

**Context.** A window turned a winit key event into a Brood key in `translate_key`, reading a
chord's character from `key_without_modifiers` — the key with no modifier applied, in the
ACTIVE layout. Under a Russian, Greek, Hebrew, Arabic or Ukrainian layout that is `ф` for the A
key, so Control+A arrived as `:ctrl-ф` and no Emacs binding (`C-x C-f`, `C-a`, `M-x`) answered
until the user switched layout. Emacs and most editors read such a chord by its Latin key.
Second, macOS Option was always Alt to winit and so always Meta to the app: a layout that types
`@ { [ |` with Option (German, French, most of Europe) could not type them. On Linux AltGr is
`ISO_Level3_Shift` and on Windows winit filters AltGr's synthetic Ctrl+Alt, so AltGr was never
Alt there — but nothing said so, and nothing tested it. Third, a dead key pressed with Control
or Alt (German Ctrl+`^`, and macOS Option+e / Option+u / Option+n, dead keys on a US Mac
layout) translated to nothing: the chord was dropped. KI-336.

**Decision.**
- The translation is a pure function, `translate_keystroke(&KeyPress, KeyModifiers,
  non_latin_layout)` in `host/gui/backend/input.rs`, over a `KeyPress` holding what it reads of
  winit's `KeyEvent` (logical key, typed text, unmodified key, physical key). The event loop
  builds one per event; the unit tests build them for any layout.
- A chord (Control, Meta or Super held) whose unmodified character is not Latin script is read
  by the key's PHYSICAL position on a US QWERTY layout (`us_layout_char`): `C-ф` is `:ctrl-a`.
  "Latin" is ASCII plus the Latin Unicode blocks, so a German `C-ö`, a French AZERTY `C-a` (the
  Q key) and a Dvorak `C-'` stay what their layout says. Some keys of a non-Latin layout type
  ASCII punctuation (Greek Q is `;`, Hebrew W is `'`); a window remembers whether its layout's
  last letter key was non-Latin (`layout_is_non_latin`), and while it was, punctuation on a US
  letter position is read by position too — so a Greek `C-q` is `:ctrl-q` while a Dvorak `C-'`
  on the same key stays `:ctrl-'`. Plain typing is untouched: it inserts the layout's text.
- A chord read by position takes the US glyph under Shift (`M-S-ю` is `:alt->`), never the
  layout's shifted character for a different key.
- A dead key in a chord is the accent it names (`:ctrl-^`), else its US position. Alone it still
  delivers nothing: the character the composition ends in arrives as the next key's text.
- A new open option, `{:option-meta :left | :right | :both | :none}` (Emacs's
  `ns-alternate-modifier` / `ns-right-alternate-modifier`), default `:left`: left Option is
  Meta, right Option composes. On macOS it sets winit's `OptionAsAlt` (so a Meta side's keys are
  read without their Option layer — left-Option+e is `:alt-e`, not a dead `´`) and the
  translation drops Alt when the only Option keys held are composing ones (`chord_modifiers`),
  so right-Option+2 on a German layout inserts `@`. Only macOS reports which side is held; with
  no side reported Alt is Meta, so the option changes nothing on Linux or Windows.
- No event changes shape: a key is still a 1-char string, a modifier keyword or `[:text …]`, and
  input methods still deliver `[:preedit …]` / `[:text …]`. What changed is WHICH key a chord
  under a non-Latin layout names.

**Consequences.** A served client (`--attach`) translates in its own window, so it gets the same
keys with nothing on the wire changing. The US position is a fallback, not the user's Latin
layout: someone who types Dvorak and Russian gets QWERTY positions for chords while Russian is
active (GTK finds the layout group that has a Latin keysym; winit does not expose the keymap).
The macOS half is reasoned from winit's source, not run: no Mac was available. Guards:
`host::gui::backend::input::adr_541_tests` (Russian, Greek, Hebrew, Arabic, Dvorak, German and
AZERTY chords; AltGr and composing-Option text; dead keys in chords; which Option is Meta), four
of them red with the positional fallback removed.

## ADR-542 — A record is its own value kind

**Status:** accepted (2026-11-04); landing in steps (below). **Supersedes** ADR-130 ("records are
maps, not a new Value kind") and ADR-168 point 2 ("a record is still a structural map").

**Context.** ROADMAP design pass item 8; the scoping is `docs/record-kind.md`. A record was a
map with a reserved `:__id__` key, and each map operation decided for itself whether the key was
there. `(assoc {:x 1 :y 2} :__id__ :point)` forged a record `=` to `(point 1 2)`; `dissoc` of the
key silently turned a record into a map; `map/reduce-kv` and `map/select-keys` saw and copied it;
the printed form `{:__id__ :point …}` read back as a forged record. Two leaks (`into`, `merge`)
had already been fixed by hand, and the forge waited on this decision because hiding the key in
every map operation puts a check on `assoc`'s hot path and leaves every future map operation one
more place to forget. The user's rule for the design pass: accidental logic is removed by design
first, by lint only where design cannot reach.

**Decision.** `Value::Record { id: Symbol, fields: MapId }`: the identity lives in the value, the
fields in an ordinary CHAMP map. Nothing that operates on a map can see or write an identity, so
the forge and every leak are impossible by construction.

1. **`type-of` is `:record`**, so its answers stay a closed set of built-in kinds; `record-id`
   gives the nominal id (`:point`, `:geo/point`); `record?` is true and **`map?` is false**.
2. **Field access is unchanged.** `get`, keyword-call, `assoc`, `update`, `dissoc`, `keys`,
   `vals`, `count`, `seq` and destructuring work on a record's fields and an `assoc`/`update`/
   `dissoc` returns the same kind with the same id. There is no reserved key: `:__id__` is an
   ordinary keyword. `fields` returns the plain map.
3. **`=` and hashing** are nominal: two records are equal when their ids and fields are; a record
   never equals a map.
4. **Printed as `#point{:x 1 :y 2}`** (`#geo/point{…}` for a module's record), a form that is
   never a map literal, so printing cannot forge. Reading the form back is a later step.
5. **The id is interned as data**: it crosses `send`, the wire format (version bumped) and the
   images as a symbol beside the field map.

**Steps**, each landing green: (1) the kernel kind — variant, GC trace/promote/freeze, equality
and hash, printer, message and wire codec — with `%make-record`, `record?`, `record-id` and
`fields` as primitives and nothing yet constructing one; (2) `defrecord` constructs through
`%make-record`, the map primitives and the VM/JIT inline `get` accept a record, and every
`:__id__` special case in the prelude and the Rust probes goes; (3) the checker moves from the
`__id__`-field shape to a Record tag carrying the id literal (sealed abilities, exhaustiveness);
(4) tests that pinned `:__id__`, downstream (bedit's ten `(get e :__id__)` reads become
`record-id`), and the docs. Proof per step on the test machine: the full suite on both engines,
`make gcstress`, a fuzz-differential pass, and `make ab`/`make ab-vm` for the `get` path.
## ADR-559 — The runtime package calls answer a failure carrying the reason

**Status:** implemented (2026-11-04).

**Context.** An app installs its plugins at runtime through `package/registry-enhancers` (the
list), `package/registry-latest-version` (update checks) and `package/registry-install`. Every
way those go wrong short of a bug — the registry unreachable or answering an error, the package
unpublished, a refused source URL, a failed download, a checksum mismatch — is something the
app's USER has to be told, with the reason. They were not told: `registry-enhancers` answered nil
for "the registry is down" (bedit showed an empty package list), `registry-latest-version` and
`registry-install` raised, and the hosted download said only `failed (HTTP 500)` or `HTTP 0`,
dropping the server's text and the transport's complaint. Under that, `http/request` promised
`{:status 0 :error …}` for a transport failure but let a connection that could not be made (`tcp/
connect`'s raise: nothing listening, a name that does not resolve, a refused TLS handshake)
escape — so the package client's own `:status 0` branch never ran. And `registry-enhancers`
handed a symbol app name (its own docstring's example, `'bedit`) to a URL builder that wanted a
string.

**Decision.**
- The three runtime calls answer a `failure` (ADR-310) carrying the reason: `registry-enhancers`
  and `registry-latest-version` on a request that failed (latest still nil for unpublished),
  `registry-install` for an invalid name, an unpublished package, a release request that failed,
  a refused URL or failed download (the fetcher's sentence becomes the failure's), a checksum
  mismatch, and an archive that does not extract (its half-extracted directory removed). A
  failure before extraction leaves an installed copy as it was.
- A hosted download's error names the reason: the transport's message, or the server's `:error`
  text (`registry-error-text`), not the bare status.
- `http/request` answers `:status 0` with the connect error when the connection cannot be made,
  as its docstring always said and `request-on` already did.
- `registry-enhancers` takes its app as a symbol or a string.
- `nest new --from <package>` (`scaffold`) stops with the failure's reason.

**Consequences.** bedit's package manager (`src/packages.blsp`) says the registry's reason in
its echo area and *Packages* status line, and runs these calls in a task. Guards:
`tests/package_test.blsp` "the runtime registry calls say why they failed" (unreachable, a 500
with an `:error`, unpublished, a failed download leaving nothing, a checksum mismatch leaving an
installed copy), `tests/http_test.blsp` "a connection that cannot be made is a :status 0
response".

## ADR-550 — A buffer's undo history is capped by size, trimmed whole groups at a time

**Status:** accepted (2026-11-04).

**Context.** `std/editor/buffer`'s undo history is a list of snapshots (`{:rope :point :mark}`),
one per undo group, and undoing is itself recorded (the undo tree). Nothing ever dropped one, so
a buffer edited for a long session kept every text it had ever held: a slow memory creep in an
editor that stays open for days (bedit's review against Emacs's bug archives, #18). Emacs caps
its `buffer-undo-list` with `undo-limit` (keep at least this much) and `undo-strong-limit`
(never more), trimmed at garbage collection.

**Decision.** The cap is the buffer's, so every editor over the toolkit gets it.

- **Size, not count.** A snapshot shares every rope leaf its step did not touch, so what it
  alone keeps alive is the text the step changed plus the leaf and path the edit copied. Its
  cost is the changed chars, old side and new (`text/changed-range` against the state after it,
  native, chunk by chunk) plus `*undo-step-cost*` (1024). The cost is known once the NEXT
  snapshot is pushed, so it is stamped on the old head then (`:cost`), and the buffer keeps the
  running sum (`:undo-size`) — no walk of the history per edit.
- **Two limits, Emacs's.** Past `*undo-strong-limit*` (3 000 000) the oldest snapshots go until
  the rest fits `*undo-limit*` (2 000 000): one O(history) pass per million of edits, never per
  keystroke. The newest group is kept whatever it costs. Both are `defdyn`s, so an editor binds
  them or re-`def`s them from its settings (every process of the image sees a `def`); nil turns
  the cap off. `trim-undo` applies them at once.
- **Whole groups.** A snapshot IS a group (amalgamation and `undo-group` fold a run into one), so
  dropping whole snapshots never cuts a group in half.
- **Only an edit trims.** An undo run walks the oldest entries, which are what a trim drops; if
  its own steps trimmed, a run at the limit would eat the history it is undoing. A run at most
  doubles the history, and the next edit trims it. A trim also shortens a stale `:pending-undo`
  by the entries it dropped, so nothing keeps them alive.

**Consequences.** Memory per buffer for undo is bounded at about the strong limit. A region undo
that consumes an entry leaves its cost in `:undo-size` (an over-count: the trim comes early and
recounts exactly). Guard: `tests/buffer_test.blsp` "buffer undo limit".
## ADR-556 — A glyphless character is laid out as its escape when `*glyphless-display*` says so

**Status:** accepted (2026-11-04).

**Context.** The invisible format characters — U+200B ZERO WIDTH SPACE, U+2060 WORD JOINER, a
BOM in mid-text, the bidi controls a "Trojan Source" attack hides in (U+202A–202E, U+2066–2069,
U+200E/F, U+061C), the tag characters that smuggle text past a reader (U+E0020–E007F) — are zero
cells in the cell layout (`string/display-width`, ADR-342), so an editor painting text through
it showed nothing where they are. Emacs shows them through `glyphless-char-display` (a hex
box). bedit could not do that on its own: a view that drew `<200b>` where the layout said zero
cells would put every caret, click and wrap after it in the wrong column, and the layout is the
kernel's — the view, the row tables, the wrap and the clip all ask the same three primitives.
Classifying a character as one of these needs Unicode data the language did not expose either.

**Decision.**
- `text_width::is_glyphless` names the class: the general-category-Cf characters with no part in
  shaping a script — U+061C, U+200B, U+200E–200F, U+202A–202E, U+2060–2064, U+2066–206F, U+FEFF,
  U+FFF9–FFFB, U+E0001, U+E0020–E007F. Left out, because showing them would break ordinary text:
  ZWNJ / ZWJ (Persian, the Indic scripts, every emoji ZWJ sequence), the prepended concatenation
  marks, U+180E, the hieroglyph / shorthand / musical format controls, and U+00AD, which fonts
  draw.
- The prelude declares `(defdyn *glyphless-display* :hidden)`. Bound to `:hex-code`, the three
  layout primitives lay each glyphless character out as `<200b>` — lowercase hex, at least four
  digits: `display-width` counts the escape's cells, `width->index` maps any cell of it to the
  character's cluster, `expand-tabs` writes the escape in its place (after the rest of its
  cluster). Read through the binding stack, as `*tab-width*` is (ADR-537).
- `string/glyphless-indices` returns the character index of each one, so a view can lay an
  escape face over the escape it now shows.
- The class is decided per character, never by its neighbours, so a line measured in chunks (a
  view's face runs) sums to the whole line. That is why the joiners are out entirely rather than
  shown "outside an emoji or a joining script": a face run ending between a Persian letter and
  its ZWNJ would measure the ZWNJ alone, as shown, while the whole line hid it.

**Consequences.** Unbound, nothing changes: zero cells, as a terminal draws them — `std/vt`'s
grid never binds it. The GUI painter's own advance for a raw glyphless character stays zero; it
never sees one from a view that expands first. A ZWJ or ZWNJ between Latin letters stays
invisible — the price of the per-character rule. Guards: `host::text_width` tests
(`hex_code_shows_each_glyphless_character_as_its_escape`, `pieces_of_a_string_sum_to_the_whole`,
…) and `tests/strings_test.blsp` "glyphless characters".

## ADR-553 — The PRIMARY selection is its own pair, beside the clipboard

**Status:** accepted (2026-11-04).

**Context.** X11 and Wayland keep two selections: CLIPBOARD, what was explicitly copied
(`C-c`, `M-w`), and PRIMARY, whatever was last highlighted, which a middle click pastes. Brood
reached only the first (`os/clipboard-get` / `os/clipboard-set`, ADR-095). An editor that wanted
a mouse drag to be pasteable elsewhere had one way to do it, writing the CLIPBOARD, and bedit did
— so every drag-select silently replaced what the user had copied in another app (Emacs, with
`select-enable-clipboard` t and `mouse-drag-copy-region` nil, leaves the CLIPBOARD alone and sets
PRIMARY). And a middle click had nothing to paste.

**Decision.** Two primitives, wrapped in `std/os.blsp` beside the clipboard pair:
`(os/primary-get)` reads PRIMARY's text (nil when empty, not text or unavailable) and
`(os/primary-set s)` owns it with `s`, returning `s`. They ride the `clipboard` feature and
arboard's Linux selection extension (`LinuxClipboardKind::Primary`, which its Wayland
data-control backend supports too); the read goes through the clipboard's reader and blocking
seam (ADR-536 — reported to a responsive process, `Busy` while another read waits on an owner),
the write through the owner's handle, so there is no new process-wide state. Off Linux there is
no such selection: the read answers nil and the write does nothing, so a caller never branches
on the platform. A separate pair, rather than a `:primary` argument on the clipboard functions,
keeps the clipboard's signatures and the common case unchanged.

**Consequences.** bedit's drag-select sets PRIMARY only, and a middle click yanks it. A served
session (ADR-539) reaches its client's PRIMARY across the link since ADR-562. Guards:
`tests/clipboard_test.blsp` (a read is nil or text and
never raises; nil without the feature or a display), `natives_never_mutate`'s desktop skip list.

## ADR-554 — A rope search takes a BOUND: where a match must end

**Status:** accepted (2026-11-04).

**Context.** An editor command confined to the region — `query-replace` with the region
active, Emacs's `perform-replace` — searches with `re-search-forward`'s BOUND: no match may end
past the region's end. `regex/rope-find` (ADR-540) had no such argument. Filtering its answers
by their end is wrong for any pattern that can match more than the bound allows: `a+` over a
region holding the first two `a`s of `aaaa` finds `aaaa`, the filter refuses it, and the region
reads as having no match where Emacs finds `aa`. Searching a copy of the region instead gets
the edges wrong the other way: `$` and `\b` would match at the copy's end where the real text
goes on.

**Decision.** `%rope-regex-find` takes an optional fifth argument, `bound` (a char index; nil
or absent is the rope's end), and `regex/rope-find` an option `:bound`. The lazy DFA's forward
scan already ran to an `end` byte with look-around fed the real byte after it (the backward
search's confirm used it); `find_forward` now passes the bound there, and the window fallback
caps its windows at it while each window still carries a character of context beyond. So a
match never ends past the bound, a greedy one stops at it, and `^` / `$` / `\b` at the bound
are judged as the text has them — Emacs's semantics.

A window that reaches the bound has nothing more to read, so the Pike VM is told so
(`pike_settled`'s `last`): a thread waiting there for more text is passed over and the match
ending at the window's end is the answer. Without that a greedy match lost its last character
— and it did already at the rope's END, before any bound existed: `\bü+` over `a üüü` (a
Unicode word boundary, so the fallback) answered `üü`. Fixed by the same flag.

**Consequences.** bedit's `M-%` / `C-M-%` over a region search with the region's end (moved as
replacements change its length) as the bound. A literal search needs no bound — a literal
match cannot be shortened — so `buffer-search-forward` is unchanged. Guards: the Rust test
`a_bound_caps_the_match_end_and_look_around_sees_past_it` (DFA and fallback paths), and
`tests/regex_test.blsp`'s `:bound` case.

## ADR-562 — A served session's PRIMARY selection is its client's

**Status:** accepted (2026-11-04).

**Context.** ADR-539 gave a served session its client's CLIPBOARD and ADR-553 gave Brood the
PRIMARY selection, but the serve protocol carried only the first. An attached editor's drag set
nothing anywhere (the daemon's PRIMARY belongs to a machine its user is not at), and a middle
click had nothing to paste.

**Decision.** The clipboard's three messages again, with their own tags: `[:primary-set text]`
session → client, a cast; `[:primary-get session ref]` answered `[:primary ref text]`. The
session side is `client-primary-set` and `client-primary-ask`, shaped exactly as the clipboard
pair (nil outside a served session, an ask answered for after the same timeout). Both client
loops handle them through the display's `:primary-set` / `:primary-get` entries when it has
them, else `os/primary-set` / `os/primary-get`, read beside the loop as a clipboard read is.
Separate tags rather than a selection argument on the clipboard messages, for ADR-553's
reason: the clipboard's wire shape, which older clients speak, stays as it was.

The messages go only to a client that SAYS it handles them. A client's attach identity carries
`:can` — this runtime's says `[:primary]` (the identity is always sent now; every daemon since
the identity attach reads it, and an older daemon's app reads the map's other keys and leaves
this one). The session notes its first client's `:can` before anything asks, the manager
re-states it for a client a session is handed (adopt, claim), and `served-client-can?` answers
the session's question; `client-primary-set` / `client-primary-ask` do nothing for a client
that said nothing. A session is matched to a returning user by who they are, `:can` left out,
so a newer client resumes the session an older one parked.

**Consequences.** bedit's attached sessions set the client's PRIMARY on a drag and paste it on
a middle click. A client that predates this has no PRIMARY: nothing is sent to it — its window
loop ships an unknown message back to the session as a key (bedit rang "is undefined" on every
drag) and its terminal loop leaves one in its mailbox — and an ask answers nil at once, which
is what such a session had before. Guards: `tests/serve_test.blsp` › "serve: the session's
clipboard is its client's" (the PRIMARY cases, and a client that does not say it can).

## ADR-563 — A file's byte-order mark is kept off the buffer and written back

**Status:** accepted (2026-11-04).

**Context.** A UTF-8 file may open with U+FEFF, the signature Windows tools write.
`buffer-from-file` kept it as the text's first character, so an editor showed it (as `<feff>`
under ADR-556), point could sit on either side of it, a search for `^#` missed the first
line, and a column counted it. Emacs decodes such a file as `utf-8-with-signature`: the mark is
no part of the buffer, and the save writes it back.

**Decision.** `file-text-decode` reads a file's text the way a buffer holds it — a leading
U+FEFF taken off, then the line endings as `eol-decode` reads them — answering `{:text :eol
:bom}`, and `file-text-encode` is its inverse. `buffer-from-file` and `revert-buffer` decode
through it and remember a mark as `:bom true` (`buffer-bom?`), beside `:eol :crlf`; `save-buffer`
encodes through it. Only a LEADING mark is a signature: one anywhere else is text (a zero width
no-break space), kept and shown.

**Consequences.** Anything that compares a file's text with a buffer's decodes it with
`file-text-decode` rather than `eol-decode`, or a file with a mark always reads as changed. A
buffer process that hosts a buffer for another frame carries `:bom` in its metadata as it
carries `:eol`. Guards: `tests/buffer_test.blsp` (read, save, CRLF together, a mark past the
start, revert).

## ADR-564 — A timer can carry on the user's command: no background ceiling on its fold

**Status:** accepted (2026-11-04).

**Context.** ADR-491 lets the loop stop a BACKGROUND fold that runs past
`*ui-event-ceiling-ms*`, keeping the model it started from — nobody asked for that work, so
nobody is there to press C-g. A timer's firing is folded as background. But an app that splits
ONE user command over several turns, so the quit key is read between them (bedit's keyboard
macro, which replays its keys in slices), continues that command from a timer: a slice holding a
key that takes longer than the ceiling (a save with format-on-save) was stopped, its model
rolled back, and the timer ran the same slice again — the key's side effects repeating until C-g.

**Decision.** A timer spec may say `:command? true`: its firing carries on the user's own
command, and `ui-run` folds it as it folds input — no background ceiling, only the quit key
stops it, as the command run in one turn would have been. Nothing else about the timer changes:
it does not count as input for `:idle?` timers.

**Consequences.** bedit's `:macro-continue` ticker is a `:command?` timer. A slice can still be
stopped by C-g mid-key, which rolls that slice back and is folded next, ending the run. Guards:
`tests/ui_test.blsp` › "a :command? timer's fold is the user's" and its plain-timer contrast.

## ADR-567 — Program output is decoded as a stream: a split escape is held, colours carried

**Status:** accepted (2026-11-04).

**Context.** A subprocess's output reaches its reader in chunks the reader did not choose. An
escape sequence cut by a chunk boundary — `ESC[1` at the end of one read, `mERROR` at the start
of the next — was handled per chunk by `ansi/strip`, which dropped the first half and left the
second as text: bedit's *compilation*, shell buffer, *Run*, *Tests* and M-! output all showed
`1mERROR` (bedit issue #24). `strip` also knew only CSI, so an OSC title (`ESC]0;title BEL`)
lost its ESC and `]` and kept its text. And stripping was the only option: a line-mode consumer
that wanted the colours (Emacs colours a compilation's and a shell's output, `ansi-color`) had
to run the output through `vt`, a whole terminal emulator with a screen and a cursor, which is
the wrong model for append-only text. Emacs's answer is `ansi-color-apply` with
`ansi-color-context`: the SGR state and an unfinished sequence are kept between chunks.

**Decision.** `ansi` gains a streaming decoder, a pure value threaded by the caller:

1. `(ansi/decoder)` → `{:attr :pending :in-string}`; `(ansi/feed decoder chunk)` →
   `[decoder' segments]`, `segments` a vector of `[text attr]` (adjacent runs of one attribute
   joined). An escape the chunk ends inside waits in `:pending` and is finished by the next
   chunk, so feeding a stream cut at ANY position decodes exactly as feeding it whole — the
   property the tests check at every split of every sample, and one character at a time.
2. SGR (`ESC[…m`, parameters only) changes `:attr`; every other escape is consumed: CSI
   (cursor, erase, private modes, `ESC[>4;2m`), OSC (titles, OSC 8 hyperlinks — ended by BEL or
   `ESC \`), DCS / APC / PM / SOS strings, charset selection, two-character escapes. Inside an
   OSC-like string the decoder keeps only the fact (`:in-string`), never the content, so an
   unterminated string costs no memory; an unfinished CSI longer than 256 characters is
   garbage and is dropped rather than held.
3. Control characters stay in the text. `\r` means one thing to a log (drop it — what `strip`
   does) and another to a progress line (overwrite — what `render` does), so the caller
   decides. A sequence still pending at the end of a stream is incomplete and dies with the
   decoder.
4. The attribute model moves from `vt` to `ansi`: `ansi/sgr` (the fold), `ansi/params`,
   `ansi/colour`, `ansi/face`, `ansi/xterm-palette`. `vt` keeps a cell's attribute in the same
   shape and calls these, so a terminal screen and a decoded log agree on what `38;5;196` is.
   `vt/colour`, `vt/face` and `vt/xterm-palette` are gone (no compatibility names: their only
   callers were vt itself and its tests).
5. `ansi/segments-text` and `ansi/segments-spans` read the segments as text and as
   `[start end attr]` ranges at an offset — what an editor appends and stamps as faces.
   `ansi/strip` becomes the decoder over a whole string (OSC removed whole), and `ansi/render`
   drops an OSC-like string through its terminator.

**Callers besides bedit.** The REPL and `nest run` show program output that may carry colour;
nest's own output capture (`with-out-str`, the MCP `EvalResult.stdout`) wants colour stripped or
kept without a split sequence corrupting it; the test runner's captured output of a test that
prints coloured text; the eval server's reply stream. Each reads chunks, which is the whole
reason the decoder is streaming. It lives in std rather than bedit because it is a mechanism
(no feature in it), it is shared with `vt`, and the terminal emulator that versions with the
kernel uses half of it.

**Consequences.** A line-mode consumer keeps one decoder per stream (stdout and stderr are
two) and never shows half an escape. bedit lays the spans on its streaming buffers as faces
under the mode's own colouring. Scanning is by ESC-split pieces — a piece is examined only as
far as its escape reaches — so plain output costs one `includes?` and colourful output one
split, not a per-character walk. Guards: `tests/ansi_stream_test.blsp` (every split of eleven
samples, SGR colours, OSC/DCS/charset consumption, the moved model), `tests/ansi_strip_test.blsp`,
`tests/vt_test.blsp`.

## ADR-570 — A pty says how it reads input (`os/pty-mode`, `os/pty-password?`)

**Status:** accepted (2026-11-04).

**Context.** A host that shows a pty child's input ITSELF — bedit's line-mode REPL (`iex -S
mix`, `nest repl`: the text after the prompt is the editor's, RET sends the line) — inserted a
password exactly as it inserted any other line, and kept it in the input history. Emacs's comint
guesses from the prompt (`comint-password-prompt-regexp`); `term` and every real terminal do the
right thing for free because they never echo locally — the line discipline does, and a program
reading a secret turns `ECHO` off in its termios (`getpass`, `sudo`, `ssh`, `git`'s credential
prompt, Erlang's `io:get_password`). Brood could spawn a pty and resize it but not ask it that,
so the only signal a Brood host had was a regexp over the screen — a guess that misses a prompt
it does not know and fires on a line that merely mentions a password.

**Decision.** `(os/pty-mode p)` over `%pty-mode`: `tcgetattr` on the pty MASTER, answering
`{:echo bool :canonical bool}` from `c_lflag`'s `ECHO` and `ICANON`. On Linux and macOS a
master's termios ioctls answer for its linked slave, so nothing new is held open. And
`(os/pty-password? p)` in std over it: echo off AND canonical on.

ECHO alone is not the signal, which is why the primitive reports two flags. A program with its
own line editor — readline's bash, Erlang's shell (OTP 26's raw tty), a raw-mode REPL — turns
echo off on EVERY read, along with `ICANON`, and echoes for itself; a password read (`getpass`,
sudo's `tgetpass`, ssh's `readpassphrase`, `stty -echo; read`) clears `ECHO` and keeps line mode.
The pair tells them apart; echo alone would call every iex prompt a password. A program that reads
its password through its own raw-mode editor cannot be told from a normal read by the terminal —
that is what a caller's prompt-text fallback is for.

`nil` when the handle is unknown or already closed (the child is gone; a caller checking at a
prompt should not have to catch a race with its exit) and off Unix, where nothing is known — so
nil leaves a caller to its fallback. A piped child throws, as `os/resize-pty` does: asking a pipe
is a bug. It is a query, read when output arrives or before a line is sent, never polled per
frame.

**Callers beyond bedit.** Any Brood program hosting an interactive child under `os/spawn-pty`
with local line editing has the same gap: a `std/vt` user that echoes the typed line in its own
widget, `nest repl` driving a child runtime in a pty, an expect-style driver (bedit's own
`tools/drive-*` harness types into a pty and wants to tell a password prompt from a hang).

**Consequences.** bedit's line-mode terminal asks `os/pty-password?` in its pty worker on each
render and, when it is true, takes the next line through a masked minibuffer read (Emacs's
`read-passwd`) that never reaches the buffer, the input history or savehist. Guard:
`tests/proc_test.blsp` "proc: a pty says how it reads input" (a real pty: `stty -echo` is a
password, `stty -echo -icanon` is not, `stty echo` is not, a closed child nil, a piped one
refused).

## ADR-573 — The regex dialect folds case and reads POSIX bracket classes

**Status:** accepted (2026-11-04).

**Context.** bedit's masked password reads (issue #26) match Emacs's
`comint-password-prompt-regexp`, which Emacs runs case-folded and writes with `[[:alpha:]]`
and `[[:blank:]]`. Brood's dialect (ADR-389) had neither: `(?i)` parsed as a capturing group
holding the characters `?i`, and `[[:alpha:]]` as a set of `[:alph` followed by a literal `]`
— both silently matched the wrong thing. The caller lowercased every line before matching and
rewrote the classes by hand, which is the workaround the prime directive forbids, and which
breaks the moment a pattern has an upper-case literal. The rope searches (ADR-540) already
had `{:fold? true}`; the string searches had no way to say it, so the two paths could not be
asked the same question.

**Decision.** Three readings join the dialect, all in `std/regex.blsp`'s parser and
translation — the engine already runs every one of them, so no Rust changes:

- `(?i)` / `(?-i)`: case folding on / off for the rest of the enclosing group (the whole
  pattern at the top level, every alternative included), Perl's scope, emitted to the engine
  verbatim; `(?i:…)` / `(?-i:…)` for one NON-capturing group, so the groups after it keep
  their numbers. Simple Unicode case folding, as the engine (and `:fold?`) does it.
- `{:fold? true}` as an optional last argument to every string search — `match?`,
  `matches?`, `find`, `find-all`, `replace`, `split` — meaning exactly `(?i)` in front, the
  way the rope searches' `:fold?` always has. One translation, so a string search and a rope
  search under the same flag agree character for character.
- POSIX bracket classes INSIDE a set: `alpha alnum digit xdigit upper lower space blank punct
  cntrl graph print word ascii nonascii`, with EMACS's meanings rather than POSIX's ASCII
  ones — `alpha` is every letter (`\p{Alphabetic}`), `upper`/`lower` every cased letter,
  `alnum` a letter or a decimal digit, `punct` Unicode punctuation and symbols — while
  `digit` stays ASCII `0-9`, as `\d` does (what `string/->number` reads). They mix with chars,
  ranges and classes and negate with their set (`[^[:space:]]`). Under `(?i)` `upper` and
  `lower` fold to every cased letter, as Emacs's do under `case-fold-search`.

What stays: the lenient malformation rule. `[[:foo:]]` (an unknown name) keeps its old
reading, `(?x)` and an unterminated `(?` mean what they did, and the stray-paren and
`incomplete?` walkers step over a class's `]` as the parser does.

**Callers beyond bedit.** Any search box over text a person wrote (the REPL's apropos, a
`nest` grep, the observer's filters) wants case folding without lowercasing the subject, which
also breaks the offsets of a non-ASCII match; and every pattern ported from Emacs, grep or
POSIX tools is written with bracket classes. The conformance corpus (rust-lang's copy of
Fowler's testregex) drops four of its ten listed divergences: `basic51` runs with `:fold?`,
`basic57`–`59` are POSIX classes.

**Consequences.** bedit's `passwd/*password-prompt-regexp*` is Emacs's pattern again, with
`(?i)` and the classes, matched against the line as it stands. Guards:
`tests/regex_test.blsp` "regex case folding", "regex POSIX classes" and "… over a rope" (the
same patterns through `find-all` and `rope-spans`), and `tests/conformance_regex_test.blsp`
with the shortened divergence list.

## ADR-579 — Text properties: data that belongs to the characters, carried by every edit

**Context.** bedit coloured a program's output (`ansi-color`) by keeping a vector of
`[start end attr]` spans beside the buffer and shifting it by hand where it knew text moved:
appends, head cuts, a splice from another frame. Every other edit — the user typing in a
shell buffer, an undo, a revert — left the colours at stale offsets, and a second frame
showing the same buffer never saw them at all, because the buffer process held only the
text. Emacs keeps these as TEXT PROPERTIES, which move with the characters because they
belong to them. `std/editor/buffer` already carried MARKERS (single positions) through every
editing primitive; it had nothing for ranges that belong to text.

**Decision.** A buffer keeps `:properties` — `{key [[start end value] …]}`, per key ascending
non-overlapping half-open spans — and the ONE tail every editing primitive shares
(`buffer-apply-edit`) carries them next to the markers and the narrowing:

- Emacs's text-property semantics, not a marker pair's: an insert inside a span splits it
  (typed text does not take the colour), one at either edge is outside it, a delete shrinks a
  span and drops one it empties, adjacent equal spans join.
- Properties are REAR-NONSTICKY, every key, always: text typed at a span's end does not
  extend it, as text typed at its start does not. That is right for what they carry — a
  program's output colours, where the user's input after a red `error:` must not turn red
  (Emacs's comint input does not inherit `ansi-color` faces either) — and it keeps one rule
  for every edit, undo and replica. Emacs's per-property stickiness (`text-property-default-
  nonsticky`, `rear-nonsticky`) is not offered: no caller wants it yet, and a sticky key
  would make every insert ask which keys extend; it is a later, additive option.
- Inserted text gets properties only when it comes with them: `insert` and `replace-region`
  take an optional `properties` (`{key spans}` relative to the new text) — a coloured chunk
  is appended in ONE edit.
- `put-properties` sets one key over a range as a PROPERTY change, not a text change: the
  text, point, mark, markers and narrowing stay exactly where they were (it first replaced
  the range by itself, which jumped every marker in it to the start and every other frame's
  cursor with it). It is still an edit — recorded for undo, refused by a read-only buffer or a
  protected range — and logged as a property entry, `[:put-properties width changes]`
  (`changes` `{key spans}` relative to its start, `[]` clearing a key), with `hi` = `lo` and
  an empty replacement, so a reader that took it for a splice would change nothing. The log
  chains on ropes, and ropes compare by TEXT, so it cannot order an entry that leaves the
  text as it was: a property entry carries the buffer's `:property-stamp` (a count of its
  property changes), and a holder's walk takes one stamped after its copy even once it has
  reached its copy's text. A holder asking "did this change?" asks `buffer-content-changed?`
  (text or property map; O(1) when neither moved), since the text alone misses it.
  `buffer-splices-since` — the text consumers' view (a language server, tree-sitter, a line
  cache) — leaves it out.
- Undo snapshots hold them; a region undo gives the text it restores the properties it had in
  the undone snapshot (`undo-region-restore` says which text each piece came from), as a plain
  undo does, and the rest keeps its own.
- The splice log records what each inserted text came with (a 7th entry element) and
  `buffer-edits-since` answers `[lo hi repl properties]`. A run of appends merges whatever its
  chunks carry — a program's coloured output, chunk after chunk, is ONE entry, the properties
  laid end to end — and a delete back into it clips them; a mid-run holder's rest of the run
  comes with the properties of its text. A run also stops at `*splice-run-chars-max*` (16 K)
  of replacement, since output chunks are kilobytes and each merge rebuilds it. An undo's
  logged splice is trimmed to what differs and WIDENED to whatever properties it gives back,
  or is a property entry when only properties came back (an undo of `put-properties`).
- When the log cannot account for a change (more than `*splice-log-max*` runs in one event,
  a text replaced wholesale), `buffer-edits-between` compares: the minimal changed range of
  the text (`text/changed-range`, no string built) widened to cover any property that
  differs, carrying the new properties over its text — so a holder ends with the same text
  and properties and nothing outside the range moves. It used to send the whole buffer,
  `[0 len text]`, with all of them: O(document), and every position in every other frame
  jumped to its edge.
- Over the buffer-process protocol a splice carries them (`buffer-splice`'s `properties`, the
  push's `:properties`), `link-fold`'s actions are `[:splice s properties]` /
  `[:text t properties]`, `content-view` seeds a late subscriber with them, `spawn-buffer`
  and the registry (`registry-share`'s `{:text :properties}`, its mirror now a buffer) start
  a process with them, and `apply-splice` / `buffer-apply-action` apply a foreign splice
  whatever the copy's read-only state — the text already changed where it is authoritative.
  A property change crosses as `[:splice [lo lo ""] [:put-properties width changes]]`: the
  process transforms its range over concurrent splices and keeps it out of its transform ring
  (which holds what moved text), and `apply-splice` applies it without touching the text.

Also fixed on the way: `replace-region` deleted `end - start` GRAPHEME CLUSTERS from `start`,
so a range holding a combining mark took the character after it too; it deletes exactly the
characters `[start, end)` now.

**Callers beyond bedit.** Any holder of a document with produced styling: the observer
painting a process's coloured log, a REPL buffer, `nest`'s test output viewer, the web mirror
— all want colours that survive an edit and reach every subscriber, which is a property of
the buffer, not of one editor.

**Consequences.** bedit's `:output-spans` and its hand-carrying (`model/ed-carry-spans`) are
gone; ansicolor's colours are the `:ansi` text property. A buffer with no properties carries
no key and pays one nil check per edit; one with properties pays a binary search per edit
(an append after every span costs only that). Guards: `tests/buffer_test.blsp` "text
properties …", "put-properties …", "undo-in-region gives back properties", "propertied
appends are one run …", "apply-splice …", "replace-region counts characters";
`tests/buffer_client_test.blsp` "text properties travel with the splices", "a property change
travels as one"; `tests/buffer_registry_test.blsp` the mirrored respawn keeping them, and a
property change.

## ADR-580 — SGR sub-parameters are read as groups; an over-long CSI is swallowed, not dropped

**Status:** accepted (2026-11-04). Amends ADR-567 points 1–2 and 5.

**Context.** Review of ADR-567's decoder found three faults in the shared escape model.
`ansi/params` read a `:` like a `;`, which was enough for `38:2::r:g:b` and wrong for
everything else ECMA-48 / ITU T.416 puts after a colon: `ESC[4:3m` (the curly underline
kitty, VTE, iTerm2 and WezTerm draw, and that compilers and linters emit for diagnostics)
became italic plus underline, and `ESC[4:0m` (no underline) reset every attribute. An
unfinished CSI past the 256-character cap was dropped at a chunk's end, so the rest of it,
arriving in the next read (`…mX`), showed as text. And `ansi/strip`, rebuilt over the
decoder, was 3.3× slower than the per-character scan it replaced (1186 ms against 361 ms on
880 KB with 80 000 escapes), paying for SGR parsing, attribute folds and segment merging it
then threw away.

**Decision.**

1. `ansi/params` keeps one entry per `;`-separated parameter; a parameter that carries `:`
   sub-parameters is the VECTOR of them — `"4:3;38:2::9:8:7"` → `[[4 3] [38 2 nil 9 8 7]]`.
   `ansi/sgr` applies a group as one parameter: `4:0`–`4:5` the underline (none, single,
   double, curly, dotted, dashed) as `:underline true` plus `:underline-style` (`:double
   :curly :dotted :dashed`; a single underline has no style key, and a plain `4` or a `24`
   clears the style); `38:` / `48:` / `58:` a colour, `5:n` or `2:r:g:b` with or without
   the colour-space id. `58` (both spellings) and `59` are the underline colour,
   `:underline-colour`, which `ansi/face` resolves like `:fg`. A group the model does not
   know, or one it cannot read, changes nothing — a sub-parameter never spills into the
   parameters after it. `vt` reads a group in a non-SGR sequence as its first number.
2. The decoder's state is `{:attr :pending :inside}`: `:inside` is `:string` (an OSC-like
   string, as `:in-string` was) or `:csi` — a CSI that ran past the cap at a chunk's end. Such
   a CSI is swallowed, not held: its bytes are discarded as they come, in any number of later
   chunks, up to its final byte (0x40–0x7E), after which text resumes; a control character
   ends it as one always cancels a CSI, and an ESC starts the next escape. Memory stays
   bounded and no tail leaks.
3. `ansi/strip` walks the same ESC-split pieces with its own scan: no parameters read, no
   attributes, no segments — the text after each escape, joined once. The CSI body is one
   native `string/span` rather than a recursive per-character walk, which the decoder shares
   (and SGR detection is a `string/span` too, not a regex). The test suite holds strip to
   exactly the decoder's text on every sample.

**Measured** (one timed run each, dev build, 880 KB with 80 000 escapes): `strip` 2197 ms
before → 313 ms, against 385 ms for the pre-ADR-567 scan on the same build; `feed` 2216 ms →
1531 ms.

**Consequences.** A caller that matched on `ansi/params` entries being ints must allow a
vector (vt's `param` / `selector` / mode setting did). A host painting faces can draw curly,
dotted and coloured underlines from `:underline-style` / `:underline-colour`. Guards:
`tests/ansi_stream_test.blsp` (colon sub-parameters; the over-long CSI cut anywhere, across
chunks, ended and cancelled; strip against the decoder), `tests/vt_test.blsp`.

## ADR-581 — Redaction: a delete that leaves no trace, across every holder

**Context.** bedit's terminal and shell move text typed ahead of a password prompt into the
masked read. That text entered the buffer as ordinary typing — a snapshot per key on `:undo`,
a splice per run in the log, a copy in every frame and in the buffer process — and moving it
out with `replace-region` recorded one more snapshot, so a single undo brought
`Password: hun` back. Nothing in `std/editor/buffer` could remove text AND its history.

**Decision.** `redact-region` deletes `[lo, hi)` and drops the undo history (any snapshot
before the delete may hold a prefix of the text, so none can be kept), records nothing for
the delete, and records the delete in the splice log as a REDACTION, its properties slot
`:redact`. Over the buffer-process protocol that slot travels like text properties (ADR-579):
the process applies a `:redact` splice, pushes it as such, and every holder's
`buffer-apply-action` (`apply-splice`) redacts its own copy, history and all. A buffer process
keeps no undo history and no splice log at all (`spawn-buffer` disables undo; `buffer-serve`
drops the log), and neither does the `{:mirror true}` registry's mirror (undo disabled, its
log dropped after every push it folds): holders undo in their own copies, and a history or a
log there would keep what a redaction took. A copy applying ANOTHER holder's redaction keeps
no log entry that names any text from before it.

A redaction must reach every holder AS a redaction, or a holder applies it as a plain delete
and keeps its per-key undo steps and log ropes with the secret in them. Two mechanisms make
that unconditional:

- The redacting buffer's log is left with the redaction ALONE, naming no text from before it
  — no rope holding the redacted characters stays in memory, not even until the next edit.
  (A first cut kept the log's earlier entries under the redaction until the next edit, so a
  holder syncing that event could walk it exactly; that kept the secret in memory meanwhile.)
- A buffer counts its redactions (`:redactions`). When the log cannot account for a change —
  always, for a holder whose copy predates a redaction —
  `buffer-edits-between` compares the texts, and when the count grew since `before` it sends
  the changed range as a `:redact` first and its new text as an insert after — every holder
  drops its history wherever in that range the secret was.

`undo-group` reads the same count: a redaction inside a group would otherwise come back with
the history the group restores around it, so the group then leaves no history at all.

**Callers beyond bedit.** Anything that lets a person type a secret into a shared buffer
before it knows it is one — a REPL asking for a token, a remote session's shell, the
observer's console.

**Consequences.** A holder syncing across a redaction always gets the comparison's edits: the
changed range redacted, then the text the event left — coarser in placement than a log walk
(the event's other edits in that range arrive merged), never a plain delete, and nothing of
the secret held by anyone. Guards: `tests/buffer_test.blsp` "redact-region …", "redaction in a buffer
process" and "a redaction reaches every holder, whatever else the event did";
`tests/buffer_client_test.blsp` "a redaction travels as one" and "a redaction after another
edit in the same event"; bedit's `tests/frames_test.blsp` (two frames, one event).

## ADR-582 — Taking back what a module's load registered: per-member writers, `:remove`, `registry/written-by`

**Context.** bedit installs and removes packages while it runs. A package's load registers
into std's tables as well as bedit's — `editor/layers`' type layers, file rules, interpreter
map and system layers, `registry/*registries*`, faces, abilities, record ids — and removing the
package left those rows pointing at undefined functions. The kernel already journalled the
module whose LOAD made each registry write (KI-136), but only per key path: a list registry
(`*system-layers*`, `*auto-type-by-file*`) had one writer for the whole list, nothing could
remove one member as an operation (a compare-and-swap is a live write an isolate restore
drops, KI-141), Brood code had no public way to ask, and `editor/layers` had no unregister.

**Decision.**

- `%registry-update!` gains `:remove` — drop the members of a list-valued global equal to the
  value, declining when there is none. An operation like `:cons-new` / `:append-new`, so a
  load journal stages and replays it. It handles lists only, and `registry/written-by` lists
  list members only: no registry op makes a vector, so a vector-valued global's elements were
  never anyone's to take back.
- **The writer journal** (`RuntimeCode::registry_writers`, a `RegistryWriters`) keeps a map
  entry's writer by its printed key path, and a LIST registry's members as one slot per member
  in the list's own order, each with the member's printed form and its writer. A member is
  found by POSITION, through the same `equal` `:remove` matches with — so two packages'
  anonymous predicates (both print `#<fn>`, never `=`) are two members with two writers, and
  `:remove` retires exactly the slot of the member it removed. The printed forms only tell
  when the list changed underneath (a swap, a `def`): the slots then answer for nothing until
  the next op realigns them, writer-less. No `Value` is held, so the journal is no collector
  root.
- **A writer is journalled when its op APPLIES.** A live write is credited as it lands; a write
  a module load stages is credited by `publish_module_load`, for the ops it actually applies
  (each `LoadWrite::Registry` carries the writer it was staged with). `discard_module_load`
  touches nothing, so a load that throws neither credits a write nor retires another module's
  member.
- **Who a write credits** (`Heap::current_registry_writer`): the namespace being compiled, else
  — for `reflect/load` of a file without a `defmodule` — that FILE, by its absolute path
  (`std::path::absolute` of the path given, not resolved further), else nobody. `%registry-
  writer` answers a module as a symbol and a file as a string; `%registry-update!`'s fifth
  argument takes either (an image replay names its module), or `false` for nobody. Only that
  load gets the file credit: the prelude, a program file, a spawned process and a file that
  declares a module keep their old attribution, and the stdlib image ignores a string writer,
  so a namespace-less write stays in the registry's own value as before.
- **Conditional retract and restore.** `%registry-update!`'s sixth argument makes the op apply
  only while the entry it targets (the key path, or the member) is still credited to that
  writer — checked under the registry lock, and again at the publish and at a restore's
  replay. `registry/retract` and `registry/restore` pass the `:writer` `written-by` reported,
  so a load in between cannot make either take an entry another module has since written.
  `registry/restore` credits the value it puts back to its third argument (the module or file
  that wrote that value) or to nobody — never to whoever is loading.
- **The isolate rolls the journal back.** `snapshot_globals` copies it with the table (under
  the registry lock, so no write lands between the two); `restore_globals` restores it and
  re-credits each replayed load's writes as their values are replayed — a removal the isolate
  made, or a discarded load's, no longer leaves a member back in its list with no writer.
- `std/registry`: `writer`, `written-by` (every entry a set of writers' loads wrote — map
  entries one or two keys deep and list members, each with its `:writer`; the module system's
  own bookkeeping excluded), `retract`, `restore`.
- `editor/layers`: `unregister-system-layer`, `unregister-type-layers`,
  `unregister-file-type`, `unregister-interpreter-type` — each the inverse of its register.

A write made at run time, outside any load, still has no writer; ownership of those is the
program's to keep (bedit claims them for the package whose command or hook is running). Two
programs wanting the same entry is theirs to order too: bedit keeps a per-entry stack of each
package's write and restores the nearest live layer when the top one goes.

**Callers beyond bedit.** Any host of hot-loaded plugins or REPL-loaded modules that must
unload one cleanly — `nest`'s dev server reloading a module whose registrations changed, the
observer's extensions.

**Consequences.** The stdlib image's attribution is unchanged (map registries, by module
symbol); a module materialised from a startup image is credited with less than its source
load — KI-357 states the exact limit. Guards: `tests/registry_retract_test.blsp` — a fixture
module's writes into `registry/*registries*` and every `editor/layers` table listed by writer,
retracted, a replaced entry restored; each `unregister-*`; two modules' alike-printing
predicates retracted independently; a throwing load changing no writer; a namespace-less
file's writes (faces included) credited to its path; a stale retract and restore refused and a
restore crediting its writer or nobody; an isolate rolling a removal's writer back; a vector
global listing nothing.

## ADR-583 — A grammar's vocabulary is queryable, and a language is checked against it

**Status:** accepted (2026-11-04).

**Context.** A tree-sitter language in an editor is a grammar plus tables written against it:
a face table keyed by node kinds and field names, an indent spec naming the nodes that open a
level, injection rules naming the nodes that hold another language, the kinds that are
definitions. `editor/treesit` checked those tables for SHAPE (`face-table-problems`,
`injection-problems`) but nothing could check them for MEANING, because the runtime never said
what a loaded grammar contained — `%tree-sitter-load-grammar` answered an ABI number and no
more. `grammar-install` fetched whatever a repository's default branch was that day, and
reused a checkout as it found it, so a grammar update that renamed `heredoc_body` produced a
language that loaded, parsed and quietly stopped colouring heredocs. Nobody could even say
which grammar revision a user had: a library does not record its revision, and nothing wrote
it down. Emacs 29's `treesit-language-source-alist` takes a revision; distributions pin.

**Decision.**

- **`%tree-sitter-grammar-info lang`** (kernel) answers the grammar's vocabulary:
  `{:lang :abi :version :name :source :named :anonymous :fields}` — its visible node kinds
  (named and anonymous, keyword sets; aliases included; hidden rules and supertypes left out,
  since no node ever has those as its kind), its field names, its ABI, the version and name an
  ABI-15 grammar records (nil before), and the library it was loaded from or `:built-in`. It
  loads a declared grammar, as a parse would. Only Rust can read the language's symbol table;
  everything built on it is Brood.
- **`editor/treesit/language-names`** collects the kinds and fields a language's tables refer
  to, from the shapes std defines: a face table (keys and every selector's `:kind`, `:parent`,
  `:field`), injection rules (`:content`, `:exclude`, `:lang-from`), an indent spec (`:blocks`,
  `:brackets`, `:verbatim` — `:dedent` and `:opens` are source text) and definitions
  (`:kinds`). **`grammar-problems info names`** is the comparison, one sorted message per
  missing name ("node kind `heredoc_body` is not in the :hcl grammar"); **`language-grammar-
  problems lang language`** runs it against the grammar loaded now, and reports a missing or
  unloadable grammar as one problem rather than raising.
- **`grammar-fingerprint info`** hashes a grammar by its shape (ABI, kinds, fields): equal for
  two builds of one revision, different when a node was renamed — the identity that matters to
  a language's tables, where the library's bytes change with the compiler.
- **Pinned fetches and the manifest.** `grammar-fetch` takes a revision (a commit hash or a
  tag; nil is the default branch today) and makes `dest` a shallow checkout of exactly that —
  `git init` once, `git fetch --depth=1 origin <rev>`, a detached checkout — so the same call
  installs, updates and pins back. A checkout at another commit than a hash pin names is an
  error, and an abbreviated hash is refused up front (git fetches a commit by its full hash
  only).
  `file://` URLs are git URLs too, which is how the tests exercise the real path offline.
  `grammar-install`'s optional argument is now an options map `{:subdir :revision}`, and it
  writes a MANIFEST beside the library (`libtree-sitter-<lang>.manifest`, one re-readable
  map: source, subdir, revision asked for, commit resolved, the ABI `parser.c` was generated
  for, the library's SHA-256). `grammar-manifest`, `grammar-manifest-path`,
  `grammar-file-hash` read it; **`grammar-identity lang`** puts the loaded grammar's info,
  fingerprint and manifest together, with `:manifest-current?` false when the library was
  replaced after the install that described it.

- **The reload epoch is per language.** A held tree is not reparsed from after its grammar
  reloads (ADR-443); the counter that said so was one for the whole runtime, so loading ANY
  grammar — which, with declarations loading at first use (ADR-481), is opening a file of a
  language not seen yet, or an install — sent every held tree of every language to a full
  parse at its next edit. Checking a grammar loads it, so this would have got worse; it is
  now counted per language, and only that language's trees parse afresh.

What is NOT here: where grammars live, which revision a language wants, and what an editor
does about a grammar that fails its check (report it, stand in with a line lexer) — all
policy, all the editor's.

**Callers beyond bedit.** Every user of `editor/treesit`'s grammar recipe (`grammar-install`
is std's): any editor or tool built on the toolkit can pin what it fetches and check its tables
with the same calls, and Brood's own grammar tests (`tests/treesit_module_test.blsp`) assert
the built-in Ruby grammar's vocabulary through it. `nest grammar` emits Brood's OWN syntax
grammar and does not manage tree-sitter libraries, so it is not a caller; brood-lsp has no
tree-sitter languages today.

**Consequences.** A language's tables become checkable at registration time against whatever
grammar is installed, and drift is a list of names instead of a file that stopped colouring.
`grammar-install`'s fifth argument changed from a subdir string to an options map — its one
caller (bedit) moves with it. A fetch with no revision now UPDATES an existing checkout to the
default branch's head, where it used to reuse the checkout untouched. Guards:
`tests/treesit_module_test.blsp` — `language-names` over every table shape, `grammar-problems`
naming missing kinds and fields, a missing grammar as one problem, the fingerprint's order
independence and sensitivity, the built-in Ruby grammar's info and a check against it, and an
install from a local repository at a pinned commit, its manifest, an update to the head and a
fetch back to the pin, an abbreviated hash refused, and an unknown revision refused; a held
Elixir tree still reparsing incrementally after the HCL grammar loads.
## ADR-586 — The terminal display writes the cells that changed, in the colours it has

**Context.** bedit ran only in a native window; over ssh or on a console it failed. The terminal
frontend (`editor/ui/*term-display*`, ADR-046) existed and already took keys, the mouse, focus and
the kitty keyboard protocol, but `term-draw` wrote every op of every frame straight to the tty. An
editor frame starts with `[:clear]`, so each keystroke erased the screen and printed all of it
again: a screenful of bytes per key, and a visible flicker over a slow link. It wrote true colour
whatever the terminal could show, left the cursor hidden (`term-enter` hides it and no op showed
it again), dropped a resize (the loop learned the new size only on its next turn) and a paste
(bracketed paste was off, so a paste arrived as typed keys an editor indents and pairs).

**Decision.**

- **A screen model in the kernel** (`builtins/terminal/native/screen.rs`, pure): a frame is
  painted into a `Screen` — a grid of cells, each a grapheme and its `Style` — over the screen the
  terminal already shows (`TERMINAL_SCREEN`, one per OS process, as the terminal is), and
  `render` writes only the cells that differ. Changed cells closer than four apart are one run (a
  cursor move costs about as many bytes). A wide grapheme takes two cells and a write over half
  of one blanks the other; a control character is drawn as a space (written raw it would move
  the cursor and misplace every cell after it). The update is bracketed as a synchronized update
  (`CSI ?2026`), with the cursor hidden while it moves. A frame that changes nothing writes
  nothing. Semantics are unchanged: a frame without `[:clear]` still paints over what was there.
- **The first frame, and a resize, repaint whole.** `term-enter`, `term-leave`, every restore
  path and a `Resize` event forget the screen; so does `(term/invalidate)`, for a program that
  wrote to the tty some other way. The forget on the panic path uses `try_lock`: the panic may be
  on the thread whose draw holds the lock.
- **Colour depth from the environment, as Emacs reads it**: `COLORTERM=truecolor|24bit` is true
  colour, a `TERM` with `256color` (or a known 256-colour terminal) is 256, `…-direct` true
  colour, anything else the 16 named colours. A true colour is drawn as the nearest cube or grey
  of the 256, or the nearest of the 16 (xterm's RGB, weighted for the eye); a named colour stays
  the terminal's own at every depth, written as SGR 30–37/90–97. `(term/colors)` reports the
  depth and sets it. The curly underline and underline colour go only where they are safe
  (true colour; 256 for the colour).
- **A default face**, `(term/bg bg fg)` — what `gui/bg` is to a window: `[:clear]` fills with
  it, and a face that names no `:bg` / `:fg` takes its colours. A theme made for a dark window
  is drawn on its own background, not on a light terminal's (where its light text was
  unreadable). nil is the terminal's own, the default.
- **The cursor** shows at the frame's last `[:cursor]` — a `:hollow` one (an unfocused pane's) only
  when there is no other — in its shape (DECSCUSR), and is hidden in a frame with none; the shape
  is reset to the user's on leave.
- **A resize is `[:resize cols rows]`, a paste `[:paste text]`.** The resize is a window's own
  spelling, so a `ui-run` app re-renders at once; bracketed paste is on while the terminal is
  entered, and the paste arrives whole. The inline seam (the REPL) drops resizes, as it drops
  focus reports.

- **Brood decodes the tty's bytes itself** (on Unix; `tty.rs`, `decoder.rs`). crossterm read
  and parsed the tty, and had no parser for xterm's `modifyOtherKeys` (`CSI 27 ; mods ; code ~`),
  the one way xterm and tmux send `C-;`, `C-.`, `C-S-a`, `C-<return>` (KI-360). The decoder turns
  bytes into crossterm's own `Event` values — so the key tracker and `key_to_value` are unchanged
  — reading everything crossterm read plus that form, and the legacy bytes 0x1C–0x1F as
  `C-\ C-] C-^ C-_` (crossterm's `C-4`…`C-7` made `C-/` no undo). A resize writes no byte: it is
  the terminal's size changing between reads, the wait sliced at 50 ms. `term-enter` asks for
  `modifyOtherKeys` 2 where the kitty protocol is not spoken, and every leave resets it. Under
  tmux, `set -g extended-keys on` passes the request through. The Windows console sends no
  bytes; crossterm still reads it.

## ADR-587 — The terminal is a frontend like a window: `display-available?`, OSC 52, one attach client

**Context.** With the terminal display able to carry an editor (ADR-586), what was left was
everything a window has that a terminal session did not: a way to ask whether a window can be
opened at all, a clipboard that reaches the user from the far end of ssh, and the thin client —
`editor/serve/attach` had a terminal loop of its own (drain frames, then `term/poll`) beside the
any-display `attach-display`, written before the terminal delivered its keys to the mailbox.

**Decision.**

- `editor/ui/display-available?`: the runtime has the GUI backend and the session has a display —
  `$WAYLAND_DISPLAY` / `$DISPLAY` on Linux and the BSDs, a desktop login rather than ssh on macOS,
  always on Windows; a headless GUI runtime counts. What a program that can run in a window or the
  terminal asks before choosing (bedit's `-nw` fallback).
- `editor/ansi/ansi-clipboard`: the OSC 52 escape; `editor/ui/term-clipboard-set` puts text on the
  desktop's clipboard when a display is reachable, else writes the escape, which the terminal
  (xterm, kitty, foot, WezTerm, iTerm2, Windows Terminal, tmux with `set-clipboard on`) turns into
  its own clipboard on the machine the user sits at. `*term-display*` carries it as
  `:clipboard-set` / `:primary-set`, so a session served to a terminal client copies there too.
- **One attach client.** `attach` is now `attach-display` over `*term-display*`; the drain-then-poll
  loop and its helpers are gone. A terminal client gets everything the window client had: input
  before frames (ADR-490), busy and texture messages dropped by a display without the entry, the
  clipboard, the ping.
- **Live resize of a served session.** A client's `[:resize cols rows]` (a terminal's SIGWINCH, a
  window dragged) becomes the remote display's `:size` before it reaches the app
  (`remote-note-resize`). A `serve-shared` session keeps its first size: its clients differ.

## ADR-588 — `sudo`: a file read or written as another user, the password kept nowhere

**Context.** Editing `/etc/hosts` needs root. Emacs reaches it through TRAMP's `/sudo::` method.
bedit wanted the same, and the capability under it — read a file as root, write it back in place,
take a password once — is not an editor's: an installer, a script fixing a system file, `nest`
installing system-wide all want it. Brood had `os/cmd` with `:stdin`, so no primitive was missing;
what was missing was the mechanism done right once, because done naively it is dangerous:
`sudo -S cmd` reads the password from the same stdin the command then reads, so when sudo needs
no password (its timestamp is fresh, or `NOPASSWD`) the PASSWORD LINE BECOMES THE FILE's first line.

**Decision.** `std/sudo.blsp`: `read`, `write`, `password-required?`.

- A password is handed to `sudo -S -p '' -v` alone — validation, no command — and kept nowhere.
  Every command then runs as `sudo -n`, which never reads a password, so the text on its stdin is
  only the text. `password-required?` asks `sudo -n -v`, which never prompts.
- A sudo that caches nothing (`timestamp_timeout=0`) fails the `-n` run after a good validation;
  then the password and the text go in one `sudo -S -k` call — `-k`, so the password is the line
  sudo reads first whatever its cache holds.
- `write` is `sh -c 'cat > "$1"'` as the target user: the file keeps its owner and mode, nothing is
  echoed back. `read` tells a missing file (nil) from a refusal (a failure). sudo's messages are
  read in the C locale.
- `sudo/*program*` names the sudo run; the tests bind a stand-in script that speaks sudo's flags,
  so no test runs the real one.
## ADR-589 — A hanging fill: `string/fill` takes `[first rest]`, `string/fill-prefixes` reads them

**Context.** bedit's M-q and auto-fill wrap with `string/fill`, which kept ONE prefix on every
line. That is a comment's `;; ` or a quote's `> `, but not the commonest prefix of all: a list
item, whose first line carries the bullet (`- `, `1. `, `- [ ] `) and whose later lines sit under
its text. Filled with one prefix, a list item either lost its bullet or put it on every line. Nor
could a paragraph whose second line is indented differently from its first (a definition under
its term, a docstring's first line inside its form) be refilled without moving one of them.
Emacs's adaptive fill keeps both: the first line's prefix, and a fill prefix for the rest taken
from the second line, or — for a one-line paragraph — from the first with its bullet blanked.

**Decision.**

- `string/fill`'s `prefix` may be a pair `[first rest]`: the first line keeps `first`, every
  later line takes `rest`, each line's room is the width less its own prefix, and each input
  line has its own prefix taken off (the first `first`, the rest `rest`). A string is the pair
  `[s s]`, so every existing call means what it did.
- `string/fill-prefixes` answers the pair a paragraph uses (Emacs's `fill-context-prefix`): the
  first non-blank line's indentation, comment or quote marker (`;;`, `#`, `//`, `--`, `>` and
  `> >`) and list bullet (`-` `+` `*` `•`, `1.` `2)`, an Org checkbox); the rest is the second
  line's indentation and marker, or the first's with the bullet's characters turned to spaces
  (a tab after it kept). A bullet needs the space after it, so `*emphasis*` and `-flag` are
  words.
- `string/fill-prefix` is the first of the pair. It now also sees a bullet (`* item` → `* `, as
  before; `- item` → `- `, where it answered `""`), and `>` markers nest (`> > `).

The patterns are written with literal tabs: `regex`'s dialect reads `\t` as a `t` (it is
Emacs's, where a tab is written as a tab), which the first cut of this got wrong.

**Callers beyond bedit.** The REPL's and the doc tools' rewrapping of docstring prose with
`-` bullets, and anything that reflows Markdown or comments — `nest format` refilling a long
comment would use exactly this pair.

**Consequences.** A paragraph that is several list items is still one paragraph to
`string/fill`: deciding where an item ends is the caller's policy (bedit narrows M-q to the item
point is in). Guards: `tests/strings_test.blsp` "string: a hanging fill (adaptive fill's two
prefixes)".

## ADR-590 — `pane-split-edge`: a pane along a side of the whole layout

**Context.** bedit's `display-buffer` rules let a user say "`*compilation*` in a bottom side
window, a third of the frame" (Emacs's `display-buffer-in-side-window`). `editor/pane` could
split only the SELECTED pane, so a side window opened from the right of two side-by-side panes
spanned half the frame, and from a different pane a different half. The tree's shape is the
toolkit's (a split's `:split :dir :ratio :a :b`, a leaf's `:pane :payload :selected`), and an
editor that built a split node itself would hold a copy of that representation.

**Decision.** `pane-split-edge tree side payload size` wraps the WHOLE tree: a new leaf along
`side` (`:bottom` `:top` `:left` `:right`) taking the fraction `size` of the frame, clamped to
`[0.1 0.9]` as a drag is, the old tree keeping the rest and its arrangement. Selection stays
where it was. The new leaf is the last in traversal order for `:bottom` / `:right` and the first
for `:top` / `:left`, so an editor finds it again by its payload (bedit marks it `:side`).

**Callers beyond bedit.** Any editor on `editor/pane` that docks a panel — the REPL editor's
output pane, the observer's log strip, a debugger's stack pane.

**Consequences.** Every path in the old tree gains a prefix (`:a` or `:b`), as after any split
above it; a caller holding a path re-reads it. Guards: `tests/pane_test.blsp` "split-edge puts
a pane along a side of the WHOLE layout, selection kept" and "a side pane's share of the frame
is its size, clamped".

## ADR-591 — `line-cache-state`: the state a line starts in, from the line cache

**Context.** bedit's electric pairs and M-q ask Emacs's `syntax-ppss` question — is point in a
string, which one, how deep in brackets — on every quote and bracket key. Answering it by
scanning the buffer from its start cost 30–260 ms a key at the end of a 1 MB file. The line
cache (ADR-471) already keeps the state each line starts in, exactly, re-lexing only what an
edit touched — but it answered only COLOURS of a window, so a caller wanting a line's state had
to smuggle it out through its spans, and every query kept a window of spans it did not want.

**Decision.** `editor/highlight/line-cache-state cache lexer rope line [change]` answers
`[cache' state]`: the state `line` starts in, lexed from the nearest checkpoint at or above it
(or the first line an edit touched), checkpoints kept as it goes, no window retained. It shares
`line-cache-update`'s cache and its edit handling (`lc-edited`, the tentative chain, back in
step when an old entry agrees), so one cache serves both and a lexer's colours and states stay
one walk. A line past the end starts in the last line's out-state; a stateless lexer's lines
all start in its `:initial`.

`line-cache-state-within cache lexer rope line limit [change]` asks the same with a budget:
`[cache' known? state]`, lexing at most `limit` lines and answering `known?` false when the
state is further than that, the checkpoints it made kept so the next ask goes on from there. A
keypress cannot afford a cold region (a 1 MB file whose cache a background task is still
building, the lines below an edit that changed every state after it); it asks within a budget
and, out of reach, answers from a bounded guess of its own.

**Callers beyond bedit.** Anything that asks a line-oriented lexer where it stands: the REPL's
editor (is the input inside a string — read another line?), `nest format` deciding whether a
line is inside a heredoc, an indenter that needs the bracket depth at a line.

**Consequences.** A query far below the last one lexes the lines between, once; after that it is
a checkpoint away. Guards: `tests/highlight_test.blsp` "line-cache-state-within — the same question with a budget" and "line-cache-state — the state a line
starts in (syntax-ppss's question)".
